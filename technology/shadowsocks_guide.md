## 1. Overview and Boundary Declared

### 1.1 The Short Answer

**Shadowsocks** is an encrypted proxy protocol family whose design objective is not authentication but **indistinguishability**. The project's own documentation describes it in one line: "Shadowsocks is a secure split proxy loosely based on SOCKS5" (✅ shadowsocks.org, *What is Shadowsocks?*, extracted this pass). The architecture is a two-sided split: a local component (`ss-local`) "acts like a traditional SOCKS5 server and provides proxy service to clients", encrypts and forwards data streams and packets from the client to a remote component (`ss-remote`), which decrypts and forwards to the target; replies are symmetric (✅ same page). That is the entire design in two sentences. Everything else in this guide is the consequence.

The consequence is this: a client wants to reach a target that a network operator has decided to block. The client encrypts *every* byte it sends to the proxy server — the SOCKS5-style target specification, the payload, the lot — so that what crosses the network is a stream of bytes with no protocol header, no version field, no handshake, and no authentication exchange for an observer to recognise. The specification states the goal directly: "The proxy traffic is indistinguishable from a random byte stream, and therefore can circumvent firewalls and Internet censors that rely on DPI (Deep Packet Inspection)" (✅ SIP022 §1, extracted verbatim). In the IMC 2020 paper's phrasing: "It attempts to avoid detection not by imitating some other protocol, but by using encryption to appear as a uniformly random byte stream" (✅ *How China Detects and Blocks Shadowsocks*, IMC '20). **Appearing to be nothing in particular is the design.** That is the whole thesis of the family, and — as §2, §6 and §7 will show — it is also the assumption that the measurement literature eventually took apart.

### 1.2 What This Guide Is, and What It Is Not

This guide is **descriptive protocol, cryptography and security research**. It explains how the protocol is designed, how it has been attacked in the peer-reviewed literature, how it has been measured on live networks, and what the legal position is in the jurisdictions where that position is documented. That is ordinary network-security work, and it sits in the same tradition as the papers cited throughout. It is deliberately **not** an installation, configuration or deployment guide (no server setup, no configuration snippets, no VPS walkthrough); **not** an operational detection-evasion playbook (no plugin selection advice for defeating a specific classifier); **not** an operational attack recipe (attacks are described at the conceptual level the published papers themselves use: mechanism, why it worked, what the fix was); and **not** a consumer product comparison (no recommended-tools tables, no reliability rankings, no pricing).

The reason for the boundary is not squeamishness. It is that the *engineering and the evidence* are the interesting and durable part, and the operational part is both volatile (it dates within months) and outside the remit of a technical reference guide. Where a plugin or a cipher is named below, it is named because its existence and its class of transformation are part of the protocol's documented surface — not because this guide is telling anyone how to deploy it.

There is one more boundary worth stating plainly: **the same properties that make this protocol family useful for reaching a blocked website make it useful for exfiltrating data from a corporate network and for hiding the command-and-control channel of malware.** That is not an incidental overlap; it is the same design property viewed from two directions. §9.6 treats it honestly and without moralising, and §12 works the enterprise consequence.

### 1.3 The VPN Versus the Proxy — the Contrast Stated Explicitly

[vpn_guide.md](vpn_guide.md) is this guide's nearest sibling and its deliberate opposite. The contrast is not cosmetic — it changes the threat model, the failure modes and the operational requirements, so it is worth stating cleanly and then getting out of the way.

| Dimension | The VPN ([vpn_guide.md](vpn_guide.md)) | The Shadowsocks family (this guide) |
|---|---|---|
| **What it is** | A routed tunnel: a virtual network interface that carries IP packets between peers ([vpn_guide.md](vpn_guide.md) §1.2–§1.3) | A proxy: a per-connection relay that carries application streams to a chosen target (✅ shadowsocks.org, *What is Shadowsocks?*) |
| **The protocol's aspiration** | Authenticated, confidential, integrity-protected carriage — the three verbs (✅ RFC 4301's "security services for traffic at the IP layer", per [vpn_guide.md](vpn_guide.md) §1.2) | Confidential carriage that is *invisible on the wire* — "indistinguishable from a random byte stream" (✅ SIP022 §1) |
| **What it proves to its peer** | Both ends authenticate (certificates, PSKs, Curve25519 keys) before any traffic flows | **Nothing.** There is no handshake and no authentication exchange; knowledge of the pre-shared key is demonstrated only implicitly, by producing ciphertext that decrypts (✅ SIP022 §1: "It is believed that using a pre-shared key without performing handshakes is best for its use cases") |
| **What the network operator sees** | An identifiable tunnel — ESP, a TLS session, or UDP on a fixed port ([vpn_guide.md](vpn_guide.md) §1.7) | A stream of bytes with no recognisable structure at all — which was the point |
| **The threat model's centre of gravity** | Network-layer adversaries and edge-device compromise ([vpn_guide.md](vpn_guide.md) §7.1's CVE roll call) | *A censor that both observes and actively probes*, and specifically a state firewall that can afford to send follow-up traffic to a suspected server (✅ IMC 2020) |
| **The failure mode** | A gateway breach is a network breach; malware inside the tunnel is a lateral-movement problem ([vpn_guide.md](vpn_guide.md) §7.1–§7.2) | A *protocol* weakness is a server-identification weakness — the server gets blocked, or its traffic gets classified (✅ IMC 2020; ✅ USENIX Security 2023) |
| **The legitimate-use story** | The managed enterprise remote-access estate ([vpn_guide.md](vpn_guide.md) §5) | Data-centre egress, application-level proxying, and research — plus a large censorship-circumvention use this guide describes but does not serve (§9, §10) |

Two things follow from the table, and they are the connective tissue between the two guides. **First**, a VPN is a *routed* tunnel and this family is a *proxied* connection: the VPN decides "you are inside the network", the proxy decides "this connection goes to that target". Which means the proxy has no equivalent of the VPN's admission control to harden, because it never claimed to have one. **Second**, the design goals are almost perfectly orthogonal — the VPN spent twenty years learning that a tunnel without strong mutual authentication is a liability ([vpn_guide.md](vpn_guide.md) §3.6 on PPTP), while this family spent the same period being deliberately unauthenticated *because* authentication is exactly what a censor would probe for. §2 explains why that trade seemed right, and §6 shows what it cost.

### 1.4 The One-Page Orientation

**What it is.** A SOCKS5-based encrypted split proxy — `ss-local` in front of the client application, `ss-remote` in front of the target — carrying every byte of the proxy conversation as ciphertext with no framing an observer can key on.

**How it evolved — three editions, each a response to a failure.** (1) **The stream-cipher era (2012 – ~2017):** a stream cipher (RC4 variants, AES in CFB/CTR modes, Camellia, Blowfish) over a password-derived key, preceded by a random initialisation vector — confidentiality only, **no integrity and no authentication**; it broke under active probing in August 2015 and under a decryption-oracle attack in February 2020 (✅ IMC 2020 §2.1). (2) **The AEAD era (February 2017 – ):** authenticated encryption added to the specification (`aes-*-gcm`, `chacha20-ietf-poly1305`, `xchacha20-ietf-poly1305`), fixing malleability and leaving a replay problem patched at the implementation level (✅ IMC 2020 §2.1; ✅ SIP002 cipher list). (3) **The 2022 Edition (SIP022):** a mandatory base64 pre-shared key with no password-stretching at all (✅ SIP022 §2.1), BLAKE3 session-subkey derivation, per-direction salts, counter nonces, a 30-second timestamp replay window and an overhauled UDP session model (✅ SIP022 throughout).

**What the measurement literature established.** That "it looks like random bytes" does not mean "it cannot be classified". The GFW combined a passive first-packet length-and-entropy heuristic with seven classes of active probes (✅ IMC 2020); three years later the same group documented a purely **passive** fully-encrypted-traffic classifier that blocked Shadowsocks, VMess and Obfs4 on set-bit fraction and printable-ASCII statistics, deployed from November 2021 (✅ USENIX Security 2023).

**What the ecosystem looks like in September 2026.** The Python original still reads "Removed according to regulations."; the C implementation was renamed and modernised in September 2026; the Rust implementation is the actively developed reference; Outline moved out of Jigsaw into its own foundation in January 2026; `simple-obfs` is formally deprecated (✅ all from the repositories, §8).

**What is legal.** Running and using this class of software is ordinary in most jurisdictions; it is restricted or criminalised in a specific list — China, Russia, Iran, Turkmenistan, Belarus and others — where the violation is generally framed around **operating or providing** circumvention services rather than possessing software; and it is a corporate-policy problem everywhere, because an unmanaged encrypted egress channel defeats DLP and logging regardless of legality (§9).

### 1.5 The Name and Term Decoder

The family vocabulary is dense and inconsistently used in secondary sources. These are the definitions this guide uses.

- **Shadowsocks** — the protocol family, and historically the name of the original Python implementation. The name is *not* an acronym and has no expansion.
- **`ss-local` / `ss-remote` (also `ss-server`)** — the two halves of the split proxy. `ss-local` speaks SOCKS5 to applications and encrypts toward the remote; `ss-remote` (binary: `ss-server`) decrypts and connects to the target (✅ shadowsocks.org). **Note the naming inconsistency** — the documentation says `ss-remote`, the shipped binaries say `ss-server`; same role.
- **SOCKS5** — the application-level proxying protocol (RFC 1928) that `ss-local` presents locally. Shadowsocks *borrows SOCKS5's address format* but does **not** implement SOCKS5's handshake or authentication between `ss-local` and `ss-remote`. This is the most misunderstood point about the protocol: the SOCKS5 in "SOCKS5-based" describes the local interface, not the tunnel.
- **AEAD** — Authenticated Encryption with Associated Data (AES-GCM, ChaCha20-Poly1305); the 2017 revision's central addition.
- **SIP** — **Shadowsocks Improvement Proposal**, the project's own numbered specification series on shadowsocks.org: SIP002 = `ss://` URI scheme; SIP003 = plugin design; SIP004 = AEAD ciphers; **SIP022 = the 2022 Edition** (✅ all four confirmed this pass).
- **OTA** — "one-time auth": a transitional stream-cipher-era mode giving each chunk its own authenticator; itself weak, because chunk length prefixes remained unauthenticated (✅ IMC 2020 §2.1).
- **IV / salt** — the random per-connection value prepended to the ciphertext. Stream-cipher era: "IV", 8/12/16 bytes; AEAD era: "salt", 16/24/32 bytes; 2022 edition: fixed per method (✅ IMC 2020 §2; ✅ SIP022 §2.1).
- **VMess / VLESS** — the V2Ray and Xray protocol family: VMess the original (weaknesses catalogued publicly in June 2020, ✅ gfw.report), VLESS the lighter successor, typically over TLS or REALITY (§8.6).
- **Trojan** — a design that does not hide the traffic but *imitates* an allowed one: "Trojan features multiple protocols over `TLS` to avoid both active/passive detections" (✅ trojan-gfw/trojan README).
- **Obfuscation plugin** — the SIP003 extension point: a separate process in front of an unmodified endpoint that transforms the byte stream (✅ SIP003).
- **DPI** — Deep Packet Inspection: classification by inspecting content and structure rather than port or address.
- **Entropy** — the statistical measure of randomness in a byte sequence. The design assumed high entropy meant unclassifiable; §7.1 shows what happened to that assumption.
- **Active probing** — the censor's follow-up: having passively flagged a suspected server, connect to it and attempt to speak known protocols to see whether it responds as a proxy would (✅ NDSS 2020 §II-A; ✅ IMC 2020 §1).
- **Fully-encrypted traffic** — the measurement literature's term for traffic with no plaintext structure at all. It is a *class*, not a compliment: the term is defined by the censor's classifier (§6.3, §7.1).

The security cluster reads as a stack, and this guide occupies an unusual position in it: it is the cluster's study of a protocol that **deliberately refused the principles the rest of the cluster teaches**. [cybersecurity_guide.md](cybersecurity_guide.md) is the umbrella; [security_by_design_guide.md](security_by_design_guide.md) is the development discipline — and this family's history is the discipline's best negative example, because shipping confidentiality without integrity is exactly the failure mode that discipline exists to prevent (§11); [distributed_auth_guide.md](distributed_auth_guide.md) owns identity and authentication, of which this protocol's wire format has none by design (§2); [threat_modeling_guide.md](threat_modeling_guide.md) owns the adversarial lens, and §6–§7 here are a threat model worked by professional adversaries against a real deployed protocol; [zero_trust_network_architecture_guide.md](zero_trust_network_architecture_guide.md) and [beyond_zero_enterprise_security_guide.md](beyond_zero_enterprise_security_guide.md) describe the identity-first controls an unmanaged proxy routes *around* (§10, §12); and [vpn_guide.md](vpn_guide.md) is the managed-tunnel counterpart whose protocol comparison (§3 there) and enterprise patterns (§5, §7 there) this guide references rather than re-derives.

## 2. The Design Philosophy

### 2.1 The Omission That Is the Design

Most secure protocols are defined by what their handshake does. This one is defined by the handshake it does not have. In an ordinary secure channel — TLS, IPsec, WireGuard, SSH — the two parties exchange identities, negotiate parameters and derive keys before any application data moves. That exchange is a burst of structured traffic at the start of every connection, and it is the single most reliable thing a classifier can look for: a ClientHello with a known cipher list, an IKE_SA_INIT with known transform types, a Noise handshake with a recognisable message pattern.

Shadowsocks has none of that. The client's first bytes on the wire are a random salt followed by ciphertext. There is no version byte, no capability list, no server identity, no challenge. The design's rationale is stated in the specification, in a sentence worth quoting twice: **"As with previous editions, Shadowsocks 2022 does not provide forward secrecy. It is believed that using a pre-shared key without performing handshakes is best for its use cases."** (✅ SIP022 §1). That sentence is the design philosophy in full: the handshake was omitted *knowingly*, and the cost — no forward secrecy — was accepted *knowingly*, because the designers' priority was the shape of the bytes on the wire.

The second half of the omission is subtler and more consequential. Not only is there no handshake; there is **no authentication exchange at all**. The 2022 edition states that the pre-shared key "is also used directly in some places" (✅ SIP022 §2) and that subkeys are derived from it — but nowhere does either party prove knowledge of the key before the other acts. In the AEAD era, the parties' mutual knowledge is demonstrated only implicitly: the server attempts to decrypt the first blob, and if the authentication tag validates, the client must have had the key. In the stream-cipher era there was not even that, because there was no tag to validate (✅ IMC 2020 §2: the stream-cipher construction "is cryptographically weak — it provides only confidentiality, not integrity or authentication").

### 2.2 What the Omission Buys on the Wire

The design's wager is easy to state and was, for a period, empirically defensible. Three properties follow from having no handshake:

1. **No protocol signature.** Every classifier that works by matching known protocol structures has nothing to match. There is no magic number, no version negotiation, no extension list, no certificate. The specification's own claim is that the traffic "is indistinguishable from a random byte stream" (✅ SIP022 §1).
2. **No server identity to probe for.** If a server responds identically to everyone, a censor cannot elicit a distinctive reply by sending garbage. In practice this was achieved by *silence*: the server tries to decrypt, fails, and closes — the behaviour NDSS 2020 characterised as "the proxies require knowledge of a secret in order to use, and the servers remain silent when probed by a censor that doesn't have the secret" (✅ NDSS 2020 Abstract).
3. **Nothing to downgrade or negotiate.** With the cipher fixed by configuration on both ends, there is no algorithm-agility surface — no downgrade attack, no weak-suite negotiation, none of the misconfiguration classes that plague negotiated protocols (compare [vpn_guide.md](vpn_guide.md) §3.1 on IPsec's option space).

The wager also buys something practical and less discussed: **minimal overhead and minimal code**. The IMC 2020 authors note that "the popularity of Shadowsocks stems from its simplicity. Its lightweight design imposes minimal overhead on proxied traffic and makes it easy to implement on a variety of platforms" (✅ IMC 2020 §1). A protocol with no handshake can be implemented in a few hundred lines, which is why there are so many independent implementations in so many languages (§8).

### 2.3 What the Omission Costs

All three of those gains turn into liabilities if the underlying cryptography does not hold. And in the stream-cipher era, it did not.

- **An unauthenticated cipher is malleable.** Without integrity protection, an attacker who can see and modify ciphertext can flip bits in the plaintext in a controlled way. For a stream cipher, flipping a ciphertext bit flips the corresponding plaintext bit — and since the plaintext at a known offset in this protocol is a SOCKS5 address type, the attacker can *enumerate* the protocol's internal state. This is precisely the August 2015 finding (§6.4): "an attacker can make many connections to a suspected Shadowsocks server, and take advantage of ciphertext malleability to try every possible value of the byte that corresponds to the address type in the target specification. Because only `0x01`, `0x03`, and `0x04` are valid address types, a known fraction of connections will time out differently from the rest" (✅ IMC 2020 §2.1).
- **A server that must decrypt before it can decide is a decryption oracle.** If the server's response depends on whether decryption succeeded, the response *leaks information about the key*. The February 2020 attack worked exactly this way: "Using the Shadowsocks server as a decryption oracle, an attacker, without knowledge of the shared master password, can get full decryption of recorded Shadowsocks connections" (✅ IMC 2020 §2.1, describing Zhiniang Peng's disclosure).
- **Silence is itself a signal.** The probe-resistance strategy of "never respond unless the probe authenticates" works only if *ordinary* servers on the internet also sometimes refuse to respond. NDSS 2020's central observation is that they mostly do not: "By sending probes comprised of popular protocols as well as random data, we can elicit responses from nearly all endpoints (94%) in our Tap dataset of over 400k IP/port pairs. For endpoints that do not respond, we find TCP behaviour such as timeouts and data thresholds that are unique to the proxies compared to other servers" (✅ NDSS 2020 §I). In other words: **the absence of a fingerprint is a fingerprint**, because almost everything else on the internet has one.
- **No forward secrecy.** Explicitly accepted by the design and still true in 2022 (✅ SIP022 §1). A recorded session is decryptable by anyone who later obtains the pre-shared key.
- **No per-user authentication.** With one symmetric key shared by all users of a server, the protocol cannot distinguish users cryptographically — a gap that the 2022 edition's optional multi-user extension work addresses and that the primary specification's text does not (§5.7, §8.1).

### 2.4 The Threat Model the Designers Held

The IMC 2020 paper's background section reconstructs the designers' implicit model accurately, and it is worth stating plainly because it explains every subsequent decision: **the adversary observes the network and blocks traffic it can classify.** Against that adversary the correct move, in the design's own terms, is to be unclassifiable: encrypt everything, add no structure, and make the server's behaviour on failure identical regardless of what it received.

That model has a crucial implicit assumption built into it — that a censor's capability is *passive classification*, and that a sufficiently random byte stream has no class. The measurement literature's entire contribution is the demonstration that this assumption is false in two ways:

1. **The censor is not passive.** It observes, forms a *suspicion*, and then acts on that suspicion by probing (✅ IMC 2020 §1, Figure 1). A censor that can send follow-up traffic has an orthogonal capability that no amount of payload randomisation defeats — because the leak is in the *timing and volume of the response*, not in the payload.
2. **A censor can classify "random-looking" traffic as a class.** The USENIX Security 2023 paper's finding is precisely this: "instead of directly defining what fully encrypted traffic is, the censor applies crude but efficient heuristics to exempt traffic that is unlikely to be fully encrypted traffic; it then blocks the remaining non-exempted traffic" (✅). Note the inversion: the censor does not need to detect Shadowsocks; it needs to detect *everything that is not something else*, and then block the residue.

### 2.5 The Threat Model the Protocol Actually Faces

The adversary the protocol has actually met, as documented across the literature this guide cites, has four capabilities: **passive statistical analysis of the first packet** — the GFW "uses the length and entropy of the first data packet in each connection to identify probable Shadowsocks traffic" (✅ IMC 2020 Abstract); **active probing at scale from a distributed infrastructure** — 51,837 probes were observed from **12,300 unique source IP addresses**, the two dominant autonomous systems being AS4837 (China169 Backbone) and AS4134 (Chinanet), with more than 75% of addresses sending more than one probe, which differs from the earlier Tor-probing literature where "95% of the addresses appear only once", and with probe source ports clustering in 32768–60999, the default Linux ephemeral range (✅ IMC 2020 §3.3–§3.4); **purely passive classification of the fully-encrypted class**, deployed from November 2021 (✅ USENIX Security 2023); and **connection-level side-channel observation** — TCP close type (FIN vs RST), abort timing and data thresholds — "sufficient to distinguish probe-resistant proxies from ordinary hosts with negligible false positives in our dataset" (✅ NDSS 2020 Abstract).

The gap between §2.4 and §2.5 is the gap this guide exists to document. It is not a story about bad cryptography — the AEAD and 2022 editions are, as far as the specifications go, competently specified. It is a story about a threat model that was correct about one adversary and silent about another.

### 2.6 The Design Table — Assumption / Reality

| The design assumed | The literature found | Where |
|---|---|---|
| Random bytes cannot be classified | First-packet length and entropy were used as a *suspicion* signal; set-bit fraction and printable-ASCII statistics classified fully-encrypted traffic passively | ✅ IMC 2020; ✅ USENIX Security 2023 |

## 3. Origin and Authorship History

### 3.1 The Author and the First Release

Shadowsocks was created by a developer using the handle **clowwindy**. Wikipedia's article gives the release date as **20 April 2012** and the original language as Python (✅ Wikipedia, *Shadowsocks*, article metadata and lead, extracted this pass — a **secondary** source). The project's own artefact trail is consistent with 2012–2013 but not precise about the first public release: the C implementation's README credits the port to "@clowwindy" and its copyright block reads **"Copyright: 2013-2015, Clow Windy <clowwindy42@gmail.com>"** (✅ shadowsocks-c README, extracted this pass).

⚠ **Flagged discrepancy.** The commonly cited 2012 origin (Wikipedia, and the widely-repeated "20 April 2012") and the 2013 start of the C-port copyright block are not the same date, and this guide cannot resolve them: the original repository's contents were removed (see §3.3), so the original commit history is not directly inspectable at the repository's public URL. The honest statement is: **the project is credited to clowwindy and dates to 2012–2013, with 2012 the widely-reported year and the C port's copyright block beginning at 2013.** Anyone who needs the exact date should treat it as unsettled.

What *is* firmly established: the original implementation was Python, and the family's subsequent implementations are ports of it in other languages, not independent reimplementations. The C implementation says so in as many words: "It is a port of Shadowsocks created by @clowwindy, and maintained by @madeye and @linusyang" (✅).

### 3.2 The Fork and Port History

The project's shape over the following decade is a classic open-source proliferation, and the "which one is the reference implementation" question has never had a stable answer.

- **2013–2015 — the C port begins.** `shadowsocks-libev` is created as a lightweight C implementation "for embedded devices and low-end boxes" (✅ shadowsocks-c README), maintained by **@madeye (Max Lv)** and **@linusyang (Linus Yang)** — both named in the README and in the copyright block. The brief's lead that Max Lv is associated with the C implementation from around 2014 is **corroborated** by the copyright block's "2014, Linus Yang" entry and the "2013-2018, Max Lv" entry (✅), though the README does not date the port's first commit.
- **2014 onward — the Rust port.** `shadowsocks-rust` is a Rust port; its README's licence block reads "Copyright (c) 2014 Y. T. CHUNG" (✅), the GitHub handle behind the `zonyitoo` account that the SIP022 acknowledgement credits.
- **2015 — the fork that became a family.** **BreakWa11** forked the project as **ShadowsocksR (SSR)**, adding protocol plugins and obfuscation options. Wikipedia documents ShadowsocksR as a distinct lineage (✅ Wikipedia, *Shadowsocks* §ShadowsocksR — secondary). BreakWa11 is also the researcher credited by the IMC 2020 paper with the **August 2015 discovery of the active-probing vulnerability in the stream ciphers** (✅ IMC 2020 §2.1) — the same person appears in both the fork history and the vulnerability history, which is part of why the fork happened at all.

### 3.3 The August 2015 Removal — What the Evidence Supports

This is the single most folklore-prone fact in the field, so this section separates the three evidence layers explicitly.

**Layer 1 — the artefact that exists today.** The repository at `github.com/shadowsocks/shadowsocks` currently has a branch named `rm` containing **one commit** and **one file**: a README whose entire content is the sentence **"Removed according to regulations."** The repository still shows 33.5k stars and 18.0k forks (✅ observed directly on GitHub, 17 September 2026). This is not a secondary retelling — it is the removal notice itself, sitting where the code used to be.

**Layer 2 — the contemporaneous account.** Wikipedia's article states: "On 22 August 2015, 'clowwindy' announced in a GitHub thread that they had been contacted by the police and could no longer maintain the project. The code of the project was subsequently branched with a removal notice." It adds that **three days later, on 25 August, the proxy application GoAgent also had its GitHub repository removed**, that the removals received media attention, that some speculated a connection to a **DDoS attack targeting GitHub several days later**, and that **Danny O'Brien of the Electronic Frontier Foundation published a statement on the matter** (✅ Wikipedia, *Shadowsocks* §Takedown — **secondary** source with citations to contemporaneous press and to the GitHub comment itself). The IMC 2020 paper independently places the same *month and year* for a different Shadowsocks event in the same period: "In August 2015, BreakWa11 discovered an active-probing vulnerability in Shadowsocks stream ciphers" (✅ IMC 2020 §2.1) — a useful cross-check that August 2015 was indeed a pivotal month for the project, though it is a different event.

**Layer 3 — what is not established.** The brief asked specifically whether the removal was a deletion or a transfer. The evidence supports: **the code was removed from the repository and replaced with a notice, and the repository itself — its stars, its forks and its name — was retained.** The `rm` branch's single commit is the shape of a deliberate replacement, not a repository deletion: an account deletion would not leave a branch, a star count and a fork network behind. That is the strongest reading the artefact supports.

- **The exact wording of the author's message.** The widely-quoted "I was asked to stop" phrasing circulates in secondary retellings. - **The mechanism's motive.** Whether the police contact was a formal legal process, an informal warning, or something else is not established by the sources consulted. ⚠
- **The causal link to the GitHub DDoS.** Wikipedia reports this as speculation by observers ("some speculating about a possible connection"), not as an established fact. ⚠

Wikipedia notes (and the implementation record confirms) that "despite the takedown, collaborators of the project have continued the development of the project" — and six sections of this guide are about software that has been in continuous active development for the eleven years since. The removal took out the original Python repository; it did not stop the protocol.

## 4. The Protocol in Detail

### 4.1 The SOCKS5 Handshake It Replaces

To understand the design, it helps to know exactly what it displaces. **SOCKS5 (RFC 1928)** is the standard application-level proxying protocol, and it works in three phases. The client connects to the proxy and sends a **version-identifier/method-selection** message — a greeting that announces "I am SOCKS5, here are the authentication methods I support". The proxy replies selecting a method. Then, depending on the method, an **authentication sub-negotiation** may occur. Then the client sends a **request** carrying the target address and port, and the proxy replies with a status code.

Every one of those phases is structured, versioned, and observable. A SOCKS5 greeting begins with a fixed byte (`0x05`) followed by a method count. A censor that sees that pattern knows exactly what it is looking at, and can block it on that basis alone.

Shadowsocks keeps the *last* phase of that sequence and discards the first two entirely. The target specification — the address and port that would have gone into a SOCKS5 request — is encrypted and sent as the first bytes of the tunnel's payload. There is no greeting, no method selection, no authentication sub-negotiation. **`ss-local` speaks real SOCKS5 to the local application** — that is the compatibility surface, and it is why ordinary applications can use it without modification — **but the wire between `ss-local` and `ss-remote` carries only salts and ciphertext** (✅ shadowsocks.org, *What is Shadowsocks?*, and ✅ SIP022 §1's statement that the protocol "uses AEAD with a pre-shared symmetric key to protect payload integrity and confidentiality").

### 4.2 The Address and Message Framing

The address format is inherited verbatim from SOCKS5 (RFC 1928 §5), which is the one piece of the original design that has survived all three editions unchanged (✅ shadowsocks.org):

```
type   1 byte
host   variable
port   2 bytes, big-endian
```

with exactly three address types defined:

- **`0x01`** — host is a 4-byte IPv4 address;
- **`0x03`** — host is a variable-length string: **a 1-byte length followed by up to a 255-byte domain name**;
- **`0x04`** — host is a 16-byte IPv6 address.

The 2022 specification confirms the lineage explicitly: the request header contains "ATYP + address + port: Target address in SOCKS5 address format", with the citation pointing at RFC 1928 §5 (✅ SIP022 §3.1.3). This is worth dwelling on because the address-type design is precisely what the 2015 active-probing attack exploited (§6.4): there are only three valid values for that first byte, so an attacker who can influence the byte can divide a server's responses into a small number of observable classes.

### 4.3 How a Connection Is Established

The documentation gives the TCP flow in four sentences, and it is worth reproducing its structure because the simplicity is the point (✅ shadowsocks.org, *What is Shadowsocks?*):

1. `ss-local` "initiates a TCP connection to ss-remote by sending an encrypted data stream starting with the target address followed by payload data" — so the *first* thing on the wire, after any keying material, is the encrypted target.
2. `ss-remote` "receives the encrypted data stream, decrypts and parses the leading target address. It then establishes a new TCP connection to the target and forwards payload data to it."
3. The reply direction is symmetric: `ss-remote` "receives reply from the target, encrypts and forwards it back to the ss-local, until ss-local disconnects."
4. For obfuscation purposes, "both local and remote SHOULD send the handshake data along with some payload in the first packet" — i.e. the design explicitly asks implementations to avoid a pattern where the first packet's size is determined solely by the target address, because that would make the packet size predictable.

**UDP** works on a different model. `ss-local` sends "an encrypted data packet containing the target address and payload" to `ss-remote`; the remote decrypts, sends the payload alone to the target, then for return traffic "prepends the target address to the payload in each packet" before encrypting back. The documentation's own characterisation is exact: "Essentially, ss-remote is performing Network Address Translation for ss-local." (✅ same page).

### 4.4 The Stream-Cipher-Era Construction

In the first edition, the design was as spare as it could be. The network stream in each direction was **one long ciphertext preceded by a random initialisation vector** (✅ IMC 2020 §2):

```
[variable-length IV][encrypted payload...]
```

Both directions used the same encryption key but different IVs. The IV length depended on the cipher: **8, 12 or 16 bytes** (✅ IMC 2020 §2). The plaintext began with the SOCKS5 target specification, then the payload — and nothing else. There was no per-chunk framing, no length prefix, no tag.

Two properties of this construction deserve explicit statement, because they are the whole of §4.6 and §6.4:

- **Nothing authenticated anything.** The IMC 2020 authors state it flatly: the stream-cipher construction "is cryptographically weak—it provides only confidentiality, not integrity or authentication, and for that reason is deprecated" (✅ IMC 2020 §2). Both constructions "intend to require the client to demonstrate knowledge of the shared password before using the proxy server (though as we will see, with stream ciphers the requirement is loose)" (✅ idem — the parenthetical is the paper's own).
- **The server had to parse before it could reject.** To decide whether a connection was legitimate, the server decrypted the first bytes and looked at the address type. That decision — and the fact that rejection happened at a *different point* depending on the decrypted content — was the leak.

### 4.5 The Cipher Roster and the Key Derivation

The authoritatively-enumerated cipher list is the one attached to the project's own SIP002 URI specification, whose generator lists exactly these methods (✅ shadowsocks.org SIP002, extracted this pass):

| Class | Methods |
|---|---|
| **Modern AEAD (2017 era)** | `aes-128-gcm`, `aes-192-gcm`, `aes-256-gcm`, `chacha20-ietf-poly1305`, `xchacha20-ietf-poly1305` |
| **2022 Edition** | `2022-blake3-aes-128-gcm`, `2022-blake3-aes-256-gcm`, `2022-blake3-chacha20-poly1305` |
| **Stream ciphers — AES block modes** | `aes-128-cfb`, `aes-192-cfb`, `aes-256-cfb`, `aes-128-ctr`, `aes-192-ctr`, `aes-256-ctr` |
| **Stream ciphers — Camellia** | `camellia-128-cfb`, `camellia-192-cfb`, `camellia-256-cfb` |
| **Stream ciphers — ChaCha (non-AEAD)** | `chacha20-ietf` |
| **Legacy and broken** | `bf-cfb` (Blowfish), **`rc4-md5`** |

This resolves the brief's cipher-history lead cleanly: **`rc4-md5` existed, AES in CFB mode existed across three key sizes, and AES in CTR mode existed likewise** — and the list also contains `camellia-*-cfb`, `bf-cfb` and `chacha20-ietf`, which the brief did not mention and which are part of the record.

**Key derivation.** In the stream-cipher era, the key was derived from the user's password by the OpenSSL-style `EVP_BytesToKey` function. This is confirmed by the 2022 specification's own prohibition of it: implementations "MUST NOT use the old `EVP_BytesToKey` function or any other method to generate keys from passwords" (✅ SIP022 §2.1), and the specification notes the change "was inspired by WireGuard" (✅ idem) — i.e. the 2022 edition replaced password-stretching with a full-entropy key provided directly by the user. `EVP_BytesToKey` is a weak, deterministic construction with no salt and no work factor; using it meant the security of the whole connection rested on the user having chosen a good password.

### 4.6 The Integrity Failure and the Deprecation

The deprecation chain is documented, dated, and worth setting out in order, because it is the clearest case study in the cluster of what "confidentiality without integrity" costs (✅ all dates and findings in this subsection are from IMC 2020 §2.1, whose own sources are the contemporaneous project discussions and disclosures): **August 2015 — the malleability discovery (BreakWa11)**, exploiting the fact that an attacker could "take advantage of ciphertext malleability to try every possible value of the byte that corresponds to the address type in the target specification", so that "a known fraction of connections will time out differently from the rest"; **the first mitigation — non-termination on unknown address type**, which is a *behavioural* patch to a cryptographic failure, because the cryptography had no way to express "this message is authentic"; **OTA, the second attempt**, where the developers introduced "one time auth" mode so that "each chunk of data would carry its own authenticator", itself broken because "a lack of integrity protection in chunk length prefixes led to another active probing vulnerability" — the fix authenticated the *payload* but not the *framing*, and the framing was what the probe could manipulate; **February 2017 — the structural fix**, when "AEAD ciphers became part of the protocol specification, fixing this authentication problem"; and **February 2020 — the postscript**, when "Zhiniang Peng disclosed a devastating vulnerability in Shadowsocks stream ciphers" in which, "[u]sing the Shadowsocks server as a decryption oracle, an attacker, without knowledge of the shared master password, can get full decryption of recorded Shadowsocks connections" — a *stream-cipher* vulnerability disclosed three years after AEAD had replaced the stream ciphers, which means the residual population of stream-cipher deployments was still large enough in 2020 to be worth attacking.

The chain therefore reads: **no integrity → malleability (2015) → behavioural patch → OTA, itself flawed → AEAD (February 2017) → the stream ciphers were still deployed widely enough in 2020 that a decryption-oracle break still mattered.** The lesson is not that the maintainers were careless — they patched promptly at every step. It is that **a cipher without integrity protection cannot be patched into having integrity protection**, and every intermediate mitigation was a heuristic standing in for a cryptographic property the primitive could not supply.

## 5. The AEAD Era and the 2022 Edition

### 5.1 The AEAD Construction of 2017

From February 2017 the specification offered a second construction in which the stream is not one long ciphertext but a **sequence of length-prefixed chunks, each encrypted and authenticated with an AEAD tag** (✅ IMC 2020 §2). The paper's own diagram of the wire format is the clearest available description:

```
[variable-length salt]
[2-byte encrypted length][16-byte length tag]
[encrypted payload][16-byte payload tag]
... (repeating)
```

Four details matter. **The length prefixes are themselves encrypted and tagged** — IMC 2020 gives the rationale: "To avoid introducing any plaintext for the censor to match on, the length prefixes are themselves encrypted and tagged" (✅). This is precisely the fix for the OTA weakness (§4.6): the *framing* is now authenticated, not just the payload. **The salt is prepended once per direction** and "is combined with the shared secret password to produce a session key for each direction. The salt may be 16, 24, or 32 bytes" (✅ IMC 2020 §2). **The subkey derivation is HKDF** — NDSS 2020's table records the client's first message as deriving `K = HKDF(password, salt, "ss-subkey")` (✅ NDSS 2020 Table I), the exact construction including the context string, and the function SIP022 later replaced with BLAKE3 (✅). **The length cap is edition-specific** — "the `0x3FFF` (16383) length cap in Shadowsocks AEAD does not apply to this edition", where a payload chunk may carry `0xFFFF` (65535) bytes (✅ SIP022 §3.1.2).

The AEAD construction is, in cryptographic terms, sound: a standard AEAD over a per-chunk counter with an encrypted length field, keyed from a password-derived secret and a random salt. Its remaining structural weakness was not the crypto — it was **replay** (§5.2).

### 5.2 The Replay Attack and the Salt Pool

Because the salt is random and chosen by the client, and because nothing in the base AEAD design tied a salt to a single use, a censor that *recorded* a legitimate session could **replay** it: the bytes are valid ciphertext under a valid salt, so the server would accept them (✅ the replay-attack discussion is referenced by both the IMC 2020 bibliography — `shadowsocks-org` issue #44, "Defend against replay attack", 2017 — and by the implementations' own feature lists).

The mitigation was implemented at the **implementation level rather than in the specification**, and the implementations diverged — which is itself the interesting fact:

- `go-shadowsocks2` documents a **Bloom filter** as its default defence, with tunables for capacity (default `1e6` recent connections), false-positive rate (default `1e-6`), and slot count, and with the capacity set to `0` disabling the feature entirely (✅ go-shadowsocks2 README).
- The **2022 specification explicitly forbids that approach** for its own salt pool: "For salt storage, implementations MUST NOT use Bloom filters or anything that could return a false positive result, because salts only have to be stored for 60 seconds" (✅ SIP022 §3.1.5). The reasoning is exactly right and worth internalising: a false positive in a replay filter means **rejecting a legitimate connection**, and the 2022 designers judged that having to store a full salt list for 60 seconds was a better trade than any probability of breaking a real user.

This is a small but genuinely instructive episode: the same problem was solved twice, once with a probabilistic data structure and once with an exact one, and the specification eventually ruled the probabilistic answer out.

### 5.3 The 2022 Edition — Its Name, Its Year, Its Primitives

**The name and number.** The specification is titled **"SIP022 AEAD-2022 Ciphers"** and opens: "This document defines the 2022 Edition of the Shadowsocks protocol. Improving upon Shadowsocks AEAD (2017), Shadowsocks 2022 addresses well-known issues of the previous editions, drops usage of obsolete cryptography, optimizes for security and performance, and leaves room for future extensions." (✅ SIP022 Abstract, extracted verbatim). The edition is therefore **the 2022 Edition**, specified as **SIP022**, superseding the 2017 AEAD edition. ⚠ The exact publication *date* of SIP022 is not pinned by this pass; the specification self-identifies by year and the project's own numbering. It is hosted on `shadowsocks.org/doc/sip022.html` and in the `shadowsocks/shadowsocks-org` repository (✅ both confirmed).

**The primitives.** Every one of the following is quoted or directly derived from the specification text extracted this pass (✅):

- **A mandatory full-entropy pre-shared key.** "Unlike previous editions, Shadowsocks 2022 requires that a cryptographically-secure fixed-length PSK to be directly provided by the user. Implementations MUST NOT use the old `EVP_BytesToKey` function or any other method to generate keys from passwords." The key "is encoded in base64 for convenience. Practically, it can be generated with `openssl rand -base64 <key_size>`." And: "This change was inspired by WireGuard."
- **Key and salt sizes, per method.** `2022-blake3-aes-128-gcm` uses 16-byte keys and 16-byte salts; `2022-blake3-aes-256-gcm` uses 32-byte keys and 32-byte salts. "The salt has the same length as the pre-shared key."
- **BLAKE3 key-derivation mode for subkeys.** The specification gives the derivation in its own pseudocode:
  `session_subkey := blake3::derive_key(context: "shadowsocks 2022 session subkey", key_material: key + salt)`
  — replacing HKDF-SHA1.
- **The mandatory methods** are `2022-blake3-aes-128-gcm` and `2022-blake3-aes-256-gcm`: "MUST be implemented by all implementations". The specification's own gloss on the name is a nice tell: "`2022` reflects the fast-changing and flexible nature of the protocol."
- **The optional methods** are `2022-blake3-chacha20-poly1305`, `2022-blake3-chacha12-poly1305` and `2022-blake3-chacha8-poly1305`, offered "when support for CPUs without AES instructions is a priority", with the reduced-round variants explicitly justified by a citation to an IACR ePrint paper (`eprint.iacr.org/2019/1492`, ✅ cited in the specification). For TCP these substitute ChaCha-Poly1305 for AES-GCM directly.
- **No forward secrecy, by design.** "As with previous editions, Shadowsocks 2022 does not provide forward secrecy. It is believed that using a pre-shared key without performing handshakes is best for its use cases."

The brief's lead on the 2022 edition primitives is therefore **confirmed in full** — BLAKE3-based key derivation, a timestamp-plus-random session construct, separate per-direction subkeys, counter nonces, and anti-replay — with the caveat that the "session ID" the brief mentions is a **UDP** concept (§5.5) and the TCP side uses a per-stream random **salt** instead.

### 5.4 The 2022 TCP Wire Format

The 2022 TCP model maps **one proxy connection per TCP connection**, carrying **two proxy streams**: "request stream and response stream. A client initiates a proxy connection by starting a request stream, and the server sends back response over the response stream." (✅ SIP022 §3.1). The chunking model is inherited from AEAD, but two things are new: **"Standalone header chunks are added to both request and response streams to improve security and protect against replay attacks"**, and **each proxy stream derives its own subkey with its own random salt** (✅ SIP022 §3.1.1). **The nonce** is "a 12-byte little-endian integer … incremented after each encryption or decryption operation" — the specification's pseudocode is `u96le counter`, a 96-bit little-endian counter (✅). This is a meaningful change from the AEAD era's implicit per-chunk sequencing, and it is a *stateful* requirement on both sides. A request stream begins with one random salt plus **two standalone header chunks**; a response stream begins with a salt and **one fixed-length header chunk that also acts as the first length chunk** (✅ SIP022 §3.1.2).

**The headers** (✅ SIP022 §3.1.3):

| Direction | Fixed-length header | Variable-length header |
|---|---|---|
| **Request** | `type` (1B, value `0`) + `timestamp` (8B, big-endian Unix epoch) + `length` (2B big-endian) | `ATYP` + `address` + `port` + `padding length` (2B) + `padding` + `initial payload` |
| **Response** | `type` (1B, value `1`) + `timestamp` (8B) + **`request salt`** (16B or 32B) + `length` (2B) | — |

The header semantics as specified (✅ idem): the **type byte** "Differentiates between client and server messages" (`HeaderTypeClientStream = 0`, `HeaderTypeServerStream = 1`), its purpose being anti-replay — it prevents a message being reused for the unintended direction. The **timestamp**: "Messages with over 30 seconds of time difference MUST be treated as replay." The **request salt in the response header** "maps a response stream to a request stream. The client MUST check this field in response header against the request salt." **Padding bounds** are `MinPaddingLength = 0`, `MaxPaddingLength = 900`; the **length cap** is `0xFFFF`.

**The replay-protection procedure** is fully specified and stateful (✅ SIP022 §3.1.5): "Servers MUST store all incoming salts for 60 seconds. When a new TCP session is established, the first received message is decrypted and its timestamp MUST be checked against system time. If the time difference is within 30 seconds, then the salt is checked against all stored salts. If no repeated salt is discovered, then the salt is added to the pool and the session is successfully established." The specification also enumerates what is *no longer* needed — clients need not check the response salt (the request salt in the header does that job), outgoing salts need not be pooled (the type field handles direction), and Bloom filters are prohibited (§5.2).

### 5.5 The 2022 UDP Session Model

UDP was "completely overhauled" (✅ SIP022 §3.2), and the model is genuinely different from the AEAD era's per-packet encryption. **Sessions, not packets:** "Each UDP relay session has a unique session ID, which is also used as salt to derive the session subkey. A packet ID acts as packet counter for the session." **The separate header is encrypted with a block cipher, not the AEAD:** "The separate header is encrypted/decrypted with the pre-shared key using an AES block cipher. The body is encrypted/decrypted with the session subkey using an AEAD cipher specific to the session" — 16 bytes on the wire (an 8-byte session ID and an 8-byte big-endian packet ID), with the subkey derived as `blake3::derive_key(context: "shadowsocks 2022 session subkey", key_material: key + separate_header[0..8])` and the AEAD nonce taken from `separate_header[4..16]` (✅ §3.2.1). **Directional separation:** "Servers MUST not use client session IDs as server session IDs" — a deliberate anti-reflection measure. **Routing by session ID, not source address:** "Servers MUST route packets based on client session ID, not packet source address", with each relay session tracking "the last seen client address" so that "UDP sessions [can] survive client network changes" (§3.2.4) — a roaming property directly comparable to WireGuard's ([vpn_guide.md](vpn_guide.md) §3.3). **Sliding-window replay protection:** "Clients and servers MUST employ a sliding window filter for each relay session to check incoming packets for duplicate or out-of-window packet IDs. Existing implementations from WireGuard MAY be used" — with the care that the packet ID may be checked early "but the sliding window state MUST NOT be updated before successful header validation". **Timing floors tied to NAT:** each relay session "MUST be remembered for at least 60 seconds", because "a shorter NAT timeout may allow attackers to successfully replay packets from an already forgotten client session". **Padding is a bounded policy knob:** "implementations MAY allow users to select from a list of predefined padding policies. Care SHOULD be taken to not exceed the network path's MTU when padding packets" (§3.2.3). **And the ChaCha UDP variant is a different shape entirely:** `2022-blake3-chacha20-poly1305` "uses XChaCha20-Poly1305 with the pre-shared key directly and a random nonce for each message", with a 24-byte nonce on the wire and the session ID and packet ID merged into the main header — so the separate-header mechanism does not exist in that mode (§4.1).

### 5.6 The Detection-Prevention Requirements

This is the section of the specification that most directly addresses the probing threat, and it is unusually prescriptive for a wire-format document. The requirements (✅ all quoted from SIP022 §3.1.4, "Detection Prevention"):

- **One write for the salt and headers.** "The random salt and header chunks MUST be buffered and sent in one write call to the underlying socket. Separate writes can result in predictable packet sizes, which could reveal the protocol in use."
- **One read, and no byte-count leak.** "To process the salt and the fixed-length header, servers and clients MUST make exactly one read call. If the amount of data received is not enough for decryption, or decryption fails, or header validation fails, the server MUST act in a way that does not exhibit the amount of bytes consumed by the server. This defends against probes that send one byte at a time to detect how many bytes the server consumes before closing the connection."
- **The RST-versus-FIN trap, and three acceptable strategies.** The specification's reasoning is precise: "do not immediately close the socket. Closing the socket with unread data causes RST to be sent. This reveals the exact number of bytes consumed by the server." It then permits any of three consistent behaviours — always send RST (set `SO_LINGER` with zero timeout and close); always send FIN (shut down the write half, then drain); or shutdown-then-`epoll`-for-`EPOLLRDHUP`-then-read-to-EOF-then-close, which bounds how much the peer can send. The requirement is **consistency**, not a specific choice — because the leak is the *variation*, not the value.
- **Padding or payload must always be present.** "In a request header, either initial payload or padding MUST be present. When making a request header, if payload is not available, add non-zero random length padding." Servers "MUST reject the request if the variable-length header chunk does not contain payload and the padding length is 0." The purpose: eliminate the case where a header's length reveals that the client had nothing to send yet.

Read together, §3.1.4 is an admission. The 2022 designers accepted that the *payload* being random was not sufficient, and that the *connection behaviour* — packet sizes, byte-consumption boundaries, close semantics — is a channel that must be managed deliberately. That is the design philosophy of §2 being revised in real time, in the specification's own text, four years after the measurement literature started saying so.

### 5.7 Adoption Status

**`shadowsocks-rust`** advertises SIP022 support explicitly in its feature list, alongside SIP002, SIP003, SIP003u (plugins with UDP) and SIP004, plus replay-attack defences (✅ README), and a commit adding **EIH (extensible identity header)** support is present in its history (✅ the `bin/` directory's "feat: add eih support" commit, April 2026). **The C implementation (`shadowsocks-c`)** — its README emphasises portability, libuv and static builds rather than enumerating ciphers; SIP022 status was **not established** this pass. ⚠ **`go-shadowsocks2`** — its README does not mention SIP022, and its documented replay defence is the Bloom filter the specification prohibits for 2022 salt storage, so its 2022-edition readiness is **questionable**; this guide does not assert either way. ⚠ **Outline** — its server's current release line and its replay-cache work (a commit of 4 September 2026 concerns resizing a shared `ReplayCache`) indicate active anti-replay engineering, but the documentation did not state SIP022 support in the material extracted. ⚠ **Clients** — SIP002 is the interoperable URI surface, and the SIP002 page notes that "SIP002 is still an optional feature unless the client supports SIP003 plugin" and that for AEAD-2022 the `userinfo` "MUST NOT be encoded with Base64URL" — a practical interop constraint the 2022 edition introduced (✅ SIP002).

### 5.8 What Remains Unresolved in the Design

Stated plainly, without hedging: **(1) No forward secrecy, permanently** — not an oversight but an explicit design decision, restated in the 2022 edition (✅ SIP022 §1); anyone who obtains the PSK can decrypt any recorded session from any time. **(2) No per-user authentication in the base specification** — the wire format authenticates *a* key, not *a user*, and multi-user operation requires an extension (EIH) that is not in the specification text extracted for this guide. ⚠ **(3) The anti-probing measures are behavioural, not cryptographic** — §3.1.4's requirements (one write, one read, consistent RST/FIN, mandatory padding) are instructions about *how an implementation must behave* and cannot be enforced by the protocol; an implementation that ignores them is still wire-compatible, which means probe resistance is a property of *implementations*, not of *the protocol*, and will vary across the ecosystem. **(4) Replay protection is stateful and bounded in time** — both the TCP salt pool (60 seconds, exact-match) and the UDP sliding window are memory-backed and time-limited; the mitigations are sound within their windows, and the security boundary is the window, not the design. **(5) The modification of message sizes is not addressed** — §3.1.4 forbids *predictable* packet sizes from the salt-and-header write and the padding policy is a knob, but there is no packet-size or timing-shaping requirement comparable to what the padding literature would suggest; the USENIX Security 2023 finding about printable-ASCII statistics is a *payload-content* observation rather than a timing one, but the general point stands that the specification's detection-prevention section is a partial answer to a broad problem. ⚠

## 6. Published Attacks

This section walks the literature paper by paper. For each entry the structure is the same: **the mechanism** (at the level of abstraction the published paper itself uses), **the paper**, **the mitigation**, and **whether it is actually fixed in the implementations available in 2026**. Nothing here is an operational recipe; the level of detail is deliberately the level the published papers chose.

### 6.1 The Active-Probing Analysis — IMC 2020

**The paper.** Alice, Bob, Carol, Jan Beznazwy and Amir Houmansadr, *How China Detects and Blocks Shadowsocks*, ACM Internet Measurement Conference (IMC '20), 27–29 October 2020, DOI 10.1145/3419394.3423644 (✅ the paper PDF extracted this pass). The authors are affiliated with the measurement platform GFW Report (three pseudonymous authors), an independent consultant, and the University of Massachusetts Amherst.

**The mechanism.** The GFW's system has two stages, and the paper's Figure 1 states the architecture in one line: "A genuine Shadowsocks client connects to a Shadowsocks server; Once the GFW passively determines that the connection maybe Shadowsocks, it directs its active probers to confirm this guess." (✅). The two stages are:

- **The passive suspicion stage.** The GFW "uses the length and entropy of the first data packet in each connection to identify probable Shadowsocks traffic" (✅ Abstract). That is the entire passive classifier: first-packet length, and first-packet entropy. Note how *little* it needs — no machine learning, no protocol fingerprint, just two statistics calibrated to "this looks like a boundary-pushed random blob".
- **The active confirmation stage.** Once a server is suspected, the GFW "sends seven different types of active probes, in different stages, to the corresponding servers to test whether its guess is correct" (✅ Abstract). The paper's taxonomy is worth recording because it shows what the probes were *for* (✅ §3.2):
  - **Replay-based probes**, whose payloads are derived from the first data-carrying packet of previously-recorded legitimate connections: **R1** (identical replay), **R2** (replay with byte 0 changed), **R3** (bytes 0–7 and 62–63 changed), **R4** (byte 16 changed), **R5** (bytes 6 and 16 changed). R3–R5 were observed only in the Outline experiment; only two R5 probes were seen at all.
  - **Seemingly random probes**: **NR1**, of lengths clustered in trios around 8, 12, 16, 22, 33, 41 and 49 bytes; and **NR2**, of length exactly 221 bytes and "roughly three times as common as all the NR1 probes together".

  The design intent the authors infer is that the probes are "designed to attack detection vulnerabilities in different implementations of Shadowsocks" — a **differential** strategy. Different implementations consume different numbers of bytes before deciding, and fail differently; the probe lengths are chosen to straddle those thresholds.

**The measurement.** 51,837 active probes collected across experiments, from **12,300 unique source IP addresses, all located in China** (✅ §3.3). The dominant autonomous systems were **AS4837 (China169 Backbone)** and **AS4134 (Chinanet)**; other ASes overlapped with the earlier Tor-probing literature, and AS17622 (China Unicom Guangzhou) accounted for a much larger fraction than in the prior work (✅ §3.3). Prober source ports clustered in 32768–60999 — "the default source port range of many Linux kernels" — and no probe used a source port below 1024 (✅ §3.4). TCP timestamps in the SYN segments showed rate structures the authors used to fingerprint the probing infrastructure (✅ §3.4). The paper also notes a network-level side channel indicating the probers, despite using thousands of addresses, are "likely controlled by a set of centralized structures" (✅ Abstract).

**The mechanism's context — the historical vulnerabilities it exploited.** The paper's §2.1 is the definitive short history: BreakWa11's August 2015 malleability finding, the non-termination mitigation, the OTA mode and its unauthenticated length prefixes, the February 2017 AEAD addition, and Zhiniang Peng's February 2020 decryption-oracle disclosure (all ✅, quoted in §4.6 above).

**The mitigation, and its honesty.** The paper says plainly that it presents "a temporary workaround that successfully mitigates the traffic analysis attack by the GFW" and that it "further discuss[es] essential strategies to defend against active probing" (✅ Abstract) — note *temporary*. The work was responsibly disclosed to the developers and, in the authors' words, "has led to more censorship-resistant tools" (✅ Abstract). A companion GFW Report blog post of **January 2021** is titled "A practical guide to defend against the GFW's latest active probing" (✅ gfw.report publications index).

**Is it fixed?** Partially, and the honest answer is that "fixed" is the wrong frame. The **cryptographic** vulnerabilities the probes exploited (malleability, the decryption oracle, unauthenticated length prefixes) are fixed in the AEAD and 2022 editions. The **probing channel itself** is not eliminable by cryptography — which is exactly the lesson of the companion paper below. And the GFW's capability did not stand still: GFW Report documented in **April 2021** that "properly configured Shadowsocks servers" were reportedly being blocked in China (✅ gfw.report, April 2021) — i.e. the mitigations were followed by a new blocking wave within months.

### 6.2 The Probe-Resistance Analysis — NDSS 2020

**The paper.** Sergey Frolov, Jack Wampler and Eric Wustrow, *Detecting Probe-resistant Proxies*, Network and Distributed System Security Symposium (NDSS) 2020, 23–26 February 2020, San Diego, DOI 10.14722/ndss.2020.23087 (✅ the paper PDF extracted this pass; all three authors at the University of Colorado Boulder).

**The mechanism — and it is the single most conceptually important result in this guide.** The paper's insight is that **the design's core defence is itself a fingerprint**. Probe-resistant proxies work by proving knowledge of a secret before responding; an unauthorised prober gets silence. The authors' observation, stated in the abstract, is: **"never responding with data is unusual behavior on the Internet."** Their measurement:

- They probed a dataset of over 400,000 IP/port pairs from a 10 Gbps university ISP tap with a battery of eight probes (HTTP, TLS ClientHello, Modbus, Siemens S7, random bytes, an empty probe, DNS AXFR and STUN) and found they "can elicit responses from nearly all endpoints (94%)" (✅ §I).
- For the remaining 6%, the **failure behaviour** distinguished them: "we find TCP behavior such as timeouts and data thresholds that are unique to the proxies compared to other servers, which provide a viable attack for identifying all existing probe-resistant proxy implementations" (✅ §I).
- They trained a **multi-class decision tree** on the tap dataset plus synthetically generated proxy samples, with classes `not-proxy`, `lampshade`, `mtproto`, `obfs4`, `ossh` and `shadowsocks-python`. The tree's split features are abort timing, TCP close type (FIN vs RST) and per-probe response — exactly the surface §5.6 of this guide shows the 2022 specification attempting to manage.
- Critically for this guide, the paper describes the AEAD-era server behaviour precisely: **"In the AEAD-mode, both server implementations wait to receive 50 bytes from the client, and if the AEAD tag is invalid, the server closes the connection."** (✅ §II-B-3). A fixed 50-byte read threshold is a measurable constant.

The paper covers five protocols — `obfs4` (Tor), Lampshade (Lantern), Shadowsocks, MTProto (Telegram) and Obfuscated SSH (Psiphon) — and finds ways to probe and distinguish every one. It reports working with the developers of Psiphon, Lantern, obfs4 and **Outline Shadowsocks** to deploy the suggested changes (✅ §I).

**The mitigation.** The paper's own remedy is behavioural: make proxies harder to distinguish from ordinary servers by **mimicking the response distribution of real services** — closing like a normal server would, at timings within the normal range, rather than uniformly going silent or closing on a fixed threshold. In practice this is the ancestor of the 2022 specification's §3.1.4 requirements.

**Is it fixed?** No — and the paper's point is that it is not *fixable* in the sense of "make the class undetectable". Silence is a choice with a statistical cost. What the ecosystem can do is reduce the distinguishability of that choice, and the 2022 specification attempts exactly that. Whether the resulting distribution is close enough to real traffic is an open empirical question. ⚠

### 6.3 The Passive Fully-Encrypted-Traffic Detection — USENIX Security 2023

**The paper.** Mingshi Wu (GFW Report), Jackson Sippe, Danesh Sivakumar, Jack Burg, Peter Anderson, Xiaokang Wang (the V2Ray project), Kevin Bock, Amir Houmansadr, Dave Levin and Eric Wustrow, *How the Great Firewall of China Detects and Blocks Fully Encrypted Traffic*, 32nd USENIX Security Symposium, August 2023, Anaheim CA, pages 2653–2670 (✅ the USENIX proceedings page and BibTeX record extracted this pass).

**Why it matters more than any other result here.** The abstract states the significance directly: "In early November 2021, the Great Firewall of China (GFW) deployed a new censorship technique that passively detects—and subsequently blocks—fully encrypted traffic in real time. The GFW's new censorship capability affects a large set of popular censorship circumvention protocols, including but not limited to **Shadowsocks, VMess, and Obfs4**. Although China had long actively probed such protocols, **this was the first report of purely passive detection**, leading the anti-censorship community to ask how detection was possible." (✅).

**The mechanism — an inversion worth understanding.** "We find that, instead of directly defining what fully encrypted traffic is, the censor applies crude but efficient heuristics to **exempt traffic that is unlikely to be fully encrypted traffic**; it then blocks the remaining non-exempted traffic." (✅ Abstract). The classifier does not ask "is this Shadowsocks?" It asks "can I recognise this as *anything*?" — and anything it cannot recognise falls into the blocked residue. The heuristics are named in the abstract: "the fingerprints of common protocols, the fraction of set bits, and the number, fraction, and position of printable ASCII characters" (✅).

**The measurement and the uncertainty.** The authors' Internet scans "reveal what traffic and which IP addresses the GFW inspects"; they "simulate the inferred GFW's detection algorithm on live traffic at a university network tap to evaluate its comprehensiveness and false positives" and "show evidence that the rules we inferred have good coverage of what the GFW actually uses" (✅). They estimate the collateral cost: "if applied broadly, it could potentially block about 0.6% of normal Internet traffic as collateral damage" (✅). That number is the closest thing the literature has to a false-positive rate for the real system, and it is an *estimate from a simulated deployment*, not a measurement of the GFW's own error rate — a distinction the authors are careful to draw and this guide preserves. ⚠

**Note the class definition.** "Fully encrypted traffic" is not a description of a protocol property; it is the censor's *category*, defined by its classifier. Traffic is "fully encrypted" when the classifier cannot exempt it. This is the single most useful reframing in the whole literature: the design goal of looking like nothing is, from the classifier's perspective, a *membership criterion* for a small and blockable class.

**The mitigation.** "Our understanding of the GFW's new censorship mechanism helps us derive several practical circumvention strategies. We responsibly disclosed our findings and suggestions to the developers of different anti-censorship tools, helping millions of users successfully evade this new form of blocking." (✅ Abstract). The strategic implication, at the conceptual level: protocols that imitate an allowed protocol (TLS-like designs — Trojan, REALITY) have an exemption to earn, whereas protocols that aim to be classless have nothing to present. That is the arc the ecosystem followed (§8.6).

**Is it fixed?** The specific heuristics were circumvented by the tools that responded to the disclosure, and the cat-and-mouse continued (§7.4's timeline records the 2025–2026 iterations). As a *class* problem it is not closed, and the paper's own framing makes clear why: any fixed statistical test of "is this unrecognisable?" can always be answered by *being recognisable as something allowed* — which is a different design decision, not a patch.

### 6.4 The Stream-Cipher Attacks

Two disclosures, both documented in the IMC 2020 §2.1 history. **August 2015 — address-type enumeration via ciphertext malleability (credited to BreakWa11).** Because the stream ciphers provided confidentiality without integrity or authentication, and because the first plaintext byte after the target framing is a 1-byte address type with only three legal values, an attacker could flip that byte's ciphertext equivalent and observe whether the server's behaviour changed — "a known fraction of connections will time out differently from the rest" (✅). The server becomes a **confirmation oracle** for the protocol's presence. The mitigation sequence was: a behavioural patch not to terminate on unknown address types; then **OTA**, giving each chunk its own authenticator, defeated because the *length prefixes* remained unauthenticated; then **February 2017**, when AEAD ciphers entered the specification, "fixing this authentication problem" (✅ all three). **February 2020 — the server as a decryption oracle (Zhiniang Peng).** "Using the Shadowsocks server as a decryption oracle, an attacker, without knowledge of the shared master password, can get full decryption of recorded Shadowsocks connections" (✅) — retroactive decryption of recorded traffic with no key knowledge required; the IMC 2020 authors call it "devastating". **Status in 2026: fixed by construction in the AEAD and 2022 editions**, since the vulnerability lived in the primitive rather than the framing. The stream ciphers remain *enumerable* in the SIP002 method list ✅, so a deployment still configured for them would still carry the weakness — a configuration-hygiene statement, not a protocol statement.

### 6.5 The Replay Attack

**The mechanism.** The AEAD construction's salt is random, client-chosen, and — in the base design — not bound to single use. A censor that records a legitimate session can replay its bytes: they are valid ciphertext under a valid salt, so the server has no way to know they are a copy, and the success of the replay *confirms* the server's identity. The mitigation was implemented at the **implementation level rather than in the specification**, and the implementations diverged: `go-shadowsocks2` documents a **Bloom filter** (default capacity one million recent connections, false-positive rate 1e-6, disable-able), while the **2022 edition mandates an exact-match salt pool** held 60 seconds and **prohibits Bloom filters outright** on false-positive grounds (✅ SIP022 §3.1.5) — because a false positive means rejecting a legitimate connection. The 2022 edition also added the direction-identifying **type** byte, which the specification says makes outgoing-salt pooling unnecessary (✅). The source of record is the project discussion `shadowsocks-org` issue #44, "Defend against replay attack" (2017), cited by IMC 2020 as ref [40] and listed as a feature by both `shadowsocks-rust` and `go-shadowsocks2` (✅ all three). **Status: fixed in the specification and modern implementations — but stateful and time-bounded**, the security boundary being the 60-second window rather than the construction (§5.8).

### 6.6 The Traffic-Analysis and Fingerprinting Results

Three results establish that *an encrypted payload does not protect the traffic's shape*: **Zhao, Ma, Li, Yu and Li, *Revisiting Website Fingerprinting Attacks in Real-World Scenarios: A Case Study of Shadowsocks***, International Conference on Network and System Security (NSS), Springer 2018, pp. 319–336 (✅ cited in the IMC 2020 bibliography, ref [58]); **Zeng, Chen, Shao, He, Han, Wen and Wang, *Flow Context and Host Behavior Based Shadowsocks's Traffic Identification***, IEEE Access 7 (2019), pp. 41017–41032, DOI 10.1109/ACCESS.2019.2907149 (✅ ref [57] there); and **Deng, *The Random Forest based Detection of Shadowsock's Traffic*** (2017) (✅-secondary via Wikipedia; ⚠ primary text not extracted). Collectively: packet sizes, directions, inter-arrival timing and the behaviour of the *host* around the flow are an independently sufficient classification signal regardless of payload encryption — the same conclusion the NDSS 2020 probing work reached from the other direction, and why §5.6 exists in the 2022 specification.

## 7. Detection and Measurement Literature

### 7.1 The Entropy Assumption and Its Refutation

The design's founding assumption — stated in the specification's own words, "indistinguishable from a random byte stream" (✅ SIP022 §1) — had a corollary the literature spent a decade dismantling: **that high-entropy traffic carries no information a classifier can use**. The refutation came in two distinct forms, and it is worth keeping them apart because they correspond to two different failure modes.

**Form 1 — entropy *itself* is a feature (2019–2020).** The GFW's passive stage, as documented by IMC 2020, does not treat randomness as a shield. It treats it as a *signal*: "the GFW uses the length and entropy of the first data packet in each connection to identify probable Shadowsocks traffic" (✅ IMC 2020 Abstract). This is the elegant and slightly cruel part. Traffic that is compressed or encrypted has high per-byte entropy; the entropy of *ordinary* traffic is usually lower because protocol headers, text and structure reduce it. So "looks like random bytes" is not the absence of a feature — **it is a positive feature with a name**. And the *combination* with first-packet length narrows it further: a first packet consisting of a fixed structural prefix plus a random blob has a length distribution that a censor can learn.

**Form 2 — the content of "random" bytes is statistically non-uniform in measurable ways (2023).** The USENIX Security 2023 result went further: even without matching a protocol, the classifier used "the fraction of set bits, and the number, fraction, and position of printable ASCII characters" (✅) — the last of these being the subtle one. Encrypted payloads *should* be uniform in the printable-ASCII sense, and the classifier's use of printable-ASCII statistics as an **exemption** criterion means it is measuring something about the *plaintext-structure likelihood* of the traffic. The precise mechanism is the paper's own inference from measurement, not a published statement of the GFW's source; the paper is explicit that it *infers* the algorithm and validates the inference against live traffic (✅).

**The honest synthesis.** The design assumption was not stupid — for a period, against a passive classifier with no statistical sophistication, appearing random worked. What the literature established is that the assumption was **unfalsifiable in the design's own terms**: "looks random" is a property that a classifier can measure, and once measured it becomes a decision boundary. The correct statement is not "random bytes can be classified" but the sharper one: **"random bytes are a class."**

### 7.2 The Fully-Encrypted-Traffic Result in Detail

Three aspects of §6.3 deserve separate emphasis. **The date:** the deployment was "early November 2021" and the publication August 2023 (✅) — a ~21-month gap between capability and public understanding, a data point for reasoning about how long a detection capability may exist before it is documented (⚠ that gap is a property of this one case, not a general estimate). **The direction of the logic:** the classifier is defined by **exemption** ("instead of directly defining what fully encrypted traffic is, the censor applies crude but efficient heuristics to exempt traffic that is unlikely to be fully encrypted traffic", ✅), which inverts the usual DPI mental model and means the defensive target is not "be unrecognisable" but "be recognisable as something permitted" — opposite engineering objectives, and the one the protocol's founding choice ruled out. **The stated cost:** the authors estimate that "if applied broadly, it could potentially block about 0.6% of normal Internet traffic as collateral damage" (✅) — an estimate from simulating the inferred algorithm on a university tap, not a measurement of the GFW's own error rate, a distinction the authors draw and this guide preserves. It does tell you the economics: the censor accepted a real collateral cost, implying either high value on blocking this class or high tolerance for over-blocking.

### 7.3 Probe Resistance and Protocol Fingerprinting

The probing literature's contribution is a generalisable principle, and it is worth stating as a rule: **an omission is not an absence of information.** A protocol that does not respond, does not declare a version, or does not authenticate is *not* invisible — it has a behaviour profile, and behaviour profiles are measurable.

- **NDSS 2020** established this for probe resistance: non-response is rare, and the byte thresholds and close semantics that produce it are distinctive (✅ §6.2).
- **IMC 2020** established the complementary result for the probing *infrastructure*: probes can themselves be fingerprinted — source-port distribution (Linux ephemeral ranges), TTL ranges (46–50), IP-ID sequences showing "no clear pattern", and TCP timestamp rates — and the prober address pools overlap only slightly with those observed in the earlier Tor and Ensafi-era probing studies while being strongly concentrated in AS4837 and AS4134 (✅ §3.3–§3.4). The authors compare their prober IP list against "934 that were observed to send active probes to Tor servers in 2018 by Dunna et al." and "22,000 that were observed to send various types of active probes between 2010 and 2015 by Ensafi et al." and find "three sets overlap only slightly" (✅ §3.3).
- **The protocol-fingerprinting angle.** The IMC 2020 work also observed that *different implementations respond differently*, which is why its probes came in seven length classes — an implicit demonstration that implementations, not just protocols, are fingerprintable. The 2022 specification's §3.1.4 requirements exist precisely to squeeze that variance out.

### 7.5 The Contested Part

Two things in this literature are genuinely unsettled, and this guide flags both rather than resolving them.

**First, the blocking-versus-measurement contradiction.** The IMC 2020 paper records a direct contradiction in the record: "Since as early as October 2017, Internet users in China have reported their Shadowsocks servers being blocked, by port or IP address. Notable blocking events were reported in October 2017 and January 2018, at the same time as two important political congresses in China. After the two congresses, many users reported their servers got unblocked. **Contrary evidence comes from Wiley et al., who during those times were testing Shadowsocks reachability every day from locations around the world, but reported not having seen any evidence of Shadowsocks blocking anywhere.**" (✅ IMC 2020 §2.2). Anecdotal user reports and systematic reachability testing disagreed for at least two years — an important epistemics lesson: **user-reported blocking is not measurement**, and systematic measurement can miss phenomena that are localised, temporal or configuration-dependent. The reported waves correlated with politically sensitive periods (✅ the same passage lists the Tiananmen 30th anniversary, the PRC 70th anniversary and the 4th Plenary Session of the 19th Central Committee), and the most recent wave the paper covers began around **16 September 2019** (✅).

**Second, the limits of the measurement's vantage points.** Both major papers are candid about this. IMC 2020's limitations section notes: "The locations of our vantage points lack some diversity, making us less likely to observe any potential inconsistencies in the probing system caused by geolocation." (✅). NDSS 2020's tap is one 10 Gbps university ISP vantage point plus ZMap scanning; its decision tree is trained on that dataset and its false-positive claim is scoped to it ("with negligible false positives **in our dataset**", ✅ Abstract). USENIX Security 2023 simulates its inferred algorithm on a university tap rather than measuring the GFW directly. **Every quantitative result in this guide's §6–§7 is vantage-point-scoped**, and any claim of the form "the GFW does X to all traffic" would be overreach.

### 7.6 The Honest Conclusion

Stated as plainly as the evidence allows: **"It looks like random bytes, so it cannot be classified" was a design assumption, and the measurement literature has not left it standing** — the GFW's passive stage used first-packet length and entropy as a positive signal (✅ IMC 2020), that is, randomness *as* a feature, and the 2023 result extended this to a purely passive classifier of the whole fully-encrypted class (✅ USENIX Security 2023). **And the decisive defeat was not statistical but architectural:** even a perfect payload ciphertext would not have helped against the probing stage, because the leak was in *behaviour* — response timing, byte thresholds, close semantics (✅ NDSS 2020); that is a channel the protocol's cryptography has no reach into, and the 2022 specification's response to it is a set of behavioural rules rather than a cryptographic guarantee (§5.6, §5.8). **What remains contested is generality and mechanism:** whether the GFW's heuristics generalise to other censors is unmeasured; whether the passive classifier's precise rule set is as inferred is an inference (the authors validate an inferred algorithm rather than reading the censor's code); and the historical contradiction between user reports and systematic measurement is unresolved (✅ §7.5). This guide asserts the *shape* of the findings, cites them to their sources with dates, and does not assert more specificity than the papers themselves claim. **The practical corollary, stated at the design level rather than the operational level:** a protocol whose camouflage strategy is *absence* has nothing to present to an exemption-based classifier, whereas a protocol whose strategy is *imitation* has something. That distinction — absence versus imitation — is the axis on which the family's subsequent evolution turned (§8.6), and it is the design lesson §11 develops.

### 8.2 The C Implementation's 2026 Rename

One ecosystem change is recent enough to be absent from almost every secondary source, and it is worth recording precisely because it is exactly the kind of fact a guide like this exists to get right.

- "In September 2026, the C implementation was modernized with a focus on self-contained builds and portability." Specifically: a build-modernisation change "bundled pinned dependency sources, removed several external dependencies, and added static-build validation across platforms", and a subsequent migration "replaced **libev** with **libuv**, added Windows IOCP and macOS kqueue support, expanded asynchronous runtime DNS coverage, and strengthened CI lint checks."

- Compatibility is explicitly preserved: "Commands such as `ss-local` and `ss-server`, the `shadowsocks.h` API, and the embedding library ABI remain compatible", and legacy library filenames and package names remain available as aliases.

The significance: **the family's second implementation, twenty years of whose lineage the community has carried, was declared a maintenance fork whose future development lives in Rust** — and then, in the same year, was revived with a runtime migration. That is an unusual and informative maintenance story: the "abandoned C project" narrative that circulates in secondary sources is, as of September 2026, wrong.

### 8.4 The SIP003 Plugin Layer

The plugin layer is the family's answer to the fact that a random byte stream is a class (§7.1). Rather than change the protocol, SIP003 lets an unmodified endpoint have its traffic transformed by a separate process. **What SIP003 specifies** (✅ all from shadowsocks.org/doc/sip003.html): the design is "very similar to the Pluggable Transport plugins from Tor project. Unlike the SOCKS5 proxy design in PT, **every SIP003 plugin works as a tunnel (or called local port forwarding)**"; plugin processes are **child processes** of the client or server, exiting with an error code on failure and terminated with the parent; arguments pass by **environment variable** (four MUST-HAVE variables plus optional `SS_PLUGIN_OPTIONS`, with escaping rules); and two restrictions matter — "**Plugin over plugin is NOT supported.** Only one plugin can be enabled when a shadowsocks service is started", and "**Only TCP traffic is forwarded.** For now, there is no plan to support UDP traffic forwarding." The one-plugin restriction is architecturally significant: the transformations do not compose, so the operator picks one strategy. (The later SIP003u addresses the UDP gap — `shadowsocks-rust` lists it separately, ✅.) Plugins being separate processes, "they can pick any license they like."

**What the plugins transform** (this guide states the transformation class, not a deployment recipe):

| Plugin | What it changes | Status |
|---|---|---|
| **`simple-obfs`** | Rewrites the stream to resemble an ordinary HTTP or TLS exchange, with a *failover* option so a server can pass unrecognised traffic through to a real web server — i.e. a plausible-protocol *appearance* plus a decoy | ✅ **Deprecated**, superseded by `v2ray-plugin` |
| **`v2ray-plugin`** | Wraps the stream in the V2Ray transport family (including WebSocket-over-TLS style shapes), giving the traffic a genuine TLS/HTTP appearance | ✅ listed in SIP003's "Known good" plugins and named in the deprecation notice |
| **`kcptun`** | **Not a camouflage plugin — a transport substitution**: carries the stream over KCP, a reliable ARQ protocol over UDP, with FEC. Canonical upstream `xtaci/kcptun`; `shadowsocks/kcptun` is a fork | ✅ verified; the repository names `xtaci/kcptun` as the single endorsed upstream |
| **`GoQuiet`**, **`Cloak`**, **`obfs4-tunnel`** | Camouflage-oriented plugins on SIP003's "Known good" list; `obfs4-tunnel` is named explicitly as the pattern for adapting Tor's Pluggable Transports | ✅ existence and listing via SIP003; ⚠ what each transforms in detail not verified this pass |

The honest observation about this layer: the two most widely referenced plugins both move the traffic **toward looking like TLS or HTTP** — i.e. toward *imitation* rather than absence, exactly the direction §7.6's design lesson points. The 2022 specification's §3.1.4 is an attempt to make the base protocol defensible enough that the plugin layer is optional rather than necessary; the plugin layer's continued existence is evidence that the base protocol's designers did not consider that attempt complete.

## 9. Legal, Compliance and Ethical Reality

This section is descriptive. It states what the sources say about the legal position, dates every claim, and does not advocate.

### 9.1 The Jurisdictions Where It Is Restricted

The pattern across restrictive jurisdictions is consistent and specific: **the regulated act is generally operating, providing or selling circumvention services — not possessing software.** The names below are those for which this guide found a dated source this pass.

- **China.** VPNs are "heavily restricted and unauthorized usage can be subject to fines and legal prosecution" (✅ Wikipedia, *Internet censorship in China*, citing its own sources — secondary); the same article reports that "as of 2022, around 3% of Chinese citizens were estimated to use VPNs" and that the Asia Society estimated in 2026 that usage remained "in the low single digits" (✅-secondary, ⚠ the underlying estimates' methodology is not visible). The **criminal enforcement precedent** is the **Deng Jiewei** case: a 26-year-old from Dongguan, Guangdong, **sentenced to nine months in prison** for selling VPN software; the judgement was posted by the **Supreme People's Court**; he **began offering the software in October 2015**, was **detained in August 2016**, formally arrested, and the sentencing was reported in **early September 2017** (✅ The Register, 5 September 2017; ✅ BBC News, September 2017; ✅ South China Morning Post; ✅ The Hacker News — four independent contemporaneous reports agreeing on the sentence, the province, the age and the 2015 start date; one outlet frames it as "the first conviction under the new crackdown", ⚠ on the "first" claim specifically). Note the charge framing reported: the offence was **selling/providing**, not using.
- **Russia.** **Federal Law No. 276-FZ (2017)** prohibits providing tools to bypass blocks for prohibited resources; a separate framework requires services operating in Russia to connect to the state system and filter per the register, with non-compliance leading to restriction (✅ Freedom House, *Freedom on the Net 2024*, Russia country report — "A 2017 law mandates the blocking of VPN services that allow their clients to access banned content"; ✅ multiple legal-summary sources agreeing). Freedom House records that **Roskomnadzor began enforcing this in March 2019**, sending ten VPN services a request to connect to the state information system (✅ Freedom House 2024). In **March 2024**, a **Roskomnadzor order (No. 196)** banning the **popularisation** of circumvention tools took effect (✅ two independent summaries; ⚠ the order number is reported consistently by legal-summary sources but was not confirmed at a government primary source this pass), and **advertising of VPNs was banned in 2024** (✅ Meduza, April 2026 — "a law banning circumvention of blocked websites appeared in 2017, authorities began mass-banning VPN services from 2021, and in 2024 their advertising was banned"). Most recently, **April 2026**: Meduza reports Russia blocking VPN access to major platforms and moving to **charge for mobile VPN traffic**, describing a new enforcement push (✅ Meduza, 30 April 2026). ⚠ Note the nuance the legal summaries consistently draw: there is **no direct prohibition on an individual using a VPN for good-faith purposes** under 276-FZ; the regulated conduct is the *provision* of bypass tools.
- **Other restricted jurisdictions.** Aggregated reporting identifies a further list — **Iran, Turkmenistan, Belarus, North Korea, Turkey, Iraq, Myanmar and the UAE** appear across the sources surveyed, generally on the basis of blocking, licensing requirements or criminal prohibition (⚠ these are aggregation-level claims from secondary sources; penalties are reported as ranging "from ISP blocking and heavy fines to provider shutdowns and, in the strictest regimes, potential criminal" consequences). This guide asserts the *existence of restrictions* in these jurisdictions and does **not** assert specific statutory citations or penalty ranges, because none was verified at a primary source this pass. ⚠
- **A licensing case rather than a ban — Indonesia.** Reported as having "no criminal prohibition, but licensing demands raised since 2019 and no clear enforcement" (⚠ secondary, dated 2026 reporting; not verified). Included to show that "restricted" is not binary.

### 9.2 The Jurisdictions Where It Is Ordinary

In most jurisdictions — the European Union, the United Kingdom, the United States, Japan, Singapore, Australia and most of the rest of the world — running a proxy or a VPN is **ordinary network engineering**. It is what a corporate egress gateway does; it is what a data-centre operator uses to route traffic out of a filtered region; it is a standard tool in the security researcher's kit; and the protocol itself is a MIT-licensed open-source project whose specification is published on a public website (✅ shadowsocks-org is MIT-licensed; ✅ the original project was MIT-licensed per Wikipedia's article metadata).

Two qualifications keep this honest. First, **legality of the tool says nothing about legality of the act performed through it** — which is a widely-stated and trivially correct principle, and it cuts both ways (using a proxy for fraud is fraud; using one to read a foreign newspaper is not a crime in most places, and is one in others). Second, **the local rule applies where the operator is**, not where the traffic transits — so a service hosted in a permissive jurisdiction and used from a restrictive one is subject to both regimes, which is precisely why the enforcement record is dominated by cases against *operators*.

### 9.3 Using Versus Operating — the Distinction That Decides Most Cases

This is the most useful single distinction in the whole legal picture, and it is worth stating as a rule:

- **Operating or providing** a circumvention service is the act that restrictive jurisdictions criminalise or regulate. The Deng Jiewei conviction was for **selling** VPN software (✅). Russia's 276-FZ is framed around **providing** bypass tools and the obligation on services to filter (✅). China's licensing regime regulates the provision of international network access.
- **Using** is, in several of those same jurisdictions, either not directly addressed by the statute (Russia, per the legal summaries in §9.1 ⚠) or addressed at the administrative level (blocking, throttling, account action) rather than criminally. In China, unlicensed use can attract fines and prosecution per Wikipedia's summary (✅-secondary), and the practical enforcement pattern has historically focused on sellers and large-scale operators.

The operational corollary for a **corporate** reader: the firm running an internal egress proxy is on the "operating" side of that line *for its own users*, which is why the enterprise control question in §10 is about governance and logging, not about legality.

### 9.4 The Corporate-Policy Dimension

**A bank blocks this class of software regardless of whether it is legal — and the reasons are not about foreign censorship law at all.** Four separate concerns, each sufficient on its own:

1. **The unmanaged tunnel defeats the egress control plane.** A regulated firm's network controls are built on the premise that traffic leaving the estate is inspected, filtered and logged: DLP on egress, web filtering, CASB or equivalent policy enforcement for sanctioned destinations, and the audit trail that a regulator's examination will eventually request. A client-side encrypted proxy **bypasses all of it** — and it does so *legitimately* from the user's perspective, which is what makes it hard to govern. Compare [vpn_guide.md](vpn_guide.md)'s §7.2 on split-tunnel risk: the split-tunnel client at least has a managed path and a kill switch; an unmanaged third-party proxy has neither.
2. **The proxy class is indistinguishable from an exfiltration channel — because it *is* one.** The protocol is a general-purpose encrypted relay. The same construction that carries a user's browser traffic to a foreign news site carries a database dump to a cloud host. From the network's point of view these are the same flow, and §12 works through exactly that problem.
3. **Shadow IT and the unenrolled endpoint.** Installing a proxy client typically requires either an unmanaged device on the network or a modification (extension, profile, agent) to a managed one. Both are control failures independent of the traffic: the device's posture becomes unverifiable, and the software supply chain for the client is whatever the user happened to download. Compare [security_by_design_guide.md](security_by_design_guide.md) on third-party component risk and [threat_modeling_guide.md](threat_modeling_guide.md) on the insider/threat-actor boundary.
4. **Regulatory expectations of data governance.** For a financial institution in Singapore, the data-governance obligations frame where data may go and what must be evidenced about the path it took. A channel that cannot be logged cannot be evidenced. Cross-ref [Financial Risk & Compliance Systems](../banking/financial_risk_compliance_systems_guide.md) for the op-risk treatment and [Banks in Singapore](../banking/banks_in_singapore_guide.md) for the regional frame. ⚠ The specific regulatory instrument is a matter for the firm's compliance function, not for a protocol guide; this guide asserts the *control* consequence and not a citation.

The management expression of all four is a **policy** decision — an acceptable-use rule that prohibits unapproved tunnelling and proxy software, paired with a **detection capability** (which §12 shows is harder than it sounds) and a **legitimate alternative** (which §10 shows is the managed remote-access estate of [vpn_guide.md](vpn_guide.md)).

### 9.5 The Sanctions and Export-Control Interface

Two distinct interfaces exist, and they should not be conflated.

- **Sanctions and the provision of circumvention services.** Providing communications tools to users in sanctioned jurisdictions raises questions under sanctions regimes, and the interaction between "supporting free access to information" and "providing a service to a sanctioned person or entity" is genuinely contested terrain. ⚠ **This guide does not assert any specific licence, general licence, or regulatory provision**, because none was verified at a primary source this pass. What can be said safely: the question exists, it has been publicly discussed, and any organisation contemplating providing proxy infrastructure across a sanctions boundary should treat it as a legal question requiring counsel — not as a protocol question.
- **Export control on the interception side.** The more concrete and better-documented interface is on the *censor's* side: the sale of deep packet inspection, network-filtering and lawful-interception platforms to restrictive states is regulated in several jurisdictions as export-controlled dual-use technology. The relevance to this guide is direct — the detection capabilities documented in §6–§7 are products of that industry, and the **September 2025 Geedge/MESA leak** analysis published by GFW Report (✅ §7.4) is, per that analysis, the largest documentary corpus yet obtained from the censor's side of that market. ⚠ This guide notes the leak's existence and the platform's published analysis; it has not examined the leaked material and makes no claims about its contents, and it does not assert a specific export-control citation.
- **The general point.** Both interfaces follow from the same fact stated in §1.2: this is a **dual-use** protocol family. An encrypted relay that defeats censorship defeats inspection. Any legal analysis that treats the two uses as separable is missing the engineering.

### 9.6 The Ethics of the Dual Use

Stated without moralising and without advocacy:

**The same properties serve both directions, and they are not incidental.** A protocol designed for indistinguishability on the wire has, by construction:
- a general-purpose encrypted relay that any client can drive to any target — which is a command-and-control channel when the client is malware;
- no server-side content inspection and no per-connection authorisation the operator can act on beyond "the peer had the key" — which is a data-exfiltration path when the client is a compromised endpoint;
- no logging requirement and no metadata the operator must retain — which is operational security when the client is a malware operator;
- and ciphertext with no recognisable structure — which defeats the network-level detection that would otherwise catch either of the above.

Three honest observations follow.

1. **The overlap is complete, and this is the strongest legitimate argument for defensive interest in the protocol.** A security team cannot protect against the exfiltration use without understanding the protocol — and understanding it means reading the same specifications and the same measurement literature that the circumvention use reads. That is why this guide's framing sentence is what it is: this is dual-use engineering, and studying it is ordinary security work.
2. **Intent is not visible on the wire.** The measurement literature in §6–§7 is a study of *classification*; none of it distinguishes a journalist's browser session from a malware beacon, because at the network layer there is nothing to distinguish. Any policy that assumes the two cases can be separated technically is built on a false premise, and §12 works through the consequence.
3. **Where the law is unsettled, say so.** The legality of *using* circumvention tools ranges from protected (most jurisdictions) through administratively discouraged (some) to criminally enforced (a specific list, §9.1) — and the enforcement record is dominated by operators, not users (§9.3). The legality of *providing* them across a sanctions boundary is contested (§9.5). The status of the *protocol* is not: it is a published, MIT-licensed specification, and reading it is lawful everywhere. This guide is written at that layer — the protocol, the cryptography, the literature and the law — and stops where operational guidance would begin.

## 10. The Enterprise and Legitimate-Use Angle

This section is deliberately short, because its job is to establish a contrast, not to argue a case.

**There is a legitimate enterprise use.** An application-level encrypted proxy is a standard component of ordinary network engineering: it lets an application (or a whole host, via transparent redirection) egress through a chosen point for reachability or policy reasons; it works where a routed tunnel cannot, because it is per-connection rather than per-interface; and it needs no PKI, no gateway appliance and no client management plane. The proxies in `ss-local`/`ss-remote` form are also, in practice, an egress-routing primitive — that is a legitimate reading of the protocol, and different implementations expose it as such (netfilter TCP redirect, PF redirect, and transparent-proxy inbounds all appear in the implementations' own feature lists, ✅ go-shadowsocks2 and shadowsocks-rust READMEs).

**Why a regulated firm treats it as a control problem anyway.** Not because the tool is unlawful — in Singapore it is not — but because the *managed* alternative exists and the unmanaged version fails four governance tests. The managed remote-access pattern in [vpn_guide.md](vpn_guide.md) §5 requires: a **device identity** (the VPN authenticates the machine, and the MDM provisioned the key); a **user identity** routed through the firm's IdP with MFA; a **posture check** before and during access; **per-group policy** on what the tunnel may reach; and **accounting** — the gateway logs that feed the SIEM and satisfy the audit trail ([vpn_guide.md](vpn_guide.md) §5.4). An unmanaged third-party proxy client supplies **none of the five**. It has one property the managed tunnel lacks — it is invisible on the wire — and that property is precisely what disqualifies it, because invisibility to the censor and invisibility to the *estate's own monitoring* are the same property. Compare [vpn_guide.md](vpn_guide.md) §7.2's split-tunnel ledger: split tunnel at least leaves the estate a managed path, a client it controls and a kill switch it configured. A third-party proxy leaves it nothing.

**The framing that makes the enterprise position coherent.** The firm is not making a judgment about censorship or about the tool's other uses. It is applying the ordinary rule that **all egress from a regulated estate must traverse an inspected, logged, policy-enforced path** — and it is noting that this protocol family's central design property is the deliberate defeat of exactly that. Cross-ref [Beyond Zero Enterprise Security](beyond_zero_enterprise_security_guide.md) for the identity-aware data-plane framing, [Zero Trust Network Architecture](zero_trust_network_architecture_guide.md) for why the replacement for "is this traffic on a trusted network" is "is this request authorised, for this identity, now", and [Business Case Development](../management/business_case_development_guide.md) for the investment framing of an egress-control and DLP programme. The legitimate-use answer is not "block proxies"; it is "provide a managed path that is better than the workaround, and detect the residual."

## 11. The Lesson for Protocol Designers

Four engineering lessons, each cited to the work that established it. They are stated as design principles, not as advice about any particular deployment.

**1. An unauthenticated design is probeable, and this is a good-faith failure of the founding assumption.** The designers omitted the handshake deliberately and documented the trade (✅ SIP022 §1). The failure was not that they chose wrongly given their threat model — it was that their threat model assigned zero capability to a censor that *acts on* a suspicion. Once the censor can connect and observe the response, the absence of an authentication exchange stops being a hiding place and becomes a **differential oracle**: the server's behaviour on a bad probe differs from its behaviour on no probe, and across implementations it differs differently (✅ NDSS 2020's 50-byte read-then-close finding; ✅ IMC 2020's seven probe classes). **Design principle: assume the adversary will interact with your endpoint, and design the failure path with as much care as the success path.** SIP022's §3.1.4 is this principle applied retroactively, in a document that admits the failure by legislating the byte-count and close-semantics behaviour it should have specified at the start.

**2. Shipping confidentiality without integrity is not a weaker version of the right thing — it is a different thing, and it cannot be patched into the right thing.** The confidentiality-only design produced two independent breaks: ciphertext malleability enabling address-type enumeration (✅ August 2015) and a server-as-decryption-oracle attack yielding retroactive decryption of recorded traffic (✅ February 2020). The intermediate mitigation — OTA — is the case study: it authenticated the payload but not the framing, and the framing was the attack surface (✅ IMC 2020 §2.1). **Design principle: integrity is not an incremental improvement on confidentiality; it is a precondition for using confidentiality safely, and any mitigation that does not add an authenticator over *every* field an attacker can influence is not a fix.** This is exactly the territory [security_by_design_guide.md](security_by_design_guide.md) covers from the process side — and this family's history is the discipline's canonical negative example.

**3. "Indistinguishable from random" is a class, not an escape from classification.** Two results establish this independently: the passive stage that uses first-packet **entropy** as a positive signal (✅ IMC 2020 Abstract), and the passive classifier that exempts recognisable traffic and blocks the residue using set-bit and printable-ASCII statistics (✅ USENIX Security 2023 Abstract). **Design principle: a camouflage strategy must answer "what does this look like to a classifier that works by exemption?", and "nothing" is an answer with a target on it.** The corollary the ecosystem has already acted on: imitation designs (Trojan's stated thesis of imitating a common service; REALITY's borrowing of a real site's TLS behaviour) have something to present, at the cost of a different detection surface — as the October 2022 report of large-scale blocking of TLS-based circumvention tools shows (✅ gfw.report).

**4. A community specification process patching a deployed protocol behaves differently from a standards body — and the difference is legible in the artefact.** Four observable differences, all visible in the documents cited here. **The specification is retrospective and remedial** — SIP022's abstract announces that it "addresses well-known issues of the previous editions" (✅), a sentence an IETF document would rarely contain, because a standards body's v2 is not usually framed as a bug-fix release for a deployed v1. **The specification carries implementation instructions that are not protocol requirements at all** — §3.1.4's one-write/one-read rules, the three acceptable close strategies and the mandatory padding-or-payload rule (✅) are *behavioural* specifications written to close an *empirical* detection channel; a standards body would have specified the wire format and left behaviour to implementers, whereas this process specified behaviour because behaviour was where the leak was. **Backward compatibility is treated as a live constraint on current designs** — SIP002 carries the note that for AEAD-2022 the `userinfo` "MUST NOT be encoded with Base64URL" while Base64URL "is recommended but optional for Stream and AEAD" (✅), a specification making an interoperability concession to a URI convention that exists because a decade of clients were built against it. **And the process documents its own ecology of forks, ports and abandoned lines** — SIP003 lists "Known good SIP003 plugins" (✅) rather than defining plugins normatively; the C implementation's README narrates its own maintenance history including the bug-fix-only phase and the 2026 rename (✅); the specification's acknowledgement credits three individual contributors by handle (✅) rather than a working group. There is no formal change control, no interoperability test suite in the specification and no deprecation policy — which is why the deprecation of the stream ciphers happened in an implementation's changelog and a paper's §2.1 rather than in a specification revision.

**The synthesis.** This family is a case study in the cost of a design that optimised one property — the shape of the bytes — and treated the rest as free. The security properties it deferred (integrity, authentication, replay resistance, behavioural consistency) each came back as an attack, and the project's response each time was to patch the deployment: first behaviourally, then with a flawed authenticator, then with AEAD, then with a whole new edition. The measurement literature's contribution is that the *last* of those deferrals — the assumption that a protocol's behaviour is not part of its protocol — was the one that could not be fixed by a specification at all, only managed by one.

## 12. The Cymbal Bank Worked Example

**Cymbal Bank is a fictional persona used across this repository's guides. Everything in this section is fiction, no real institution is described, and the technical facts it reasons from are the cited facts of §1–§9.**

### 12.1 The Scenario

Cymbal Bank's security operations centre raises an alert from the network flow telemetry: several managed endpoints in the Singapore head office are establishing long-lived outbound TCP sessions to a small set of addresses in a public cloud provider's range. The sessions are high-volume, sustained, and — per the flow records — carry **no identifiable application protocol**: TLS record inspection finds nothing to parse, no certificate has been observed in the handshake for these flows, and the volume and duration profile does not match any sanctioned SaaS dependency the asset inventory knows about.

Two hypotheses are live, and the team cannot yet tell them apart:

- **H1 — a legitimate workaround.** A developer or analyst is routing traffic through a personal proxy to reach a region-restricted service, or to get around a corporate content policy they consider obstructive. This is a policy violation with no malicious intent.
- **H2 — exfiltration.** A compromised endpoint or an insider is using an encrypted relay as an outbound channel for data.

The team's instinct is to look for the traffic's shape. That instinct is wrong, and the reason is the subject of this guide.

### 12.2 What the Network Evidence Can Establish

Working within the constraints of the protocol as specified (✅ §4, §5), the team can establish four things. **(a) That the flows are encrypted proxies of *some* kind** — from behaviour, not payload: the payload is uninformative by design (✅ SIP022 §1), but the **connection behaviour** is not, and the team has the two signals the measurement literature used: an **unusual absence of any protocol fingerprint** where everything else on the estate's egress presents a recognisable TLS or HTTP shape (compare NDSS 2020's 94% response rate for ordinary endpoints), and a **sustained unidirectional volume profile** characteristic of a relay. This is the inference the GFW's passive stage makes with first-packet length and entropy (✅ IMC 2020 Abstract), performed at far lower sophistication. **(b) Where the connections terminate** — server addresses, their ASNs, whether they are known cloud-hosting ranges; the protocol does nothing to hide the destination IP, because reachability is the point of a proxy. **(c) Which endpoints and user accounts are involved** — from the estate's own endpoint telemetry and identity logs, not the network, and the most important fact the team has, because §9.4's concerns are all about *governance*, and governance is per-identity. **(d) Whether the endpoint's posture is otherwise intact** — EDR presence, patch state, whether the proxy client is a known-unsigned binary — the control that separates H1 from H2 far more reliably than the traffic does (cross-ref [vpn_guide.md](vpn_guide.md) §7.4's posture discipline).

### 12.3 What It Cannot Establish, and Why

- **It cannot read the traffic.** Not "should not" — cannot. The payload is AEAD-encrypted with a pre-shared key the estate does not possess and cannot derive (✅ §5.3: a full-entropy PSK, no `EVP_BytesToKey`, no password recovery). There is no key escrow, no weak key derivation to attack, and no plaintext structure.
- **It cannot distinguish exfiltration from browsing by content, volume or protocol shape.** Both are the same protocol carrying the same kind of ciphertext to the same kind of destination. §9.6 states the reason: the design has no notion of intent, and at the network layer there is nothing to distinguish.
- **It cannot confirm which implementation or variant is in use.** Separating `ss-libev` from `shadowsocks-python` from a VMess or Trojan deployment requires the multi-probe behavioural fingerprinting of NDSS 2020 and IMC 2020 (✅) — a research-grade capability needing a controlled probe infrastructure, a labelled dataset and the legal authority to probe. A bank's SOC does not have that and should not build it.
- **It cannot, therefore, resolve H1 versus H2 from network evidence alone.** The determination must come from the endpoint side (which process opened the socket, what it read locally) and the identity side (does this user's role explain a reason to route traffic through a foreign proxy). **The protocol's design property that makes it hard to classify is the same property that makes the investigation hard.** A team that plans for "we will detect the traffic and then investigate it" has the order backwards: the investigation is the hard part, and the detection only says where to look.

### 12.4 The Proportionality Problem

The response decision does not reduce to a technical answer. **The H1 case is a policy violation and largely a management problem** — if the cause is content-policy friction the team did not know about, the control failure is upstream of the user, and treating it as a security incident burns trust and teaches nothing; but the estate cannot know it is H1 without investigating, and investigating everyone is not proportionate. **The H2 case is a serious incident** requiring endpoint isolation and the full DFIR process ([vpn_guide.md](vpn_guide.md) §7.4 is the template). **The distinguishing evidence is not in the network** — it is the process that opened the socket (EDR), what that process read and wrote locally (DLP/endpoint telemetry), the user's role and working hours, whether the endpoint shows other anomalies, and whether the destination has been seen before. **None of those five is a network fact**, so the estate's ability to answer depends entirely on how good its *endpoint* telemetry is — a control a network-centric team may not have invested in. **And the trap to avoid** is treating use of the protocol as sufficient grounds for the strongest response: it is a policy breach, not evidence of exfiltration, and overreacting to the H1 case is how an organisation loses the cooperation of the engineers whose judgement it needs in a real incident.

### 12.5 The Policy Gap

Whatever the outcome, the incident reveals a gap upstream of the technology. The **acceptable-use policy** almost certainly prohibits it in general terms ("unapproved tunnelling or proxy software") and never named it explicitly — because the policy was written about VPNs; cross-ref [vpn_guide.md](vpn_guide.md) §5 for what a managed remote-access clause looks like when written properly. There was **no approved alternative** for the need the user had: a policy that forbids a workaround without providing a path guarantees workarounds, the same lesson the cluster's paradigm guides teach about the perimeter ([zero_trust_network_architecture_guide.md](zero_trust_network_architecture_guide.md) §1) — a control that obstructs a legitimate need does not prevent the need, it relocates it. **Detection was scoped to the wrong layer** — the estate's egress monitoring assumed traffic it could not parse was traffic it could not have, which §7.1 shows to be the exact assumption the measurement literature retired; flow-level detection (destination reputation, volume profile, protocol-absence scoring) is the layer that works. And **the logging question was never asked**: §9.4's point is that the estate's obligations are about *evidence*, and the gap is not that traffic got out but that the estate cannot say with confidence what got out — an op-risk finding independent of the incident's resolution (cross-ref [Financial Risk & Compliance Systems](../banking/financial_risk_compliance_systems_guide.md)).

### 12.6 The Control Recommendations

Stated as controls, not procedures:

| Control | What it addresses | Why it works here |
|---|---|---|
| **Flow-level egress analytics** — destination reputation, volume/duration profiling, protocol-absence scoring | The detection gap | The protocol defeats payload inspection but not connection metadata; the measurement literature's own inference is behavioural (✅ IMC 2020; ✅ NDSS 2020) |
| **Endpoint telemetry as the primary investigative instrument** — process-to-socket attribution, local read/write volumes, DLP events | The investigation gap | The only layer where H1 and H2 are distinguishable, because it observes *the process*, not the traffic |
| **Posture and application control on managed endpoints** — block unapproved binaries and extensions; require MDM enrolment for network access | The shadow-IT vector (§9.4) | Removes the client, which is the one part of the chain the estate controls |
| **An approved alternative for the legitimate need** — a sanctioned egress path or a logged policy exception | The driver of H1 | Converts an uninspectable channel into an inspectable one; the [vpn_guide.md](vpn_guide.md) §9.4 phased pattern is the template |
| **Explicit acceptable-use language naming the proxy/tunnelling class, with a defined exception route**; an identity-centric response playbook; egress evidence retention | The policy, proportionality and logging gaps | Names the behaviour so it can be enforced proportionately; investigates the account and device rather than the flow; turns "we cannot say what left" into a bounded, auditable statement ([vpn_guide.md](vpn_guide.md) §7.4) |

**The closing honesty of the example.** Cymbal Bank's team did not solve this on the wire. They solved it by accepting that the network evidence would tell them *where to look* and nothing more, and by having the endpoint and identity telemetry to answer the question the network could not. That is the correct lesson from this protocol family for an enterprise defender: **the protocol's design goal is to make the flow uninformative, so build the investigation on the layers it does not reach.** A defender who plans to "inspect the traffic" has chosen the one layer where this protocol is, by design, unbeatable.

## 15. Glossary

- **Entropy (in this context)** — the statistical randomness of a byte sequence. The design treated high entropy as camouflage; the measurement literature treated it as a feature (§7.1).
- **`EVP_BytesToKey`** — the OpenSSL password-to-key function used in the stream-cipher and AEAD eras and **explicitly prohibited** in SIP022, which requires a full-entropy user-supplied key (§5.3).
- **Fully-encrypted traffic** — the measurement literature's term for traffic with no exemptable plaintext structure. It is the censor's *class*, defined by the classifier, and being in it is a liability (§6.3, §7.1).
- **IV (initialisation vector)** — the stream-cipher era's per-connection random prefix, 8/12/16 bytes depending on cipher; called a **salt** in the AEAD era (§1.5, §4.4).
- **OTA (one-time auth)** — a stream-cipher-era mode giving each chunk its own authenticator; defeated because chunk length prefixes remained unauthenticated (§4.6).
- **Obfuscation plugin** — a SIP003 extension process that transforms an endpoint's byte stream; **cannot be stacked** ("Plugin over plugin is NOT supported") and by the base SIP003 design **carries TCP only** (§8.4).
- **Outline** — the best-known Shadowsocks-based service, created under Google's Jigsaw and moved to an independent `OutlineFoundation` in January 2026 (§8.3).
- **Probe resistance** — the design goal of refusing to reveal protocol identity to an unauthorised prober; NDSS 2020 showed the refusal itself is a fingerprint because non-response is rare on the internet (§6.2).
- **PSK (pre-shared key)** — in SIP022, a mandatory full-entropy base64 key of 16 or 32 bytes depending on method (§5.3).
- **Salt** — the per-connection (TCP) or per-session (UDP) random value combined with the key to derive session subkeys; 16 or 32 bytes in SIP022, equal in length to the key (§5.3).
- **SIP** — Shadowsocks Improvement Proposal: the project's own numbered specification series on shadowsocks.org. SIP002 = `ss://` URI scheme; SIP003 = plugin design; SIP004 = AEAD ciphers; SIP022 = the 2022 Edition (§1.5).
- **SOCKS5** — the application-level proxying protocol (RFC 1928) that `ss-local` presents locally and whose address format the protocol borrows. It is **not** the tunnel's own protocol (§1.5, §4.1).
- **`ss-local` / `ss-remote` / `ss-server`** — the two halves of the split proxy. The docs say `ss-remote`; the binaries say `ss-server` (§1.5).
- **Stream cipher (in this protocol's sense)** — the pre-2017 construction: one long ciphertext preceded by an IV, with **no integrity or authentication**. Deprecated, and enumerated in the SIP002 method list (§4.4, §4.5).
- **VLESS / VMess** — the V2Ray/Xray protocol family; VMess is the original, whose weaknesses were catalogued publicly in June 2020, and VLESS the lighter successor typically carried over TLS or REALITY (§8.6).
- **2022 Edition** — the current protocol edition, specified as SIP022, replacing the 2017 AEAD edition (§5.3).

## 17. Closing Summary

Shadowsocks is a SOCKS5-based encrypted split proxy whose founding design decision was to have **no handshake and no authentication exchange**, because a handshake is exactly what a classifier looks for — and the specification still states that rationale in its own words, accepting the price of no forward secrecy rather than paying it ("It is believed that using a pre-shared key without performing handshakes is best for its use cases", ✅ SIP022 §1). Three editions followed from that decision and from what it cost: the **stream-cipher era's** confidentiality-without-integrity, which fell to ciphertext malleability in August 2015 and to a decryption oracle in February 2020; the **AEAD revision** of February 2017, which added the authenticators the first edition lacked and left a replay problem that implementations patched with Bloom filters and the 2022 specification ultimately solved with an exact 60-second salt pool; and the **2022 Edition (SIP022)**, with its mandatory full-entropy pre-shared key, BLAKE3-derived per-direction session subkeys, counter nonces, 30-second timestamp replay windows and overhauled UDP session model — plus a detection-prevention section that is, in effect, the specification legislating the behavioural leaks the measurement literature had by then documented.

What the literature established is the durable lesson. The design's assumption — that a random byte stream is unclassifiable — was refuted twice: once by a censor that used first-packet **entropy as a positive signal** and then confirmed its suspicion with **seven classes of active probes**, 51,837 of them from 12,300 Chinese addresses (✅ IMC 2020); and once by a purely **passive** classifier that worked by exempting everything it could recognise and blocking the residue on set-bit and printable-ASCII statistics, deployed from November 2021 against Shadowsocks, VMess and Obfs4 alike (✅ USENIX Security 2023). And the deepest result was neither of those: it was the demonstration that **silence is a fingerprint**, because 94% of ordinary endpoints answer a probe battery and the proxies that do not answer with a distinctive byte threshold, abort timing and close semantics (✅ NDSS 2020). A protocol cannot patch its way out of a channel its cryptography cannot reach, and the 2022 specification's answer is behavioural rules rather than a guarantee — which is what a specification must do when a cryptographic guarantee is not available: legislate the behaviour, and hope the implementations follow it.

The ecosystem in September 2026 is more alive than its folklore suggests and more fragile than its star counts suggest: the original Python repository still reads "Removed according to regulations." eleven years after the police contact that ended its maintenance; the C implementation was renamed and modernised in September 2026 with its future development declared to be in Rust; `shadowsocks-rust` is the actively developed reference; Outline moved out of Google's Jigsaw into its own foundation in January 2026; `simple-obfs` is formally deprecated in favour of a TLS-imitating successor; and the client layer has consolidated onto multi-protocol cores — Xray, sing-box, v2rayN — precisely because no single protocol's camouflage has a long shelf life. The related family splits on one axis: **absence** (Shadowsocks's founding choice, VMess's default posture) met a classifier that blocks the class of the unclassifiable, while **imitation** (Trojan's stated thesis, REALITY, NaiveProxy, the TLS-shaped plugins) met a documented campaign against circumvention tools that imitate TLS. Neither strategy has won, and any guide that says otherwise is repeating folklore.

The legal picture is narrow and specific: running and using this class of software is ordinary network engineering almost everywhere, and it is restricted or criminalised in a specific list of jurisdictions where the regulated act is generally **operating or providing**, not using — the enforcement precedent being a nine-month sentence for *selling* VPN software in Guangdong, reported in September 2017 (✅ The Register; BBC; SCMP). In every jurisdiction, a regulated firm treats it as a **control problem** regardless, because a channel the estate cannot inspect is a channel it cannot log, govern or evidence — and because the same protocol properties that defeat a censor's classifier defeat the firm's DLP. Which is the honest enterprise lesson of §12: when the flow is designed to be uninformative, the investigation has to be built on the layers the design does not reach.

And the engineering lesson, for anyone designing a protocol that needs to be unremarkable — or defending a network against one that is — is the one this family paid for three times over: **confidentiality without integrity is not a lesser form of security, it is a different and broken thing; an omission is not the absence of information, it is a behaviour profile; and a design that answers "what does this look like?" with "nothing" has not escaped classification, it has joined a class.** Look like nothing and you are merely a member of the smallest, most suspicious class on the network. The durable option is not invisibility but plausibility — and the protocol whose three editions taught the field that lesson is, for better and worse, the indistinguishable stream.
