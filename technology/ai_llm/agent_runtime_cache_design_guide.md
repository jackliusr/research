## 1. 为什么 Agent 需要运行时缓存

### 1.1 Agent 是 token 消耗大户

LLM Agent（如基于 LangChain、LlamaIndex、Semantic Kernel 或自研编排框架的智能体）与传统单轮 LLM 应用的根本区别在于：**一次用户请求 = 一次多轮推理执行**。一个典型的 Agent 任务会展开成以下 token 消耗结构：

- **多轮工具调用（multi-turn tool use）**：Agent 需要规划 → 调用工具 → 观察结果 → 再规划 → 再调用，往往 3–10 轮。每一轮都要把**完整的对话历史 + 工具结果 + 系统提示**重新发送给模型（除非使用持久化 KV cache 的流式推理服务）。工具结果（尤其检索出的文档片段）动辄数千 token，乘上轮数，一次请求的输入 token 可能是用户问题本身的 **50–100 倍**。
- **重复上下文（repeated context）**：系统提示、工具 schema、角色设定、合规声明（银行场景尤其冗长）每轮重发；多 Agent 协作（见 [hybrid_multi_agent_systems_guide.md](hybrid_multi_agent_systems_guide.md)）中，每个子 Agent 各自携带一份完整上下文，上下文被复制到 N 个执行单元。
- **相同查询（repeated queries）**：同一组织内，不同用户会问高度相似的问题——产品条款、利率查询、法规条文、FAQ；同一用户也会在会话中反复问"我的申请到哪一步了"这类状态查询。真实生产环境中，**20–40% 的查询是重复或近似重复的**（FAQ 场景可达 70%+）。

结论：Agent 的边际成本结构是"一次执行贵、重复执行更贵"。如果不做任何缓存，每一个近似重复的查询都会完整重走一遍 LLM 推理 + 外部工具调用 + RAG 检索的全链路——这是成本的线性放大。

### 1.2 缓存带来的直接收益

| 维度 | 无缓存 | 有缓存（命中时） |
|---|---|---|
| 端到端延迟 | 完整 Agent 调用 **5–30 秒**（多轮 LLM + 工具） | **10–100 毫秒**（内存/向量库查找） |
| 单次请求成本 | 全量 token + 外部 API 调用 | 近似为零（仅缓存查找） |
| 外部 API 配额 | 每次重复调用都消耗 | 命中不消耗 |
| 上游系统负载 | 数据库/市场数据源被重复查询 | 显著降低 |
| 用户体验 | 等待 + 偶发超时 | 即时响应 |

在延迟维度上，缓存命中比"更快地跑完 Agent 全流程"（见 [llm_latency_optimization_guide.md](llm_latency_optimization_guide.md)）有数量级的优势——后者是把 5–30 秒优化到 2–5 秒，前者是直接降到毫秒级。

### 1.3 先厘清：LLM 推理层的四种缓存机制

在进入 Agent 特定的缓存设计之前，必须先区分模型推理层面已经存在的四种缓存。它们由推理服务/模型提供商自动或半自动管理，Agent 应用层通常"免费获得"，但设计时需要理解其边界：

1. **Prompt caching（前缀缓存 / context caching）**：对**完全相同的输入前缀**（通常是系统提示 + 历史消息的开头部分）只计算一次 KV 状态，后续请求复用。Anthropic 对缓存命中的输入 token 提供最高 **90% 折扣**，OpenAI 提供 **50% 折扣**（不同模型/时段略有差异）。这是当前**成本收益比最高**的缓存手段——详见 [rag_vs_long_context_llms_guide.md](rag/rag_vs_long_context_llms_guide.md) 中对长上下文与缓存交互的讨论。
2. **KV cache 复用**：推理框架（vLLM、TGI 等，见 [on_prem_llm_deployment_guide.md](../on_prem_llm_deployment_guide.md)）在**前缀相同的并发/连续请求**之间复用 attention 的 Key/Value 状态（如 RadixAttention、PagedAttention 的 prefix sharing），避免重复 prefill。这是服务端优化，应用层几乎无感知。
3. **语义缓存（semantic caching，如 GPTCache）**：对查询做 embedding，与已缓存查询计算相似度，超过阈值则直接复用缓存的答案——**不调用 LLM**。这是应用层缓存，也是本指南 L1 层的核心。
4. **结果缓存（exact-match result caching）**：对**完全相同的请求**（相同 prompt + 相同参数 + 相同模型配置）命中已有响应，直接返回。简单、零误命中风险，但命中面窄。

需要强调：**这四类缓存解决的是"同一模型调用"层面的重复；Agent 运行时缓存要解决的是"整个 Agent 执行链路"层面的重复**——包括工具调用、检索、规划、记忆读写等 LLM 之外的昂贵环节。两者的关系是互补的：即使底层模型做了 prompt caching，Agent 层的工具调用和检索依然每次全量执行。

## 2. Agent 特定缓存层

Agent 运行时缓存与普通 Web 缓存的最大区别：**缓存对象不止是"响应"，而是执行链路中的每一种中间产物**。以下六类缓存层共同构成 Agent 的缓存全景。

### 2.1 工具调用结果缓存（Tool Result Cache）

**缓存对象：** 外部 API 的响应——市场数据、搜索接口、数据库查询、汇率查询、公司信息查询等。

**动机：** Agent 每轮工具调用的开销 = 网络往返 + 上游系统负载 + 外部 API 费用。**相同参数的工具调用不应当重复执行**。例如一个"比较三家银行定期存款利率"的 Agent，可能在 30 分钟内被 50 个用户触发，每次都去实时拉取同一组利率数据。

**关键区分：确定性 vs 非确定性工具。** 这是工具缓存的第一原则：

- **确定性工具**（相同参数 → 相同结果，如"查询某公司注册信息""查询法规 X 第 3 条"）：结果可安全缓存，TTL 取决于数据源的变更频率。
- **非确定性工具**（相同参数 → 结果随时间变化，如实时汇率、行情、随机数、时间敏感查询）：**缓存即错误数据**，见第 6 章禁止清单。

### 2.2 上下文/记忆缓存（Context & Memory Cache）

**缓存对象：** 对话历史摘要、工作记忆（working memory）、用户画像摘要、会话状态。

**动机：** 长会话中，Agent 需要反复读取/重放历史。把对话历史压缩为结构化记忆（摘要、实体、偏好）并缓存，避免每次请求都重新总结整个历史。这与 [beyond_rag_guide.md](rag/beyond_rag_guide.md) 中第 5 范式"记忆系统（Memory Systems）"直接相关——记忆层本身就需要缓存策略来避免重复计算。

**注意：** 记忆缓存是**会话/用户级**的，天然带隐私属性——其存储与访问必须遵循第 6 章的 PII 约束（只缓存必要的最小化信息，加密存储，严格隔离）。

### 2.3 检索缓存（Retrieval Cache）

**缓存对象：** RAG 链路中的向量搜索 top-k 结果、重排（rerank）分数、混合检索（关键词 + 向量）的融合结果。

**动机：** 检索 + 重排是 Agent 链路中开销可观的环节（embedding 计算 + 向量库 ANN 搜索 + 交叉编码器重排）。**文档不变即可复用检索结果**——同一查询对同一文档集的 top-k 结果在索引更新前是确定的。

**详见：** [rag_optimization_techniques_guide.md](rag/rag_optimization_techniques_guide.md) 中关于检索优化的讨论；文档更新驱动的缓存失效见 [rag_with_data_streaming_guide.md](rag/rag_with_data_streaming_guide.md) 的流式失效模式。

### 2.4 中间推理缓存（Intermediate Reasoning Cache）

**缓存对象：** 思考过程（chain-of-thought）、规划结果（plan）、任务分解（task decomposition）、子目标状态。

**动机：** 相同/相似问题不必重新规划。一个 Agent 收到"分析 Q2 财报并生成摘要"的请求，其规划结果（拆解为 5 个子任务）对相似请求是可复用的模板。对于 reasoning 模型，思考 token 的生成成本极高——缓存规划结果能跳过整个"想"的阶段。

**风险：** 规划结果与具体问题强相关，语义缓存命中困难；且规划错误被缓存会**固化错误路径**。建议只缓存"与具体数据无关的规划模板"，且规划结果随执行结果做质量校验。

### 2.5 代码执行缓存（Code Execution Cache）

**缓存对象：** 沙箱中代码执行的输出、数据分析结果、临时计算结果。

**动机：** Agent（尤其数据分析类 Agent，见 [llm_agent_use_cases.md](llm_agent_use_cases.md)）经常生成并执行 Python/SQL 代码。相同代码片段 + 相同输入 → 相同输出，可缓存。业界已有成熟先例：Jupyter 的 cell 输出缓存、Make/ccache 的构建缓存原理完全适用。

**关键点：** 缓存键必须包含**代码哈希 + 输入数据版本 + 依赖环境版本**；执行结果若含敏感数据（如客户明细分析结果），落入第 6 章禁止清单。

### 2.6 LLM 输出缓存（Response Cache）

**缓存对象：** 完整的查询-回答对（question → answer），语义重复的查询直接复用完整回答。

**动机：** 这是最直观也最需要谨慎的一层。对"完全相同"的请求，结果缓存直接命中；对"语义相似"的请求，语义缓存命中。**质量门槛是命门**：只有高质量、通用性、非个性化的回答才允许写回缓存（见第 10 章"带质量门槛的写回"）。

**边界：** 完整回答缓存与个性化、权限、时效性天然冲突——第 6 章的大部分禁止内容都落在这一层。

## 3. 缓存层级架构：L1–L5

把上述缓存层按"查询到执行"的路径组织，得到五层缓存架构。**查询从 L1 开始逐层向下查找，命中的层越靠前，节省越多；但越靠前的层，误命中与安全风险也越高。**

```
用户查询
   │
   ▼
┌─────────────────────────────────────────────────────┐
│ L1 语义缓存（查询级）       最快命中 · 风险最高       │
│    查询规范化 → embedding → 相似度 > 阈值 → 直接返回  │
└─────────────────────────────────────────────────────┘
   │ 未命中
   ▼
┌─────────────────────────────────────────────────────┐
│ L2 工具结果缓存（参数键）   确定性工具安全             │
│    工具名 + 规范化参数 → 命中则跳过外部 API 调用      │
└─────────────────────────────────────────────────────┘
   │ 未命中
   ▼
┌─────────────────────────────────────────────────────┐
│ L3 检索缓存（文档级）       文档不变即可复用           │
│    query → top-k 文档 + rerank 分数                   │
└─────────────────────────────────────────────────────┘
   │ 未命中
   ▼
┌─────────────────────────────────────────────────────┐
│ L4 模型级缓存（KV / prompt cache） 安全但收益有限      │
│    前缀复用由推理服务处理，应用层只负责前缀稳定        │
└─────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────┐
│ L5 应用级缓存（会话/用户级）  上下文、记忆、偏好        │
│    会话内复用，不跨会话/用户                          │
└─────────────────────────────────────────────────────┘
   │
   ▼
Agent 全量执行（LLM + 工具 + 检索 + 推理）
```

### 3.1 各层详细对比

| 层级 | 缓存对象 | 命中率（典型） | 收益 | 风险 | 典型 TTL | 失效方式 |
|---|---|---|---|---|---|---|
| **L1 语义缓存** | 查询 → 完整回答 | 20–40%（FAQ 70%+） | 最高：跳过整个 Agent 执行 | **最高**：误命中、串用户、越权、固化错误 | 分钟–小时级 | TTL + 版本失效 + 质量门槛 |
| **L2 工具结果缓存** | 工具名 + 参数 → 外部 API 响应 | 30–60%（重复型工具） | 高：省 API 费用与延迟 | 中：非确定性工具缓存错误数据 | 秒–分钟级（按工具配置） | TTL + 写失效（数据更新事件） |
| **L3 检索缓存** | 查询 → top-k 文档 + 分数 | 40–70%（稳定文档集） | 中高：省 embedding + 重排 | 中：文档更新后返回旧文档 | 小时–天级 | 事件驱动：索引更新 → 失效 |
| **L4 模型级缓存** | KV 状态 / prompt 前缀 | 取决于前缀复用率 | 中：省 prefill 成本 | **低**：模型内部机制，无逻辑风险 | 分钟级（服务商管理） | 服务商自动；应用层保持前缀稳定 |
| **L5 应用级缓存** | 会话上下文、记忆、偏好 | 会话内接近 100% 复用 | 中：省上下文重建 | 中高：PII、串会话 | 会话生命周期 | 会话结束即失效；显式清除 |

### 3.2 层级设计要点

- **顺序即策略**：L1 命中的收益是"毫秒级返回"，L2/L3 命中是"省一次外部调用"，L4 命中是"省一段 prefill"，L5 是"省一段上下文重建"。**缓存设计的目标是把尽量多的请求推给更靠前的层，同时把更靠前的层的风险控制住。**
- **L1 的风险上限决定了整条链的信任度**：语义缓存一旦误命中（相似度阈值过低、查询规范化的 bug），返回的是"看起来合理但错误"的答案——这比没有缓存更危险，因为错误被固化了。银行场景中，L1 通常**默认关闭或仅对白名单内容类型开启**（见第 12 章）。
- **L4 需要应用层配合**：prompt caching 的折扣取决于前缀是否稳定。应用层的配合动作是：**把系统提示、工具 schema、静态上下文固定在 prompt 的头部且顺序不变**；频繁变化的动态内容（时间戳、随机 ID）放到前缀之后。这是"免费的午餐"，任何 Agent 应用都应做。
- **L5 是隔离边界**：会话级/用户级缓存的本质是把"跨用户共享"从缓存设计中排除——所有跨用户共享的缓存都必须是 L1–L3 中经过严格审查的内容。

## 4. 值得缓存的内容（✓ 可缓存清单）

本章给出"允许进缓存"的正面清单。判断一条内容能否缓存，先看四个特征——**确定性（deterministic）、非敏感（non-sensitive）、通用性（non-personalized）、可失效（invalidatable）**——四个都满足，才进入下面的清单；任何一条不满足，跳到第 6 章的禁止清单。

### 4.1 确定性工具结果

**✓ 可缓存。** 排除"当前时间"因素后结果不变的查询：

| 工具/查询类型 | 示例 | 建议 TTL |
|---|---|---|
| 汇率历史数据（非实时报价） | "2023 年 USD/SGD 月均汇率" | 天–周级 |
| 公司/机构静态信息 | 注册信息、主营业务、财报发布时间 | 天级 |
| 法规条款 | 监管条文原文、生效日期 | 月级（低频变化） |
| 产品文档 | 银行产品说明书、费率表 | 天–周级（带版本） |
| 静态参考数据 | 国家代码、货币代码、节假日表 | 周–月级 |

### 4.2 幂等 API 响应（GET 类请求）

**✓ 可缓存。** HTTP 语义上幂等（idempotent）且无副作用（side-effect-free）的只读请求——GET/HEAD 类。对第三方 API 的调用：同样的参数、同样的认证上下文，响应可复用。注意两个边界：

- **认证上下文变化必须失效缓存**：同一 URL 在不同租户/用户下可能返回不同数据（例如"我的订阅"类接口），这类接口按"URL + 认证主体"组合键缓存，或直接禁止跨主体共享。
- **状态型 GET 不缓存**：返回的是可变状态（如"当前持仓"）的 GET，本质是非确定性的，归入第 6 章。

### 4.3 检索结果（向量搜索 top-k + 重排分数）

**✓ 可缓存（文档不变时）。** RAG 链路的确定性部分：同一 query 对同一版本的文档索引，向量搜索的 top-k 集合与重排分数是确定的。缓存内容 = 文档 ID 列表 + 分数 + **索引版本号**。文档集更新（新增/删除/修改 chunk）时按版本失效。

- 收益点：跳过 embedding 计算、ANN 搜索、交叉编码器重排这三段最贵的检索开销。
- 详见 [rag_optimization_techniques_guide.md](rag/rag_optimization_techniques_guide.md)；文档变更驱动的失效事件设计见 [rag_with_data_streaming_guide.md](rag/rag_with_data_streaming_guide.md)。

### 4.4 嵌入向量（Embedding）

**✓ 可缓存（预计算）。** 文档 chunk 的 embedding 是纯确定性计算，**一次计算、长期复用**——文档不变，向量不变。生产实践：

- 离线预计算 + 入库时写入向量库，运行期不再重复调用 embedding API；
- 查询侧的 embedding 可做短 TTL 缓存（同一查询在多轮/多 Agent 间复用，见 [hybrid_multi_agent_systems_guide.md](hybrid_multi_agent_systems_guide.md) 中多 Agent 共享检索的场景）；
- embedding 模型升级 = 全量向量失效重算，缓存键必须带 embedding 模型版本。

### 4.5 重复的完整查询-回答对（高频常见问题）

**✓ 可缓存（带质量门槛）。** 高频 FAQ 类问题——产品条款、开户流程、手续费说明、系统状态解释——完整回答可以直接命中 L1 语义缓存。**前提**：

1. 回答经过质量校验（见第 10 章写回门槛）；
2. 回答是**通用性**的（不引用具体用户数据）；
3. 回答对时效不敏感（或带"截至某日有效"的显式声明）。

### 4.6 系统提示与静态上下文（Prompt 前缀）

**✓ 可缓存（L4，近乎白拿的收益）。** 系统提示、角色设定、工具 schema 定义、合规声明、few-shot 示例——这些内容**每轮、每个会话都重复发送**。利用 prompt caching 的 50–90% 输入 token 折扣，只需要遵守一条规则：**静态内容放前缀最前面，动态内容（时间、随机 ID、检索片段）放后面**，且静态内容拼装顺序保持稳定。银行场景中冗长的合规声明（"本对话仅作参考，不构成投资建议……"）正是前缀缓存的理想内容。

### 4.7 工具 schema 定义

**✓ 可缓存（应用内常量）。** 工具的 OpenAPI/JSON Schema 描述通常数 KB 到数十 KB，且低频变化。应作为**应用启动时加载的静态配置**缓存于内存，并带 schema 版本号（schema 变更 → 版本号变更 → 相关缓存键失效）。这既是性能优化，也是正确性要求：**模型升级后工具调用格式可能变化，schema 版本必须进缓存键**（见第 5 章）。

### 4.8 用户会话中的短期事实（用户 ID、偏好——注意隐私）

**⚠ 有条件缓存。** 会话内的确定性事实（语言偏好、时区、UI 偏好、会话内已确认的上下文）可以缓存以避免重复询问/重复解析。**红线**：

- 只缓存**最小化**的信息（数据最小化原则同样适用于缓存，见第 12 章 PDPA 部分）；
- 缓存范围**严格限定在会话/用户隔离域内**（L5），绝不进入跨用户共享缓存；
- 带自动过期（会话结束即清除），并允许用户主动清除。

### 4.9 模型配置快照（Model Config Snapshot）

**✓ 可缓存（作为缓存键的一部分）。** temperature、top_p、max_tokens、seed、模型名称与版本、工具列表版本——这些参数决定输出的确定性边界。**模型配置不直接作为缓存内容，而是作为缓存键的组成部分**：同一查询在不同 temperature 下的回答不能混用；模型版本升级后，相同缓存键必须命中新模型的回答（通过版本号入键实现自动失效，见第 5 章）。

### 4.10 货币/汇率静态数据（短 TTL）

**✓ 可缓存（短 TTL）。** 与 4.1 的"历史数据"不同，这里指**准实时但低波动**的数据——如银行挂牌汇率（非实时市场报价）。此类数据**可以**缓存，但 TTL 必须短（秒–分钟级），且要显式标注缓存时间戳，回答中注明"数据截至 X 时刻"。区分标准：**允许的陈旧程度（stale tolerance）**。挂牌汇率允许 1–5 分钟陈旧；实时市场报价不允许任何陈旧 → 归入禁止清单。

### 4.11 法规条文（长 TTL）

**✓ 可缓存（长 TTL + 版本校验）。** 监管文本（MAS 法规、新加坡 PDPA、国际制裁清单等）低频变化，是长 TTL 的理想对象。但银行场景有额外要求（详见第 12 章）：

- 缓存内容带**条文版本号 + 生效日期**；
- 命中时校验"当前生效版本 = 缓存版本"；
- 法规更新事件 → 显式失效。

### 4.12 公司/产品知识库（中长 TTL，带版本）

**✓ 可缓存（中长 TTL + 版本）。** 内部知识库文档、产品目录、定价表——小时到天级 TTL，配合文档版本号。知识库内容变更通过变更事件（CDP/数据流）触发失效，机制与 4.3 的检索缓存一致：**知识库文档是检索缓存和问答缓存共同的失效源**。

## 5. 缓存键设计

缓存键（cache key）决定了"什么算作同一次请求"。键设计错误是缓存 bug 的最大来源——**键太粗 → 串数据；键太细 → 命中率趋近于零**。

### 5.1 缓存键类型

| 键类型 | 构造方式 | 适用层 | 优点 | 缺点 |
|---|---|---|---|---|
| **精确键（exact key）** | `hash(规范化后的完整请求)` | L4 结果缓存 | 零误命中 | 命中面窄；请求中任何噪声（时间戳）都导致 miss |
| **参数键（parameter key）** | `tool_name + canonicalized(params)` | L2 工具缓存 | 命中面宽；语义明确 | 需要参数规范化；非确定性参数（时间）需剔除 |
| **语义键（semantic key）** | `embedding(query)` + 相似度阈值 | L1 语义缓存 | 命中面最宽 | **误命中风险最高**；阈值难调；需防注入 |
| **会话键（session key）** | `session_id` | L5 上下文/记忆缓存 | 天然隔离 | 生命周期=会话；跨会话无效 |
| **用户键（user key）** | `user_id` | L5 个性化缓存 | 用户级隔离 | **PII 风险**；禁止进入跨用户共享缓存 |

### 5.2 键设计五原则

1. **包含版本号——模型升级必须失效缓存。** 缓存键的推荐形态：
   ```
   cache_key = f"{model_version}:{tool_schema_version}:{knowledge_base_version}:{content_type}:{content_hash}"
   ```
   模型版本升级、工具 schema 变更、知识库版本更新、embedding 模型变更，任何一项变化都应改变键——**这是"升级后返回旧答案"问题的唯一根治方案**。模型升级是 Agent 缓存中最常被忽略的失效触发器：不换键，用户会拿到旧模型时代的回答。

2. **包含 TTL 维度。** 不同内容类型挂不同的 TTL，键中携带内容类型（content_type），使分层 TTL 配置（第 7 章）可以按类型路由。

3. **参数规范化（canonicalization）。** 构造参数键前，对参数做统一处理：
   - **参数顺序无关**：按 key 排序后再序列化（`{"b":"x","a":"y"}` 与 `{"a":"y","b":"x"}` 同一键）；
   - **格式统一**：金额统一为小数/精度、日期统一为 ISO 8601、大小写归一；
   - **剔除时间噪声**：把"当前时间"类参数从键中移除，改为在 TTL 层处理（否则每次 miss）；
   - **数值等价**：`1` 与 `1.0`、`"USD"` 与 `"usd"` 归一。

4. **敏感数据不入键。** **用户 PII 绝不进入缓存键**：不用 `user_id + 敏感属性` 拼键，不用身份证号、手机号、账户号做键。理由：缓存键常出现在日志、监控指标、调试工具、错误信息中——PII 入键等于把 PII 散布到整个可观测性体系。用户级缓存的键应使用**不可逆的内部标识符（opaque ID）**而非自然属性。

5. **语义键必须配阈值与命名空间。** 语义键不是单个字符串，而是"embedding 向量 + 相似度阈值 + 缓存命名空间"三元组：
   - 阈值过低 → 误命中（不同问题复用错误答案）；
   - 命名空间（namespace）隔离不同业务域的缓存，防止跨域语义串扰（信贷 FAQ 的答案绝不能命中到交易 FAQ 的查询上）。

### 5.3 键的组成检查清单

设计完一个缓存键后，逐项自查：

- [ ] 键里是否包含模型版本？（模型升级 → 键变 → 自动失效）
- [ ] 键里是否包含工具/schema/知识库版本？（任何内容源版本变化 → 键变）
- [ ] 参数是否已规范化？（顺序、格式、精度、大小写）
- [ ] 是否剔除了时间噪声？（时间相关改为 TTL 策略处理）
- [ ] 键里有没有 PII 或敏感属性？（有 → 改为 opaque ID 或移除）
- [ ] 键是否包含内容类型/命名空间？（保证分层 TTL 与域隔离）
- [ ] 键的哈希算法是否防碰撞？（见第 8 章缓存键碰撞）

## 6. 绝不缓存的内容（✗ 禁止缓存清单）

> **本章是全指南的核心。** 缓存设计失败的大多数事故不是"缓存不够多"，而是"缓存了不该缓存的东西"。下面的清单每一条背后都有真实事故：数据泄露、越权访问、错误答案、监管处罚。判断标准很朴素：**这条内容被一个无关的人读到、或在错误的时间被读到，后果是什么？** 后果不可接受 → 禁止缓存。

### 6.1 含 PII 的请求/响应

**✗ 绝对禁止。** 客户姓名、身份证号（NRIC）、护照号、手机号、邮箱、住址、账户信息、生物特征——任何包含个人可识别信息（Personally Identifiable Information, PII）的请求或响应，**默认禁止进入任何缓存**，包括加密缓存。

- **为什么加密也不行**：加密解决"存储被攻破"的静态风险，但缓存有**正常业务流程中的二次暴露面**——缓存日志、监控指标、调试快照、缓存键、命中审计记录都可能携带明文或可推断信息；且密钥管理本身增加复杂度。GDPR/PDPA 对 PII 的处理有合法依据要求，缓存不是"处理 PII 的合法依据"。
- **合规锚点**：新加坡 PDPA（Personal Data Protection Act）的"数据最小化（data minimisation）"与"目的限制"原则、欧盟 GDPR 第 5 条都要求：PII 的处理范围以必要为限——**缓存从来不是必要的**。完整的安全与合规框架见 [llm_development_risks_security_guide.md](../llm_development_risks_security_guide.md)（LLM06 敏感信息泄露、LLM02 不安全输出处理）。
- **工程红线**：缓存层入口做 PII 检测（正则/实体识别/字段白名单），命中 PII 规则即拒绝写入；用户级缓存只允许存"最小化的非敏感派生信息"（如"用户已验证身份"这一布尔结论，而非身份本身）。

### 6.2 敏感金融数据

**✗ 绝对禁止（长期缓存）。** 账户余额、交易明细、信用评分、授信额度、交易对手信息、内部头寸。即使加密存储，也不应长期缓存：

- 金融数据的价值在于**新鲜与准确**——缓存引入的陈旧窗口（哪怕 1 秒）都可能成为错误决策依据；
- 交易明细的缓存副本扩大了数据泄露的爆炸半径（一次泄露 = 全量明细）；
- 审计与监管要求对客户财务数据的访问留痕——缓存命中路径往往不在业务审计范围之内，形成**审计盲区**。

允许的例外：**超短 TTL 的进程内缓存**（如单个请求执行链路内，同一数据被多轮工具调用重复读取，秒级内复用，不落盘、不跨请求），且必须配置为内存级、自动清理。

### 6.3 非确定性工具结果

**✗ 禁止缓存（除非显式短 TTL + 时间戳标注）。** 实时价格、市场行情、实时汇率报价、随机数、倒计时/时点数据、任何"同一参数不同时间结果不同"的数据。**缓存即错误数据**——命中缓存返回的"实时报价"是历史报价，在金融场景可能直接导致错误交易决策。

判断方法：工具返回内容里是否含"as of / 截至时间"？数据源是否声明实时？对**准实时但可容忍陈旧**的数据（如挂牌汇率），允许短 TTL（秒–分钟级）并显式标注缓存时间；对真正的实时数据，一律直连。

### 6.4 个性化输出

**✗ 绝对禁止（进共享缓存）。** 基于用户上下文生成的回答——"根据您的风险偏好……""针对您的持仓……"。个性化输出一旦进入共享缓存：

- **串用户**：用户 A 触发写入，用户 B 语义相似的查询命中，拿到 A 的答案；
- 答案中的"您"所指不明，产生严重的产品与合规事故（把 A 的投资建议展示给 B）。

隔离规则：个性化输出只允许存在于**用户级隔离域**（L5）且带严格 TTL；任何跨用户共享缓存（L1–L3）在写入前必须通过"是否引用用户上下文"的检查。

### 6.5 权限相关的数据

**✗ 绝对禁止（共享缓存）。** 不同用户/角色对同一查询的可见结果不同（数据权限、行级安全、产品可见性、地区限制）。这是**同缓存键不同权限用户的经典安全漏洞**：

```
用户 A（VIP 客户，可见利率 3.5%）发起查询 → 答案写入共享缓存
用户 B（普通客户，可见利率 2.8%）发起相同查询 → 命中缓存 → 看到 3.5%
```

- **权限校验必须在缓存命中时重新执行**——"命中缓存就跳过鉴权"是越权漏洞的头号来源（见 8.3）；
- 权限维度（角色、租户、产品线）必须纳入缓存隔离边界：**要么进键（按权限域分键），要么禁止共享**。银行场景的推荐是后者——只读公共知识的缓存不涉权限，涉权限的数据一律不共享缓存。

### 6.6 流式/实时数据

**✗ 禁止缓存。** 新闻快讯、警报、系统状态更新、事件流、通知。此类数据生命周期以秒计，缓存的价值趋近于零，而"读到旧警报"的代价是真实的（用户依据过期警报做了错误决策）。流式数据的消费应直连事件源；如需防抖/聚合，用流处理（见 [rag_with_data_streaming_guide.md](rag/rag_with_data_streaming_guide.md) 的流式架构）而非缓存。

### 6.7 临时性数据（一次性凭证）

**✗ 绝对禁止。** 一次性 token、验证码、OTP、重置链接、会话票据、短时签名。这类数据的语义就是"一次性有效"，缓存与一次性天然矛盾：

- OTP 被缓存 → 重放攻击窗口；
- 缓存副本延长了凭证的存活期，违反凭证生命周期管理。

**任何形式的缓存都不允许**（包括内存缓存与日志），此类数据应使用专门的短时存储（如 Redis 的 EX 键）并严格限定用途。

### 6.8 模型输出中的偏见/幻觉（质量门槛缺失的输出）

**✗ 禁止写入（无质量门槛时）。** 缓存会把错误固化：一条幻觉回答被缓存后，会被成千上万个相似查询复用——**错误被放大成系统性问题**。规则：

- **只有通过质量校验的输出才允许写回缓存**（第 10 章的写回门槛）；
- 校验手段：与黄金答案的相似度、工具结果的引用一致性（grounding check）、人工抽样复核、用户反馈信号；
- 无法自动校验的输出类型（开放式建议、预测性内容）**默认不写缓存**。

### 6.9 正在变更的法规/政策

**✗ 禁止缓存（失效窗口内的内容）。** 处于修订中、征求意见稿、即将生效/刚废止的法规条文——其内容可能在任意时刻变化，缓存窗口内任何时刻的命中都可能返回错误版本。处理：只有**已生效的稳定版本**允许缓存（带版本号 + 生效日期，见 4.11），变更事件一到即显式失效；变更窗口内的内容直连权威源。

### 6.10 加密密钥/Secret/凭据

**✗ 绝对禁止，任何形式。** API key、数据库口令、私钥、JWT secret、云凭据。不进缓存、不进日志、不进缓存键、不进监控标签。凭据应只存在于专用的密钥管理系统（Vault/KMS），应用运行时通过引用（reference）而非值传递。这条不需要更多论证——**把 secret 放进缓存等于把钥匙放在门口脚垫下**。

### 6.11 用户对话中的敏感意图

**✗ 禁止缓存（进共享缓存）。** 交易指令（"帮我卖出 X 股票"）、转账意向、投诉内容、法律相关陈述。这类内容：

- **审计需求**：监管要求交易指令的完整审计链，缓存副本会造成"指令在缓存里，审计日志里没有"的断链；
- **意图敏感**：用户的金融意图本身就是敏感信息，即使匿名化也应谨慎；
- 处理方式：写入**审计存储**（append-only、防篡改）而非缓存；会话内短期记忆（L5）可以保留必要上下文，但必须随会话终止清除。

### 6.12 合规边界内容

**✗ 禁止缓存。** 客户投诉、监管沟通、法律往来、争议记录、内部调查材料。这类内容受专门的记录保留（record retention）与保密义务约束，缓存会破坏其保密边界与保留策略。它们应进入合规记录系统，走正式的文档生命周期管理。

### 6.13 缓存上述内容的法律风险

把 6.1–6.12 违反后的后果汇总——这些风险在银行场景不是"可能"，而是"审计必查"：

| 风险 | 触发场景 | 后果 |
|---|---|---|
| **GDPR/PDPA 数据泄露** | PII 入缓存后缓存被攻破/越权读取 | 最高达全球营业额 4%（GDPR）的罚款；PDPA 最高 100 万 SGD（2021 修正案后） |
| **监管处罚** | 错误数据（过期汇率/越权内容）导致客户损失 | MAS 执法、业务限制、罚款 |
| **审计失败** | 缓存成为审计盲区（敏感数据路径无留痕） | 内部审计发现、外部审计保留意见、监管质询 |
| **SR 11-7 模型风险管理失败** | 缓存行为未纳入模型风险管理文档 | 模型使用未获批准、回滚、资本与声誉成本 |
| **客户信任损失** | 串用户（A 的答案给了 B）、越权内容泄露 | 客户流失、品牌损害、诉讼 |
| **错误决策放大** | 幻觉/偏见被缓存固化 | 系统性错误答案，影响面乘数级放大 |

完整的 LLM 安全与治理框架见 [llm_development_risks_security_guide.md](../llm_development_risks_security_guide.md)；SR 11-7 对模型组件的要求在 12.6 展开。

## 7. 失效与一致性策略

缓存设计的下半场是失效（invalidation）。**没有失效机制的缓存不是缓存，是数据黑洞**——永远返回"曾经的新鲜"。

### 7.1 TTL 策略：按内容类型分层

TTL 必须与内容的"允许陈旧程度"匹配，而不是一刀切：

| 内容类型 | 典型 TTL | 理由 |
|---|---|---|
| 实时行情/报警类（若允许缓存） | 秒级（5–30s） | 陈旧窗口必须最小 |
| 实时汇率/挂牌价 | 秒–分钟级（30s–5min） | 标注"数据截至 X" |
| 工具结果（确定性） | 分钟级（1–15min） | 按数据源变更频率配置 |
| 检索结果/知识库问答 | 小时–天级 | 文档集低频变化 |
| 产品文档/FAQ | 天–周级 | 带版本号 |
| 法规条文（已生效） | 月级 | 低频变化 + 版本校验 |

### 7.2 显式失效（事件驱动）

**数据更新事件 → 缓存失效**，不等 TTL 自然过期：

- 数据源发布变更事件（CDC、消息队列、webhook）→ 订阅方删除/刷新相关缓存键；
- 与流式数据管道配合的模式详见 [rag_with_data_streaming_guide.md](rag/rag_with_data_streaming_guide.md)——其"流式失效"章节讨论的是同一问题的检索侧版本；
- 显式失效的粒度：键级（精确）、前缀级（`tool_name:*`）、命名空间级（整域）。

### 7.3 版本失效（Version-Based Invalidation）

**版本号入键**（第 5 章原则 1）是最可靠的失效机制——不依赖事件到达，旧版本内容天然不可达：

- 模型升级：`model_version` 变化 → 全部相关缓存键变化；
- 工具 schema 变更：`schema_version` 变化；
- 知识库/文档集更新：`kb_version` 变化（增量场景可用"文档级版本"而非全库版本）；
- embedding 模型升级：向量全部重算，旧向量键失效。

### 7.4 写失效（Write-Through Invalidation）

业务写入发生时**主动删除**受影响缓存：数据变更 API 在执行写操作的同时，删除该数据相关的缓存键（如"更新产品利率 → 删除利率类工具缓存与 FAQ 缓存"）。适用于"写路径已知、影响面可枚举"的场景。写失效的常见遗漏：**间接影响**——更新一条利率可能影响 20 个缓存键（工具结果、检索结果、FAQ 回答），需要维护"数据实体 → 缓存键"的影响映射。

### 7.5 懒失效（Lazy Validation）

命中时校验新鲜度：缓存条目携带**数据源时间戳/版本**，命中时与数据源做一次轻量校验（如查版本号，不查全量数据）。适合"校验代价低、数据源有版本标识"的场景。懒失效与 TTL 组合是默认配置：**TTL 负责兜底，事件与版本负责精确**。

### 7.6 一致性模型：强一致 vs 最终一致

| 模型 | 特征 | 适用 |
|---|---|---|
| **强一致（strong consistency）** | 缓存永远与数据源同步；读路径阻塞等待校验 | 金融决策、交易类、余额类（几乎不用缓存，或必须同步失效） |
| **最终一致（eventual consistency）** | 允许短暂陈旧窗口；事件驱动的异步失效 | **Agent 缓存默认选择**：知识问答、FAQ、检索结果、文档类工具结果 |
| **有界陈旧（bounded staleness）** | 明确陈旧上限（TTL）+ 过期即失效 | 大多数工具的实用折中 |

**原则：Agent 缓存通常最终一致即可**——对话辅助、知识问答场景下"几分钟前的知识库版本"完全可接受。但**金融决策场景需要更高保证**：涉及客户资产、交易、合规判断的数据路径，要么强一致，要么不缓存（直连数据源），并记录"本回答基于的缓存版本与时间戳"以备审计。

## 8. 缓存安全

缓存是新的攻击面。**攻击者不会放过一个"存储了所有重复答案"的系统**——本指南的安全要求与 [llm_development_risks_security_guide.md](../llm_development_risks_security_guide.md) 的威胁模型一脉相承，这里聚焦缓存特有的六类风险。

### 8.1 缓存投毒（Cache Poisoning）

攻击者通过**污染缓存内容**影响其他用户：构造恶意输入触发 Agent 执行，将带毒回答写入共享缓存，后续相似查询全部命中带毒内容——**一次投毒，批量中毒**。在语义缓存下尤其危险：攻击者可以精心构造与目标问题"语义相似"的恶意查询来命中他人的缓存键。

防线：

- **写回质量门槛**（第 10 章）：校验输出与工具结果的引用一致性，投毒内容通常过不了 grounding 校验；
- **写回权限**：只有经过完整 Agent 执行链路的输出才允许写缓存，禁止外部输入直接写缓存；
- **内容消毒**：命中缓存后仍按不安全输出处理（[llm_development_risks_security_guide.md](../llm_development_risks_security_guide.md) LLM02）——缓存内容视为"不可信输入"，渲染前消毒；
- **限速与异常检测**：单用户高频构造近语义查询（探测缓存键）是投毒前置行为。

### 8.2 缓存键碰撞（Key Collision）

不同内容映射到同一缓存键 → 串数据。来源：哈希碰撞、规范化 bug（5.3）、键截断。防线：使用强哈希（SHA-256 及以上）；键中保留结构化前缀（`content_type:namespace:version`），把碰撞概率压到可忽略；键碰撞检测作为缓存测试用例（构造边界参数对验证键唯一性）。

### 8.3 越权读取（命中缓存必须重新鉴权）

**权限校验必须在缓存命中时重新执行**——命中缓存 ≠ 有权读取。经典漏洞：

```
L1 语义缓存：查询 Q 的答案由 VIP 用户触发写入
普通用户查询 Q（语义相似）→ 命中 → 返回 VIP 答案
```

规则：**鉴权在缓存之前，而不是只在缓存之后**。缓存命中路径与未命中路径必须走相同的鉴权、租户隔离、数据权限检查；缓存层只负责"内容是否新鲜"，不负责"用户是否有权"。

### 8.4 加密存储

需要落盘的缓存（磁盘/外部存储）必须加密（静态加密 + 传输加密）。但注意 6.1 的原则：**加密 ≠ 可以缓存 PII**——加密降低泄露的**概率与影响**，不改变**缓存 PII 本身的合规问题**。加密对象应仅限于"已通过白名单的缓存内容"。

### 8.5 多租户隔离

**绝不能跨租户共享缓存。** 租户 A 的缓存内容对租户 B 不可见：

- 缓存基础设施层面隔离（独立实例/命名空间/前缀）或键内强租户维度；
- 共享缓存只允许存放"全局公共且无权限差异"的内容（如公开法规条文）；
- 云上部署注意缓存服务（Redis/Memcached）的网络安全组与认证配置——未认证的缓存端口是常见泄露点。

### 8.6 缓存日志审计

合规要求缓存可审计：**命中/未命中/写入/失效**四类事件都应记录（谁、何时、哪个键、哪个用户、权限上下文）。设计要点：

- 键不含 PII（第 5 章原则 4）——日志里出现身份证号即审计事故；
- 命中事件与用户身份关联，使"某用户读取了缓存中的某内容"可追溯；
- 审计日志防篡改（append-only），保留周期遵循当地监管要求。

## 9. 成本收益分析

### 9.1 命中率与成本节省测算（行业经验值）

| 缓存层 | 典型命中率 | 节省内容 | 成本节省幅度 |
|---|---|---|---|
| L1 语义缓存 | 20–40%（FAQ 场景 70%+） | 整个 Agent 执行（LLM + 工具 + 检索） | 单次命中省 100% 执行成本 |
| L2 工具结果缓存 | 30–60%（重复型工具） | 外部 API 费用 + 网络往返 | 省对应工具的全部外部费用 |
| L3 检索缓存 | 40–70%（稳定文档集） | embedding + ANN + rerank | 省检索链路 80%+ 开销 |
| L4 prompt caching | 取决于前缀复用率 | 输入 token（prefill） | **省 50–90% 输入 token 成本**（Anthropic 最高 90% 折扣 / OpenAI 50%） |
| L5 会话缓存 | 会话内接近 100% | 上下文重建、重复解析 | 会话内显著 |

**示例测算**（知识型客服 Agent，日 10 万查询，单次完整执行成本 $0.05）：

- 语义缓存命中率 30% → 3 万查询免执行 → 日省 **$1,500**；
- 剩余 7 万查询中，工具缓存与检索缓存再消掉约 40% 的外部 API 费用；
- prompt caching 再对全部执行的输入 token 打 50–90% 折扣。
- 三层叠加后，**日成本可降至无缓存方案的 20–30%**。

### 9.2 收益清单

- **成本下降**：token 费用（L4 + L1）、外部 API 费用（L2）、检索基础设施开销（L3）；
- **延迟下降**：缓存命中 10–100ms vs 完整 Agent 调用 5–30s——**数量级差异**，直接影响用户留存与超时率；
- **外部 API 配额节省**：市场数据商（Bloomberg、Reuters 类）按调用计费/限流，工具缓存直接节省配额并规避限流；
- **上游系统减负**：数据库、数据源不再被重复查询，峰值容量需求下降；
- **一致性红利**：同一问题多用户拿到同一答案，客观上提升回答一致性（利于质量评估与审计）。

### 9.3 风险与成本清单

- **一致性风险**：陈旧数据窗口；金融决策场景需更高保证（7.6）；
- **数据泄露风险**：缓存成为新的泄露面（第 6、8 章）；
- **缓存维护成本**：键设计、失效机制、监控、安全审查——缓存不是零维护组件；
- **调试复杂度**：缓存命中掩盖了上游故障（数据源已坏，缓存还在返回旧数据）。

### 9.4 何时不值得缓存

缓存不是越多越好。以下场景**明确不值得**：

| 场景 | 原因 |
|---|---|
| 低重复率查询（长尾、一次性、高度定制） | 命中率趋近于零，缓存开销纯亏 |
| 实时性要求极高（行情、交易执行） | 任何陈旧窗口不可接受 |
| 成本敏感度低（内部小规模、低流量） | 收益小于实现与维护成本 |
| 缓存实现复杂度高（异构数据源、频繁 schema 变更） | 失效机制的成本超过缓存收益 |
| 内容高度个性化/权限分化严重 | 能缓存的部分太少，隔离成本过高 |

**判断公式**：`缓存收益 = 命中率 × 单次节省 − 维护成本 − 风险敞口`。收益为正且风险可控才做。

**架构要点**：

- **鉴权前置 + 命中复核**（8.3）：② 和 ⑤ 之间，权限检查贯穿始终；
- **质量门槛在写回之前**（6.8）：不达标的输出只返回给当前用户，不进缓存；
- **写回是"慢路径"**：不阻塞用户响应（异步写回），失败不影响主流程；
- **失效事件总线**：数据更新事件 → 失效处理器（7.2），与主链路解耦。

### 10.2 代码示例一：语义缓存命中检查（Python 伪代码）

```python
class SemanticCache:
    def __init__(self, store, embedder, threshold=0.85, namespace="default"):
        self.store = store          # 向量存储（如 Redis/FAISS/PGVector）
        self.embedder = embedder    # embedding 模型（版本入键）
        self.threshold = threshold  # 相似度阈值——宁高勿低
        self.namespace = namespace  # 业务域隔离

    def _key(self, model_ver: str) -> str:
        # 版本号必须入键：模型升级 → 键空间整体切换 → 自动失效
        return f"sem:{self.namespace}:{model_ver}"

    def get(self, query: str, authz_ctx: dict) -> str | None:
        # 鉴权前置：无论命中与否，权限检查都执行
        if not authorize(authz_ctx):
            raise PermissionDenied(authz_ctx.user_id)

        q_vec = self.embedder.embed(normalize_query(query))
        hit = self.store.search(
            vector=q_vec,
            k=1,
            namespace=self._key(self.embedder.version),
            # 过滤条件：TTL 内 + 质量标记 + 非个性化
            filter={"quality_ok": True, "personalized": False},
        )
        if not hit or hit.score < self.threshold:
            return None                      # 未命中
        # 命中后仍要复核权限与新鲜度（懒失效）
        if hit.stale(now=time.now()):
            self.store.delete(hit.id)
            return None
        return hit.answer

    def put(self, query: str, answer: str, quality_gate_ok: bool,
            ttl_seconds: int, authz_ctx: dict) -> None:
        if not quality_gate_ok:              # 质量门槛：不过关不写
            return
        if contains_pii(answer) or is_personalized(answer):
            return                           # 6.1 / 6.4：PII 与个性化不写
        q_vec = self.embedder.embed(normalize_query(query))
        self.store.upsert(
            vector=q_vec, payload=answer,
            namespace=self._key(self.embedder.version),
            ttl=ttl_seconds,
            tags={"quality_ok": True, "personalized": False},
        )
```

### 10.3 代码示例二：工具缓存键构造（参数规范化）

```python
import hashlib, json

def build_tool_cache_key(tool_name: str, params: dict, schema_ver: str,
                         model_ver: str, authz_scope: str) -> str:
    # ① 剔除时间噪声：时间类参数不参与键（由 TTL 层处理）
    params = {k: v for k, v in params.items() if not is_time_noise(k, v)}
    # ② 规范化：key 排序、数值归一、格式统一
    canonical = canonicalize_params(params)   # 见下方 canonicalize_params
    payload = json.dumps(
        {"tool": tool_name, "params": canonical},
        sort_keys=True, separators=(",", ":"),
    ).encode("utf-8")
    digest = hashlib.sha256(payload).hexdigest()
    # ③ 版本与权限域入键；PII 绝不入键（原则 4）
    return f"tool:{tool_name}:{schema_ver}:{model_ver}:{authz_scope}:{digest[:32]}"

def canonicalize_params(params: dict) -> dict:
    out = {}
    for k, v in sorted(params.items()):
        if isinstance(v, float) and v.is_integer():
            v = int(v)                       # 1.0 → 1
        if isinstance(v, str):
            v = v.strip().lower()            # 大小写归一
        if isinstance(v, dict):
            v = canonicalize_params(v)       # 递归
        if isinstance(v, list):
            v = sorted(canonicalize_params(i) for i in v)  # 顺序无关
        out[k] = v
    return out
```

```python
    "regulation_text":       {"ttl": 30,  "unit": "d",  "cache": True, "versioned": True,
                              "effective_date_check": True},
    "session_memory":        {"ttl": None, "unit": "session", "cache": True, "scope": "user"},
}

def get_ttl(content_type: str) -> int:
    policy = TTL_POLICY[content_type]
    if not policy["cache"]:
        return 0                              # 禁止缓存 → 不写
    if policy["unit"] == "session":
        return -1                             # 会话级，随会话失效
    return policy["ttl"]                      # 秒
```

### 10.5 写回质量门槛（Quality Gate）实现要点

质量门槛是 L1 缓存安全的最后防线，建议实现为独立组件而非散落的 if：

- **grounding 校验**：回答中引用的实体/数字必须能在工具结果或检索文档中找到（引用一致性）；
- **确定性校验**：回答不含时间敏感表述（"当前汇率是……"而无时间戳）；
- **通用性校验**：PII 检测 + 人称检测（"您/贵司"类个性化表述）；
- **长度与结构校验**：截断、空回答、错误格式直接拒绝；
- **抽样人工复核**：写入的缓存条目按比例人工抽检，作为质量门槛的校准回路。

## 11. 缓存监控

没有监控的缓存等于盲飞。**至少**监控以下五类指标：

| 指标 | 度量 | 告警建议 |
|---|---|---|
| **命中率** | 每层（L1–L5）的 hit/miss 比例 | 命中率骤降 → 键设计回归/版本升级事故；命中率异常升高 → 检查是否过度泛化误命中 |
| **内存/存储占用** | 缓存条目数、字节数、驱逐率（eviction） | 接近容量上限 → 扩容或调整 TTL；驱逐率过高 → TTL 过短 |
| **失效延迟** | 事件发布 → 缓存删除的时延 | 超过业务允许的陈旧窗口（如知识库更新后 1 分钟缓存仍未失效） |
| **缓存正确性抽样验证** | 定期将缓存命中结果与"新鲜执行结果"对比（影子验证） | 不一致率超阈值 → 失效机制/阈值配置有 bug |
| **误命中与安全事件** | 低相似度却命中的比例、越权读取尝试、投毒特征请求 | 任何非零误命中 → 立即调查 |

**影子验证（shadow validation）**是缓存正确性的核心手段：按比例（如 1%）对缓存命中请求同时执行完整链路，对比两路结果，差异即缓存 bug。**这是金融场景缓存上线的必检项**——用真实流量持续证明缓存没有在悄悄返回错误内容。

监控数据本身也是审计证据（8.6）：命中率趋势、失效事件流、驱逐记录应可回溯。

## 12. 银行场景特别设计

本章把前面的所有原则收敛到银行/金融机构（新加坡 Cymbal Bank 场景）的具体设计决策。**总纲：银行的 Agent 缓存是"窄而稳"——缓存面窄，稳定性与合规性优先。**

### 12.1 银行 Agent 缓存策略总览

| 决策项 | 银行默认值 | 说明 |
|---|---|---|
| 缓存内容范围 | **只缓存非敏感静态知识**：产品文档、法规条文、FAQ、公开市场数据（非实时） | 见 4.1–4.12 |
| 客户特定数据 | **绝不缓存**（余额、交易、持仓、客户画像） | 6.1–6.2 |
| 工具缓存 | **仅限只读查询类工具**（产品目录、利率历史、法规查询） | 写类工具（转账、下单）永不缓存 |
| TTL 默认值 | **短 TTL + 严格失效**：宁可多 miss，不可给陈旧数据 | 实时类秒级、文档类小时级、法规类月级带版本 |
| 审计 | 命中/写入/失效全留痕，键不含 PII | 8.6 |
| 租户隔离 | 严格多租户隔离，跨租户共享缓存仅限"全局公共内容" | 8.5 |
| 鉴权 | **缓存命中仍须鉴权**，权限检查贯穿命中路径 | 8.3 |
| L1 语义缓存 | **默认关闭**；仅对白名单内容类型（FAQ/条款）开启 | 风险控制优先 |

### 12.2 监管文本缓存：版本 + 生效日期校验

法规条文的缓存必须带**版本号 + 生效日期**，命中时执行三步校验：

1. 权威源当前生效版本 == 缓存版本？
2. 当前日期在条文的生效日期与废止日期之间？
3. 该条文是否有修订中状态（征求意见稿等）？

任何一步失败 → 视为 miss，直连权威源并触发失效。**法规回答中必须标注条文版本与生效日期**（"依据 MAS Notice XXX，2026 年 1 月生效版本"），使回答本身可被审计。

### 12.3 SR 11-7：缓存是模型系统组件

美联储 SR 11-7（及 MAS 对应的模型治理要求）要求模型及其组件纳入风险管理生命周期。**Agent 缓存是模型系统的组件**，必须文档化：

- 缓存组件纳入模型文档（model documentation）：结构、数据流、失效机制、风险点；
- **缓存行为作为模型行为的一部分做变更管理**：TTL 调整、阈值调整、新增缓存内容类型 = 模型变更，需走审批；
- 模型验证（validation）覆盖缓存：验证"缓存不会导致输出偏离已批准行为"——即影子验证（第 11 章）的结论进入验证报告；
- 监控与告警覆盖缓存指标（命中率、正确性抽样）。

**务实建议**：把缓存设计文档作为模型文档的附录，明确"缓存什么、不缓存什么、失效规则、质量门槛"，审计时可以完整回答"这个缓存为什么存在、为什么安全"。

### 12.4 PDPA 合规：数据最小化同样适用于缓存

新加坡 PDPA 的同意、目的限制、数据最小化原则**完整适用于缓存**：

- 缓存中的客户数据 = "处理个人数据"，需要有合法依据与通知；
- **缓存副本超出数据最小化原则**——能证明"缓存是必需的"才可缓存（实际几乎无法证明，所以客户数据默认不缓存）；
- 数据保留限制（retention limitation）约束缓存 TTL——缓存条目的保留期必须短于业务允许的保留期；
- 跨境部署注意 PDPA 的跨境传输规则同样适用于缓存同步（如多区域缓存复制）。

### 12.5 故障场景：缓存失效风暴与降级策略

**缓存雪崩（cache avalanche）**：大量缓存同时过期（如统一 TTL、重启后冷启动），全部请求同时涌向下游——Agent 场景下是 LLM API + 工具 API 的瞬时洪峰，可能触发限流与费用尖峰。

| 场景 | 触发 | 降级策略 |
|---|---|---|
| 缓存雪崩 | 统一 TTL 到期/全量重启 | **TTL 抖动（jitter）**：TTL 加随机偏移；分级预热（先预热高频键）；多级缓存（本地 + 分布式） |
| 缓存击穿（hotspot） | 单一热键过期，并发同时 miss | 互斥重建（single-flight）：同键只允许一个请求重建，其余等待 |
| 缓存穿透 | 查询根本不存在的内容，永远 miss | 空值缓存（短 TTL）+ 参数校验前置 + 布隆过滤器 |
| 上游故障时缓存失效 | 数据源宕机，事件无法送达 | 失效重试队列；降级为"用旧缓存 + 显式陈旧标注"（比直接报错更可用，需产品确认） |
| 缓存服务故障 | Redis 等不可用 | **缓存降级为旁路（fail-open 只读）**：直接走完整执行链路；绝不让缓存服务成为可用性单点 |

**银行场景的降级原则**：缓存永远是可丢弃的加速层——**缓存故障不能阻塞业务**，业务路径必须能在无缓存模式下完整运行。

### 12.6 银行缓存内容决策速查

银行场景下遇到"要不要缓存"的疑问时，按此顺序回答：

1. 内容含客户数据/PII？→ **不缓存**（6.1–6.2）
2. 内容与权限/角色相关？→ **不共享缓存**（6.5）
3. 内容实时变化？→ **不缓存**（6.3、6.6）
4. 内容是公开静态知识（产品/法规/FAQ）？→ 可缓存，短 TTL + 版本
5. 是只读工具结果？→ 可缓存，参数键 + 数据源版本 + 短 TTL
6. 命中时仍鉴权？质量门槛过了？审计留痕了？→ **三项缺一不可**

## 13. 常见误区与反模式

| # | 反模式 | 表象 | 后果 | 正确做法 |
|---|---|---|---|---|
| 1 | **缓存一切**（包括 PII） | "反正有缓存，全存上" | GDPR/PDPA 违规、泄露面扩大 | 按第 4/6 章清单逐类审查 |
| 2 | **语义缓存无阈值**（或阈值过低） | 相似度 0.6 就命中 | **误命中 → 错误答案**，且错误被固化放大 | 阈值宁高勿低（0.85+），按域调优，误命中告警 |
| 3 | **缓存键不含版本** | 键 = hash(question) | 模型升级后返回旧模型答案 | 版本号入键（5.2） |
| 4 | **命中缓存跳过鉴权** | "缓存命中就返回吧" | **越权漏洞**（6.5 经典场景） | 命中路径与未命中路径走相同鉴权（8.3） |
| 5 | **长 TTL 缓存实时数据** | 汇率 TTL 设 24h | 过期错误数据，金融决策事故 | 按内容分层 TTL（7.1） |
| 6 | **缓存个性化内容** | 把"您的组合建议"写入共享缓存 | **串用户**，产品与合规事故 | 个性化只进用户隔离域（6.4） |
| 7 | **无失效机制** | 只设 TTL 不设事件失效 | 数据黑洞：知识库更新后永远返回旧内容 | TTL + 事件 + 版本三层失效（第 7 章） |
| 8 | **无监控** | 上线后从不看命中率 | 不知道缓存是否在工作、是否正确 | 第 11 章监控清单 + 影子验证 |
| 9 | **缓存敏感字段**（指望加密兜底） | "加密了就可以存" | 加密 ≠ 合规；二次暴露面仍在 | 敏感数据默认不缓存（6.1） |
| 10 | **多租户共享缓存** | 一个 Redis 全租户共用 | **跨租户泄露** | 严格隔离（8.5） |
| 11 | **缓存键含 PII** | `user_id+phone` 做键 | PII 散布到日志与监控 | opaque ID / PII 不入键（5.2） |
| 12 | **无质量门槛写回** | 所有输出都写缓存 | 幻觉/偏见被固化放大 | 质量门槛前置（10.5） |
| 13 | **缓存当数据库用** | 把缓存当唯一数据源，不设兜底 | 数据丢失/陈旧 | 缓存永远是加速层，数据源是真相源 |
| 14 | **忽视缓存故障** | 缓存挂掉业务全挂 | 可用性单点 | 旁路降级（12.5） |

## 14. 总结与决策框架

### 14.1 内容分类决策表

对任何"要不要缓存"的问题，查这张表：

| 内容类型 | 是否缓存 | TTL | 风险等级 | 关键约束 |
|---|---|---|---|---|
| 含 PII 的请求/响应 | ✗ 绝不 | — | 🔴 极高 | GDPR/PDPA；加密也不行 |
| 敏感金融数据（余额/交易/信用） | ✗ 绝不 | — | 🔴 极高 | 直连数据源；审计留痕 |
| 实时行情/实时汇率/随机数 | ✗ 绝不 | — | 🔴 高 | 缓存即错误数据 |
| OTP/一次性凭证/Secret | ✗ 绝不 | — | 🔴 极高 | 任何形式禁止 |
| 个性化输出 | ✗ 不进共享缓存 | 会话级 | 🔴 高 | 仅用户隔离域 |
| 权限相关数据 | ✗ 不进共享缓存 | — | 🔴 极高 | 命中仍鉴权 |
| 敏感意图/投诉/监管沟通 | ✗ 不缓存（走审计存储） | — | 🔴 高 | append-only 审计链 |
| 变更中法规/政策 | ✗ 变更窗口内禁止 | — | 🟠 中高 | 仅缓存生效稳定版 |
| 流式/警报/状态更新 | ✗ 不缓存 | — | 🟠 中 | 直连事件源 |
| 确定性工具结果（静态查询） | ✓ 缓存 | 分钟–天级 | 🟢 低 | 参数键 + 数据源版本 |
| 幂等 GET 响应 | ✓ 缓存 | 分钟级 | 🟢 低 | 认证主体隔离 |
| 检索结果（top-k + 分数） | ✓ 缓存 | 小时–天级 | 🟢 低 | 文档版本失效 |
| 嵌入向量 | ✓ 预计算缓存 | 长期 | 🟢 低 | embedding 模型版本 |
| 高频 FAQ 问答对 | ✓ 语义缓存 | 天级 | 🟠 中 | **质量门槛 + 阈值 + 白名单** |
| 系统提示/工具 schema/静态上下文 | ✓ L4 prompt cache | 服务商管理 | 🟢 低 | 前缀稳定，版本入键 |
| 法规条文（已生效） | ✓ 缓存 | 月级 | 🟢 低 | 版本 + 生效日期校验 |
| 产品文档/知识库 | ✓ 缓存 | 天级 | 🟢 低 | 带版本 + 事件失效 |
| 准实时挂牌汇率 | ⚠ 条件缓存 | 秒–分钟级 | 🟠 中 | 显式时间戳标注 |

### 14.2 核心原则

**可缓存的共同特征（四个特征缺一不可）：**

1. **确定性**（deterministic）——相同输入产生相同输出（或陈旧可容忍）；
2. **非敏感**（non-sensitive）——不含 PII、金融敏感数据、凭据；
3. **通用性**（non-personalized）——不依赖用户上下文，可跨请求共享；
4. **可失效**（invalidatable）——有明确的失效机制（TTL/事件/版本）。

**绝不可缓存的共同特征（命中任一即禁止）：**

1. **个性化**（personalized）——串用户风险；
2. **敏感**（sensitive）——PII、金融数据、合规边界内容；
3. **实时**（real-time）——缓存即陈旧；
4. **权限相关**（permission-scoped）——越权泄露风险；
5. **临时性**（ephemeral）——一次性凭证、短生命内容。

### 14.3 设计清单（Checklist）

上线一个 Agent 缓存系统前，逐项确认：

**设计期**

- [ ] 缓存内容逐类过了一遍第 4/6 章清单（正面 + 负面）
- [ ] 缓存键含版本号（模型/工具/schema/知识库）且不含 PII
- [ ] 参数规范化规则已定义（顺序、格式、精度、时间噪声剔除）
- [ ] TTL 按内容类型分层配置，实时类走最短档或禁止
- [ ] 失效机制三件套齐备：TTL 兜底 + 事件显式失效 + 版本失效
- [ ] L1 语义缓存有阈值、命名空间、白名单，默认保守
- [ ] 质量门槛组件已实现（grounding/PII/通用性校验）

**安全期**

- [ ] 鉴权在缓存命中路径重新执行（非跳过）
- [ ] 多租户隔离边界明确（跨租户共享仅限全局公共内容）
- [ ] 落盘缓存加密；敏感数据按"默认不缓存"执行
- [ ] 缓存投毒防线：写回校验 + 内容消毒 + 异常检测
- [ ] 审计日志（命中/写入/失效）完整且键不含 PII

**运行期**

- [ ] 五类监控指标上线（命中率/占用/失效延迟/正确性抽样/安全事件）
- [ ] 影子验证按比例持续运行，差异即告警
- [ ] 缓存故障旁路降级已验证（缓存挂掉业务不挂）
- [ ] TTL/阈值/内容类型的任何调整走变更管理（SR 11-7 视角）
- [ ] 定期审计：缓存内容抽样复核 + 缓存键 PII 扫描

### 14.4 一句话总结

> **Agent 运行时缓存的价值在于把"重复执行"变成"重复命中"；其风险在于把"错误、越权、过期"也一起命中。设计的全部艺术在于：用版本与事件保证新鲜，用质量门槛与阈值保证正确，用鉴权与隔离保证安全，用分层 TTL 与旁路降级保证可控——而对"敏感、个性化、实时、权限相关、临时"五类内容，直接说不。**
