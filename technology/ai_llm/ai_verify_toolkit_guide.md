## 1. The Toolkit at a Glance

AI Verify is an **AI governance testing framework *and* software toolkit**. The monorepo README carries the canonical scope statement, quoted verbatim because it defines both the promise and the boundary:

> "AI Verify is an AI governance testing framework and software toolkit that validates the performance of AI systems against a set of internationally recognised principles through standardised tests... It is a single integrated toolkit that operates within an enterprise environment. It can perform technical tests on common supervised learning classification and regression models for most tabular and image datasets. It however does not define AI ethical standards and does not guarantee that any AI system tested will be free from risks or biases or is completely safe."

Three things matter there. It is **enterprise-integrated, not SaaS** — it runs inside your perimeter against your models and data. Its technical tests target **traditional supervised learning** (classification and regression) over **tabular and image** data, not LLM text. And it **does not define ethics or certify safety**: the output is evidence, not a verdict. The sample report reinforces the last point — "only reports generated by AI Verify Toolkit in accordance with the AI Verify Testing Framework, and without modification are AI Verify Reports."

### 1.2 What 2.0 changed

The four named 2.0 changes explain the deployment shape in Section 2: a **modular architecture** ("re-architected to be more modular"); **independent test algorithms** ("Each test algorithm can now be run as a separate Python module, giving you the freedom to use and develop algorithms independently" — what makes Section 9 tractable); a **redesigned backend test engine worker**; **new frontend workflows**, **Veritas integration** ("Including Veritas into AI Verify allows financial institutions to meet common safety baseline and financial testing requirements") and **improved Computer Vision support**.

### 1.3 What it is / is not

| It is | It is not |
|---|---|
| A self-hosted toolkit for fairness, robustness and explainability tests | A hosted SaaS or an outbound API |
| A classification/regression harness over tabular and image data | An LLM evaluation suite (separate product line) |
| A report system with composable widgets, input blocks and templates | A certified compliance certificate |
| Extensible by plugin: your algorithms, widgets, input blocks, templates | A model-training or model-serving platform |
| Apache-2.0, forkable, air-gap-friendly by construction | A managed service with an SLA |

The official toolkit page frames the audience as "data scientists and compliance teams" who use it "to streamline your AI testing process, and ensure the reliability and fairness of your models" — a joint technical-and-compliance workflow, which is why the portal pairs technical tests with process checklists.

### 1.4 The runtime tiers in one sentence

`aivt-integration-testing` describes itself as "AIVT Integration Testing Consisting of APIGW, Standalone Plugins and Portal Test Cases": a **Portal** (Next.js), an **API Gateway** (backend service), and **plugins that can run standalone**, with a queue and an engine worker between gateway and execution.

## 2. The Architecture

### 2.1 Monorepo layout

| Path | Role |
|---|---|

| `aiverify-portal` | Frontend portal — Next.js UI (canvas designer, test run form, results) |

Root files: `CHANGELOG.md`, `LICENSE`, `NOTICE.md`, `README.md`, `SECURITY.md`, `package.json`, `.pre-commit-config.yaml`, `ruff.toml`, `.dockerignore`.

### 2.2 The tiers

1. **Portal (Next.js).** Select model and dataset, configure algorithms, design the report canvas, read results. Verified paths: `app/results/run/{page,layout}.tsx`, `components/TestRunForm.tsx`, `components/QueryProvider.tsx`, hooks `useSubmitTest`, `useGetTestRuns`, `useCancelTestRun`, `useDeleteTestRun`, and `view_tests/components/{ActiveTestsList,FilterButtons}.tsx`. The wiki notes the portal "also functions as a reverse proxy for the API Gateway".
2. **API Gateway (`aiverify-apigw`).** Accepts submissions, holds the run registry, enqueues work, serves results, streams progress back.
3. **Queue.** Decouples submission from execution.
4. **Test engine worker.** The executor: it "consumes test tasks from a Redis queue, executes the specified algorithms against AI models, and returns the results... processing potentially long-running and resource-intensive operations asynchronously." Core functions as documented: **1 task consumption, 2 model loading, 3 data processing, 4 algorithm execution, 5 result generation, 6 progress tracking.**

A run is slow and heavy (loading a model, iterating a dataset, generating corrupted image variants), so submission and execution must be decoupled. The **worker is the tier you scale**, and the tier needing the most CPU and RAM.

### 2.3 The plugin model

Per the developer documentation, a plugin is "the primary mechanism for extending AIVerify's functionality, allowing you to add custom algorithms, widgets, input blocks, and templates... A plugin in AIVerify is a container for one or more of the following components":

- **Algorithms** — Python code computing a metric or a perturbed dataset, executed against a model plus dataset.
- **Widgets** — MDX report components rendering results.
- **Input blocks** — interactive configuration collected *before* an algorithm runs (e.g. the Fairness Tree).
- **Templates** — pre-composed report structures (Veritas ships five).

A plugin is not "an algorithm" but a *vertical slice of a test* — configuration, computation, presentation. Robustness Toolbox holds one algorithm and three widgets; Veritas holds one algorithm, five templates and eight widgets.

### 2.4 Execution order

The portal configures the test (model, dataset, per-algorithm inputs, input-block data) and submits; the gateway enqueues; the worker picks up the task, **loads the model** through a model plugin, **processes the data** through a converter/deserializer chain, **executes the algorithm**, and **generates results** as artefacts and test results while **progress updates flow back**; the portal renders results through **widgets** bound by component id (CID) and widget group id (GID).

### 2.5 Data flow

```text
┌──────────────────────────────────────────────────────────────────────┐
│  PORTAL (Next.js)                                                    │
│  • plugin store        • canvas designer (grid for report widgets)   │
│  • TestRunForm         • project data selection                      │
│  • results/run pages   • view_tests (ActiveTestsList, filters)       │
└───────────────┬───────────────────────────────────▲──────────────────┘
                │ REST (submit / query / cancel)     │ progress + results
                ▼                                   │
┌──────────────────────────────────────────────────────────────────────┐
│  API GATEWAY (aiverify-apigw)                                        │
│  POST /api/test_runs/run_test   GET /api/test_runs                   │
│  GET  /api/test_runs/:id        POST /api/test_runs/:id/cancel       │
│  DELETE /api/test_runs/:id                                           │
└───────────────┬──────────────────────────────────────────────────────┘
                │ enqueue task
                ▼
┌──────────────────────────────────────────────────────────────────────┐
│  QUEUE (Valkey Stream / Redis-compatible)                            │
└───────────────┬──────────────────────────────────────────────────────┘
                │ consume task
                ▼
┌──────────────────────────────────────────────────────────────────────┐
│  TEST ENGINE WORKER (aiverify-test-engine-worker)                    │
│  1 task consumption → 2 model loading → 3 data processing            │
│  4 algorithm execution → 5 result generation → 6 progress tracking   │
│  uses: aiverify-test-engine + installed plugins                      │
└───────────────┬──────────────────────────────────────────────────────┘
                │ writes artefacts + test results (keyed gid:cid)
                ▼
        artefact & result store  ──────►  widgets (MDX) render in portal
```

The `gid:cid` keying is the contract between computation and presentation: widgets fetch results via `getResults(cid)` and artefacts via `getArtifacts(cid)`, mapped by `${widget.gid}:${cid}`. A wrong CID renders "No algorithm results available" — which is why the documented error-handling pattern exists.

### 2.6 The queue is Valkey Stream

The project documents the queue inconsistently. The **engine architecture description** says the worker "consumes test tasks from a Redis queue"; the **worker README** and the **architecture wiki** both say it is backed by **Valkey Stream** ("read and execute tasks from a task queue, which is managed by Valkey Stream"). Valkey is the Linux Foundation fork of Redis, wire-compatible where it matters here. Treat "redis queue" as shorthand: the authoritative requirement is "**Valkey**: Required for the message queue", host default `127.0.0.1`, port default `6379`.

### 2.7 The worker's execution-isolation model

The worker has a **build module** and an **execute module**, selectable by environment variable, deciding *where and how* an algorithm runs:

| Variable | Default | Documented alternatives |
|---|---|---|
| `PIPELINE_BUILD` | `virtual_env` | `docker_build` |
| `PIPELINE_EXECUTE` | `virtual_env_execute` | `docker_run`, `kubectl_run` |

A test can be built into a virtual environment and run there; or built into a **Docker image** (optionally pushed to a private registry via `DOCKER_REGISTRY`) and run as a container; or run in **Kubernetes** via `kubectl run`/`exec`, pulling from `KUBECTL_REGISTRY` (defaults to `DOCKER_REGISTRY` if set, else `localhost:5000`). This is the tier that lets an on-prem enterprise sandbox untrusted third-party plugins away from core services.

## 3. The Test Engine

`aiverify-test-engine` is the foundation. Its description names the responsibility boundaries exactly:

> "AI Verify Test Engine provides core interfaces, converters, data, model and plugin managers to facilitate the development of tests for AI systems. It is used as a base library for all AI Verify official stock-plugins and can be used to develop custom plugins."

The engine does **not** contain the tests — it contains the machinery tests are written against, so a custom plugin is a first-class citizen. It ships to PyPI, so a data-science team can pull it without cloning the monorepo.

### 3.1 Package tree

Verified from the engine README and the PyPI description (they agree): four sub-packages, seven interfaces. `pipeline` is first-class — a model *pipeline* (transformers plus final estimator) differs from a bare estimator, and the engine models it explicitly.

```text
aiverify-test-engine/
├── aiverify_test_engine/
│   ├── interfaces/    # algorithm, converter, data, model, pipeline, serializer, plugin
│   ├── io/            # Data and model IO related logic
│   ├── plugins/       # Loading and execution of algorithm, data, model, pipeline, plugins
│   └── utils/         # Utility functions and validators
├── tests/             # Test cases
└── pyproject.toml     # Project configuration (hatch build backend)
```

### 3.2 The two interfaces that matter most

**`IAlgorithm`** — algorithms are plugins adhering to `IAlgorithm`; the engine loads them and executes them against a model plus dataset. This is the interface you implement to extend the toolkit (Section 9). **`IModel`** is the model abstraction: `is_supported()` (capability probe — does this plugin support the loaded model object?), `predict()` (hard-label / point prediction), `predict_proba()` (probability output, where supported), and `score()` (where available). `predict_proba()` matters for fairness — some parity metrics are threshold-free and rely on class scores, others are threshold-dependent and rely on labels — so a model plugin that cannot supply probabilities constrains which metrics are meaningful.

### 3.3 Category 1 — Model

| Framework | Plugin file | Supported classes (as documented) |
|---|---|---|
| Scikit-learn | `sklearnmodel.py` | `LogisticRegression`, `DecisionTree`, `RandomForest`, and peers |
| XGBoost | `xgboostmodel.py` | `XGBClassifier`, `XGBRegressor`, `Booster` |
| TensorFlow | `tensorflowmodel.py` | Sequential models |
| LightGBM | `lightgbmmodel.py` | `LGBMClassifier` |

Two asymmetries that bite. **Gradient boosting is asymmetric**: XGBoost lists classifier, regressor and the low-level `Booster`; LightGBM lists only `LGBMClassifier`, so a LightGBM regressor is **FLAGGED** as undocumented. **TensorFlow lists only Sequential models** — subclassed `tf.keras.Model` implementations, a common production pattern, are not named; **FLAGGED** pending a source read of `tensorflowmodel.py`.

### 3.4 Category 2 — Model Pipeline

Scikit-learn and PyTorch are both supported in pipeline form (a transform chain plus a final estimator). A pipeline is the realistic artefact: tabular and credit models ship as scaler + encoder + estimator. The example table confirms it — several rows require a **[`Pipeline Folder`]** upload rather than a **[`Model File`]** upload (`regression_tabular_donation`, `sample_fashion_mnist_sklearn`, `bc_tabular_credit`, `mc_image_fashion`). The portal exposes **two distinct upload methods** ("Upload AI Model" vs "Upload Pipeline"); choosing the wrong one is an immediately visible mis-wiring.

### 3.5 Categories 3 and 4 — Deserializer and Data Type

| Layer | Supported |
|---|---|
| Deserializer | Delimiter (delimited flat files, CSV and friends); Joblib; Pickle; TensorFlow (TensorFlow/Keras artefacts); Image |
| Data Type | Delimiter — separator variants **colon, comma, pipe, semicolon, space, tab**; Pandas (DataFrame/Series, incl. pickle); Image — **JPG, JPEG, PNG** |

The six documented separators mean a `|`-delimited extract or a tab-delimited export needs no pre-conversion. The image formats are a hard constraint: TIFF or DICOM is out of scope without a custom deserializer or data type (**FLAGGED**).

| Command | What it adds |

| `pip install aiverify-test-engine[tensorflow]` | Optional TensorFlow and Keras dependencies. |

The apigw and worker READMEs state **Python 3.11+** and **Debian** as tested OS; the portal needs **Node.js 18+**; the developer-tools install page pins **Python 3.11** and **NodeJS 22**. Local development:

```bash
cd aiverify/aiverify-test-engine
pip install '.[dev]'
python -m pytest tests        # test suite

```

### 4.1 Fairness — classification

The algorithm "computes a list of fairness metrics to measure how correctly your model predicts among the given set of sensitive features". These are the **group-parity** family:

| Metric (exact repo name) | Reads on |
|---|---|
| False Negative Rate Parity | Missed positives, by group |
| False Positive Rate Parity | False alarms, by group |
| False Discovery Rate Parity | Share of flagged positives that are wrong, by group |
| False Omission Rate Parity | Share of cleared negatives that are wrong, by group |
| True Positive Rate Parity | Recall, by group |
| True Negative Rate Parity | Specificity, by group |
| Positive Predictive Value Parity | Precision, by group |
| Negative Predictive Value Parity | NPV, by group |

Note what is absent: no disparate impact ratio, no four-fifths rule, no equal-opportunity *difference* or average-odds difference as named metrics. If a compliance template demands "disparate impact ratio" you compute a ratio from the group rates — it is not a named output (**FLAGGED**).

**Input:** `Sensitive Feature Name`, an **array** of sensitive feature names; "You may select multiple sensitive features of interest, and as a guide these are usually demographic features". **Input block:** the **Fairness Tree**, which "helps you to select the most relevant fairness metrics for your use case" — the toolkit's explicit anti-mechanism, a decision tree driven by the harm being guarded against, documented at `/appendix/use-fairness-tree/` in the user guide.

**Widgets:** Bar Chart (Selected), Interpretation (Selected), Description (Summary), Interpretation (Summary), Table of Definition, Fairness Metrics (All) — a *Selected* pair driven by the tree plus an *All* view, which is how a well-built plugin narrows scope without losing the audit trail.

### 4.2 Fairness — regression

| Metric | Widget that renders it |
|---|---|
| Mean Absolute Error parity | Bar Chart (MAE) |
| Mean Square Error parity | Bar Chart (MSE) |
| R2 score parity | Bar Chart (R2) |

Widgets: Introduction, Understanding Bar Chart, Bar Chart (MAE/MSE/R2), Interpretation (MAE/MSE/R2), Recommendation, Table of Definitions. Same input contract (array). Classification fairness concerns *decision rates* across groups; regression fairness concerns *error parity*. A regression model that underpredicts loan amounts for one demographic by 30% is unfair even though there is no positive label to attach a parity metric to.

### 4.3 Robustness — the Robustness Toolbox

The README describes a **boundary attack**: it "starts by adding a large amount of noise to a data point intentionally to cause a model [to be] misclassified... This plugin uses Salt-and-pepper noise... Then, it will reduce the amount of noise added while maintaining misclassification. This algorithm does not depend on the underlying model's architecture or parameters." That last sentence is the important property: **black-box, model-agnostic**, needing only query access. The project also warns it was "developed for image dataset but can also be used to create noise on tabular dataset. However... testing on tabular dataset may warrant caution when interpreting the results as this is not well-tested."

Inputs are the **annotated ground truth path** (images: the uploaded dataset of filenames + labels; tabular: select the ground-truth dataset) and the **name of the column containing the image file name** (images: that column; tabular: key in `NA`), both `string`. **Outputs** (README; confirmed in the sample report): **Total Number of Samples**, **Successful Perturbed Rate**, and **accuracy of the original vs the perturbed dataset**. Widgets: Description (Summary), Bar Chart (Accuracy), Description (Technical).

### 4.4 Robustness — the Image Corruption Toolbox

"It tests the robustness of AI models to natural corruptions" across four groups "at 5 different severity levels (default) for each corruption function", calculating "the accuracy of the model... with the new corrupted datasets".

| Group | Corruption functions (exact names) |
|---|---|
| General | Gaussian, Poisson, Salt and Pepper |
| Blur | Gaussian, Glass, Defocus, Horizontal Motion, Vertical Motion, Zoom |
| Digital | Brightness Up and Down, Contrast Up and Down, Saturate Up and Down, Random Perspective, JPEG Compression |
| Environmental | Snow, Fog, Rain |

**Four algorithms**, not one — Blur Corruptions, Digital Corruptions, Environment Corruptions, General Corruptions — each of which "adds [group] corruptions... across thresholds of interests, and calculates the accuracy of the model". Widgets: Introduction, Understanding Bar Chart, Bar Chart (by corruptions type), corruption sample widgets, Recommendation.

The example table shows the parameter shape — `Name(s) of Corruption to Run: all` plus a group-specific threshold: `Gaussian Blur Sigma Value(s): 1.0` (Blur), `Gaussian Noise Sigma Value(s): 1.0` (General), `Snow Intensity Value(s): 1.0` (Environment), `Brightness Down Factor Value(s): 1.0` (Digital). The example dataset is Fashion-MNIST (`raw_fashion_image_10`), run across **all three** frameworks — **Sklearn, PyTorch and TensorFlow** — the clearest evidence that the CV path is framework-portable.

### 4.5 Explainability — SHAP, PDP and ALE

**SHAP Toolbox** — "explains how your features affect your overall predictions by using Shapley Values":

| Input | Description | Type |
|---|---|---|
| Type of explainability | `global` (default) or `local`. Global explains the overall dataset; local explains a random data point. | `string` |
| Path of the background data | Background data path | `string` |
| Size of the background / of the test dataset | Background samples / data samples (e.g. 25 each) | `int` |

The size inputs are the cost levers — SHAP cost scales with background x test x features, and the example uses **25 background and 25 test samples**. Widgets: Introduction, Understanding Bar Chart, Bar Chart (Summary), Bar Chart (Technical), Recommendations. Output is a **Global Explainability Chart** ranking features by absolute mean SHAP value.

**Partial Dependence Plot** — "explains how each feature and its feature value contribute to the predictions", "visualised as line graphs for each feature", rendered **for each feature in each class output** (a multi-class model produces a grid). Widgets: Introduction, PDP Line Graphs, Recommendation; no additional algorithm parameters per the example table.

**Accumulated Local Effect** — same phrasing and same per-class line-graph visualisation as PDP, but the underlying quantity is the accumulated local effect rather than the marginal average. Package `aiverify_accumulated_local_effect`; widgets Introduction, ALE Line Graphs, Recommendation. ALE exists because **PDP is wrong under feature correlation** — it extrapolates into feature combinations that do not exist in the data. **Guidance, labelled as reasoning rather than repo fact:** with correlated tabular features (loan_amount with income, say), ALE is the defensible choice and PDP the misleading one. The toolkit does not enforce this; it ships both and renders whichever you picked.

### 4.6 Veritas — the finance plugin

The README singles Veritas out in 2.0: "Including Veritas into AI Verify allows financial institutions to meet common safety baseline and financial testing requirements." Its own README describes it as an "AI Verify port of Veritas Methodology on Fairness & Transparency Assessment".

| Component | Contents |
|---|---|
| Algorithm | **Veritastool** — "Veritas Diagnosis tool for fairness & transparency assessment" |
| Templates | Veritas Base Classification Report; Veritas Base Regression Report; **Veritas Credit Scoring Report**; Veritas Customer Marketing Report; Veritas Predictive Underwriting Report |
| Widgets | Cover page; User Responses - Generic Veritas Checklist; Veritas Generic Performance Tests; User Responses - Veritas Fairness Checklist; Veritas Fairness Performance Tests; User Responses - Ethics and Accountability Veritas Checklist; User Responses - Veritas Transparency Checklist; Veritas Transparency Techical Tests |

Two observations. Veritas is the **only stock plugin shipping templates**, and it ships five — one per financial use case, i.e. it is meant for a risk or model-validation team rather than assembled widget-by-widget. And the checklist/performance-test pairing mirrors the toolkit's philosophy: quantitative tests interleaved with documented self-assessment, so the report carries both the number and the rationale. The template names reference a "**FEAT** checklist" (fairness, ethics, accountability, transparency), cited verbatim.

**Documented inputs:** `Privileged Group: ['SEX','1'], ['MARRIAGE','1']`; `Model Type: CLASSIFICATION`; `Positive Label: 1`; `Performance Metric: accuracy`; `Transparency Analysis Rows-1: 20`; `Transparency Analysis Rows-2: 40`; `Maximum Transparency Samples: 1000`. Note the "Privileged Group" shape — a list of `[column, value]` pairs, i.e. Veritas takes an explicit privileged reference group rather than inferring one. The example model (`cs_model`, a `.pkl`) must sit "inside a folder named `cs_model` and [be] uploaded via the Upload Pipeline method" — a packaging constraint, not a free-form file drop. **FLAGGED**: the internal metric set `Veritastool` computes beyond the `Performance Metric` input is not enumerated on any public page I could read.

### 4.7 The non-technical plugins, and what the library omits

- **`aiverify.stock.process-checklist`** — the structured self-assessment paired with technical results in one report: **85 process checks**, split 32 Yes / 29 No / 24 Not Applicable in the sample. The official site's "parallelized workflow" claim depends on it: "run technical tests and compliance teams to work on their checklists independently before combining into a full report."
- **`aiverify.stock.reports`** — report templates (widgets/MDX); the plugin carrying the layout primitives other widgets compose into.
- **`aiverify.stock.decorators`** — **FLAGGED**: named in the listing; role inferred from the name ("section decoration for reports"), low-confidence.
- **Not covered:** no LLM text evaluation; no unstructured text, audio or video; **no time-series tests** (a time-series model can be shaped into a regression test via lag features, but there is no backtest or leakage test — **FLAGGED**: no stock time-series plugin found); and **no fairness metric selection automation** — the Fairness Tree advises, the user chooses, the report renders the choice.

## 5. Installation and Deployment

Three distinct installation stories; confusing them is the commonest source of wasted days — **library-only** (the engine, one pip command), **developer workstation** (the full toolkit locally, to develop plugins), and **server deployment** (portal, apigw and worker as services).

### 5.1 Library-only

```bash
pip install 'aiverify-test-engine[all]'
```

Python `>=3.10, <3.13` (extras in Section 3.6). Enough to import `aiverify_test_engine`, implement `IAlgorithm`, and run an algorithm against a model plus dataset in your own harness — but **not** enough to produce a portal report.

### 5.2 Developer workstation

```text
<working directory>/
├── aiverify/  { aiverify-shared-library/  common/ }
├── aiverify-developer-tools/  { aiverify-algorithm-template/  aiverify-plugin/  template_plugin/ }
├── my_plugin/
└── .venv/
```

Dependencies (Ubuntu 22 path; macOS equivalents documented with Homebrew). `jq` and `zip` are not optional niceties — the tooling uses `jq` to process manifest JSON and `zip` to package a plugin. Sparse-checkout the monorepo modules the tooling needs (`--filter=blob:none --sparse` avoids downloading the full history and tree), build the shared library the tooling links against, then install and verify the developer tool. Clone it in the same parent directory:

```bash
sudo apt update && sudo apt-get install -y jq zip
sudo add-apt-repository ppa:deadsnakes/ppa && sudo apt update && sudo apt install python3.11
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash - && sudo apt-get install -y nodejs

python3 -m venv .venv && source .venv/bin/activate
pip install --upgrade pip && pip install cookiecutter pytest 'aiverify-test-engine[all]'

git clone --no-checkout git@github.com:aiverify-foundation/aiverify.git
cd aiverify && git sparse-checkout init --cone
git sparse-checkout set aiverify-shared-library common && git checkout main
cd aiverify-shared-library && npm install && npm run build && cd ../..

git clone https://github.com/aiverify-foundation/aiverify-developer-tools.git
cd aiverify-developer-tools/aiverify-plugin
npm install && npm link ../../aiverify/aiverify-shared-library
sudo npm install -g        # may need sudo
```

`aiverify-plugin --help` lists: `generate-plugin [gid]` (alias `gp`), `generate-widget <cid>` (`gw`), `generate-inputblock <cid>` (`gib`), `generate-algorithm <cid>` (`ga`), `zip [pluginDir]`, `validate`, `test-widget` (`testw`), `test-algorithm` (`testa`), `test-all`, and `playground`. It is a Node CLI wrapping cookiecutter templates — which is why Python, Node and the shared library are all prerequisites. The four `generate-*` verbs map one-to-one onto the four plugin components. `zip` produces the distributable, `validate` gates it, `test-*` runs it, and `playground` saves you deploying the whole stack to see whether a widget renders.

Two pieces of **cosmetic documentation drift** are worth flagging: the sparse-checkout instruction references `aiverify/ai-verify-shared-library` in one place while the directory created is `aiverify-shared-library`, and the developer-tools clone URL still points at the legacy `IMDA-BTG` organisation. Harmless if you read for intent; an hour lost if you copy the text literally.

### 5.3 Server deployment

| Component | Requirement | Default port | Install route |
|---|---|---|---|
| `aiverify-apigw` | Python 3.11+, Node 18+, Debian | **4000** | Hatch dev env, `install-amd64.sh` / `install-arm64.sh`, or Docker |
| `aiverify-portal` | Node.js 18+ | **3000** | `npm install` + `npm link ../aiverify-shared-library`, or Docker |

| Valkey | Task queue | **6379** | Your platform's Valkey/Redis service |

The apigw's sparse-checkout differs from the developer-tools one — it checks out `aiverify-apigw`, adds `common` and `stock-plugins`, and targets the **`v2.x` branch**. The `aiverify-apigw-node` step is easy to miss and is not optional: "The NodeJS scripts are used by the API-GW to validate and parse MDX files." Without it the gateway cannot handle widget definitions. Docker equivalent: build with `docker buildx build -t aiverify-apigw -f aiverify-apigw/Dockerfile .`, then `docker run -d --name=aiverify-apigw -p 4000:4000/tcp -v "$PWD/data:/data" aiverify-apigw`.


```bash

cd ../aiverify-portal && npm install && npm link ../aiverify-shared-library && npm run dev   # :3000
```

The worker runs via `hatch run dev`; its tests need `pip install pytest pytest-mock faker` and `pip install -e ../aiverify-test-engine[all]`.

### 5.4 What `deployment/` actually ships

> "This folder contains reference deployment scripts for Docker Compose and Kubernetes environments... **These scripts are for reference purposes only.** It is crucial to customize them according to your specific environment and requirements."

Read that as the maintainers telling you there is **no supported production topology** — no hardened manifests, no Helm chart with defaulted secrets. You fork the compose or Kubernetes files and own them. The wiki additionally carries `AIV2-Deployments` and `Manual Installation & Setup`.

### 5.5 Common setup failures (documented)

| Symptom | Cause | Fix (as documented) |
|---|---|---|
| Plugins not loading / stale plugins | The apigw "scan[s] the plugins from source and cache[s] it into a database" on **first startup only** | Stop apigw, delete `aiverify-apigw/data/database.db`, restart |
| `Error: fetch failed on /home` | Backend unreachable or misconfigured | Check apigw is running on port 4000; verify `.env` |
| `Module not found` in the portal | Shared library not built or not linked | `npm install` + `npm run build`; verify the link |
| SQLite concurrency errors | SQLite "does not support concurrent writes" | Use PostgreSQL for multiple apigw instances or a large DB |
| TensorFlow test failures on GPU machines | GPU/`ptxas` interaction | Force CPU via the documented env-var line (Section 3.6) |

The plugin-cache trap is the one to internalise: change a plugin, restart the gateway, and you will see the *old* plugin.

### 5.6 Prerequisites, sizing and air-gap

| Concern | Status |
|---|---|
| Python | `>=3.10, <3.13` for the engine; apigw and worker document **3.11+** |
| Node | **18+** for portal and apigw tooling; developer guide pins **22** |
| OS | **Debian** documented as tested for apigw and worker; developer guide covers Ubuntu 22 and macOS |
| Container arch | Install scripts for **amd64 and arm64** |
| Message queue | **Valkey** required by the worker |
| Storage | `APIGW_DATA_DIR` defaults to `./data`; may be an S3 URI with `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN` |
| CPU/RAM/disk sizing | **FLAGGED** — no minimum hardware specification published |

**Sizing — reasoning, labelled as inference.** The **worker is the expensive tier**, dominated by (a) model deserialization — loading a TensorFlow or PyTorch model is memory-hungry — and (b) the algorithm: Image Corruption at 4 groups x (3-6 functions) x **5 severity levels** generates dozens of corrupted copies of the test dataset, a disk and CPU event rather than a rounding error, while SHAP cost scales with background x test x features. The **portal and apigw are light** (a Next.js frontend and a FastAPI service with SQLite by default). Because the worker scales horizontally through Valkey Stream, the correct move is *more workers*, not a bigger single worker — subject to SQLite on the apigw becoming the bottleneck first.

**Air-gapped / on-prem.** The toolkit is air-gap-friendly: no telemetry, no call-home, and the official framing is that it "operates within an enterprise environment". **FLAGGED**: no *documented* air-gapped procedure exists. The verified building blocks: sparse-checkout with `--filter=blob:none --sparse` for a mirror; PyPI-based install satisfiable from a local mirror or vendored wheels; `DOCKER_REGISTRY` and `KUBECTL_REGISTRY` so built test images go to a **private registry**; `APIGW_DATA_DIR` on an S3-compatible endpoint (on-prem usually MinIO); and `PIPELINE_BUILD=virtual_env` (the default), which needs **no** registry at all. The realistic plan: mirror repo and wheels, keep the default virtual-env pipeline, skip `docker_build` entirely, point `APIGW_DATA_DIR` at internal object storage.

## 6. Configuration and Wiring

Configuration happens at three levels: the **services** (env vars / `.env` files), the **test run** (model, dataset, algorithms, inputs) and the **report** (widgets, grid, properties).

### 6.1 API gateway configuration

| Variable | Description | Default |
|---|---|---|
| `APIGW_LOG_LEVEL` | `debug`, `info`, `warning`, `error`, `critical` | `info` |
| `APIGW_DATA_DIR` | Storage directory. If an S3 URI, credentials come from `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` | `./data` |
| `APIGW_DB_URI` | Database URI; any SQLAlchemy 2.0 URL | `sqlite:///{APIGW_DATA_DIR}/database.db` |
| `APIGW_HOST_ADDRESS` | Bind host; `127.0.0.1` means local-only | `127.0.0.1` |
| `APIGW_PORT` | Bind port | `4000` |
| `APIGW_MAX_PART_SIZE_MB` | Maximum size of the test result form, in MB | `20` |

Three deserve a sentence each. **`APIGW_DB_URI`** — the README states that "sqlite does not support concurrent writes and should NOT be used if there is a need to spawn multiple instances of apigw. If the database is large or need to run multiple instances of apigw, then a client/server database like **PostgreSQL** should be used"; plan PostgreSQL from the start, since migrating later means migrating the plugin cache and run history. **`APIGW_DATA_DIR`** — where uploaded models, datasets and results land; S3 support keeps artefacts off the app server, and it uses standard boto3 environment-variable credentials. **`APIGW_MAX_PART_SIZE_MB`** — a hard **20 MB** default on the test-result form; image datasets and model files blow through it, and *not* raising it produces an opaque upload failure. The FastAPI interactive documentation is served at `http://{APIGW_HOST_ADDRESS}:4000/docs/`.

### 6.2 Portal and worker configuration

| Variable | Description |
|---|---|
| `APIGW_HOST` | Host address of the API gateway; `http://localhost:4000` when local |
| `PROXY_TIMEOUT` | Proxy timeout, default **600000 ms (10 minutes)** |

The 10-minute timeout signals expected run durations: exceed it at the portal layer and you hit a configuration limit before a compute limit, with the symptom "the page hung". Worker variables (full table in the worker README): `TEWORKER_LOG_LEVEL` (`info`), `APIGW_URL` (`http://127.0.0.1:4000`), `VALKEY_HOST_ADDRESS` (`127.0.0.1`), `VALKEY_PORT` (`6379`), `PYTHON` (`python3` — the interpreter used to run tasks; set it explicitly if you manage multiple environments), `PIPELINE_BUILD` (`virtual_env`), `PIPELINE_EXECUTE` (`virtual_env_execute`), `DOCKER_REGISTRY` (none), `KUBECTL_REGISTRY` (`DOCKER_REGISTRY` if set, else `localhost:5000`).

### 6.3 Data formats and model wiring

Data format and wiring. Tabular inputs are delimited text with **colon, comma, pipe, semicolon, space or tab**, plus **Pandas pickle** and **Joblib**; images are **JPG, JPEG, PNG**; ground truth uses the same tabular formats, or an *annotated ground-truth dataset* mapping filename to label for images. The image pattern is always the same pair: a **raw image dataset** plus an **annotated ground-truth dataset** (a pickle or delimited table with filename and label columns). The robustness and image-corruption plugins both take these and both ask you to name the filename column — for the Fashion-MNIST examples that column is literally `file_name` and the label column `label`. Follow the user guide's preparation flows (`/detailed-guide/input-preparation/prepare-tabular/` and `.../prepare-image/`) rather than reverse-engineering column expectations.

| Upload method | For | Examples from the stock example table |
|---|---|---|
| **Upload AI Model** (a `Model File`) | A single serialized estimator | `sample_bc_credit_sklearn_linear.LogisticRegression.sav` |
| **Upload Pipeline** (a `Pipeline Folder`) | Transform chain + final estimator, or a framework model folder | `regression_tabular_donation`, `bc_tabular_credit`, `mc_image_fashion`, `sample_fashion_mnist_sklearn` / `_pytorch` / `_tensorflow`, `cs_model` |

Deserializers cover **Joblib, Pickle, TensorFlow and Image**. The `.sav` extension in the examples is the toolkit's convention for a serialized artefact, not a portable format — the underlying serialization is pickle/Joblib.

**A gRPC or REST "call the live model" wiring mode is FLAGGED as unverified.** The support matrix lists only *Model* and *Model Pipeline*, and every example is a file or folder upload. I found no documented mode in which the engine calls a running endpoint over HTTP or gRPC. The robustness attack is model-agnostic, implying query access suffices in principle — but *shipping* a live-endpoint model plugin is not a stock path. Treat "point AI Verify at our serving endpoint" as a **custom plugin project** (Section 9), not a configuration toggle. That single fact has an outsized effect on adoption cost for teams whose models only exist behind an API.

### 6.4 Protected attributes, ground truth, run modes and schemas

- **Protected/sensitive attributes.** Supplied per-algorithm as the `Sensitive Feature Name` **array** (both fairness toolboxes), or as an explicit `Privileged Group` list of `[column, value]` pairs (Veritas). The attribute must be *present in the test dataset*, which the tests slice by. Note the asymmetry: the parity toolboxes ask "which attributes are sensitive?"; Veritas asks "which group is reference?".
- **Ground truth.** Required by every supervised metric — typically a column in the same dataset for tabular tests (the example table shows `default` for the credit datasets, `donation` for the regression pipeline dataset), or the separate annotated-ground-truth dataset plus a named filename column for images.

Failures here are the most common *silent* mis-wirings: a parity metric computed against the wrong ground-truth column produces a plausible number that is simply wrong. The example table's explicit `Ground Truth Dataset` and `Ground Truth Column` columns exist because this is the step people get wrong.

The primary run mode is **interactive, through the portal**; the API exposes the same lifecycle programmatically (Section 8.1). There is **no documented standalone CLI** for "run a test and emit a report" (**FLAGGED**) — the closest thing is `aiverify-plugin test-algorithm`, which runs an algorithm's own tests. Headless operation means API calls, which follows from the architecture: the gateway owns the run registry and the artefact store.

`common/schemas` holds the shared schemas (wiki page: `AIV2-Schemas`). They are what make the plugin contract enforceable — the portal grid layout, widget `meta.json`, algorithm input definitions and test-result structure all have shapes both frontend and engine agree on. **FLAGGED**: I did not read the individual schema files. What is verified is that the directory exists and that both the developer-tools install flow and the apigw sparse-checkout explicitly include `common`. Read `common/schemas` before writing a plugin; it is the real specification, and the prose docs describe it less precisely than the files do.

## 7. Outputs and the Report

A run emits **test results and artefacts** keyed by `gid:cid`, rendered by **widgets** into a **report**, readable in the portal and printable to PDF.

### 7.1 The machine-readable layer

| Prop | Type | Meaning |
|---|---|---|
| `testResult` / `inputBlockData` | `TestResultData` / `InputBlockData` | Results and input-block data mapped by `${widget.gid}:${cid}` |
| `artifacts` | `string[]` | Artefacts mapped by `${widget.gid}:${cid}` |
| `getResults(cid)` / `getArtifacts(cid)` / `getIBData(cid)` | helpers | Fetch results / artefacts / input-block data by CID |

Results are **structured data** and widgets are presentation over it, so a script can post-process the same values a widget renders — but do not assume a documented public JSON schema for the on-disk artefact files (**FLAGGED**; see `common/schemas`). **Artefacts** are files — rendered charts, perturbed sample images, uploaded references; the robustness report shows "Example of a perturbed sample and its predicted value", the corruption report shows "corruption samples". Those are files, not computed values, which is why `APIGW_DATA_DIR` being S3-addressable matters.

### 7.2 The widget/MDX rendering model

Reports are **composed, not generated by a fixed template**. A widget is an MDX file receiving props (`id`, `properties`, `artifacts`, `testResult`, `inputBlockData`, `getIBData`, `getResults`, `getArtifacts`, `width`, `height`), and the portal's **canvas designer** places widgets on a grid. Per the authoring guide in `stock-plugins/readme.md`: **properties come from `meta.json`** and are user-editable on the grid (`<h1>{props.properties.heading1}</h1>`); the **CID is exported for reference** (`export const cid = "your_algorithm_cid";`); **missing data must be handled** by a ternary on `props.getResults(cid)` falling back to "No algorithm results available" (every stock widget does this); **charts are React components inside MDX** — `BarChart` and `LineChart`, configured with `xAxisDataKey`, `bars`, `lines`, `chartProps`, `legendProps` (ALE/PDP use `lines={[{ dataKey: "ale" }]}`; a vertical bar chart uses `chartProps={{ layout: "vertical" }}`); **responsiveness uses the `width`/`height` props** (charts need explicit dimensions, headers subtracted via `calc(100% - 40px)`); and **React `key`s** derive from the unique `id` prop.

### 7.3 Print mode — the PDF path

The authoring guide devotes explicit guidance to page breaks, which tells you the intended output is a **paged document**: `pageBreakInside: "avoid"` / `breakInside: "avoid"`; `pageBreakBefore/After: "always"` and `breakBefore/After: "page"`; `orphans: 3` and `widows: 3`. So **PDF is produced by printing the portal report**, and widget authors own the pagination. There is no documented server-side PDF renderer; a PDF in CI means a headless browser driving the portal (**FLAGGED**: not a documented automation path).

### 7.4 The official sample report, as actually seen

`https://aiverifyfoundation.sg/downloads/AI_Verify_Sample_Report.pdf` extracted is a **71-page** document:

| Element | Observed content |
|---|---|
| Title block | "AI GOVERNANCE TESTING FRAMEWORK AND TOOLKIT — SUMMARY REPORT — **BINARY CLASSIFICATION MODEL FOR CREDIT RISK** — ABC COMPANY PTE LTD — 06 JUN 2023" |

Three observations visible only by reading it. **It is a narrative, not a data dump** — every test page carries "What it means" and "Recommendation(s)" prose next to the number, and those interpretations ship with the *widgets*, which is why the widget library holds so many "Interpretation" and "Understanding Bar Chart" components. **Process checks carry the same weight as tests** — the summary leads with the Yes/No/Not-Applicable split across 85 checks, because the 11-principle structure demands documentary evidence alongside the metrics. And **this sample is a 2023 credit-risk classifier**, predating the 2.0 re-architecture: the layout has evolved, while the *content contract* (summary, model information, per-principle narrative, technical test pages) is durable. **FLAGGED**: no 2.0-era sample report is published separately, so the precise 2.0 page structure is not independently verified.

### 7.5 Self-assessment and reproducibility metadata

The process-checklist plugin *is* the self-assessment mechanism, captured in the same report: per principle, the check counts, the unmet criteria, "What it means" and recommended actions. Veritas extends this for finance with explicit checklist widgets ("User Responses - Veritas Fairness Checklist", "User Responses - Ethics and Accountability Veritas Checklist", "User Responses - Veritas Transparency Checklist"), each paired with the matching performance-test widget. **FLAGGED**: no separate, standalone "declaration" or conformity-statement file is emitted — the self-assessment lives *inside* the report as checklist data. If your assurance process expects a signed declaration, you compose it from the report.

The sample report records the **model filename**, **test dataset filename** and **completion timestamp** — the minimum viable provenance triple — but does *not* visibly record the **engine version** or a **plugin version set** (**FLAGGED**). Since the engine moved 2.0.0 → 2.2.1 and algorithm behaviour is version-dependent, record engine and plugin versions yourself alongside the report. For audit-grade evidence that annotation is on you.

## 8. Automation and CI/CD

The honest headline: **AI Verify is designed for interactive, portal-driven use; its automation surface is an API plus a test suite, not a first-class CI product.**

### 8.1 The API surface

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/test_runs/run_test` | Submit a new test |
| `GET` | `/api/test_runs` | Get all test runs |
| `GET` | `/api/test_runs/:id` | Get one test run |
| `POST` | `/api/test_runs/:id/cancel` | Cancel a test run |
| `DELETE` | `/api/test_runs/:id` | Delete a test run |

A clean, complete run lifecycle — submit, list, inspect, cancel, delete — enough to build a headless driver, but *not* a CI primitive out of the box: no documented "wait for completion and return results" endpoint, no webhook, and no standalone OpenAPI artefact I could read (**FLAGGED** — the FastAPI app serves `/docs/` at port 4000, where the authoritative request/response schemas live). Any CI integration is a poll-`GET /api/test_runs/:id`-until-done loop.

### 8.2 What CI the project actually runs

Verified by path: **`.ci/run-unit-test.sh`**; **`.github/workflows/v2-smoke-test.yml`**; and **`aivt-integration-testing`** — "AIVT Integration Testing Consisting of APIGW, Standalone Plugins and Portal Test Cases" — the integration layer exercising the gateway, the standalone plugin path and the portal. `CONTRIBUTING.md` adds that pull requests "will be put through simulated testing environments. Unit tests, linting, and various dependency checks, including those on licences will be conducted... through GitHub Actions", so the merge gate is unit tests + lint + dependency/licence checks. That is a reasonable *product* CI story; it is a thin *user* CI story — no documented GitHub Action, no "run AI Verify against my model on every commit" recipe.

### 8.3 `moonshot-cicd` is not this

The **`moonshot-cicd`** repository in the same organisation (last touched 2026-09-10) is **not** toolkit CI. It belongs to the **Moonshot** product line — LLM evaluation and red-teaming — and is a different product. Anyone searching the org for "AI Verify CI" and landing there will be misled.

### 8.4 Where a test run sits in the model lifecycle

Condensed cross-reference: the toolkit is a **post-training, pre-deployment gate** and a **periodic re-attestation** step.

```text
 train → validate → register (model registry) → [AI VERIFY GATE] → deploy → monitor
                                                        │
                                        fairness parity, robustness,
                                        explainability, process checklist
```

Two constraints shape the wiring. **The toolkit consumes artefacts, not endpoints** (Section 6.3), so your CI step must export the candidate model and a *fixed* test dataset, then upload — a registry exposing only a serving URL is not directly consumable without writing a model plugin. And **a run is minutes-to-hours, not seconds** (the 10-minute proxy timeout is a hint), so run the fast decisive tests (fairness parity, SHAP at small sample sizes) per-commit and heavy sweeps nightly or per release candidate — engineering judgement, labelled as such. For model-lifecycle context see `technology/openshift_ai_alternatives_guide.md`, `technology/on_prem_llm_deployment_guide.md`, `technology/enterprise_data_platforms_guide.md`, `technology/cloud_providers_guide.md` and the model-registry discussion under `technology/architecture/`.

### 8.5 Versioning and reproducibility of test runs

| Need | Status |
|---|---|
| Identify a specific run | **Yes** — `GET /api/test_runs/:id` |
| See which model and dataset were tested, and when | **Yes** — recorded in the report, with a "Report Completed" timestamp |
| Pin the engine version that produced the result | **FLAGGED** — not recorded in the report; annotate externally |
| Pin plugin versions | **FLAGGED** — not recorded; annotate externally |
| Re-run and get byte-identical results | **FLAGGED** — no determinism guarantee documented; the robustness boundary attack and SHAP sampling are randomised, and SHAP `local` mode explicitly explains "a random data point" |
| Store results as data | **Partially** — structured `TestResultData` keyed `gid:cid`, but no documented public on-disk schema |

The practical recipe, as engineering advice: **freeze three things alongside every report** — the `aiverify-test-engine` version, the plugin set with versions, and the exact test dataset by hash. The tool gives you the report; you supply the provenance around it.

## 9. Custom Extension

The extension model is the toolkit's strongest design feature: an algorithm is a Python package implementing one interface, developed with a CLI, validated by a command, packaged as a zip.

### 9.1 The four components you can add

| Component | Language | Generated by | What it does |
|---|---|---|---|
| **Algorithm** | Python | `generate-algorithm <cid>` | Computes a metric or produces a perturbed dataset |
| **Widget** | MDX (React) | `generate-widget <cid>` | Renders results; needs `meta.json` |
| **Input block** | MDX/React | `generate-inputblock <cid>` | Collects configuration before a run (e.g. the Fairness Tree) |
| **Template** | Report composition | `generate-plugin` scaffold | Pre-arranges widgets for a use case |

### 9.2 Writing an algorithm — the base class

An algorithm implements **`IAlgorithm`** from `aiverify_test_engine.interfaces`; the engine loads it, hands it a model and a dataset, and collects results. The repo's convention (verified by path) is `stock-plugins/<plugin-dir>/algorithms/<algo_name>/<aiverify_pkg_name>/algo.py`, with `tests/unit_tests/test_algo.py` and `tests/e2e/test_e2e.py` beside it.

Because the model arrives through `IModel`, your algorithm should call `predict()` / `predict_proba()` / `score()` rather than reaching into the raw model object — that is what makes it work across scikit-learn, XGBoost, TensorFlow and LightGBM without four code paths. And since the abstraction is `is_supported()`-gated, an algorithm needing `predict_proba()` should degrade gracefully (or fail clearly) when the model plugin cannot supply it.

**FLAGGED**: the full method-by-method signature of `IAlgorithm` — constructor arguments, return-object shape, required `meta.json` fields — is not published on a page I could read; the developer-docs path I probed (`/plugins/algorithm/create_algorithm/`) returned **404**. The authoritative sources are the interface module itself and the output of `aiverify-plugin generate-algorithm`. Do not hand-write the class from a blog post: generate it, read the generated file, then read `aiverify_test_engine/interfaces/<algorithm>.py`.

### 9.3 The CID, packaging and validation

Every algorithm has a **component id (CID)**, the join key across the system: the algorithm is generated with a CID; the widget declares which CID it wants (`export const cid = "..."`) and fetches results with `props.getResults(cid)`; the engine keys results and artefacts by `${widget.gid}:${cid}`, where the **GID** is the widget/plugin group id assigned at plugin level (`generate-plugin [gid]`); and the widget's `meta.json` defines its user-configurable `properties`. Choose the CID deliberately — it is effectively a public identifier in a report, and changing it later breaks every widget bound to it.

```bash
aiverify-plugin validate        # validate the plugin against the schema
aiverify-plugin test-widget     # widget + input-block tests
aiverify-plugin test-algorithm  # algorithm tests
aiverify-plugin test-all        # both, with default options
aiverify-plugin zip [pluginDir] # produce the distributable
```

The zip is the distribution unit handed to a toolkit administrator to load into the plugin store. `validate` is the gate — run it before `zip`, not after a failed load. `playground` gives a local render environment so widget iteration needs no full deployment.

### 9.4 Contributing upstream

`aiverify-developer-tools/CONTRIBUTING.md` documents the process: the **Developer Certificate of Origin** applies ("This project utilises the [Developer Certificate of Origin]" — sign off your commits); **fork and PR** against `main`, rebasing on `main` before pushing; **Conventional Commits** for messages (`feat:`, `fix:`, `chore:`, `docs:`, `style:`, `refactor:`, `test:`, `perf:`, `ci:`, `other:`); **tests are mandatory in the right place** — Python tests go in a `test-engine` `tests/` folder named `test_*.py`, and for plugin algorithms the documented path is `algorithms/*/tests/unit_test` (note the doc says `unit_test` while the on-disk stock convention observed is `unit_tests`), with Node tests in `__test__` named `*.test.js`/`.mjs`/`.ts`; **third-party plugins** must meet the same unit-test, linting, dependency and licence checks; **large features** should be discussed with maintainers *before* a PR; and the **merge gate** is GitHub Actions unit tests, linting and dependency/licence checks. The label taxonomy is real project hygiene (`bug`, `feature request`, `enhancement`, `documentation`, `question`; severity `high critical`/`low critical`; status `in progress`/`verified`; engagement labels including `good first issue`, `help wanted`, `needs review`, `needs testing`, `ready for development`) — though Section 10.1 explains why it does not translate into a fast review queue.

### 9.5 The pragmatic extension strategy for a bank

Labelled as reasoning, not repo fact, in priority order. **First, a model plugin for the firm's serving path.** If models only exist behind an inference endpoint, wrap that endpoint as an `IModel` implementation (`predict`/`predict_proba` against the API; `is_supported() = True` for your wrapper type) — this converts *every* stock algorithm into something that works against live models, a far smaller job than porting each algorithm (**FLAGGED** as a pattern I am proposing; no stock example of an endpoint-backed model plugin was found). **Second, a metric plugin for firm-specific policy** — e.g. a disparate-impact ratio if the firm's policy names it, as a thin `IAlgorithm` over rates the engine already surfaces. **Third, a report template** matching the firm's model-risk documentation standard, composed from stock widgets plus the firm's own text widgets. Item one is the leverage; two and three are polish.

### 10.3 Who runs it in production

**FLAGGED — cannot be verified independently.** The official toolkit page publishes three named testimonials: **X0PA, Dell and Singapore Airlines**. Treat "widely deployed" as a marketing claim and "adopted by the Foundation's corporate members, with three named public references" as the defensible statement. For a bank the implication is that **reference implementations are scarce** — the Veritas plugin's existence and the Foundation's financial-sector membership are the closest thing to sector validation, and they come from the toolchain rather than published case studies.

### 10.4 Fit assessment

**Right choice when:** your models are **tabular or image classification/regression**, serialized as pickles/Joblib/framework folders with a frozen test dataset; you need a **single artefact** combining quantitative technical tests with a structured process self-assessment (the 11-principle report is the differentiator — nothing else in open source pairs parity metrics with an 85-item checklist in one document); you are regulated where the AI Verify Testing Framework is recognised; **data cannot leave your perimeter** (self-hosted, no telemetry, no external registry required on the default pipeline); you need **financial-services fairness testing** in the Veritas sense; or you want **composability** of widgets, templates, algorithms and report layout.

**Wrong choice when:** your subject is an **LLM or generative system** (use the LLM product line or `technology/ai_llm/llm_evaluation_frameworks_guide.md`); your models are **only reachable as endpoints** (without a model plugin, nothing in stock can score them); you need a **hosted service or vendor SLA**; you need **real-time or per-request fairness checks** (this is batch, report-producing, not a runtime guardrail); you need **certification** (it produces evidence, not a certificate); or your regime mandates a **specific named metric** out of the box — you can add it as a plugin, but the toolkit will not emit it under that name.

One line: **if your AI estate is tabular/image supervised learning, your governance posture is Singapore-anchored or Singapore-adjacent, and you want composable self-hosted assurance evidence with a narrative report, this toolkit is a strong fit with no direct open-source substitute. If your estate is generative, endpoint-only, or needs real-time assurance, it is the wrong tool and no configuration changes that.**

### 10.5 Operating advice, and the adjacent product line

- **Fork and pin** the monorepo and the `aiverify-test-engine` version; record both with every report. Expect to fix issues yourself.
- **PostgreSQL from day one** if more than one person or instance will use it; **raise `APIGW_MAX_PART_SIZE_MB`** before trying an image dataset; **delete `data/database.db`** whenever plugin sources change (Section 5.5).
- **Prefer the default virtual-env pipeline** unless you specifically need sandboxing; then move to `docker_build` + `docker_run` with a private registry. **Split fast and slow tests** across per-commit and nightly CI (Section 8.4).
- **Read `common/schemas`** before authoring a plugin; it is the real specification.

One mention, as promised: **Project Moonshot** — the LLM evaluation and red-teaming tool in the same organisation — is a *different product*, covers the generative-AI case this toolkit does not, and is owned by the governance companion `technology/ai_verify_guide.md`. Do not mix the two in a single assurance story; they produce different evidence about different systems.

## 11. Cymbal Bank Worked Example

**Cymbal Bank** is the banking persona used across this repository's worked examples; the conventions here (a model owner, a model-risk function, a fixed validation dataset, an audit trail) follow the other Cymbal Bank walkthroughs under `technology/`.

> **All numeric results below are ILLUSTRATIVE** — plausible shapes for the metrics the toolkit actually emits, not measurements of any real model. Commands are shown in the documented shape of the tools' usage.

Cymbal Bank has a **loan default classifier** (binary classification, tabular) — the same class of model as the official sample report's credit-risk model. The model owner is preparing for the annual model-risk review and the responsible-AI attestation: produce a defensible **fairness + robustness + explainability** evidence pack, and complete the **process checklist** jointly with compliance. The model is a logistic regression inside a scikit-learn `Pipeline` (`StandardScaler` + encoder + `LogisticRegression`); it is exported as a pipeline folder and uploaded via **Upload Pipeline**, tested against a frozen 5,000-row holdout `cymbal_loan_test_holdout.csv` (comma-delimited) with ground-truth column `default`, sensitive attributes `gender` and `age_band`, and the bank's policy decision threshold fixed for the review.

### 11.1 Steps 1–2 — install, stand up, load

Install per Section 5.2 (`jq`/`zip`, Python 3.11, Node 22, `aiverify-test-engine[all]`, the sparse-checkout and shared-library build), then stand up the services. In a bank the realistic configuration is PostgreSQL and managed storage rather than SQLite and a local directory: point `APIGW_DB_URI` at a PostgreSQL URL (`postgresql+psycopg://aiverify:***@cymbal-pg.internal:5432/aiverify`), `APIGW_DATA_DIR` at `/srv/aiverify/data` (or an S3/MinIO URI), `APIGW_HOST_ADDRESS` at `0.0.0.0`, `APIGW_PORT` at `4000`, and raise `APIGW_MAX_PART_SIZE_MB` to `200`; on the worker set `APIGW_URL` to the internal gateway address, `VALKEY_HOST_ADDRESS`/`VALKEY_PORT` to the internal Valkey (`6379`), and keep `PIPELINE_BUILD=virtual_env` with `PIPELINE_EXECUTE=virtual_env_execute`.

Verify the gateway before touching the portal, whose documented failure mode is a fetch error when it is not running: `curl -s http://localhost:4000/docs/ >/dev/null && echo "apigw up"`.

In the portal, use the documented upload methods — this is where teams go wrong: **Upload Pipeline** (not "Upload AI Model"), because the Cymbal model is a `Pipeline`, not a bare estimator; then upload `cymbal_loan_test_holdout.csv` as the test dataset; then confirm the model loads (deserializer Pickle/Joblib; scikit-learn model plugin) and that `is_supported()` succeeds. If the model is not selectable, the deserializer or model plugin rejected it — check the serialization format before assuming a toolkit bug.

### 11.2 Step 3 — configure the test set

| Test | Plugin | Key inputs (illustrative) |
|---|---|---|
| Fairness (classification) | Fairness Metrics Toolbox for Classification | `Sensitive Feature Name`: `["gender","age_band"]`; ground-truth column `default`; fairness-tree selections recorded |
| Robustness | Robustness Toolbox | `Annotated ground truth path`: the holdout; `Name of column containing image file name`: `NA` (tabular mode) |
| Explainability (global) | SHAP Toolbox | `Type of explainability`: `global`; background data path: holdout; `Size of the background`: 25; `Size of the test dataset`: 25 |
| Explainability (local effects) | Partial Dependence Plot **(or ALE)** | No parameters; run against the holdout |
| Process | Process Checklist | 85 checklist items answered Yes / No / Not Applicable |

The **Fairness Tree** input block is completed before the fairness run. Cymbal's compliance function selects the parity metrics matching the harm it guards: for a lending decision a false negative (declining a creditworthy applicant) and a false positive (approving a default) are different harms, so `False Negative Rate Parity` and `False Positive Rate Parity` are selected, with `True Positive Rate Parity` and `Positive Predictive Value Parity`. Recording *why* those four and not all eight is part of the audit trail — exactly the step the toolkit refuses to automate. On the explainability row there is a deliberate choice: Cymbal's features are correlated (`income` with `loan_amount`, `age_band` with tenure), and under correlation **ALE is methodologically safer than PDP** (Section 4.5). The worked example notes PDP as the toolkit's documented default and ALE as the defensible selection for this feature set, and states that reasoning in the report commentary — making the choice explicit is itself part of the evidence.

### 11.3 Step 4 — run and read the raw outputs

Submit through the portal, which calls `POST /api/test_runs/run_test`, then `GET /api/test_runs` to poll and `GET /api/test_runs/:id` to inspect. The worker consumes the Valkey task, loads the pipeline and executes. **Illustrative results** — the shapes the algorithms emit, not measurements of a real Cymbal model.

*Fairness Metrics Toolbox for Classification, `gender`, fixed decision threshold:*

| Metric | Group A | Group B | Interpretation |
|---|---|---|---|
| False Negative Rate Parity | 0.18 | 0.31 | Group B creditworthy applicants denied at ~1.7x the rate of Group A |
| False Positive Rate Parity | 0.11 | 0.09 | Near parity on false alarms |
| True Positive Rate Parity | 0.82 | 0.69 | Recall disparity of ~13 points |
| Positive Predictive Value Parity | 0.74 | 0.71 | Precision broadly comparable |

*Robustness Toolbox (tabular):* Total Number of Samples **5,000**; Successful Perturbed Rate **62.40%**; accuracy original **0.79** vs perturbed **0.61**. *SHAP Toolbox — Global Explainability Chart, top features by absolute mean SHAP value:* 1 `loan_amount`, 2 `income`, 3 `age_band`, 4 `prior_default_count`, 5 `tenure_months`, 6 `home_ownership`, 7 `employment_length`, 8 `loan_purpose`. *Process checklist:* illustrative split of 85 checks — **46 Yes, 24 No, 15 Not Applicable**.

### 11.4 Step 5 — read the report, and annotate it

The portal assembles the run into the structure the sample report evidences: a summary with technical-test completion (5/5 run, 0 failed, 0 skipped) and the process-check split; an AI Model Information block recording model and dataset filenames and the completion timestamp; per-principle sections interleaving checklist results with "What it means" and "Recommendations(s)" prose; and technical-test pages for the fairness parity charts, the robustness original-vs-perturbed accuracy chart, and the SHAP global explainability chart. Print to PDF from the portal; the widget page-break rules (Section 7.3) are what make it paginate cleanly, so check for orphaned charts before circulating. The report does not record software versions (Section 7.5), so attach a cover note:

```text
aiverify-test-engine==2.2.1
plugin set: stock v2 (fairness-classification, robustness, shap, pdp, process-checklist)
dataset sha256: <recorded hash of cymbal_loan_test_holdout.csv>
model artefact sha256: <recorded hash of the exported pipeline>
```

### 11.5 Step 6 — the engineering work to close the findings

The findings are illustrative; the *shape* of the closure work is general, and every finding maps to engineering rather than more testing:

| Finding | Engineering work | Note |
|---|---|---|
| FNR parity 0.18 vs 0.31 on `gender` | Re-examine feature encoding and the fixed threshold; consider group-aware thresholding **with legal review** | Threshold changes are policy, not model tuning — involve compliance first |
| TPR parity gap of ~13 points | Investigate whether a proxy feature correlates with `gender`; consider removing or transforming it and re-validating | Removing a proxy costs accuracy; record the trade-off, do not hide it |
| Robustness: accuracy 0.79 → 0.61 | Establish whether the perturbation resembles realistic production input shift; if so, harden inputs and add upstream validation | The tabular robustness path is explicitly "not well-tested" — treat the number as a signal, not a verdict |
| SHAP: `age_band` ranks third | Confirm `age_band` is a policy-permitted feature for this decision and document the rationale | Explainability surfaces the feature; permissibility is a compliance call |
| 24 process checks "No" | Assign each an owner and a date | Cheapest findings to close and the most visible in the report summary |
| No engine/plugin versions in the report | Build the provenance wrapper around every run (hashes + versions) | One small script, permanent value |

The pattern to internalise: **the toolkit found the findings; it cannot close them.** Its job ends at evidence, and it says so in its own scope statement. Closing them is model, data and process engineering — which is precisely why the toolkit is a *gate* and not a *fixer*. For repeatability, keep the frozen dataset and the pinned engine version, re-run on model change, and diff the metric tables; and because there is no determinism guarantee and SHAP `local` mode is explicitly random (Section 8.5), compare distributions of runs rather than single numbers when a metric moves slightly.

## 12. The Summary

The AI Verify toolkit is a **self-hosted, Apache-2.0, plugin-extensible assurance harness for tabular and image supervised learning**. Its architecture is a Portal (Next.js) → API Gateway (FastAPI + database) → Valkey Stream queue → test-engine worker, with `aiverify-test-engine` supplying the interfaces (`IAlgorithm`, `IModel`, and the converter/data/pipeline/serializer/plugin set) every plugin is written against. Eleven stock plugins deliver fairness parity metrics for classification (eight rate-parity families) and regression (MAE/MSE/R2 parity), adversarial boundary-attack robustness, natural image corruption across four groups and five severity levels, SHAP/PDP/ALE explainability, and the finance-oriented Veritas toolkit with five report templates — alongside a process checklist that makes the produced report as much a governance artefact as a technical one.

The strengths are real: a genuinely extensible plugin model with a working CLI, a report renderer producing a narrative document rather than a data dump, permissive licensing, and an architecture that fits behind a firewall. The weaknesses are equally real and should be planned around rather than discovered later: maintenance is steady but slow, documentation drifts, the deployment scripts are explicitly "reference only", and there is no published sizing, no headless CLI, no model-endpoint wiring mode, and no determinism guarantee. The two decisions that most change total cost of ownership are whether your models can be exported as artefacts (if not, you are writing a model plugin) and whether PostgreSQL and object storage are provisioned from the start (if not, you will migrate).

Used for what it is designed for, the toolkit does something no other open-source project does as completely: it produces a single, composable, printable report carrying technical fairness, robustness and explainability results next to a structured process self-assessment — and it tells you plainly that it does not guarantee anything. That honesty is its best feature.

## What Could Not Be Verified

1. **The full `IAlgorithm` interface** — method signatures, constructor arguments, return-object shape, required `meta.json` fields. The developer-docs path `/plugins/algorithm/create_algorithm/` returned **404**; the authoritative sources are the interface module and the output of `aiverify-plugin generate-algorithm`, neither of which I read. Do not hand-write an algorithm from memory. The same gap covers **the plugin manifest schema in full** — a widget has a `meta.json` with user-configurable `properties` and a plugin is generated with a GID, but I did not read a complete manifest.
2. **`common/schemas`, the on-disk test-result format, and the API's result contract** — the directory is verified and required by apigw and the tooling, and widget prop types (`TestResultData`, `InputBlockData`) are documented, but no public JSON schema for the artefacts written to `APIGW_DATA_DIR` was found, and no standalone OpenAPI specification is published (the FastAPI `/docs/` endpoint served the live schema, which I did not extract).
3. **The `Veritastool` algorithm's full metric set** — documented inputs are listed (Section 4.6); the internal metrics behind "Veritas Generic/Fairness/Transparency Performance Tests" are not enumerated publicly. Separately, the exact role of **`aiverify.stock.decorators`** is inferred from its name and is low-confidence.
4. **Whether a 2.0-era sample report exists** — only the 2023 report is published, so the 2.0 page structure (and whether the canvas designer changed it) is unverified.
5. **Hardware sizing guidance and a documented air-gapped installation procedure** — neither found; Section 5.6 offers reasoning labelled as inference and lists the building blocks.
6. **A standalone CLI for production test runs** — none found; the `aiverify-plugin` CLI tests plugins, it does not run production tests. Likewise **no model-endpoint (gRPC/REST) wiring mode** is documented, so endpoint-only models require a custom model plugin and no stock example of one exists.
7. **Determinism of test runs** — no guarantee documented; the robustness boundary attack and SHAP sampling (SHAP `local` mode explains "a random data point") are randomised, so byte-identical re-runs are not promised. Relatedly, **engine and plugin versions are not recorded inside the report**, which records only model filename, dataset filename and timestamp — so its own outputs are not self-identifying.
8. **Independent production case studies** — the three published references are vendor-page testimonials; no independent, verifiable deployment account at scale was found.
9. **Whether the developer-tools `v2.x` branch tracks engine 2.2.1's plugin contract** — the README says the v2.x branch "should be used to create plugins for AI Verify Toolkit version v2.x", and the repo was last updated 2025-07-08, eleven months before this verification. Separately, **no stock time-series plugin was found**, and I cannot state definitively that none exists in a third-party repository outside the organisation.
