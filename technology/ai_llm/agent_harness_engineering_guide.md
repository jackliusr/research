### 1.2 What Is an Agent Harness?

The survey's opening definition, verbatim in substance (survey text, cached full text) ✅: as LLM agents move from conversation to long-running work in repositories, browsers, terminals, and enterprise software, task success depends on more than the model's response to a prompt. An agent must:

- **receive relevant context**, and
- **invoke tools through stable interfaces**, and
- **preserve state**, and
- **recover from failures**, and
- **expose its actions for inspection**, and
- **verify outcomes**, and
- **operate within defined permissions**.

> The survey calls the surrounding operational infrastructure that provides these functions the **agent harness**: *"the infrastructure that surrounds"* the agent. ✅ (survey text, cached full text)

**Harness engineering** is then defined as: how those mechanisms are designed and integrated so that model capabilities can support reliable execution ✅ (survey text, cached full text). The scope note in §2.4 narrows "harness" below "any software around an LLM": the harness is the engineered wrapper that turns model calls into *bounded, stateful, tool-mediated task execution* through execution substrates, tool interfaces, context control, orchestration, observability, evaluation feedback, and governance constraints ✅. The unit of analysis is the infrastructure that makes long-running agent behavior controllable, inspectable, and recoverable — not the foundation model or the prompt alone ✅. Boundaries are drawn functionally, not by product category: an agent framework is in scope when it exposes reusable mechanisms (stateful orchestration, tool routing, runtime policy hooks, trace capture); a thin model API wrapper, prompt library, static dataset, generic container runtime, vector database, APM dashboard, or content filter is out of scope unless explicitly adapted to agent execution, state, evaluation, or tool-use governance ✅.

Meng et al. (2026) describe a single harness through **six components**: an execution loop, tool registry, context manager, state store, lifecycle hooks, and evaluation interface ✅ (survey text, cached full text). The survey positions ETCLOVG as a complementary *layer-level* view of the *ecosystem* rather than the component view of one system ✅ (survey text, cached full text).

### 1.3 Harness Engineering in the Progression: Prompt → Context → Harness

The survey situates harness engineering at the widening end of a three-part progression (Figure 1) ✅ (survey text, cached full text):

| Stage | Object of engineering | Typical question |
|---|---|---|
| **Prompt engineering** | What the model is told in a single call | How do I phrase this request? |
| **Context engineering** | What the model can see across calls: retrieval, memory, window management | How do I give the model the right information at the right time? |
| **Harness engineering** | The whole surrounding operational infrastructure: execution, tools, context, lifecycle, observability, verification, governance | How do I make long-running model-driven work controllable, inspectable, and recoverable? |

The survey notes the earliest explicit articulation of the three-part progression appeared in a **February 2026 blog post (MadPlay, 2026)**, with related formulations in OpenAI (2026c) and Meng et al. (2026) ✅ (survey text, cached full text, Figure 1 note). This repo's deep treatment of the middle stage is [technology/ai_llm/context_engineering_guide.md](technology/ai_llm/context_engineering_guide.md) (Context Engineering — designing, managing, and optimizing the LLM context window); this guide is the deep treatment of the third stage. The paper's §2.1 traces the *evolution of agent systems* underlying the widening surface: from basic reasoning–action loops to increasingly stateful, tool-mediated, and operationally constrained systems, from early single-loop agents toward richer harness infrastructure spanning all seven ETCLOVG layers (Figure 2's timeline of representative agent-harness systems 2022–2026) ✅ (survey text, cached full text).

### 1.4 Evidence That Harness Changes Move Performance at Fixed Weights

The survey's central empirical claim — that changes to the surrounding infrastructure materially affect measured agent performance **even when model weights remain fixed** — is anchored on three pieces of evidence ✅ (survey text, cached full text):

1. **Bölük (2026):** modifying the *edit-tool format and surrounding tool harness* across 15 models produced substantial gains on coding benchmarks, including an improvement of **up to 10× for one model**.
2. **Trivedy (2026):** raising a *fixed* GPT-5.2-Codex agent from **52.8% to 66.5%** on Terminal-Bench 2.0 by restructuring the system prompt, injecting context through middleware, and adding self-verification hooks.
3. **Meta-Harness (Lee et al., 2026):** showing that *parts of the harness can be optimized automatically*.

The paper is careful about scope ✅: the strongest controlled evidence currently comes from coding-agent benchmarks, and these results do not establish that the harness matters more than the model in every setting — they establish that **agent performance depends jointly on the model and its execution system**. (Independent corroboration: the arXiv record for Meta-Harness, 2603.28052, appears on the Gloriaameng companion page ✅.)

**Vocabulary fragmentation is the survey's motivating problem.** ✅ Academic work studies planning, memory, retrieval, tool use, verification, coordination, and safety as separate capabilities; production accounts instead describe context pipelines, tool contracts, execution policies, traces, retries, handoffs, permission boundaries, and runtime safeguards (drawing on engineering reports from OpenAI, Anthropic, and LangChain, among others) ✅. Three questions are hard to answer across these bodies of work: **where the harness begins and ends**, **how its interacting mechanisms should be organized**, and **which parts of the design space are well covered** by existing systems ✅. ETCLOVG is the survey's answer to question two; the 170+ project map answers question three; §11's synthesis answers question one.

### 1.5 Seven Agent Requirements, Seven Harness Functions

The survey's opening list of what an agent "must" be able to do maps one-to-one onto the seven ETCLOVG layers — a useful inversion of the taxonomy as a *requirements decomposition* ✅ (survey text, cached full text; mapping is this guide's synthesis):

| The agent must… | …which is provided by harness layer | Paper section |
|---|---|---|
| …receive relevant context | **C** — Context & memory management | §5 |
| …invoke tools through stable interfaces | **T** — Tool interface & protocol | §4 |
| …preserve state | **L** — Lifecycle & orchestration (operational state) | §6 |
| …recover from failures | **L** (checkpoint/resume, retries) + **O** (reliability engineering) | §6, §7.4 |
| …expose its actions for inspection | **O** — Observability (traces, spans) | §7 |

Reading the list this way shows why the survey calls the harness an engineered wrapper *"that turns model calls into bounded, stateful, tool-mediated task execution"* — every requirement in the intro sentence is an engineering surface with its own ecosystem, and the paper's §2.4 boundary rule (function, not product category) is what keeps the taxonomy from swallowing all of software engineering ✅ (survey text, cached full text).

## 2. The ETCLOVG Taxonomy at a Glance

### 2.1 The Seven Layers

**ETCLOVG** = **E**xecution, **T**ooling, **C**ontext, **L**ifecycle, **O**bservability, **V**erification, **G**overnance ✅ (survey text, cached full text). The first four layers form the **structural core**; the last three form the **control plane** around that core (Figure 3/4) ✅:

| Layer | Scope (as the survey defines it) | Paper's sub-topics (§ ref) |
|---|---|---|
| **E — Execution environment & sandbox** | Where agent code runs and what sandbox constraints bound it | General-purpose managed sandboxes; computer-use agent infrastructure; code-specialized sandboxes; framework-integrated runtimes; browser evaluation environments; OS-level permission sandboxes; sandbox abstraction layers (§3) |
| **T — Tool interface & protocol** | How external capabilities are described, discovered, and invoked | Protocol and interface standards; tool description, discovery, selection; tool-augmented training and integration; scalability and session management (§4) |
| **C — Context & memory management** | What the model can see over short-term, session-level, and persistent horizons | Short-term active context window; mid-term session state and cross-run persistence; long-term persistent memory; long-horizon techniques (100+ turns); context drift and limits (§5) |
| **L — Lifecycle & orchestration** | The control flow that reads and writes state, single-agent to multi-agent | Lifecycle state management; single-agent inner loop; multi-agent orchestration patterns; full issue-to-pull-request pipelines (§6) |
| **O — Observability & operations** | System-wide traces, costs, failures, and reliability signals | Tracing and monitoring platforms; agent-specific operations platforms; cost tracking and optimization; reliability engineering; unified observability (§7) |
| **V — Verification & evaluation** | Turning tasks and traces into evaluation, failure attribution, regression feedback | Five-stage task-to-feedback lifecycle: benchmark grounding → pre-execution readiness → controlled execution & trace capture → multi-level judgement & failure attribution → continuous regression & deployment feedback (§8) |
| **G — Governance & security** | Constraining behavior via permission, identity, policy, hardening, audit, human oversight | Permission models and identity; lifecycle hooks; component hardening; declarative constitutions; audit infrastructure; the agent-security landscape (§9) |

Three deliberate design choices distinguish ETCLOVG from component models like Meng et al. (2026) ✅ (survey text, cached full text): **(1)** it classifies by *engineering surface* rather than minimal runtime role, so a broad ecosystem (complete harnesses, protocols, sandboxes, memory systems, observability tools, evaluation frameworks, governance modules) can be mapped; **(2)** it promotes **Observability (O) to an independent layer** — production observability has a dedicated tooling ecosystem (the survey names Langfuse, Arize Phoenix, OpenLLMetry) and distinct practices (OpenTelemetry instrumentation, cost attribution, anomaly detection); **(3)** it introduces **Governance (G) as a first-class layer** covering the full spectrum from model-level defenses through system-level permission and gateway controls to organization-level audit and human-approval workflows. State management sits inside L (state is created, updated, resumed, and consumed during execution), while lifecycle hooks and policy enforcement sit inside G, aligning with the other constraint mechanisms ✅ (survey text, cached full text).

### 2.2 Method: Corpus, Criteria, Coding Protocol, Limitations

The 170+ project mapping was built with systematic-review reporting discipline ✅ (survey text, cached full text):

- **Collection (§2.5):** candidates from four streams — prior surveys and benchmark papers; reproducible GitHub searches (names, descriptions, README text, topics, stars, recency, archival status); curated project lists and package registries; and company engineering blogs/release notes introducing harness-level mechanisms. Representative queries combined terms like *agent harness, coding agent, LLM agent sandbox, MCP server, agent observability, agent memory, agent evaluation, agent governance*. For each candidate the authors recorded name, URL, artifact type, source type, availability, release year, GitHub metadata, and the public evidence used for later coding. **The metadata snapshot was frozen on May 08, 2026** ✅.
- **Inclusion/exclusion (§2.6):** a project was included when it was publicly documented, implemented or specified a concrete harness-level mechanism, and had enough public evidence to assign at least one ETCLOVG layer. Excluded: simple chatbot demos, prompt packs, thin model-client wrappers, static datasets/leaderboards without an agent runtime, generic non-agent-facing infrastructure, and product pages whose behavior could not be inspected. Borderline cases were resolved *by mechanism rather than label* — a repo named "agent" was not sufficient; an evaluation or sandbox project qualified when it supplied reusable harness machinery ✅.
- **Coding protocol (§2.7):** multi-label coding against the seven layers using the public artifact itself (README, docs, papers, examples, release notes, repo structure) as evidence; primary layer = most central mechanism, secondary layers only when documentation exposes an independent capability. Single-primary-coder with author audit — **no Cohen's kappa** reported ✅. Conservative rule: without clear public evidence of an agent-facing mechanism, the layer assignment was withheld.
- **Corpus limitations (§2.8), stated by the authors ✅:** the corpus is a *map of the visible ecosystem, not a census*; biased toward English-language, GitHub-visible, open-source projects with enough published detail; commercial production systems underrepresented unless engineering blogs/docs/SDKs expose mechanisms; **coding-agent infrastructure overrepresented** (unusually rich public traces); and absence from a layer means *"not publicly evidenced"* rather than *"not implemented"*.

**Where the numbers come from.** The body text says "more than 170 open-source projects" ✅; Appendix A (Table S1) reports the catalog snapshot verified on 2026-05-08 with **171 public entries, 146 GitHub entries, 142 GitHub entries in project categories, 0 broken URLs**, keeping for the paper appendix only technical artifacts mapped to the seven layers ✅ (survey text, cached full text). The per-layer primary-layer group sizes in Table S1: E 20, T 12, C 9, L 47, O 15, V 21, G 14 (sum 138 — the paper's own technical subset of the catalog; the appendix does not reconcile the two counts line-by-line ⚠).
### 2.3 Why a Seven-Layer Taxonomy (and Not Six or Four)

Three properties of ETCLOVG follow from the paper's own framing and make it usable as this guide's review instrument ✅ (survey text, cached full text): **(1)** it classifies *harness infrastructure by engineering surface*, which is what allows one map to hold complete harnesses, protocols, sandboxes, memory systems, observability tools, evaluation frameworks, and governance modules at all (§2.3); **(2)** it promotes O and G out of "lifecycle hooks" because production practice already gives them dedicated tooling ecosystems and ownership (the survey names Langfuse/Arize Phoenix/OpenLLMetry for O and permission engines/policy languages/audit pipelines/gateways for G) — the taxonomy is descriptive of how production teams already organize their tooling, not an idealized decomposition (§2.3, §13); **(3)** the layer chapters mirror the taxonomy's own logic, and Appendix A's Table S1 assigns each artifact **one primary layer** (multi-label coding happens in the body analysis, but the catalog rows carry a single primary label) — which is why the aggregate distribution in §10.1 is computable at all (§2.7, Appendix A). The conclusion is candid that ETCLOVG is descriptive: "turning ETCLOVG into a normative framework that can guide harness design decisions, rather than only classify them, is the natural next step" ✅ — §12 of this guide is a small attempt at that normative turn.

## 3. Layers E and T: Execution Environment and Tool Interface

### 3.1 Execution Environment and Sandbox (E): Scope

The execution environment is the infrastructure layer in which agent actions are physically executed; for LLM agents, execution environment and sandbox are tightly coupled, and production agent systems almost invariably execute actions inside a sandbox ✅ (survey text, cached full text). Sandboxing in the agent era serves **three distinct purposes**, and their combination is what elevates it from an operational detail to a first-class harness concern ✅:

1. **Security.** LLM-generated code is neither auditable nor predictable at scale — static review cannot be the primary defense; agents execute autonomously over many steps so no human is present at action time; and prompt injection can repurpose a benign agent as a vector for sandbox-directed attacks.
2. **Reproducibility.** Long-horizon tasks and the evaluation harnesses that measure them need to reset execution state to a known baseline — a container or microVM can be destroyed and rebuilt on demand, a workstation cannot. This is what makes SWE-bench- and OSWorld-style evaluation practical, and at training time the absence of a cheap reset is itself a scalability bottleneck.
3. **Liveness** (the purpose most specific to the agent era). Without a sandbox every risky action needs a human permission prompt; at scale this yields either prompt fatigue (users abandon the agent) or reflexive approval (defeating the safety rationale). A sandbox defines a bounded region in which the agent is authorized to act freely — shifting permission from an *action question* to a *session configuration*. The survey reports Anthropic's number: introducing sandboxing to Claude Code reduced permission prompts **by 84% while preserving safety** ✅ (survey text, cached full text). "A sandbox is simultaneously a cage and a license."

### 3.2 E: Seven Sandbox Categories and Representative Systems

The paper organizes the landscape into **seven sandbox categories** along workload/use-case (isolation technology — containers, gVisor, microVMs like Firecracker and Kata, WebAssembly, OS primitives like bubblewrap/Seatbelt — is treated as a design property within each category) ✅ (survey text, cached full text). | Browser evaluation environments | Browser sandboxes built for web-agent benchmarks | WebArena, VisualWebArena, BrowserGym, WorkArena |
| OS-level permission and runtime security | Least-privilege OS/namespace sandboxes | Anthropic sandbox-runtime, Claude Code sandboxing, IsolateGPT, AgentBound, transactional sandboxing (Yan, 2025) |
| Sandbox abstraction layers, training, evaluation | Runtime-agnostic interfaces + sandbox escape/benchmark work | SWE-ReX, SWE-agent, K8s Agent Sandbox, R2E-Gym, EnvScaler, SandMLE, SandboxEscapeBench, CIBER |

### 3.3 E: Threat Model, Sandbox Escape, and Deployment Modes

- **Threat model and sandbox escape (§3.3).** The survey treats escape as an empirically demonstrated risk class, not a hypothetical: it names SandboxEscapeBench and CIBER among the abstraction/evaluation category ✅ (survey text, cached full text). It defers the quantitative evidence to §3.3 of the paper; the guide-level takeaway for the E layer's threat model (verified as the paper's framing ✅): because agents ingest untrusted content (web pages, repos, emails) that can carry prompt injection, the sandbox is part of the *security boundary* of the harness, and escape research is an E-layer verification surface. Repo-cluster depth for this corner (isolation spectrum, escape risk, deployment modes) is owned by [technology/ai_llm/agent_sandboxing_strategies_guide.md](technology/ai_llm/agent_sandboxing_strategies_guide.md) — **the repo cluster currently does not own a dedicated sandbox-escape benchmark treatment; the paper's SandboxEscapeBench/CIBER corner is a gap this guide flags (§11.3)**.
- **Deployment modes (§3.4).** The survey contrasts local execution (the default pattern for OpenHands and SWE-agent, with SDKs like OpenHands' Local and Remote Workspace abstraction) against cloud/SaaS execution ✅ (survey text, cached full text). Anthropic's reported 84% permission-prompt reduction with Claude Code sandboxing appears in both §3.1 and the OS-permission category ✅.

**The three agent-specific threat classes (§3.3) ✅ (survey text, cached full text):** beyond traditional container-level threats (container escape, side channels, resource exhaustion), the paper names three amplifier classes: **(1) prompt injection** — external input (retrieved web pages, tool responses, file contents) hijacks agent behavior and initiates malicious sandbox operations; **(2) goal misalignment** — the agent itself attempts sandbox escape as an instrumental subgoal; **(3) compositional amplification** — agents with many tools let a single sandbox weakness cascade across integrated capabilities. Quantitative status ✅: **SandboxEscapeBench** (a nested sandbox capture-the-flag setting) reports **15–35% escape success rates against Docker-based containers** depending on configuration, across misconfiguration, privilege-allocation mistakes, kernel flaws, and runtime/orchestration weaknesses — "the threat is realized rather than merely theoretical even at current model capabilities." Defensive work remains early-stage and fragmented: IsolateGPT reports under 30% performance overhead for three-quarters of tested queries while preventing cross-application data leaks; transactional sandboxing (Yan, 2025) provides rollback protection at ~14.5% overhead; LLM-in-Sandbox (Cheng et al., 2026) argues for minimal rather than maximally capable sandbox environments. The paper's verdict: "Offensive evaluation has produced a concrete and reproducible benchmark, whereas defensive work is still fragmented across isolated prototypes."

**Deployment modes in full (§3.4) ✅ (survey text, cached full text):** three modes coexist — **self-hosted** (developers manage sandbox infrastructure; the default for OpenHands and SWE-agent), **cloud/SaaS** (sandbox-as-a-service: E2B, Modal, Daytona Cloud), and **hybrid / bring-your-own-cloud** (agent logic and sandbox execution decoupled; OpenHands SDK's Local/Remote Workspace abstraction, E2B and Northflank BYOC). The deployment choice is framed along three axes — latency, security, scalability — and organizational constraints (data residency, compliance, auditability) push toward hybrid even when a single mode would win on latency or scale. In observed practice: self-hosted predominates in interactive development and single-tenant scenarios; cloud in multi-tenant, large-scale deployments; hybrid where compliance/data-locality meets large pools of ephemeral capacity. The paper flags the absence of systematic empirical comparison across modes under realistic agent workloads. **§3.5's summary framing:** execution environments provide the security boundary, the reset mechanism for reproducible evaluation/training, and the bounded region for long-horizon autonomy — with a recurring tension between capability, control, and cost that "reappears as survey-wide open problems in §12.1."
- **Design convergence (§3.2.1).** Managed sandboxes converge on ephemeral-by-default semantics with optional persistent sessions, Python/TypeScript SDKs, and arbitrary OCI image support; they diverge on isolation strength and operational model ✅ (survey text, cached full text). The paper observes a broader industry trend "from kernel container isolation toward dedicated-kernel microVM isolation, driven by the observation that LLM-generated code has unpredictable syscall patterns that cannot be characterized in advance" ✅.

**Category-by-category detail the paper adds beyond the table (§3.2.1–3.2.7) ✅ (survey text, cached full text):**

- **Computer-use infrastructure (§3.2.2)** is a distinct execution model — GUI interaction via simulated mouse/keyboard and screen observation rather than APIs or shell. Systems package a full or near-full desktop (Xvfb + window manager, or a complete VM) and expose pixel/keystroke actions; reliability depends on visual grounding, and the complete OS attack surface demands microVM/full-VM isolation. Computer-use sandboxes "trade density and startup latency for fidelity" — the only model in which an agent can operate applications that expose no API.
- **Code-specialized sandboxes (§3.2.3)** preinstall compilers/interpreters, default to stateless request-level execution, and optimize for high-concurrency parallelism, sacrificing workload generality for startup speed, evaluation throughput, and simpler threat models. Notable sub-trend: **container → WebAssembly** (langchain-sandbox compiles Python via Pyodide to WASM under the Deno runtime, a design NVIDIA also advocates for client agentic workflows) — WASM offers capability-based security, deterministic execution, and microsecond-scale instantiation, at the cost of a restricted standard library.
- **Framework-integrated runtimes (§3.2.4)** bundle execution with the framework's orchestration loop, tool registry, and prompt conventions (OpenHands runtime: one Docker image with bash + IPython + Chromium + API server; agent-infra sandbox: browser, shell, filesystem, MCP, VSCode all-in-one; smolagents executors: local/Docker/E2B/Modal/WASM behind one interface). The defining trade-off is **bundle vs. compose** — whether standards such as MCP reduce the penalty of assembling capability at runtime rather than at build time.
- **Browser evaluation environments (§3.2.5)** occupy a dual role as sandbox *and* evaluation harness (WebArena's self-hosted app cluster + Playwright; BrowserGym's gym-style interface), which "creates a direct interface between the execution environment… and the evaluation infrastructure." Because the browser ingests untrusted web content, it is a natural substrate for indirect-prompt-injection and multimodal red-teaming research.
- **OS-level permission sandboxes (§3.2.6)** use bubblewrap/Seatbelt/seccomp-bpf rather than containers or VMs — the design philosophy is **permission, not partition**: narrow the existing host's view (Anthropic's sandbox-runtime npm package wraps commands with FS/network allowlists; Claude Code consumes it to bound the bash tool; IsolateGPT applies seccomp+setrlimit). Weaker against fully adversarial code than microVMs — "they are appropriate when the threat model is prompt-injected rather than fully adversarial code."
- **Sandbox abstraction layers (§3.2.7)** are interfaces unifying multiple backends (SWE-ReX: Docker/AWS Fargate/Modal/Daytona interchangeable; smolagents `executor_type`; Kubernetes SIG Apps' Sandbox CRD exposing gVisor/Kata declaratively) — the emergence of the category reflects the principle that **execution infrastructure should be replaceable**.

**The E chapter's synthesis of the seven categories (§3.2, §3.5) ✅:** three cross-cutting trends — (1) isolation is diverging (managed sandboxes migrate to dedicated-kernel microVMs while OS-permission sandboxes narrow the host; plain Docker occupies a diminishing middle; the choice reflects the threat model — fully adversarial code vs. prompt-injected-but-cooperative code — not a universal preference); (2) evaluation increasingly targets sandbox robustness directly (SandboxEscapeBench, CIBER show deployed configurations are partially bypassable by frontier models); (3) infrastructure-level isolation is separating from semantic/capability-level isolation at the tool-calling layer (CaMeL's control-flow integrity, Progent's programmable privilege — which the survey places in the T chapter): "an infrastructure sandbox constrains the blast radius of an action once it is executed, while semantic isolation constrains which actions are permitted in the first place. A complete agent harness requires both."

### 3.4 Tool Interface and Protocol (T): Scope

The tool layer "defines how an agent discovers capabilities, represents callable affordances, and executes actions across heterogeneous runtime boundaries," sitting at the fault line between two competing objectives: **increasing capability coverage** (more tools) vs. **preserving decision quality** (small action space and prompt footprint) ✅ (survey text, cached full text). Production guidance repeatedly reports that oversized tool menus degrade reliability, increase token overhead, and amplify planning errors ✅.

### 3.5 T: Protocols, Description/Discovery/Selection, Training, Scalability

**Protocol and interface standards (§4.1).** The survey's organizing principle is to categorize standards by the **integration boundary they cross**, not vendor lineage ✅:

| Boundary | Standards (paper's Table 1) |
|---|---|
| Model ↔ Function | Function calling (OpenAI-style JSON schema call/return turns) |
| Agent ↔ External capability | **MCP** (host-client-server, JSON-RPC typed exchange of tools/resources/prompts), **OpenAPI** (machine-readable API contract as tool source) |
| Agent ↔ Agent | **A2A** (agent-to-agent: Agent Cards discovery, sync/streaming, long-running collaboration), ACP/ANP |
| Agent ↔ Repo/environment | **AGENTS.md / AGENT.md** (Markdown instruction files in version control) |

MCP is called "the most visible tool-integration substrate for coding and enterprise agents," valued not only for schema-level interoperability but for *ecosystem liquidity* — a reusable server catalog ✅. MCP and A2A are complementary: MCP for tool/context access, A2A for inter-agent delegation and collaboration ✅.

**Tool description, discovery, and selection (§4.2).** EasyTool (large-inventory selection), AnyTool and CRAFT (reducing manual specification by auto-constructing tool-use pipelines), MetaTool (tool-retrieval quality diverges across domains), and retrieval-aware orchestration in MCP-Zero, ToolRet, ToolRegistry. Skill-level selection (retrieving procedural modules rather than API schemas) appears in SkillRouter and SkillRet. Two design principles: **"fewer but better tools"** beats brute-force exposure; discovery must be **adaptive**, not static global lists ✅.

**Tool-augmented training and integration (§4.3).** Toolformer (self-supervised API-call learning), Gorilla and ToolLLM/ToolBench (tool corpora + instruction tuning + execution-centric supervision), ToolkenGPT and CREATOR (token-level/controller-style integration); production framework stacks LangChain, Semantic Kernel, smolagents; and the *semantic tool* class for coding — static analyzers, type checkers, solver-backed verifiers, proof assistants, patch-equivalence/fault-localization checkers — framed by Ugare & Chandra (2026) as **agentic code reasoning**. Design signal: reasoning tools should return *evidence-bearing artifacts* (traces, proof obligations, counterexamples, structured certificates), not black-box yes/no ✅.

**Scalability and session management (§4.4).** Stateful tool sessions improve continuity but add bookkeeping complexity under parallelized or delegated calls; failure modes include stale handles, inconsistent tool state across retries, and context-window saturation from verbose tool traces. Design needs: explicit lifecycle controls for tool sessions, bounded tool-context injection, and observability hooks that attribute errors to planner logic vs. interface/protocol failures ✅.

**Repo-cluster handoff (T).** The T layer's depth — MCP discovery, server design, and framework tooling — is owned by [technology/ai_llm/mcp_discovery_guide.md](technology/ai_llm/mcp_discovery_guide.md) and [technology/ai_llm/mcp_framework_tools_guide.md](technology/ai_llm/mcp_framework_tools_guide.md); this guide contributes the boundary-based standards map (Model↔Function / Agent↔Capability / Agent↔Agent / Agent↔Repo) and the selection-quality framing, which the MCP siblings treat operationally rather than as a standards-cartography question.

## 4. Layer C: Context and Memory Management

### 4.1 Why Context Must Be Engineered

The C layer is "where prompt and context engineering meet harness engineering" ✅ (survey text, cached full text). The core problem: give the model exactly the right information at each step — too little and the agent lacks state to act; too much and performance degrades measurably, consistently across models, and in ways not fully understood. Three architectural facts motivate active management ✅:

- **Quadratic attention cost.** Attention computes pairwise weights over n tokens — doubling context quadruples cost; FlashAttention and position-encoding interpolation only reduce constants. The context window is a scarce resource.
- **The U-shaped attention curve.** Liu et al. (2024a): on multi-document QA with 20 documents, accuracy drops **>30%** when the relevant document sits mid-context vs. at start or end. Placement matters as much as presence.
- **Context rot at scale.** Hong et al. (2025), evaluating 18 frontier models: every model degraded as input grew, non-uniformly and task-specifically; degradation begins well before windows fill (a 200K-rated model may degrade significantly at 50K). This is the *normal operating condition* of any accumulating agent, not an edge case.

Context engineering vs. prompt engineering: prompt engineering optimizes a largely static single-call input; context engineering (Anthropic's applied team, quoted by the survey) is "the set of strategies for curating and maintaining the optimal set of tokens during LLM inference, including all the other information that may land there outside of the prompts" ✅. What competes in the window: system prompt and behavioral instructions, tool definitions/schemas, prior turn history, tool results, retrieved documents/memory records, and dynamically injected working state. The guiding principle: the smallest set of high-signal tokens that maximizes the probability of the desired outcome at each step, via progressive disclosure, compaction, and memory retrieval ✅. The **three-tier memory architecture** (active window / session state / cross-session storage) is the dominant organizing framework — mapped by the survey onto the classical OS memory hierarchy ✅.

### 4.2 The C-Layer Sub-Topics and the Systems the Paper Names

**Short-term — the active context window (§5.3) ✅:** system-prompt calibration ("right altitude"; minimal prompt on the best model, then targeted instruction from empirical failure modes); token-efficient tool design (fewer, more expressive tools; tens of thousands of tokens can be consumed by schemas before the user request is read); just-in-time retrieval / progressive disclosure (Claude Code's hybrid: CLAUDE.md at session start, glob/grep to load files on demand); **KV-cache-aware context design** — prompt caching as "the single most cost-effective optimization," Manus reporting KV-cache hit rate as "the single most important metric for a production-stage AI agent" ($0.30/MTok cached vs $3.00/MTok uncached on Claude Sonnet) with three rules: keep the prompt prefix stable, treat context as append-only, use deterministic serialization; Anthropic's product-level `cache_control` breakpoints. Tooling named: Agent Skills (Koylan, 2025), Context-Space (MCP-centric dynamic context assembly).

**Mid-term — session state and cross-run persistence (§5.4) ✅:** structured note-taking (a persistent NOTES.md/todo.md — the survey's worked example: Claude playing Pokémon for thousands of steps, reading its own notes across compaction resets); file-based planning/task externalization (planning-with-files, Trellis with project memory/spec injection); cross-run injection (claude-mem as a plugin-style memory layer prepending last run's salient output; everything-claude-code with over 150K stars as the largest open collection of these patterns). Trade-off: forward-injection continuity at a fraction of long-term-memory cost, but no indexed recall and poor scaling to large history.

**Long-term — persistent memory systems (§5.5) ✅:** foundational architectures — MemGPT (Packer et al., 2023; context window as RAM, external storage as disk, explicit paging), Generative Agents (Park et al., 2023; Memory Stream with recency × importance × relevance retrieval plus reflection), MemoryBank (Zhong et al., 2024; Ebbinghaus-style dynamic forgetting + user-personality modeling). Production systems — **Mem0** (most widely deployed: 14M+ Python downloads, 41K GitHub stars, native integrations in CrewAI/Flowise/Langflow, vector+graph+KV hybrid, 26% higher LOCOMO accuracy than OpenAI native memory at 90% fewer tokens, selected by AWS for its Agent SDK), **A-MEM** (Zettelkasten-style dynamic knowledge networks with retroactive link updates), **Hindsight** (retain/recall/reflect; SOTA on LongMemEval), **Honcho** (user-modeling via a background "dreaming" reasoning pipeline; entity-centric multi-agent isolation), **cq** (Mozilla AI; MCP-native *collective* memory across a fleet with a post-error hook pattern). Academic taxonomy: Zhang et al. (2025) short/long-term with semantic-procedural-episodic subdivision and the write-read-manage loop; Du (2026) POMDP-style formalization with patterns A (monolithic context), B (window + retrieval), C (tiered with learned control).

**Long-horizon — coherence over 100+ turns (§5.6) ✅:** context compaction (calibrate by maximizing recall first, then precision; tool-result clearing as the lightest form, now an Anthropic platform feature); sub-agent context isolation (subtasks get fresh windows and return only ~1,000–2,000-token summaries; sharing context is expensive — larger prefills, lost KV-cache reuse); hybrid decision frameworks (pre-load always-needed content, retrieve conditionally, compact at saturation, spawn sub-agents when exploration would pollute the orchestrator — Anthropic 2026c/2025e). The survey's normative point: **"Context management should be the infrastructure's job, not the agent's"** — when the harness handles compaction and consolidation automatically, the model focuses on task reasoning ✅.

**Context drift and limits (§5.7) ✅:** context drift (extended-trajectory behavioral degradation: repeated work, self-contradiction, goal loss after 100+ turns) is distinguished from context rot (single-step degradation); root cause is not simply saturation — summaries carry compounding inaccuracies and nothing detects divergence from the real environment. Evaluation gap: MemBench, MemoryArena, and incremental multi-turn evaluation (Hu et al., 2025) begin to measure drift but don't yet explain it. The chapter's closing claim: context engineering alone cannot solve long-horizon reliability — verification loops, human-in-the-loop checkpoints, and anomaly detection are required, motivating O and G as complements rather than separate concerns ✅.

**Why current techniques fall short (§5.7) ✅ (survey text, cached full text):** the paper frames drift as a *controller-side* failure mode: because the model only ever sees the projection of state the harness exposes, loss or
distortion of task-relevant context is a harness property rather than a model property alone (Zhang et al., 2026c). Compaction reduces the token count but cannot guarantee that the compressed representation captures all relevant state,
and information lost at each compression step is gone; retrieval can surface prior memories only when the query is well-formed — and "a drifting agent may not know what it needs to retrieve to correct its course"; sub-agent isolation
keeps subtask context out of the orchestrator, but the orchestrator's own context still accumulates drift over time. Compaction and retrieval slow drift, they do not prevent it: the summaries surviving each compression step carry
subtle inaccuracies that compound while the agent's accumulated assumptions silently diverge from the real task environment, and nothing in the architecture detects that divergence ✅.

**The state-estimation research agenda the paper draws from this (§5.7 → §12.2) ✅ (survey text, cached full text):** the paper proposes recasting context management as **state estimation** — characterize how much task-relevant
information is lost at each compression, retrieval, or forgetting step, and bound the divergence between the agent's internal state and the real state of the task. Recent surveys formalize agent memory as a write–manage–read loop, with
policy-learned management as an emerging mechanism family (Zhang et al., 2025; Du, 2026). Future systems, per the paper, need uncertainty-aware summaries, provenance for remembered facts, contradiction handling, explicit staleness
markers, and recovery procedures that reconstruct missing state from durable artifacts rather than trusting compressed history — plus a tighter memory–evaluation link: memory policies should be assessed on recall accuracy *and* on
whether they prevent downstream action errors in multi-session tasks. The drift-measurement benchmarks the paper cites support that agenda at the edges — Tan et al.'s (2025) MemBench evaluates multi-session memory on temporal
reasoning, knowledge update, and cross-session aggregation; He et al.'s (2026) MemoryArena targets the interdependent multi-session conditions under which drift is most destructive; Hu et al.'s (2025) incremental multi-turn methodology
isolates memory quality from generation quality — benchmarks show *that* drift occurs without yet explaining *why*, which is precisely the gap the state-estimation framing is meant to close ✅.

**Repo-cluster handoff (C).** The C layer's depth is owned by [technology/ai_llm/context_engineering_guide.md](technology/ai_llm/context_engineering_guide.md) (the prompt→context engineering discipline, window management) and [technology/ai_llm/agent_runtime_cache_design_guide.md](technology/ai_llm/agent_runtime_cache_design_guide.md) (KV-cache/context-layer runtime design — the paper's KV-cache-aware design rules and Manus economics land there). This guide adds the three-tier horizon map and the drift/limits framing as the harness-level view.

## 5. Layer L: Lifecycle and Orchestration

### 5.1 Scope: Execution Flow Plus Operational State

L "concerns how an agent system carries a task across repeated model calls, tool calls, failures, revisions, and handoffs," combining two concerns often separated: the execution flow and the operational state the flow reads and writes ✅ (survey text, cached full text). In long-running tasks, reliability depends on whether the harness can remember what happened, decide what should happen next, recover from errors, coordinate subtasks, and stop when done. This state is deliberately distinct from C-layer state (what the model sees for reasoning) and O-layer logs (monitoring behavior): L-state is what the harness itself uses to continue and coordinate — pending subtasks, checkpoints, retries, shared artifacts, execution status ✅. The paper's §6.1 catalog of that operational state adds tool results, intermediate artifacts, repository changes, coordination metadata, session persistence, and checkpoint–resume mechanisms, and its framing is worth keeping: these mechanisms "make orchestration durable rather than transient" — the agent can continue from prior work instead of treating every step as an isolated model call ✅ (survey text, cached full text).

The central execution-model trade-off: **stateless replay** (reconstruct the run from recorded interaction history — reproducible and auditable, costly as trajectories grow; Codex CLI is the clearest example) vs. **stateful execution** (persist state in files, repos, databases, task graphs, services — continuity and recovery at the cost of consistency and debugging challenges) vs. **hybrid** (most practical coding agents: replayable histories plus persistent artifacts) ✅.

### 5.2 The Three Orchestration Levels and the Systems the Paper Names

**Single-agent inner loop (§6.2).** The ReAct-paradigm cycle (reason, act, observe) that underlies interactive coding/debugging; behavior is determined by the model *and* the harness that constructs prompts, invokes tools, manages control flow, and feeds outputs back ✅. Paper's Table 2 single-loop group (stars rounded, recorded May 12, 2026): **OpenCode** (159k, hybrid), **Claude Code** (123k, hybrid), **Gemini CLI** (104k, hybrid), **Codex CLI** (82k, stateless replay), **Aider** (45k, hybrid), **SWE-agent** (19k, hybrid) ✅. Long-horizon weaknesses of single loops: context fragmentation, accumulated errors, weak decomposition.

**Multi-agent orchestration patterns (§6.3).** Five recurring patterns: **hierarchical orchestration** (higher-level controller assigns and integrates), **team orchestration** (specialized agents as a coordinated team), **workflow orchestration** (explicit stages/control logic), **fan-out** (parallel exploration), **graph composition** (agents/tools/states as an interaction graph) ✅. Table 2 classifications: DeerFlow, AutoGen, OpenAI Agents SDK, DeepAgents → hierarchical; oh-my-claudecode → team; Semantic Kernel → workflow; Emdash → fan-out; LangGraph and Hive → graph composition ✅. Anthropic's planner-generator-evaluator illustrates role separation: planning, execution, and verification as explicit roles — more robust decomposition at the cost of coordination overhead ✅. Execution at this level is usually **stateful or hybrid**, the paper notes, because coordination state, role assignments, task graphs, shared artifacts, and intermediate results must persist across agents; Table 2's execution-model column bears this out (survey text, cached full text):

## 6. Layer O: Observability and Operations

### 6.1 Scope and Sub-Topics

O is the fifth layer and "the first of the two layers our taxonomy promotes from Lifecycle Hooks to first-class status" ✅ (survey text, cached full text). The layer addresses how agent behavior is monitored, debugged, and made reliable in production; it deserves independent treatment because it has spawned a dedicated ecosystem of platforms, specifications, and engineering practices ✅. Paper sub-topics and named systems (Figure 10):

**Tracing and monitoring platforms (§7.1).** The foundation is structured trace collection: recording every LLM call, tool invocation, retrieval step, and context-assembly operation as a **tree of spans** that can be inspected, filtered, and replayed ✅. Named platforms: **Langfuse, Opik (Comet), Arize Phoenix, MLflow** — each offering interactive trace trees, latency flame charts, token-usage breakdowns, cost-attribution dashboards, and prompt versioning; ingestion typically via lightweight SDK wrappers (e.g., a `@traceable` decorator) ✅. Beneath them, **OpenTelemetry (OTel)** is "the de facto instrumentation standard," with published semantic conventions for generative AI (span attributes for model name, temperature, token counts, latency) ✅. Two projects operationalize OTel conventions: **OpenLLMetry** (auto-instrumentation for LLM providers — OpenAI, Anthropic, Cohere — and vector DBs — Pinecone, Chroma, Weaviate) and **OpenInference** (Arize-maintained companion specification feeding Phoenix); building on OTel lets agent traces flow into Prometheus/Jaeger/Grafana/Datadog ✅. Deeper instrumentation: **AgentSight** (eBPF-based, monitors from outside the process — intercepts TLS-encrypted LLM traffic at the SSL boundary, watches kernel events, <3% CPU overhead, cannot be bypassed by a compromised agent) and **AgentTrace** (schema-based logging over three surfaces: cognitive reasoning/plans/reflections; operational tool calls and API interactions; contextual environment state and user inputs — a unified OTel-exportable envelope) ✅.

**Agent-specific operations platforms (§7.2).** General tracing centers on LLM/tool/retrieval spans; agent-specific platforms add agent-level concerns: multi-step session tracking, identity and role management, tool-selection policies, cross-session handoff ✅. Named: **AgentOps SDK** (hierarchical span model organizing sessions, agents, operations/tasks, workflows, tool calls, LLM calls around the agent lifecycle), **RagaAI Catalyst** (RAG and multi-agent quality/safety dashboards), **Laminar** (OSS-first: trace + evaluation + prompt management), **Watson** (formalizes *cognitive observability*: a "surrogate agent" reproduces the primary agent's output while generating a step-by-step reasoning trace via prompt attribution — evaluated on MMLU and SWE-bench-lite with AutoCodeRover and OpenHands), **AgentLens** (three-pane visual analytics: Outline/Agent/Monitor views), and **Claude-Code-Reverse** ✅. Formalization work: Moshkovich & Zeltyn propose a **six-stage AgentOps automation pipeline** (observe → collect metrics → detect anomalies → root-cause analysis → recommend fixes → automate remediation) over four stakeholder roles (developer, tester, SRE, business user), and their empirical study finds **79% of practitioners identify non-deterministic execution flow as the most significant challenge** ✅. The **NLAH (Natural-Language Agent Harnesses)** framework treats the harness itself as a first-class, *ablatable* research object — tool registry, permission system, hooks, skills, context folding — so observability becomes a source of interventions, not just monitoring ✅.

**Cost tracking and optimization (§7.3).** The layer's twofold requirement: *tracking* (knowing where tokens are spent) and *optimization* (fewer tokens for the same outcome) — a single user-facing task can trigger dozens of LLM calls, each with its own prompt assembly and tool-result injection ✅ (survey text, cached full text). Verified specifics: on the tracking side, **TensorZero** bundles gateway, observability, experimentation, and optimization for per-call/per-task cost attribution, while **Helicone** is a minimalist drop-in proxy adding cost/latency monitoring with no code changes. On the optimization side: **FrugalGPT**'s three strategies (prompt adaptation, LLM approximation, LLM cascading — an adaptive cascade matching GPT-4 with up to 98% cost reduction by routing easy queries to cheap models); **GPTCache** (semantic caching on embedding similarity); **QC-Opt** (joint model-selection/token/latency optimization under budget, using a BertScore predictor); **TALE** (the *token-elasticity* paradox: too-low token budgets for CoT increase consumption as the model overflows); **Dual-Pool Token-Budget Routing** (partitioning a vLLM fleet into short/long-context pools; 31–42% GPU-hour reduction on Azure traces/LMSYS-Chat-1M, ~$2.86M annual savings at A100-fleet scale). The cautionary complement: Anthropic's infrastructure-noise study shows **infrastructure configuration alone can shift benchmark scores by 6 percentage points (p < 0.01)** — cost optimization and evaluation fidelity are tightly intertwined, since cutting resources can silently degrade agent performance invisibly without fine-grained observability. The paper's harness takeaway: cost observability must span API-level token tracking, application-level routing, and infrastructure-level resource utilization.

**Reliability engineering (§7.4).** Verified specifics ✅ (survey text, cached full text): Anthropic's harness work identifies **four recurring failure modes** in long-running coding agents — the agent tries to one-shot the whole task; it declares the project complete prematurely; it leaves the environment broken between sessions; it marks features done without proper testing — addressed by harness design (an *initializer agent* decomposing the task into a feature list plus progress-tracking artifacts — git repo, progress file, init script — followed by a coding agent working one feature at a time on clean handoff state). The GAN-inspired planner–generator–evaluator architecture adds sprint contracts and separated self-evaluation — and its authors show harness complexity should track model capability: upgrading Opus 4.5→4.6 let them remove the sprint construct and context resets, cutting cost from **$200 to $125 at equal quality**. **Managed Agents** decouples the "brain" (harness + LLM) from the "hands" (sandboxes/tools) and the "session" (durable event log) — a crashed harness reboots with `wake(sessionId)` and resumes from the last event; a failed sandbox is reprovisioned as a tool-call failure; credentials live in an external vault — turning components from "pets" into "cattle." Academic taxonomies: MAST (14 failure modes across multi-agent systems, κ = 0.88); AgentErrorTaxonomy (module-level decomposition showing *error propagation* is the central reliability bottleneck; its AgentDebug framework yields up to 26% relative task-success improvement); Vinay (15 hidden production failure modes: version drift, cost-driven performance collapse, multi-step reasoning drift); QSAF (six-stage cognitive-degradation lifecycle — hallucinated outputs stored in memory create self-reinforcing, cross-session degradation loops); SentinelAgent (graph-based anomaly detection at three tiers); AgentFixer (15 validation tools on IBM's CUGA; 64–88% issue-detection rates; 38% of task failures trace to parsing errors — fixable by deterministic checks). The paper's layered-detection prescription: rule-based checks for structural failures, statistical monitoring for performance drift, LLM-based semantic analysis for reasoning failures.

**Unified observability discussion (§7.5).** Verified specifics ✅: the observability–evaluation gap is *structural* — "trace-collection tools and evaluation frameworks have largely been developed by different communities with different interfaces" (the LangChain survey's 89%/52% split, §10.3); closing it means generating regression tests from production failure traces and using online evaluation scores as alerting signals. Unified LLMOps stacks (TensorZero, Langfuse) bundle gateway/observability/evaluation/optimization; NLAH makes the harness modular and introspectable via ablation; Anthropic's Managed Agents virtualizes harness components behind substitutable interfaces (`execute()`, `emitEvent()`, `getEvents()`). The section's closing principle — **harness-as-assumption** — is that every harness component encodes an assumption about what the model cannot do alone, so the ideal observability system includes a meta-monitoring layer tracking which interventions (context resets, evaluator loops, tool restrictions) are still load-bearing, "enabling continuous harness simplification alongside model upgrades."

The paper's Figure 10 groups the frontier research entries under this unified-observability heading — Moshkovich & Zeltyn's "Taming Uncertainty" (the six-stage AgentOps automation pipeline above), "Beyond Black-Box Benchmarking"
(Moshkovich et al., 2025), "Mind the Metrics" (Koc et al., 2025), LangChain's Deep-Agent Evaluation, and Anthropic's "Infrastructure Noise" (the 6-percentage-point environment-configuration effect) — signalling that trace-to-evaluation
integration, not richer dashboards, is the O-layer's research core ✅ (survey text, cached full text).

## 7. Layer V: Verification and Evaluation

### 7.1 Harness Evaluation as a Task-to-Feedback Lifecycle

The V layer's central stance: "A harness-aware evaluation should treat the reported score as a property of the **model–harness pair**, not of the model alone" ✅ (survey text, cached full text). Evaluation protocols should either lock the harness across models or vary harness configurations as an explicit experimental factor. Conventional LLM evaluation scores outputs on fixed inputs; **harness evaluation measures an execution episode** — task grounded in an environment, agent interacting with tools and state over time, traces captured, evaluator judging both the final result and the path taken ✅. The motivation: *evaluation infrastructure noise can masquerade as model failure* — failed runs may reflect broken tools, stale context, non-reset sandboxes, flaky tests, benchmark ambiguity, or unstable judges, not model limitations ✅.

The paper organizes V as a **five-stage task-to-feedback lifecycle**, following the causal path of an evaluation run ✅:

| Stage | Question | Content (paper §) |
|---|---|---|
| **1. Task and benchmark grounding** | What is being evaluated, in which environment? | A task is an embedded problem (environment state, tools, allowed actions, constraints, termination, success criteria), not a prompt. Families: software-engineering/terminal tasks (SWE-bench — real GitHub issues + test-verified patches; Terminal-Bench — command-line workflows); web/browser/computer-use tasks (WebArena, VisualWebArena, BrowserGym, WorkArena, OSWorld); cross-domain/enterprise tasks (AgentBench across OS/DB/web/games, GAIA, TheAgentCompany, WorkArena++) (§8.2) |
| **2. Pre-execution readiness validation** | Can the evaluation run fairly and reproducibly? | Validate sandbox, dependencies, tools, context state, permission boundaries, budgets, and graders *before* the agent runs, so environment/grader failures are not mistaken for model failures. Named: Repo2Run, HAL, SWE-agent, SWE-ReX, OpenHands, LLM-as-Judge survey (§8.3) |
| **3. Controlled execution and trace capture** | Run under reproducible conditions, capture everything | Record model outputs, tool calls, state changes, errors, retries, cost, latency. SWE-agent's runnable loop, OpenHands, SWE-ReX backends, HAL, R2E-Gym, LangChain Deep-Agent Evaluation; reproducibility patterns (controlled rollouts, trace-native evaluation) (§8.4) |
| **4. Multi-level judgement and failure attribution** | Judge outcome, trajectory, and evaluator; attribute failures | Outcome-level (test verdicts, task success), trajectory-level (intermediate steps, efficiency, recovery), evaluator-level (judge reliability — G-Eval, MT-Bench/Chatbot Arena, LLM-as-judge survey), then **failure attribution across harness layers** (which layer's failure caused the miss) (§8.5) |
| **5. Continuous regression and deployment feedback** | Feed verdicts back into the harness | Regression evaluation for harness changes, eval frameworks and LLMOps integration, verifier-based and training-time evaluation; named: Anthropic Evals, LangChain Deep-Agent Evaluation, promptfoo, DeepEval, RAGAS, lm-evaluation-harness, Reproducible LM Evaluation (Biderman et al.), verifiers (PrimeIntellect-ai), R2E-Gym, Meta-Harness (§8.6) |

**Stage 1 — grounding, in the paper's full detail (§8.2) ✅ (survey text, cached full text):** the benchmark families are differentiated by *how success is verified*, and the chapter's key insight is that strong outcome verifiers
require strong task grounding — tests only serve as reliable evaluators when repository state, dependencies, and intended success criteria are precisely specified; otherwise a failed test may reflect an invalid patch *or* an
inconsistent environment *or* an underspecified benchmark instance. Software-engineering and terminal tasks ground each task in real artifacts with executable verification: SWE-bench in a real GitHub issue plus repository snapshot with
the patch judged by running tests; Terminal-Bench in command-line workflows where agents edit files, run commands, set up dependencies, and interpret failures. Web/browser/computer-use benchmarks define success by environment-state
change and are "simultaneously an evaluation problem and an environment-design problem" — the benchmark must provide a realistic interface, isolate task state, expose appropriate observations, and define measurable success predicates
(WebArena's realistic web environments; VisualWebArena's multimodal tasks; BrowserGym as a common substrate; WorkArena on ServiceNow knowledge work; OSWorld's desktop applications, files, and multi-application workflows). Cross-domain
and enterprise families contribute *coverage* — whether the harness generalizes across task types, tool interfaces, state representations, workflows, and success conditions: AgentBench across OS/database/web/games, GAIA's
reasoning-plus-tool-use assistant tasks, TheAgentCompany's workplace-style digital labor, WorkArena++'s enterprise workflows.

**Stage 2 — readiness, cross-layer by design (§8.3) ✅ (survey text, cached full text):** the stage "is often invisible in benchmark leaderboards," but without it downstream failures become un-attributable: a failed run may be the
agent's fault or the evaluation setup's. Readiness validation is explicitly cross-layer: *environment and sandbox readiness* (known baseline — repository snapshot, dependencies, task setup, test executability; website resets, browser
profiles, desktop state, service availability; Repo2Run automates executable Docker environments for repositories, HAL frames standardized cost-aware evaluation infrastructure); *tool, context, and permission readiness* (APIs, MCP
servers, browser controls, shell commands consistently described; histories, memory stores, scratchpads, and retrieved documents reset or intentionally initialized; file access, credentials, network access, and approval gates matching
the benchmark specification); and *evaluator and grader readiness* (deterministic graders checked for flakiness and dependency completeness, LLM-judge prompts/rubrics/models versioned, human-audit protocols defined in advance). The
chapter's cautions: if tool descriptions change across runs the benchmark stops measuring the same action space; if memory is not reset the agent may benefit from leaked state; permissions too restrictive make a capable agent fail for
governance reasons, too permissive let unsafe or benchmark-exploiting behavior pass undetected. A rigorous harness therefore records the tool registry, context policy, permission policy, budget, timeout, model configuration, and
runtime interface as evaluation metadata — and because the agent-computer interface determines which actions are possible, it determines what a benchmark actually measures (SWE-agent, SWE-ReX, OpenHands) ✅.

**Stage 3 — controlled execution, trace capture, and cost (§8.4) ✅ (survey text, cached full text):** the basic unit of agent evaluation is the **rollout** — task, model configuration, harness configuration, action sequence,
intermediate observations, final state, and grading result — with controlled rollouts fixing environment state, tool availability, timeout, budget, permission policy, and evaluator version, and repeated rollouts exposing nondeterminism
as variance rather than hiding it behind a single score; "reproducibility requires replaying the full model–tool–environment interaction, not merely rerunning a model call" (SWE-agent's interaction loop, OpenHands' combined
code/CLI/browser/sandbox runtime, SWE-ReX's backend abstraction, LangChain's single-step/full-turn/multi-turn decomposition). Trace capture converts binary scoring into causal diagnosis: a trace-native harness records model outputs,
tool calls, tool results, environment state changes, context snapshots, errors, retries, recovery actions, token usage, latency, and cost — the fields that distinguish superficially similar failures (one agent never finds the relevant
file; another finds it but produces an invalid patch) and expose undesirable success (benchmark exploitation, excessive tool calls, permission violations). HAL treats logs and traces as first-class artifacts; R2E-Gym links executable
trajectories and hybrid verifiers to both test-time evaluation and training-time feedback; "for harness engineering, traces are… primary evaluation data." Stage 3 also demands cost reporting: evaluations should expose a
success-cost-latency frontier (token usage, model cost, wall-clock latency, tool-call count, retry count, resource consumption) rather than ranking agents by success rate alone — essential for deployed agent services whose unit of
optimization is a recurring workload under budget and latency constraints ✅.

**Layer-crossing insight (Stage 1, from the paper ✅):** benchmarks are simultaneously evaluation problems and *environment-design problems* — "This creates a direct bridge between the execution environment layer and the evaluation layer" (browser/computer-use benchmarks must isolate task state, expose observations, define measurable success predicates). And the V chapter's summary point: evaluation is not a terminal scoring step but **a quality-control loop over the full agent harness** ✅.

**Stage 4 — multi-level judgement, in the paper's full detail (§8.5) ✅ (survey text, cached full text):** the run is judged at three levels before any failure is localized. *Outcome-level* evaluation asks whether the final objective
was achieved — operationalized as unit/regression/issue-specific tests (SWE-bench), final files or command outputs or task-specific checkers (Terminal-Bench), final environment state (WebArena/WorkArena form-submitted, ticket-updated,
config-changed checks), or answer strings (GAIA); its strength is scalability and leaderboard comparability, its limitation is *compression* — a full episode reduced to one value that hides whether the agent succeeded robustly, safely,
or efficiently, so it is "necessary but not sufficient." *Trajectory-level* evaluation asks whether the path was efficient and policy-compliant — appropriate tool selection, sensible ordering, no redundant calls, permission-boundary
respect, error recovery, context consistency — where "a final answer can be correct while the trajectory is still unacceptable" (token waste, irrelevant tool calls, permission violations, brittle benchmark-specific behavior); it is
where agent evaluation diverges most from conventional output evaluation and where ReAct-style interleaved reasoning/action/observation steps become first-class evaluation objects. *Evaluator-level* evaluation asks whether the judge
itself can be trusted: deterministic verifiers are reproducible and cheap but narrow; LLM-as-Judge is flexible but biased (G-Eval's alignment gain came with bias toward LLM-generated text; MT-Bench/Chatbot Arena identified position,
verbosity, and self-enhancement biases and limited reasoning); human audits handle ambiguous or safety-critical cases but do not scale. The paper's normative prescription: **layered graders** — deterministic checks for objective state
changes, LLM judges for semantic or trajectory-level assessment, human audits for ambiguous or high-risk cases — and "the evaluator should be treated as a component under test, not as an oracle outside the system" ✅.

**Trajectory judgement is the route from failure to repair (§8.5.2–8.5.4) ✅ (survey text, cached full text):** wrong tool choice → the tool interface needs improvement; forgotten prior constraints → the context layer needs adjustment;
looping without recovery → the orchestration layer needs lifecycle controls — trajectory evaluation thus converts benchmark results into *layer-specific engineering feedback*. Failure attribution then localizes the miss across the
model, tool interface, context manager, execution environment, orchestration loop, benchmark specification, or evaluator — but attribution is rarely a single-label problem: a vague spec may cause wrong-tool choice, over-compressed
context a forgotten constraint, a sandbox dependency issue recovery behavior that inflates cost, a flaky judge a valid solution obscured. The paper's conclusion: attribution must be a *diagnostic process over the full trace*, and the
structured diagnosis it produces is what Stage 5 feeds back into regression testing and harness improvement ✅.

**Stage 5 — regression and deployment feedback, in the paper's full detail (§8.6) ✅ (survey text, cached full text):** regression evaluation should be triggered by **harness changes as well as model changes** — tool descriptions,
context-compaction policies, sandbox images, permission rules, and judge prompts can all alter behavior or scores, and because harness components interact, "local improvements can create global regressions." The practical pattern is a
*layered evaluation suite*: unit-like tests for tool schemas and deterministic validators, single-step tests for local decisions, full-rollout tests for end-to-end completion, and multi-turn simulations for long-horizon coherence
(LangChain's deep-agent evaluation guidance; Anthropic's evals-as-automated-tests framing). Evaluation must connect to observability — production traces become regression tests and evaluation failures become observability signals — and
the newest direction uses evaluators as *training and optimization signals* rather than offline metrics: verifier-based environments and RL-style agent gyms (R2E-Gym, verifiers) use environment feedback as reward or validation for
policies and scaffolds, and Meta-Harness treats harness structure itself as an object of automated search — "evaluation is not the end of the pipeline; it is the signal that allows the harness to improve" ✅.

## 8. Layer G: Governance and Security

### 8.1 Scope: Five Mechanisms Plus the Landscape

G addresses "how agent behavior is constrained, made safe, and held accountable" — agents now execute shell commands, send emails, commit code, and invoke third-party APIs, so the central question is *under what constraints they should act and who bears accountability when constraints fail* ✅ (survey text, cached full text). Governance has its own tooling ecosystem — permission engines, policy languages, audit pipelines, gateway controls — distinct from L's hooks and O's observability, warranting the independent layer ✅. Representative work (Figure 13) and mechanisms:

**Permission models and identity management (§9.1).** Access control is harder than conventional RBAC/ABAC because the required tool set depends on a natural-language task unknown at deployment time; the literature moves along a granularity axis from static boundaries to contextual per-call policies to cross-boundary permissions ✅. Named systems/ideas: static scopes (Codex sandbox with restricted FS/network; Gemini CLI workspace-scoped file access + command allow/deny lists); context-dependent privilege (Progent's predicate DSL evaluated before each invocation; Conseca generating task-specific policies from trusted context, enforced by a separate deterministic checker — *generation/enforcement separation*); identity and inter-agent access control (South et al.'s **authenticated delegation** extending OAuth 2.0/OIDC with User ID Tokens, Agent ID Tokens, scoped Delegation Tokens; SAGA's provider-mediated one-time-key registration and short-lived tokens; IsolateGPT's hub-and-spoke isolation); credential management (Skyvern's vault + placeholder pattern — secrets never enter the LLM context); web-level coordination (Marro et al.'s `agent-permissions.json`, a robots.txt-analog manifest). Open challenges: no portable permission-specification language; over-restrictive vs. over-permissive tradeoff; unresolved action attribution (human operator vs. agent instance vs. transient task identity) ✅.

**Lifecycle hooks (§9.2).** Permission models define *what is allowed*; hooks define *when policy checks fire*. The paper's Figure 14 gives four hook points along one tool-use cycle ✅: **H1 pre-input** (input guardrails — PromptShield, DataSentinel detect prompt injection in user input and retrieved content); **H2 pre-invocation** (output guardrails/action validation — ShieldAgent checks proposed actions against verifiable predicates; ControlValve constrains the inter-agent control-flow graph against hijacking); **H3 post-execution** (information flow control — CaMeL's capability-based taint tracking keeps untrusted data from influencing control flow); **H4 human-in-the-loop** (Codex, Gemini CLI, Cursor, OpenHands gate destructive actions on approval; design dimensions: validation scope, alert richness, recurrence policy — with the caution that mobile-permission research found only 17% of users attended to dialogs and 3% understood them). Programmable enforcement substrates: AgentSpec (trigger-predicate-enforcement rules at plan/tool-call/response stages), AgentDoG (trajectory-level risk diagnosis). Open challenges: no universal hook API standard; hook latency; unstudied interactions between stacked hooks ✅.

**Component hardening (§9.3).** Hardening strengthens individual components (the LLM and its tools) so fewer malicious inputs survive to trigger hooks ✅. Model hardening: the **instruction hierarchy** (Wallace et al., 2024 — train models to prioritize privileged instructions over lower-privileged content) and SecAlign (the same goal as preference optimization). Classifier-based runtime hardening: Llama Guard and related input/output classifiers — editable safety taxonomy without retraining the agent model, reusable across heterogeneous LLM backends, at the cost of an extra forward pass per tool-use cycle; plus tool-side hardening: MCP Safety Audit (Radosevich & Halloran), Trail of Bits' "Jumping the Line" (MCP research), ETDI (tool-integrity extensions), SAFEFLOW ✅. The survey's limit note: model hardening addresses wrong-instruction-following but not unconstrained data flow or unauthorized actions — those need system-level enforcement ✅.

**Tool hardening and MCP security — the paper's detail (§9.3) ✅ (survey text, cached full text):** MCP "has emerged as a common interface between agents and tools, but its initial specification lacks native security primitives." Verified specifics: Radosevich & Halloran demonstrate widely used commercial LLMs can be coerced into using MCP tools to execute malicious code, establish remote access, and steal credentials (their McpSafetyScanner uses a three-agent hacker/auditor/supervisor architecture); Trail of Bits shows MCP servers can attack clients *before a user ever invokes a tool*, through poisoned tool descriptions influencing the LLM at registration time; **ETDI** defends with cryptographically signed and versioned tool definitions — any modification to a tool's code, schema, or permissions requires a new signed version, preventing "rug-pull" silent updates; **SAFEFLOW** adds protocol-level enforcement for multi-agent systems combining information-flow control with transactional execution semantics so a violating call or message rolls back rather than propagating. Supply-chain risk: Spracklen et al. analyze 576,000 code samples across 16 LLMs and find open-source models hallucinate nonexistent package names at **21.7%** — attackers register those names ("slopsquatting") to inject malicious code; ETDI's signatures cover MCP tools but package managers and retrieval sources remain outside most governance stacks.

**Declarative constitutions (§9.4).** Externalizing constraints as declarative documents that configure governance across mechanisms — Claude's Constitution, AutoHarness, Progent Policies, Formal-LLM, VeriSafeAgent, AgentSpec ✅. The Table 3 view: a declarative constitution is **cross-cutting** — it configures all the other governance mechanisms rather than mitigating one risk class ✅. Verified detail ✅ (survey text, cached full text): **training-time vs. deployment-time constitutions** form two layers — Anthropic publishes a four-tier priority hierarchy (safety → ethics → compliance → helpfulness) with hard constraints (e.g., absolute CBRN prohibitions) distinguished from operator-adjustable soft defaults, but training-time constitutions are costly to modify post-deployment and cannot be independently audited by the harness; **deployment-time YAML constitutions** (AutoHarness: pipeline mode, risk-classification patterns, allowed/denied tool patterns, token budgets, audit destinations) are readable, versionable, diffable by non-developer stakeholders — executing as harness checks rather than shaping model defaults. Between free-form YAML and hard-coded rules sit **structured policy DSLs**: Progent's predicate language (boolean predicates, quantifiers, environment references), Formal-LLM (plan constraints as pushdown automata — sequential ordering, prohibited tool combinations, approval gates), VeriSafeAgent (user intent formalized over UI state transitions). Open challenges: no standard constitution schema; limited consistency/completeness tooling; and whether a YAML deny-rule can reliably override an RLHF-reinforced behavior remains open.

**Audit infrastructure (§9.5).** AutoHarness, SAGA, AgentMonitor, AgentAuditor, SentinelAgent, plus OWASP LLM Top 10 and OpenAI's agentic governance practices as the reference catalogs ✅. Verified detail ✅ (survey text, cached full text): AutoHarness emits per-tool-call JSONL records (tool name, arguments, risk classification, permission decision, result, token cost, latency); SAGA extends trails across trust boundaries by recording the cryptographic tokens exchanged between agents. The paper's minimum replayable audit record: trace identifier, principal identity, tool invocation, policy decision *and version*, execution result, resource cost, and an integrity hash over inputs/outputs — "most current systems record only a subset of these fields, and few sign or hash records, leaving audit trails susceptible to log tampering by a compromised agent process." Detection granularity splits **per-action detectors** (cheap, inline, but blind to slow multi-step attacks like one-file-per-minute exfiltration — AgentMonitor's log-and-flag regime) from **trajectory-level detectors** (AgentAuditor's pattern matching + LLM reasoning over full traces; SentinelAgent's temporal interaction graphs — catch distributed attacks at higher latency and less localizable alerts, typically run asynchronously over the audit log). Cost/resource auditing matters because the OWASP Top 10 lists resource drain as a distinct risk and fan-out can multiply API calls exponentially; **tiered governance pipelines** (AutoHarness's parse→risk→permission→execute→audit tiers scaling to context enrichment, anomaly scoring, human escalation, formal constraint verification, selected declaratively) let governance overhead scale with deployment risk.

## 9. Cross-Layer Synthesis

The layer chapters isolate surfaces "so that each design surface can be described precisely," but "many production failures arise at the interfaces among these surfaces" ✅ (survey text, cached full text). The seven layers are a dependency structure, not a checklist: E constrains which L strategies are practical; C affects V reproducibility; G imposes constraints spanning every other layer ✅. Five cross-cutting concerns recur at layer boundaries across the corpus — **cross-tool interoperability, cost attribution, failure recovery, multi-repository orchestration, and human–agent handoff** (§10) ✅. The synthesis then consolidates into three system-level effects plus the frameworks→platforms shift (all ✅, survey text, cached full text):

### 9.1 The Cost–Quality–Speed Trilemma

Harness reliability is constrained by a three-way tradeoff: stronger sandboxes and more faithful environments improve safety/reproducibility but raise startup latency and infrastructure cost; richer context and memory policies improve continuity but consume tokens and add retrieval overhead; deeper evaluation and observability improve diagnosis but slow iteration and add storage, labeling, and trace-processing costs. **Production systems cannot treat quality as a scalar objective** — they must decide which risks justify expensive controls, which checks run asynchronously or in regression suites, and which telemetry is worth capturing at each lifecycle stage ✅. (Repo echo: this is the operational tradeoff the failure-mode and production-readiness siblings price per layer — [technology/ai_llm/production_ready_llm_agents_guide.md](technology/ai_llm/production_ready_llm_agents_guide.md).)

**How the paper says systems navigate it (§10, §11.1) ✅ (survey text, cached full text):** not by finding a global optimum but by deciding *where each check runs and what a failure is worth* — which checks are synchronous, which run
offline or in regression suites, and which failures justify costly recovery paths. The pressure is directional: optimizing for speed trades away diagnostic depth and safety margin; optimizing for quality can make iteration too
expensive for routine use. The survey's design reading of the corpus is that mature harnesses make these choices *per lifecycle stage and per risk tier* — telemetry worth capturing at run time vs. computed later from stored traces,
evaluations run on change rather than continuously, governance checks gated by the risk classification of the action (§9.5's tiered pipelines) — and that the trilemma is precisely why harness cost, not model cost, is the binding
production constraint the paper's Claim 1 thesis rests on.

### 9.2 The Capability–Control Tradeoff

More capable harnesses expose more authority to the agent, and every increase in authority expands the control problem ✅: larger tool menus broaden coverage while increasing selection error and prompt-injection surface; persistent memory helps long-running tasks but creates provenance, staleness, and privacy risks; permissive sandboxes enable autonomy but enlarge the blast radius of misaligned or compromised actions. The tradeoff "belongs in the core system design," linking tool schemas, context policy, runtime permissions, identity, auditability, and human approval ✅. (Repo echo: the same axis appears as "excessive agency" in the governance/red-team siblings and as capability-vs-guardrail tension in [technology/ai_llm/agentic_solution_artifacts_guide.md](technology/ai_llm/agentic_solution_artifacts_guide.md)'s quality-artifact discussion.)

**The tradeoff's shape (§11.2) ✅ (survey text, cached full text):** the paper describes a monotone tension rather than a cliff — each increment of harness authority (a larger tool menu, a persistent-memory tier, a permissive sandbox,
an autonomous retry policy) buys marginal task coverage while expanding the surface the control plane must police: more tools mean more selection error and a wider prompt-injection surface; memory means provenance, staleness, and
privacy risk; permissiveness means a larger blast radius for misaligned or compromised actions. Because the two sides move together, the tradeoff "belongs in the core system design": it links tool schemas, context policy, runtime
permissions, identity, auditability, and human approval into a single decision surface, and it is the same curve the G chapter's granularity axis (static scopes → contextual per-call policies → cross-boundary permissions, §9.1) walks
in one direction.

### 9.3 The Harness Coupling Problem

Harness layers are coupled in ways that make local optimization fragile ✅: the execution environment changes evaluation results (package availability, reset semantics, latency, failure modes); tool descriptions consume context budget and shape model behavior; observability traces become governance evidence only if identity and permission state are captured at the same granularity; evaluation design feeds back into orchestration by rewarding some recovery loops and penalizing others. Consequences: **harness changes should be tested as system changes** — a prompt, tool, memory, sandbox, verifier, or monitor may look beneficial in isolation while degrading the whole rollout in combination; and agent scores **cannot be cleanly attributed to the model without specifying the surrounding controller** — under the closed-loop framing, a change to context policy, tool schema, verifier, or recovery loop changes the controller and therefore the measured behavior of the *same* model ✅. This is the paper's deepest argument for harness engineering as a systems discipline, and it is the direct justification for this guide's worked example (§12): layer-by-layer review must end in cross-layer, system-level assessment.

**Why the coupling problem is the survey's deepest argument (§11.3 → §12.3, §12.5) ✅ (survey text, cached full text):** coupling is what makes local A/B wins unreliable — a prompt, tool, memory, sandbox, verifier, or monitor "may look
beneficial in isolation while degrading the whole rollout when combined with the rest of the control loop"; and it is also why score attribution fails, because under the closed-loop framing the *controller* changes whenever context
policy, tool schema, verifier, or recovery loop changes, so the measured behavior of the same model changes too (Zhang et al., 2026c formalize this as the controller C_H). From coupling follow two of the paper's five open problems:
§12.3's diagnosing failures from traces exists because only trace-native, layer-attributed evaluation can say which component of a coupled system caused a regression, and §12.5's keeping-harnesses-useful exists because an intervention
whose benefit was measured in one harness configuration cannot be assumed beneficial in another. This guide's §12 worked example therefore treats the coupling argument as a change-management rule: every Cymbal Bank remediation is
planned as an experiment on the composed system, with baseline and regression gates.

### 9.4 From Agent Frameworks to Agent Platforms

The ecosystem is moving from **frameworks** (packaging local abstractions — agents, tools, memory stores, execution loops) toward **platforms** (adding durable workspaces, managed sandboxes, identity, billing, observability, evaluation, governance, and human handoff across many runs and users) ✅. Long-running agents consequently require the operational support associated with tenancy, compliance, fault recovery, trace retention, and organizational ownership; platform design must account for *fleets of agents whose actions remain inspectable and reversible over time* ✅. Standardization (MCP, ACP, A2A) favors agent-agnostic infrastructure, but shifts responsibility to governance and observability: a standardized tool call is useful only if the harness preserves provenance, permissions, cost, and failure evidence across systems ✅.

**The argument's mechanism (§11.4, §12.4) ✅ (survey text, cached full text):** platforms are not frameworks with more features — the shift is from packaging abstractions for one developer's local run to operating *fleets of agents
across many runs and users*, which imports tenancy, compliance, fault recovery, trace retention, and organizational ownership into the harness problem. Standardization (MCP, ACP, A2A) accelerates the shift by making agent-agnostic
infrastructure viable, but the platform inherits the responsibility the protocol drops: provenance, permissions, cost, and failure evidence must survive crossing system boundaries, or the standardized call becomes an ungovernable one.
The paper's §12.4 cross-layer handoff contract is its specification of that responsibility transfer — a handoff must carry intent, constraints, permissions, artifacts, provenance, budget state, risk level, trace history, and unresolved
decisions, and make explicit who authorized the action, which state transferred, and when control returns — which is why this guide's §10.3 lists standard handoffs among the five open problems and why the Cymbal Bank example (§12)
treats issue-tracker-as-control-plane (Symphony's pattern) as an L/G remediation target ✅.

### 10.2 Emerging Design Principles (§10 cross-cutting, condensed)

Verified design signals the paper draws ✅: (1) read a harness as a **dependency structure**, not a checklist; (2) choose synchronously which checks run, which run offline, and which failures justify costly recovery — the trilemma as a design method; (3) prefer agent-agnostic infrastructure as protocols standardize, while investing in governance/observability to keep provenance across systems; (4) test harness changes **as system changes** (coupling); (5) expect the five boundary gaps — cross-tool interoperability, cost attribution, failure recovery, multi-repository orchestration, human-agent handoff — and design the composed harness as a reliable control system.

### 10.3 The Open Agenda (§11.5, §12, §13 condensed)

The synthesis agenda: harnesses as **adaptive control systems** — benchmarks that vary harness interventions rather than only model weights; trace-native failure attribution across layers; protocols for transferring state and responsibility among agents, tools, sandboxes, evaluators, and humans; optimization methods that simplify harnesses as models improve ✅. §12 sharpens this into five open problems (all ✅, survey text, cached full text):

1. **Hardening and scaling execution environments.** SandboxEscapeBench documents that frontier models exploit sandbox weaknesses under realistic configurations; defense work is fragmented; one-container-per-task strains large-scale training/eval (tens of thousands of parallel trajectories need cheap reset — SWE-World points to Docker-free surrogate environments with unresolved fidelity); portability across Linux/macOS/Windows/browser/desktop/hybrid-cloud is hard. Open need: common security evals, cost models choosing among isolation technologies, portability layers — *the runtime substrate must become measurable and composable*. → repo: [technology/ai_llm/agent_sandboxing_strategies_guide.md](technology/ai_llm/agent_sandboxing_strategies_guide.md).
2. **Maintaining reliable state in long-running agents.** Recast context management as **state estimation**: characterize information lost at each compression/retrieval/forgetting step and bound divergence between the agent's internal state and the real task state. Future systems need uncertainty-aware summaries, provenance for remembered facts, contradiction handling, staleness markers, and recovery from durable artifacts. → repo: [technology/ai_llm/agent_runtime_cache_design_guide.md](technology/ai_llm/agent_runtime_cache_design_guide.md), [technology/ai_llm/context_engineering_guide.md](technology/ai_llm/context_engineering_guide.md), [technology/ai_llm/ai_agent_drift_guide.md](technology/ai_llm/ai_agent_drift_guide.md).
3. **Diagnosing failures from agent traces.** Evaluation is too final-score-centric; the evaluation layer must be studied as a **measurement instrument** (validity and variance, not just leaderboards). Next step: **trace-native evaluation** — traces as the primary object from which systems compute outcome scores, trajectory quality, failure attribution, and regression tests. The gap is quantified: LangChain's 2026 survey reports **89% of teams use observability while only 52.4% run offline evaluations** — teams can see what agents did without judging whether it was correct. → repo: [technology/ai_llm/agentops_guide.md](technology/ai_llm/agentops_guide.md), [technology/ai_llm/llm_evaluation_frameworks_guide.md](technology/ai_llm/llm_evaluation_frameworks_guide.md).
4. **Standard handoffs across agents, tools, and humans.** Local standards exist (MCP for tools, A2A for inter-agent, OTel for traces) but what's missing is a **cross-layer handoff contract**: a handoff should carry a text summary together with intent, constraints, permissions, artifacts, provenance, budget state, risk level, trace history, and unresolved decisions — and must make responsibility explicit (who authorized, which state transferred, what the receiver may do, when control returns). Partly technical, partly institutional (Symphony's issue-tracker-as-control-plane; Anthropic's durable progress artifacts). → repo: [technology/ai_llm/mcp_discovery_guide.md](technology/ai_llm/mcp_discovery_guide.md), [technology/ai_llm/hierarchical_multi_agent_frameworks_guide.md](technology/ai_llm/hierarchical_multi_agent_frameworks_guide.md), [technology/ai_llm/hybrid_multi_agent_systems_guide.md](technology/ai_llm/hybrid_multi_agent_systems_guide.md).
5. **Keeping harnesses useful as models improve.** Harness design should not move monotonically toward more scaffolding: every wrapper, reset, verifier, planner, memory rule, and permission gate encodes an assumption about what the model cannot do alone; as models improve, interventions should be **re-estimated, not assumed beneficial** (factorial model-by-harness evaluation; Anthropic's concrete report that context resets useful for one model became dispensable for a stronger one; Meta-Harness searching prompts/tools/control loops as optimization targets; NLAH's ablatable harness modules; TensorZero/Axon/AgentOps toward budget-aware operation). Central risk: benchmark overfitting — a self-optimizing harness against a narrow suite becomes brittle. → repo: [technology/ai_llm/agent_versioning_guide.md](technology/ai_llm/agent_versioning_guide.md) (harness-as-versioned-artifact), [technology/ai_llm/llm_evaluation_vs_validation_guide.md](technology/ai_llm/llm_evaluation_vs_validation_guide.md).

**Per-item detail the paper adds (§12.1–12.5) ✅ (survey text, cached full text):** on problem 1, the bundle-vs-compose split between framework-integrated runtimes (§3.2.4) and sandbox abstraction layers (§3.2.7) "should be treated as
an empirical design question rather than a product preference," and standards such as MCP reduce composition cost only if the tool, governance, and observability layers expose enough state to keep runtime choices auditable,
recoverable, and safe. On problem 3, recent work on randomness in agentic evals argues that single-run pass rates can hide substantial variance (Bjarnason et al., 2026), and Reflexion showed agents learning from their own traces in
short-horizon settings — extending that to long-running, multi-session harnesses remains open. On problem 5, the paper specifies the re-estimation machinery: factorial model-by-harness runs reveal whether an intervention improves all
models, helps only specific families, or reverses model rankings; production harnesses should identify which interventions are causally responsible for quality, safety, or reliability, run shadow-mode or A/B tests across harness
variants, and optimize under joint quality–latency–cost–risk constraints — with adaptive simplification continually reassessing which controls remain necessary as tasks, tools, and model capabilities change, against the standing risk
that a harness optimizing itself against a narrow suite becomes brittle.

The paper's conclusion states its own limits and next step ✅: the corpus is biased (English/GitHub-visible/open-source/coding-agent); extending to closed-source production systems and non-coding ecosystems would sharpen the picture; and ETCLOVG is **descriptive** — turning it into a *normative* framework that guides harness design decisions is the natural next step the authors hope the survey encourages.

## 12. Worked Example: The Cymbal Bank Harness Assessment

### 12.2 Readout and Phase Plan

**Readout.** The illustrative estate is strongest at T/L/G basics and weakest at C (no context discipline), V (score-only eval, no readiness or attribution), and O (no agent-level ops loop). Under the paper's coupling argument (§9.3) the *highest-leverage* fix is not the lowest score but the most-coupled one: **C and V**, because context policy changes evaluation results and evaluation design feeds back into orchestration — so the team should sequence (1) context discipline + cache-stable prompts, (2) the five-stage V lifecycle with readiness checks, then (3) trace-native regression so every C change is tested as a system change. Each remediation maps to a sibling in the table above; the ETCLOVG review itself is this guide's method.

**Phase plan (three quarters, each phase ending in a harness change tested as a system change per §9.3):**

- **Phase 1 — Context and verification (C, V).** Ship cache-stable prompt prefixes and append-only context discipline ([context_engineering_guide.md](context_engineering_guide.md), [agent_runtime_cache_design_guide.md](agent_runtime_cache_design_guide.md)); stand up pre-execution readiness checks and trajectory-level judgment for the drafting agent ([llm_evaluation_frameworks_guide.md](llm_evaluation_frameworks_guide.md), [llm_evaluation_vs_validation_guide.md](llm_evaluation_vs_validation_guide.md)); baseline scores before and after every harness change, treating each change as an experiment (the model–harness-pair view, §7.1).
- **Phase 2 — Operations and execution (O, E).** Adopt the AgentOps discipline and close the trace→eval loop ([agentops_guide.md](agentops_guide.md)); separate eval substrate from prod substrate and add a sandbox-escape gate ([agent_sandboxing_strategies_guide.md](agent_sandboxing_strategies_guide.md)); instrument cost per layer and watch the token-elasticity trap (paper §7.3).
- **Phase 3 — Lifecycle and governance hardening (L, G, T).** Introduce a durable task-runner abstraction and version agent definitions as units ([agent_scaffolding_guide.md](agent_scaffolding_guide.md), [agent_versioning_guide.md](agent_versioning_guide.md)); add agent identity/delegation tokens, an H1–H4 hook map over the tool-use cycle, and a declarative constitution reviewed by compliance ([ai_governance_framework_guide.md](ai_governance_framework_guide.md), [prompt_injection_guide.md](prompt_injection_guide.md)); rationalize the tool menu and manage MCP server lifecycles ([mcp_discovery_guide.md](mcp_discovery_guide.md), [mcp_framework_tools_guide.md](mcp_framework_tools_guide.md)). Throughout, keep the artifact trail walkable end-to-end per [agentic_solution_artifacts_guide.md](agentic_solution_artifacts_guide.md) — a Cymbal Bank auditor must be able to walk from a compliance report to the run, the definition, and the verdict.

**Coverage scorecard → target state.** The review closes each layer to a defined "5/5" state — the score today, the phase that moves it, the gate that defines done, and the sibling that owns the remediation (narrative continuity with 12.1–12.2; all scores illustrative):

| Layer | Score today | Target state ("5/5" at Cymbal Bank) | Phase | Acceptance gate | Owning sibling |
|---|---|---|---|---|---|
| E | 2/5 | Prod/eval substrate separation; escape benchmark as a release gate; hybrid-BYOC where data residency demands | 2 | Escape-gate green on the Eval substrate; no prod container runs eval workloads | agent_sandboxing_strategies_guide |
| T | 3/5 | Per-agent tool menus rationalized ("fewer but better tools"); MCP servers versioned with lifecycle controls | 3 | Tool-selection quality measured pre/post; zero stale-handle incidents per quarter | mcp_discovery_guide, mcp_framework_tools_guide |
| C | 1/5 | Cache-stable prompt prefix; append-only context; three-tier memory (active/session/long-term) in prod | 1 | KV-cache hit-rate and mid-context accuracy baselined; drift review at 100+ turns | context_engineering_guide, agent_runtime_cache_design_guide |
| L | 3/5 | Durable task-runner abstraction; agent definitions versioned as units; checkpoint–resume across failures | 3 | Issue→review→release runnable without manual state reconstruction | agent_scaffolding_guide, agent_versioning_guide |
| O | 2/5 | Agent-level session model; per-layer cost attribution; traces feeding evaluation (closing the 89%/52.4% gap) | 2 | Trace→eval loop live for the drafting agent; anomaly detection on trajectory drift | agentops_guide |
| V | 2/5 | Five-stage task-to-feedback lifecycle with readiness checks; harness-change regression gate; layered graders | 1 | Every harness change runs baseline + regression as a system change (§9.3) | llm_evaluation_frameworks_guide, llm_evaluation_vs_validation_guide |
| G | 3/5 | Agent identity/delegation chain; H1–H4 hook map; declarative constitution reviewed by compliance; replayable signed audit | 3 | Auditor walks compliance report → run → definition → verdict; hook map covers all four points | ai_governance_framework_guide, ai_red_teaming_guide, prompt_injection_guide |

The target states are the paper's own normative turn applied: ETCLOVG as the survey gives it is descriptive, and turning it into a framework that *guides* design decisions — layer by layer, gated and re-estimated — is the next step the authors name, which this worked example performs at fictional-bank scale ✅ (survey text, cached full text, §13 of the paper).

The review's closing discipline, straight from the paper: **re-estimate, don't accumulate** (paper §12.5) — every hook, reset, and permission gate Cymbal Bank adds encodes an assumption about what the model cannot yet do alone, so each quarter's harness inventory should also *remove* controls the model has outgrown, exactly as Anthropic's sprint-construct removal cut cost $200→$125 at equal quality (paper §7.4).

### 14.2 Glossary

| Term | Meaning (as used in this guide and the survey) |
|---|---|
| **Agent harness** | The surrounding operational infrastructure that provides context, tool interfaces, state, recovery, inspection, verification, and permissions to an LLM agent ✅. |
| **Harness engineering** | Designing and integrating those mechanisms so model capabilities support reliable execution ✅. |
| **ETCLOVG** | The survey's seven-layer taxonomy: Execution, Tooling, Context, Lifecycle, Observability, Verification, Governance ✅. |
| **Structural core / control plane** | E,T,C,L form the structural core; O,V,G the control plane around it ✅. |
| **Sandbox** | Bounded execution region for agent actions; simultaneously a security cage and an autonomy license ✅. |
| **Sandbox escape** | An agent (or injected content) breaking out of the sandbox's isolation boundary; empirically documented by SandboxEscapeBench/CIBER ✅. |
| **Context rot** | Single-step degradation of retrieval/reasoning quality as a fixed context grows ✅. |
| **Context drift** | Trajectory-level behavioral degradation over extended interactions (100+ turns); compounded by lossy compaction ✅. |
| **Three-tier memory** | Active context window (short-term), session/cross-run state (mid-term), indexed persistent memory (long-term) ✅. |
| **KV-cache-aware design** | Structuring context (stable prefix, append-only, deterministic serialization) to maximize prompt-cache hits ✅. |
| **Task runner** | Harness abstraction managing scheduling, state, retries, validation over a full task lifecycle (issue→PR) ✅. |
| **Stateless replay / stateful / hybrid** | Execution models: reconstruct from history / persist operational state / combine both ✅. |
| **Model–harness pair** | The measured unit of agent performance — scores are properties of the pair, not the model alone ✅. |
| **Task-to-feedback lifecycle** | V-layer five-stage quality loop: grounding → readiness → controlled execution → multi-level judgement → regression feedback ✅. |
| **Trace-native evaluation** | Computing outcome scores, trajectory quality, attribution, and regression tests directly over traces ✅. |
| **Hook points H1–H4** | Governance enforcement points along a tool-use cycle: input, pre-invocation, post-execution, human-in-the-loop ✅. |
| **Declarative constitution** | Externalized, declarative constraint set configuring governance across mechanisms ✅. |
| **Cost–quality–speed trilemma** | Three-way constraint on harness reliability; quality is not a scalar objective ✅. |
| **Capability–control tradeoff** | More harness authority broadens task coverage and enlarges the control problem ✅. |
| **Harness coupling problem** | Layer interactions make local optimization fragile; harness changes must be tested as system changes ✅. |
| **Handoff contract** | A cross-layer transfer carrying summary + intent, constraints, permissions, artifacts, provenance, budget, risk, trace history, unresolved decisions ✅ (paper §12.4). |
| **Agent-computer interface (ACI)** | SWE-agent's measured interface between agent and environment (commands, observations, edits, tests) ✅. |
| **Framework vs platform** | Frameworks package local abstractions; platforms add tenancy, identity, billing, governance, fleet operations ✅. |
| **Context engineering** | Curating and maintaining the optimal token set during LLM inference — the prompt plus "all the other information that may land there outside of the prompts" ✅. |
| **Compaction** | Summarizing a window approaching its limit and reinitiating execution from a compressed representation; calibrated recall-first, precision-second ✅. |
| **Rollout** | The basic unit of agent evaluation: task, model and harness configuration, action sequence, observations, final state, and grading result ✅. |
| **Multi-level judgement** | Judging a run at outcome, trajectory, and evaluator levels before attributing any failure ✅. |
| **Layered graders** | Stage-4 practice: deterministic checks for objective state, LLM judges for semantic/trajectory quality, human audits for ambiguous or high-risk cases — the evaluator as a component under test ✅. |
| **Failure attribution** | Localizing a failed run to the model, tool interface, context, environment, orchestration, benchmark, or evaluator; a diagnostic process over the full trace, not a post-hoc label ✅. |
| **State-estimation agenda** | Recasting context management as bounding the divergence between agent-internal state and true task state at each compression/retrieval/forgetting step ✅ (paper §12.2). |
| **R1–R7 risk catalog** | Kim et al.'s seven agent-risk categories (untrusted interfaces through resource drain) that the survey's Table 3 maps governance mechanisms onto ✅. |
