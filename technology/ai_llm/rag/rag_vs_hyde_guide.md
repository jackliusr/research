## 1. Introduction: RAG vs HyDE at a Glance

Retrieval-Augmented Generation (RAG) is the dominant architecture for grounding LLM answers in an external corpus. HyDE (Hypothetical Document Embeddings) is a retrieval-side enhancement that fixes RAG's most common failure mode: the mismatch between how users *ask* and how documents *state*.

**The one-line difference:** RAG embeds the **query** and searches; HyDE embeds a **hypothetical answer** (generated by an LLM) and searches with that. Everything else — vector search, top-k retrieval, context assembly, generation — stays the same.

**Why HyDE exists:** a user query ("What are the risks of high-frequency trading?") and a relevant document ("HFT strategies are exposed to latency arbitrage, adverse selection, and systemic liquidity risk…") barely overlap lexically and sit far apart in embedding space. An LLM-generated paragraph *answering* the question is written in the same declarative register as real documents, so its embedding lands much closer to them.

**TL;DR comparison:**

| Dimension | Standard RAG | RAG + HyDE |
|-----------|-------------|------------|
| What gets embedded | The raw user query | An LLM-generated hypothetical document |
| Extra LLM call | None | +1 (or more) per query |
| Latency impact | Baseline | +100–500 ms per query |
| Cost impact | Baseline | +token cost for generation |
| Best for | Concrete, factual, entity-heavy queries | Abstract, conversational, vocabulary-mismatched queries |
| Failure mode | Query–document semantic gap | LLM hallucination drifts retrieval |

The two are **not competitors in practice** — production systems combine them: route simple queries to standard RAG, run HyDE (optionally ensembled with the query embedding) for complex ones, and rerank in both paths.

## 2. What Is RAG?

### 2.1 Definition

**Retrieval-Augmented Generation** augments an LLM's response with external knowledge retrieved on demand from a corpus. Instead of answering from parametric memory alone, the system retrieves the most relevant passages for the query and conditions generation on them:

```
query → embed → vector search → top-k documents → prompt(query + context) → grounded answer
```

RAG was introduced by Lewis et al. (2020, "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks") and has become the default pattern for enterprise LLM applications because it is simple, model-agnostic, and requires no training.

### 2.2 The Standard RAG Pipeline

```
                ┌──────────────────────────────────────────────────┐
                │                 OFFLINE (indexing)                │
                │  Documents → chunk → embed → vector index        │
                │                       (+ BM25 inverted index)     │
                └──────────────────────────────────────────────────┘
                                          │
query ──► embed ──► vector search ──► top-k docs ──► rerank ──► assemble context
   │                                                              │
   └──────────────────────────────────────────────────────────────┘
                                        ▼
                        prompt(query + context) ──► LLM ──► grounded answer
```

**Stage-by-stage:**

| Stage | What happens | Typical choice |
|-------|--------------|----------------|
| **Chunking** | Split documents into retrievable units | 200–1000 tokens, overlap 10–20%, structure-aware splits |
| **Embedding** | Map each chunk to a dense vector | text-embedding-3, bge, E5, Instructor, Contriever |
| **Indexing** | Store vectors + metadata for fast search | FAISS, Milvus, pgvector, Qdrant, Elasticsearch |
| **Retrieval** | Find top-k similar chunks | Dense (vector), sparse (BM25), or hybrid |
| **Reranking** | Reorder top-k with a stronger model | Cross-encoders: Cohere Rerank, bge-reranker |
| **Context assembly** | Pack retrieved chunks into the prompt | Dedup, truncate, order by relevance |
| **Generation** | LLM answers with retrieved context | Any instruct-tuned LLM |

**Retrieval flavours:**

- **Dense vector search** — semantic similarity via embeddings. Handles paraphrase and synonymy, but needs the query to be *semantically close* to documents.
- **Sparse / BM25** — lexical term matching. Handles exact terms and rare identifiers (product codes, LEIs, regulatory IDs) but misses paraphrase.
- **Hybrid** — run both and fuse (Reciprocal Rank Fusion, weighted scores). The production default because the two failure modes are complementary.

### 2.3 Strengths

- **Grounded answers, fewer hallucinations** — the LLM conditions on retrieved evidence rather than memory alone; it can be instructed to answer only from context.
- **Up-to-date knowledge without retraining** — refresh the index, not the weights. Knowledge changes (new regulations, new products) propagate by re-ingesting documents.
- **Source citations** — retrieved chunks give the LLM *something to cite*; the provenance trail is auditable, which is non-negotiable in regulated industries.
- **Domain adaptation at low cost** — enterprise docs (policies, filings, runbooks) become queryable without fine-tuning the LLM.
- **Cost-effective** — one generation call per answer, no training runs, no model hosting beyond standard inference.

### 2.4 Limitations

- **Retrieval quality is the bottleneck** — garbage in, garbage out. If the top-k are wrong, the best LLM in the world produces a fluent wrong answer.
- **Query–document vocabulary mismatch** — queries are short, interrogative, and abstract; documents are long, declarative, and concrete. "Capital requirements" must match "Basel III CET1, capital conservation buffers, leverage ratios".
- **Embedding misalignment** — question embeddings and document embeddings often do not align well in vector space, especially for abstract or indirect queries. The embedding model must bridge a gap it was never explicitly trained to bridge.
- **Chunking artifacts** — a bad chunk split severs an answer across two chunks, or stuffs one chunk with two topics; retrieval then finds half-answers.
- **Retrieval failures propagate** — errors upstream are invisible downstream: the user sees a confident but unsupported answer and cannot tell retrieval failed.

## 3. The Fundamental Problem: The Query–Document Semantic Gap

Every RAG limitation above traces to one root cause: **the query is not in the same semantic space as the documents.**

| | Queries | Documents |
|---|---------|-----------|
| Register | Interrogative ("What is…?", "How does…?") | Declarative ("The framework requires…") |
| Length | 2–15 words, elliptical | 200–1000+ tokens per chunk |
| Abstraction | Vague, high-level, intent-laden | Specific, concrete, factual |
| Context | Assumes shared background | Self-contained prose |
| Vocabulary | User words ("return on the loan") | Domain terms ("EAD, LGD, PD, ECL staging") |

A query is a *pointer to* information; a document *contains* information. Dense retrieval works by embedding both into one vector space and hoping the pointer lands near the content — the embedding model must bridge the gap implicitly.

- For **concrete queries** ("What is Crédit Agricole CIB's LEI?"), the bridging works: entity names and exact terms overlap with document text, and both lexical and dense signals agree.
- For **abstract queries** ("What are the compliance implications of moving our risk aggregation to the cloud?"), the bridging fails: no term overlap, and the question's embedding points toward the *concept of asking*, not toward any particular document's content.

This is the precise failure HyDE attacks: instead of asking the embedding model to bridge the gap, HyDE *removes the gap* by manufacturing a document-shaped query.

**Worked banking example:**

```
Query: "Can we still use our vendor's cloud risk platform after the merger?"
Docs:  "…outsourcing arrangements require prior notification to MAS under the
        Notice on Outsourcing… intra-group service arrangements…"
```

No terms are shared: the question's embedding points toward "merger / cloud / vendor", the document's toward "outsourcing / MAS notification / intra-group services". Even a well-trained embedder will struggle to connect them. HyDE turns the query into a passage that names outsourcing notices and regulatory notification — the terms the documents actually use — and the vector search lands in the right neighbourhood.

## 4. What Is HyDE?

### 4.1 Definition and Origin

**HyDE (Hypothetical Document Embeddings)** was proposed by Gao, Ma, Lin, and Callan in **"Precise Zero-Shot Dense Retrieval without Relevance Labels"** (arXiv:2212.10496, December 2022; ACL 2023). The paper addresses a hard problem: dense retrieval without any relevance labels to train on — truly zero-shot.

**Core idea:** instead of embedding the raw query, use an LLM to generate a **hypothetical document** — a plausible answer-like paragraph — embed *that*, and run vector search with the hypothetical document's embedding. The paper's framing: *"documents should be retrieved based on their similarity to the answer, not the question."*

### 4.2 The Intuition

A hypothetical answer is semantically closer to real documents than the query is:

```
Query:  "What are the risks of high-frequency trading?"
                │  (interrogative, abstract — weak retrieval signal)
                ▼
HyDE doc: "High-frequency trading (HFT) strategies are exposed to latency
arbitrage, adverse selection, and order-flow toxicity. HFT has been linked
to increased market volatility, including the 2010 Flash Crash, and raises
systemic risk concerns for market stability and fair access."
                │  (declarative, concrete — matches document prose)
                ▼
Real doc: "…latency arbitrage exposes HFT desks to adverse selection…
the Flash Crash of May 2010 demonstrated systemic fragility…"
```

Even if the hypothetical document is *factually imperfect*, its **form** is what matters: it lives in the documents' region of embedding space, so nearest-neighbour search finds the right neighbourhood. HyDE is a *form transplant*, not a fact-transplant — hallucination of detail is tolerable as long as the topic and register are right.

### 4.3 The HyDE Pipeline

```
query
  │
  ▼
[LLM]  "Write a hypothetical paragraph that would answer: {query}"
  │
  ▼
hypothetical document (answer-like prose)
  │
  ▼
[embedder] ──► embedding of the hypothetical document
  │
  ▼
vector search ──► top-k REAL documents
  │
  ▼
(optional) ensemble with query-embedding results
  │
  ▼
[RAG generation]  prompt(query + retrieved context) ──► answer
```

### 4.4 Two Components

HyDE is a composition of two off-the-shelf pieces — **no training, no labels, no fine-tuning**:

1. **An instruction-following LLM** — generates the hypothetical document. The original paper used GPT-3 (text-davinci-003) with instructions like *"Write a paragraph that answers the question"* or task-specific variants (*"Write a Wikipedia-like passage…"*). Any instruction-tuned model works; quality scales with the model's world knowledge.
2. **A contrastively-trained encoder** — embeds the hypothetical document and searches. The paper used **Contriever** (Izacard et al., 2021), an unsupervised contrastive retriever, precisely to stay zero-shot. In practice, any embedding model works — including your existing RAG embedder, which keeps infrastructure unchanged.

### 4.5 Zero-Shot by Construction

HyDE requires **no relevance labels, no query–document pairs, no training pipeline**. It is a *prompt-level* technique: swap what gets embedded, keep the whole retrieval stack. This is why it spreads so easily — it is a drop-in change at the query-representation step of any dense RAG system.

### 4.6 Why HyDE Works

- **Semantic alignment** — the hypothetical answer is declarative prose in the documents' semantic space, not an interrogative pointer. Cosine similarity now measures *content-to-content* closeness.
- **It removes the root cause** — the query–document gap is the reason dense retrieval fails on abstract queries; HyDE eliminates the gap rather than hoping the embedder bridges it.
- **The LLM's world knowledge fills in missing context** — the LLM expands "what are the risks of HFT?" into a passage naming latency arbitrage, adverse selection, Flash Crash, systemic risk — terms that actually appear in the corpus. The hypothetical doc is a *query expansion with prose coherence*.
- **Works zero-shot** — no labeled data, no fine-tuning, no training pipeline, no relevance labels; portable across domains (legal, medical, financial) without adaptation work.
- **Orthogonal to the retriever** — HyDE improves whatever dense retriever you already have; it does not require changing the index or the embedder.

## 5. HyDE Limitations

HyDE is not a free lunch. The same properties that make it powerful create failure modes:

| Limitation | Mechanism | Mitigation |
|------------|-----------|------------|
| **Hallucination drift** | LLM generates factually wrong or off-topic hypothetical doc → search drifts to wrong documents | Use high-quality LLM; low temperature; validate retrieval; fall back to query embedding |
| **Latency + cost** | Extra LLM call + extra embedding per query (100–500 ms, extra tokens) | Small/fast LLM (Haiku-class), cache repeated queries, route only complex queries |
| **LLM-quality dependence** | Weaker LLMs generate weaker hypothetical documents → smaller gains | Match LLM to query difficulty; use domain-tuned prompts |
| **Not always better** | Simple/factual queries: direct query embedding already retrieves well; HyDE adds cost with no gain | Query-type routing — skip HyDE for concrete queries |
| **Edge cases** | Very specific queries, domain jargon, non-textual content (tables, images, code) — HyDE prose may not represent them | Combine with BM25/hybrid; keep query embedding in the ensemble |
| **Multi-hop queries** | One hypothetical doc captures a single interpretation; other hops' evidence is missed | Generate multiple diverse hypothetical docs; decompose query |
| **Retriever style mismatch** | If the corpus chunks are terse (headlines, tables), a fluent hypothetical paragraph may sit far from them | Match HyDE prompt style to document style ("Write in the style of our policy documents") |

**Hallucination drift, in detail:** HyDE's tolerance for hallucination has a boundary. If the LLM invents specifics that contradict the corpus (wrong regulation number, wrong product name), the nearest neighbours may be documents about the *invented* topic. The hypothetical doc is never shown to the user — but it silently steers retrieval. This is why production HyDE systems keep the original query embedding in the loop (ensemble) and treat HyDE as a recall booster, not a replacement.

**When HyDE genuinely adds nothing:** entity-lookup queries ("What is the ISIN of this bond?", "Show the Q3 capital ratios") retrieve perfectly with the raw query — exact identifiers dominate. Running an LLM to generate a hypothetical document for those queries is pure latency and token spend.

**Quick diagnostic — try HyDE if your system shows any of these:**

- Retrieval recall on abstract queries is visibly worse than on concrete ones
- Query terms rarely appear verbatim in the documents that should answer them
- Users ask conversationally while the corpus is formal, declarative prose
- You have no relevance labels and no budget to fine-tune the embedder
- You run dense-only retrieval with no BM25/hybrid fallback
- You can absorb 100–500 ms and a small token cost per complex query

If none apply — especially if your queries are short, exact, and match document vocabulary — HyDE is likely overhead, not help.

## 6. RAG vs HyDE: Head-to-Head Comparison

### 6.1 The Core Difference

Both RAG and HyDE end with the same step — feeding retrieved context to an LLM for generation. They differ **only in what gets embedded for retrieval**:

| | Standard RAG | HyDE |
|---|--------------|------|
| Embedding input | The user's query | An LLM-generated hypothetical answer |
| Extra LLM call | None | +1 per query |
| Latency | Baseline | +100–500 ms |
| Cost | Baseline | +generation + embedding tokens |
| Query–document gap | Must be bridged by the embedder | Removed by construction |
| Works for concrete queries | ✅ Excellent | ✅ Fine (but wasteful) |
| Works for abstract queries | ❌ Often fails | ✅ Strong |
| Failure mode | Embedding misalignment | LLM hallucination drift |
| Training required | No | No (zero-shot) |
| Complexity | Low | Low–moderate (extra call + prompt) |

### 6.2 When RAG Wins (keep standard retrieval)

- **Concrete / factual queries** — specific entity names, product names, exact terms, identifiers. Lexical and dense signals agree; HyDE adds nothing.
- **Well-aligned query–document vocabularies** — the corpus uses the same terms users type (FAQ-style knowledge bases).
- **Latency-sensitive applications** — interactive chat, real-time assistants; every millisecond counts and 100–500 ms of HyDE generation is visible.
- **Cost-sensitive at scale** — millions of queries/day; even $0.0005 extra per query compounds. Standard RAG is the cheapest correct option.
- **Good existing embedding alignment** — if your embedding model was fine-tuned on (query, document) pairs for your domain, the gap is already bridged.

### 6.3 When HyDE Wins (add HyDE to retrieval)

- **Abstract / conversational queries** — vague questions, indirect references, "what about…?" follow-ups that no longer match anything literally.
- **Heavy vocabulary mismatch** — user terms never appear in documents (users say "loan returns", documents say "expected credit loss, EAD × LGD").
- **Complex reasoning queries** — multi-faceted questions whose answer spans documents written in different words.
- **Zero-shot scenarios without fine-tuning** — new domain, no labels, no budget to train a retriever: HyDE is the fastest path to decent retrieval.
- **Dense-only systems** — if you have no BM25/lexical fallback, HyDE is the cheapest way to recover the recall that hybrid search would have provided.
- **Out-of-domain queries** — the LLM's broad world knowledge bridges gaps the domain-trained embedder cannot (e.g., a user asks about a new product category not yet in the corpus vocabulary).

### 6.4 Quantitative Findings

From the HyDE paper (Gao et al., 2022) and subsequent reproductions:

- HyDE reports **roughly 15–20% improvements in retrieval quality (recall@k / nDCG@10) over standard zero-shot dense retrieval** on TREC-COVID and several other BEIR benchmarks — in a fully zero-shot setting (no relevance labels, no fine-tuning).
- **Gains vary dramatically by dataset**: the biggest gains are on abstract/conversational tasks (queries with high vocabulary mismatch, e.g., TREC-COVID's complex medical questions, arguana's topic-style queries); the smallest are on factual, entity-heavy tasks (e.g., entity-lookup and FAQ-style datasets) where raw query embeddings already work.
- **HyDE with GPT-3 outperformed a supervised retriever (Contriever fine-tuned with relevance labels) on several benchmarks** — notable because HyDE used zero labels while the baseline used supervised training. This made the paper's point: retrieval quality for abstract queries is gated by the query–document gap, not by label volume.
- **Ensembling both representations (query embedding + HyDE embedding) is often better than either alone** — the two retrieve complementary neighbourhoods (query-close and answer-close documents).

**Where the gains concentrate:** in the paper's BEIR experiments the largest relative gains appeared on datasets with abstract or conversational queries — e.g., TREC-COVID (complex medical questions), arguana (topic-style statements), and fiqa (financial questions) — while FAQ-style and entity-centric datasets showed the smallest deltas. fiqa is the banking-relevant data point: financial questions phrased by non-specialists over documents written by professionals is exactly the query–document mismatch HyDE is built for.

Interpretation for practitioners: treat HyDE as a **recall lever with dataset-dependent upside**. Measure it on *your* corpus before assuming the paper's average applies.

## 7. Combining RAG and HyDE

HyDE is not an alternative to RAG — it is a **retrieval strategy inside RAG**. The five standard ways to combine them, from simplest to most robust:

### 7.1 Approach 1 — HyDE as a Retrieval Strategy Within RAG

Replace the query embedding with the HyDE embedding at the retrieval step. Same RAG pipeline, different query representation:

```python
def hyde_retrieve(query, llm, embedder, vector_store, k=5):
    hyde_doc = llm.generate(HYDE_PROMPT.format(query=query))
    hyde_emb = embedder.embed(hyde_doc)
    return vector_store.similarity_search_by_vector(hyde_emb, k=k)
```

**When:** you have confirmed HyDE beats query embedding on your corpus and you want the simplest deployment. **Risk:** pure HyDE loses the exact-match neighbourhood — a query-close document can be missed.

### 7.2 Approach 2 — Ensemble Retrieval (Query + HyDE)

Retrieve with **both** the query embedding and the HyDE embedding, merge, deduplicate, and feed the union to the LLM:

```python
q_results  = vector_store.search(embed(query),  k=k1)
h_results  = vector_store.search(embed(hyde_doc), k=k2)
fused = rrf_fusion([q_results, h_results])   # Reciprocal Rank Fusion
context = dedupe(truncate(fused, max_chunks))
```

RRF scores each document by `Σ 1/(k + rank)` across result lists — no score normalisation needed:

```python
def rrf_fusion(result_lists, k=60):
    scores = {}
    for results in result_lists:
        for rank, doc in enumerate(results):
            scores[doc.id] = scores.get(doc.id, 0) + 1 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

**Why this is the production standard:** it catches both query-close and answer-close documents, and it is robust to HyDE failure — if the hypothetical doc drifts, the query-embedding list still anchors retrieval. Cost is one extra embedding (cheap) and one extra vector search.

### 7.3 Approach 3 — Query-Type Routing

Classify each query and route to the cheapest adequate path:

```
query ──► classify ──► simple/concrete  ──► standard RAG (query embedding, fast, cheap)
               │
               └──────► abstract/complex ──► HyDE or ensemble (better recall, +latency/cost)
```

- **Classifier:** rule-based (term overlap with corpus vocabulary, query length, presence of entity patterns) or LLM-based ("Is this query likely to match documents literally?") — the same routing pattern used for query-rewriting in the [Query Rewriting in RAG guide](query_rewriting_rag_guide.md).
- **Benefit:** cost–latency optimisation — most real-world query mixes are majority-concrete, so routing confines HyDE's extra cost to the minority that needs it.
- **Fallback:** when in doubt, route to the ensemble — it is the safest default.

### 7.4 Approach 4 — Iterative / Multi-Draft HyDE

Generate **multiple hypothetical documents** (diverse phrasings, different interpretations, different answer angles), embed all, retrieve the union, rerank:

```python
hyde_docs = llm.generate_n(HYDE_PROMPT, n=3, temperature=0.7)  # diverse drafts
results = [vector_store.search(embed(d), k=k) for d in hyde_docs]
fused = rrf_fusion(results + [vector_store.search(embed(query), k=k)])
```

**Trade-off:** more coverage — multi-hop queries are less likely to collapse onto one interpretation — at multiplied generation cost. Use for high-stakes queries only; 1–3 drafts is the practical ceiling.

### 7.5 Approach 5 — HyDE + Cross-Encoder Reranking

The **recommended production combo**: HyDE (or ensemble) for *recall*, then a cross-encoder reranker (Cohere Rerank, bge-reranker, cross-encoder/ms-marco) for *precision*:

- HyDE widens the retrieved neighbourhood (recall ↑).
- The reranker scores each candidate against the *original query* with a full cross-attention model — the strongest available relevance signal (precision ↑).
- They are complementary: HyDE alone returns a noisier top-k; reranking alone cannot recover documents the first stage never retrieved.

```
query + hyde_doc
   │
   ▼
[recall stage: query emb ⊕ hyde emb, RRF] ──► top-20
   │
   ▼
[precision stage: cross-encoder rerank against original query] ──► top-5
   │
   ▼
LLM generation
```

### 7.6 Production Pipeline Recommendation

```
                    ┌────────────── query ──────────────┐
                    ▼                                   │
             classify_query()                           │
              │        │                                │
      simple/concrete  │                                │
              │        │                                │
              ▼        │                                │
   ┌─────────────────┐ │                                │
   │ standard path   │ │   complex/abstract             │
   │ embed(query)    │ │        │                       │
   │ search top-k    │ │        ▼                       │
   │ rerank          │ │   HyDE path:                   │
   │ generate        │ │   hyde_doc = LLM(HYDE_PROMPT)  │
   └─────────────────┘ │   emb_hyde = embed(hyde_doc)   │
              │        │   emb_query = embed(query)     │
              └────────┼──► RRF( search(emb_query,k1)    │
                       │        ⊕ search(emb_hyde,k2) ) │
                       ▼                                │
                  cross-encoder rerank                  │
                       ▼                                │
                  context assembly                      │
                       ▼                                │
                  LLM generation ◄──────────────────────┘
```

**Operational rules:**

- Start with the **ensemble + rerank** default for everything; add routing only once you have data on which query classes HyDE helps.
- Keep the **HyDE generation LLM small** (Haiku/mini-class) — generation quality saturates quickly for retrieval purposes.
- **Cache** hypothetical documents for repeated/near-duplicate queries (regulatory FAQs are heavily repeated).
- **Fallback:** if the HyDE generation fails or times out, degrade gracefully to query-embedding retrieval — never block the answer on HyDE.

## 8. Variants and Related Techniques

### 8.1 Query Rewriting vs HyDE vs Query Expansion

All three attack the query–document gap, but at different objects:

| Technique | What it changes | Mechanism | Generative or extractive |
|-----------|----------------|-----------|--------------------------|
| **Query rewriting** | The **query** | LLM rewrites the query into a more retrievable form (multi-query, step-back abstraction, decomposition) | Generative |
| **HyDE** | Creates a synthetic **document** | LLM writes an answer-like paragraph; embed *it* | Generative |
| **Query expansion (PRF)** | The **query** | Retrieve first pass, extract terms from top documents, expand the query | Extractive |

**Key distinction:** rewriting changes the *question*; HyDE creates a synthetic *answer*; pseudo-relevance feedback (PRF) borrows terms from *real* retrieved documents. HyDE is essentially "generative PRF" — it synthesises the pseudo-relevant document with an LLM instead of extracting terms from a first-pass search. The [Query Rewriting in RAG guide](query_rewriting_rag_guide.md) covers the rewriting family in depth; HyDE sits at its intersection with retrieval optimisation.

### 8.2 Other RAG Enhancement Families

| Technique | What it does | Relationship to HyDE |
|-----------|--------------|----------------------|
| **Self-RAG** (Asai et al., 2023) | LLM decides *when* to retrieve via reflection tokens; critiques retrieved passages | Orthogonal — HyDE improves *what* is retrieved; self-RAG decides *whether* |
| **RAG-Fusion** (Rackspace, 2024) | Generates multiple query variations, retrieves each, fuses via RRF | Sibling — same fusion machinery; HyDE drafts can serve as one variation |
| **CRAG** (Yan et al., 2024) | Evaluates retrieval quality, corrects or discards poor retrievals | Complementary — CRAG's evaluator can catch HyDE drift |
| **RAPTOR** (Sarthi et al., 2024) | Recursively summarises document clusters; retrieves at multiple abstraction levels | Complementary — helps when the answer lives at summary level, not chunk level |
| **GraphRAG** (Edge et al., 2024) | Builds a knowledge graph over the corpus; graph-based retrieval | Complementary — graph handles relational queries; HyDE handles vague ones |
| **Query2Doc** (Wang et al., 2023) | Extends HyDE: generates a full expanded document for both embedding and keyword retrieval | Direct extension |
| **REPLUG** (Shi et al., 2023) | Retrieve → inform LLM → rewrite → retrieve again | Compatible — HyDE can seed the first pass |
| **Step-back prompting** (Zhou et al., 2023) | Abstracts the query to retrieve broader context | Different direction — HyDE concretises into an answer; step-back abstracts into a principle |

**Orthogonality is the key property:** HyDE changes only the query representation at the retrieval step, so it layers under or over most of these techniques. A maximal pipeline (routing → HyDE ensemble → RAG-Fusion → cross-encoder rerank → self-RAG-style critique → CRAG correction) is coherent, but each layer must earn its latency and cost on your data.

## 9. HyDE for Banking

Banking corpora are a natural HyDE environment: long, declarative, regulation-dense documents queried by humans who use everyday words.

### 9.1 Use Cases

- **Regulatory query answering** — abstract questions like *"What are the compliance implications of moving our risk aggregation to the cloud?"* must bridge to BCBS 239, MAS 610, and GDPR/PDPA text. The user's words barely appear in the documents; HyDE's generated passage names the actual instruments and obligations.
- **Policy and procedure search** — employees ask conversational questions ("how do I approve a new counterparty?") against procedural documents that never phrase it that way. Heavy vocabulary mismatch; classic HyDE territory.
- **Financial research** — abstract research questions ("What drove the widening of credit spreads in Asian financials?") over filings, reports, and news. HyDE concretises the question into claim-like prose that matches report language.
- **Client-facing knowledge assistants** — complex client queries ("what happens to my derivatives positions if the reference entity defaults?") against product documentation written for specialists.
- **Risk and compliance document search** — long regulatory texts with abstract queries; also where multi-draft HyDE (7.4) helps because regulatory answers span multiple documents and interpretations.

### 9.2 Banking Considerations

| Area | What to do |
|------|------------|
| **Latency budget** | HyDE adds an LLM call: regulatory/internal apps tolerate 1–3 s (fine); client-facing chat may not — route those to standard RAG or pre-warm HyDE for known question types |
| **Cost** | HyDE adds generation tokens per query; at enterprise scale use a small/fast model (Claude Haiku, GPT-mini class) for the hypothetical document, and cache hypothetical docs for repeated queries (regulatory FAQs repeat heavily) |
| **Accuracy validation** | Evaluate retrieval quality on banking queries (recall@k, nDCG); A/B test HyDE vs standard RAG on real query logs before rollout; monitor answer quality in production |
| **Data governance** | Hypothetical documents are LLM outputs derived from possibly sensitive queries: log them, redact PII before persistence, apply retention rules, keep an audit trail for regulatory queries, and record which queries triggered HyDE |
| **Explainability** | HyDE is transparent: you can show the user (or an auditor) the hypothetical document *and* the real retrieved sources. Expose both in the audit UI — the synthetic doc explains *why* those sources were chosen |
| **Model risk (SR 11-7)** | HyDE inserts an LLM dependency into the retrieval path. Document the added component (model, version, prompt), validate it as part of the model inventory, log its outputs, and define a fallback to standard RAG if the HyDE LLM fails or degrades (resilience) |
| **Observability** | Track HyDE generation failures/timeouts, retrieval quality metrics, and latency/cost per query type; alert when HyDE's retrieval starts underperforming the query-embedding baseline (drift in the generation model or corpus) |

**Compliance prompt hygiene:** for regulatory queries, the HyDE prompt itself should carry a neutrality instruction (generate the *hypothetical passage* without asserting regulatory conclusions), because the hypothetical doc influences which sources are surfaced — an auditor will want to know it is a retrieval aid, not an interpretation.

## 10. Implementation

### 10.1 Reference Architecture (Pseudocode)

```python
def answer(query, cfg):
    q_type = classify_query(query)                # "simple" | "complex"

    if q_type == "simple":
        results = vector_search(embed(query), k=cfg.k_simple)
    else:
        hyde_doc = llm.generate(HYDE_PROMPT.format(query=query))   # 1-3 drafts
        emb_hyde = embed(hyde_doc)
        emb_query = embed(query)
        rq = vector_search(emb_query, k=cfg.k1)   # query-close neighbourhood
        rh = vector_search(emb_hyde,  k=cfg.k2)   # answer-close neighbourhood
        results = rrf_fusion([rq, rh])

    reranked = cross_encoder_rerank(query, results, top=cfg.top_n)
    context = assemble(reranked)                  # dedupe, truncate, order
    return llm.generate(GENERATION_PROMPT.format(query=query, context=context))
```

Key parameters: `k1=k2=10–20` for the recall stage, `top_n=4–6` after reranking, RRF `k=60`. The HyDE generation call should have its own timeout (e.g., 800 ms) and a failure fallback to the query-embedding path.

### 10.2 Prompt Templates

**Canonical HyDE prompt (from the paper's family):**

```
Write a hypothetical paragraph that would answer the question:
{question}
```

**Document-style variant (better when the corpus is formal):**

```
Write a textbook passage that answers the following question. Be specific,
use domain terminology, and write in declarative prose:
{question}
```

**Banking-domain variant:**

```
In the context of banking regulation and risk management, write a paragraph
from an internal policy document that would answer the following question.
Use the terminology found in Basel/MAS/BCBS documents:
{question}
```

**Style-matched variant (for terse corpora):**

```
Write a short, factual passage in the style of our policy documents that
would answer: {question}
```

### 10.3 Prompt Engineering Guidance

| Lever | Guidance |
|-------|----------|
| **Task framing** | Frame as "write a document/passage" (declarative) rather than "answer the question" — the goal is document-shaped text |
| **Domain hints** | Name the domain and document type ("banking regulation", "policy document", "research report") to pull the generated text toward corpus register |
| **Length control** | Paragraph (100–250 words) is the sweet spot; sentence-length drafts carry too little vocabulary, essays dilute the embedding |
| **Multiple drafts** | Generate 2–3 drafts and keep all (ensemble) or pick the best (e.g., by embedding distance to the query, or simply the first) |
| **Temperature** | Low (0–0.3) for factual domains — hallucination drift is the main HyDE risk; higher (0.5–0.7) only when you deliberately want diverse drafts for multi-hop coverage |
| **Few-shot examples** | Add 1–2 exemplar (query → document-style passage) pairs for unusual corpora (e.g., legal opinions, technical specs) |

### 10.4 Framework Support

- **LangChain** — `HypotheticalDocumentEmbeddings` (LLM + embedder wrapper); pair with `EnsembleRetriever` (query + HyDE) and `ContextualCompressionRetriever` for reranking.
- **LlamaIndex** — `HyDEQueryTransform` inside `QueryPipeline`; `QueryFusionRetriever` with mode `reciprocal_rerank` for the ensemble.
- **Cohere** — Cohere Rerank as the precision stage; Command-R for generation.
- **Custom** — any LLM + any vector store; the whole technique is ~10 lines of glue (10.1).

## 11. Evaluation

HyDE changes retrieval, so evaluation must measure both retrieval quality and final answer quality — and compare against the standard RAG baseline on *your* corpus.

### 11.1 Retrieval Metrics

| Metric | What it measures | Why it matters for HyDE |
|--------|------------------|-------------------------|
| **Recall@k** | Fraction of relevant docs in top-k | The primary HyDE claim — recall for abstract queries should rise |
| **Precision@k** | Fraction of top-k that are relevant | Catches HyDE drift (relevant neighbourhood, wrong docs) |
| **nDCG@k** | Ranking quality with graded relevance | Captures whether the *most* relevant docs rank first |
| **MRR** | Rank of the first relevant doc | For single-answer questions |
| **Hit rate** | Did any relevant doc appear in top-k | Simplest online proxy; easy to log |

### 11.2 Generation Metrics

- **Faithfulness / groundedness** — is every claim supported by retrieved context?
- **Answer relevance** — does the answer address the user's question?
- **Citation accuracy** — do cited chunks actually support the cited claims? (Banking requirement.)
- **RAGAS** (Es et al., 2023) — the standard open-source framework: computes faithfulness, answer relevance, and context relevance (context precision/recall) with LLM-as-judge; a natural fit for comparing RAG vs HyDE pipelines end-to-end.

### 11.3 A/B Testing and Golden Datasets

1. **Build a golden dataset** — 100–300 curated (question, relevant doc IDs) pairs sampled from real query logs, covering the query-type mix: concrete, abstract, conversational, jargon-heavy, multi-hop.
2. **Offline evaluation** — run standard RAG vs HyDE vs ensemble vs ensemble+rerank over the golden set; compare recall@k, nDCG, and per-query-type breakdowns. Decide routing rules from the breakdown (which query classes does HyDE actually help?).
3. **A/B test online** — shadow-test or split traffic on live queries; compare answer quality scores, user feedback, citations used, and latency/cost.
4. **Monitor continuously** — track retrieval metrics and answer quality in production; watch for drift (corpus changes, generation-model changes, query-mix shifts). Alert when HyDE underperforms the query-embedding baseline.

**Suggested evaluation matrix:**

| Query class | Primary metrics | Decision signal |
|-------------|-----------------|-----------------|
| Concrete / entity-heavy | Recall@k, MRR | If already high, HyDE adds cost without value → standard RAG |
| Abstract / conversational | Recall@k, nDCG@k | HyDE's target class — largest expected delta; route here |
| Multi-hop / multi-facet | Recall@k per facet | Consider multi-draft HyDE (7.4) |
| High-stakes / regulatory | Citation accuracy + faithfulness | Ensemble + rerank mandatory; audit the hypothetical doc |

**Practical note:** validate HyDE's benefit per query class before committing to routing — in most banking corpora the win is concentrated in the abstract/conversational minority, which is exactly why routing (7.3) pays for itself.

## 12. Conclusion and Decision Framework

### 12.1 Decision Table

| Corpus type | Query type | Latency budget | Cost budget | Existing retrieval quality | Recommended approach |
|-------------|------------|----------------|-------------|----------------------------|----------------------|
| FAQ / entity-heavy | Concrete, term-matching | Tight (<500 ms) | Tight | Good | **Standard RAG** (query embedding + hybrid) |
| FAQ / entity-heavy | Mixed | Moderate | Moderate | Good | Standard RAG + reranking |
| Policies / regulatory docs | Abstract, conversational | Loose (1–3 s) | Moderate | Poor on abstract queries | **HyDE ensemble + rerank** |
| Policies / regulatory docs | Mixed | Loose | Moderate | Mixed | **Routing**: simple → RAG, complex → HyDE ensemble + rerank |
| Research reports / filings | Abstract research questions | Loose | Comfortable | Poor | **Multi-draft HyDE + ensemble + rerank** |
| Client-facing assistant | Mixed | Tight | Moderate | Mixed | Routing with small HyDE LLM + caching; fallback to standard RAG |
| Any | Unknown (new system) | Moderate | Moderate | Unknown | **Ensemble + rerank default**, evaluate per class, then add routing |

### 12.2 Rule of Thumb

1. **If retrieval quality is already good** (concrete queries, well-aligned embeddings) → keep **standard RAG**. HyDE would add latency and cost without measurable gain.
2. **If retrieval fails on abstract/complex queries** → **try HyDE** — it directly attacks the query–document gap that causes those failures.
3. **If you can afford the latency/cost** → **ensemble (query + HyDE) + rerank** — the most robust configuration; it hedges HyDE's hallucination risk with the query-embedding anchor.
4. **Production default:** ensemble + rerank with query-type routing, a small HyDE generation LLM, caching for repeated queries, and a fallback to standard RAG when HyDE fails.

### 12.3 Key Takeaways

1. **RAG's bottleneck is retrieval, and retrieval's bottleneck is the query–document semantic gap** — not model quality, not chunk size, not index speed.
2. **HyDE removes the gap instead of bridging it** — embedding an LLM-generated hypothetical answer puts the search in the documents' semantic space, zero-shot, with no training or labels.
3. **HyDE is a retrieval strategy inside RAG, not a competitor to it** — the generation stage is unchanged.
4. **Expect dataset-dependent gains** (~15–20% on the paper's abstract-query benchmarks, near-zero on entity-heavy ones) — measure on your corpus before committing.
5. **Ensemble beats either alone** — query embedding + HyDE embedding fused with RRF, then a cross-encoder rerank, is the production recommendation.
6. **HyDE is transparent and auditable** — you can show the hypothetical document and the real sources, which suits banking's explainability and model-risk requirements.
7. **In banking, route, don't blanket-deploy** — most queries are concrete; confine HyDE's latency and cost to the abstract minority that needs it, and validate per query class.
