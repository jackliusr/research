# Agent Loop Implementations Compared — deepseek-harness, Codex, Claude Code and deepagents

> **Standfirst.** Four widely used coding-agent systems, one question asked of each: where does the *loop* live — the cycle that takes a model response, executes the tools it asked for, appends the results, and continues until something says stop — and how is that cycle actually written? This guide answers that from the source code that is public: the DeepSeek Harness agent-loop package, OpenAI's `codex-rs` Rust core, and the LangChain Deep Agents middleware graph. For Anthropic's Claude Code it answers a different and more honest question, because the loop's source is not public: what does the product *document*, and what can and cannot be claimed about a loop you cannot read. The comparison is deliberately narrow. This is not a harness survey, not a TUI review, and not an SDK tour; it is a read of the nine axes that define an agent loop, applied identically to four systems, and then set side by side.

## 1. Overview, Decoder, Scope and Versions

### 1.1 What this guide is

The agent loop is the smallest interesting unit of an agentic system. Everything else — the sandbox, the tool registry, the prompt builder, the TUI, the SDK — exists to serve a cycle that, stripped down, is four moves long: *send the accumulated conversation to a model; read what it wants (text and/or tool calls); execute the tool calls; append the results; repeat until nothing more is asked for.* That cycle is the subject here. It is small enough that four implementations can be read against each other and large enough that the differences between them are real engineering decisions rather than naming preferences.

The finding this guide tests, rather than assumes, is that **the four systems differ most sharply not in *what* the loop does but in *where its control lives*** — and that where control lives determines almost everything downstream: how interruption is delivered, how state is compacted, how a sub-agent is spawned, and what a `stop` even means.

### 1.2 The decoder

These terms are used consistently across all four system sections. Each is defined once here, with a one-line note on how the four systems instantiate it (the full treatment is in the per-system sections).

- **The agent loop** — the repeated cycle that turns a static conversation into a multi-step task: model request → model response → tool execution → result appended → repeat. It is *not* the whole agent (the harness owns prompts, sandboxes, memory, UX); it is the control structure that decides what happens next.
- **The turn** — one user-initiated unit of work inside the loop, from an accepted input to a terminal stop. A turn may contain one model call or many. All four systems have a first-class turn boundary: DSH appends durable `turn/start` and `turn/end` events; Codex models turns through `TurnState` and a per-turn `TurnContext`; Claude Code documents a *per-turn* hook cadence; deepagents inherits LangGraph's step semantics where a turn is one `invoke()`.
- **The tool call** — a model-emitted request to run a named capability with arguments. All four express it as a structured object the harness validates before dispatch.
- **The tool result** — the value produced by executing a tool call, appended to the conversation so the next model call can see it. The pairing of a call with its result is what makes history replayable.
- **The transcript** — the ordered history of everything model-visible (user messages, assistant messages, tool calls, tool results), as distinct from log-only events (stream deltas, lifecycle markers, telemetry). Every system separates these two: DSH appends raw stream frames as log-only and derived messages as surface; Codex keeps `ResponseItemEnvelope`s; deepagents keeps `AnyMessage` state; Claude Code's transcript is only visible indirectly, through `/context` output.
- **The compaction** — any operation that shrinks the transcript so the loop can continue past the context window: summarisation, shadowing, truncation of old tool results, or a hard reset. Compaction is where loop correctness is hardest to preserve.
- **The stop condition** — the predicate that ends a turn. In all four it is *at minimum* "the model produced no further tool calls"; the interesting differences are the additional conditions (token ceilings, stop hooks, depth limits, recursion limits, an operator's cancel).
- **The sub-agent** — a nested agent invoked by a parent loop, usually through a tool call, running its own loop with its own context. The question that matters is always *what the child inherits*: model, tools, permissions, depth budget, history.
- **The steering** — input injected into an *already-running* turn or step, as opposed to input that starts a new turn. Steering is the axis on which the four systems diverge most in naming and least in intent.

**How each system instantiates the decoder (summary).** The per-system sections expand these; the table is a quick orientation so the nine axes read coherently.

| Term | DSH | Codex | Claude Code | deepagents |
|---|---|---|---|---|
| Turn | `turn/start`…`turn/end` events | `TurnContext`/`TurnState`, `TurnCompletedNotification` | per-turn hook cadence; `Stop` | one graph `invoke()` |
| Step | `step/start`…`step/end` | one sampling request inside the turn `loop` | per-tool-call "agentic loop" (documented) | a graph step |
| Tool call / result | `tool/call` + `tool/result` events | `executed_tool_calls` + tool result metadata | `PreToolUse`/`PostToolUse` events | LangGraph tool node messages |
| Transcript | the session log (surface messages) | `Session` history, cloned per request | undocumented; `/context` surface | LangGraph `messages` state |
| Compaction | surface replacement (shadowing) | `CompactionPhase::{PreTurn,MidTurn,PostTurn}` | `PreCompact`/`PostCompact` hooks | summarisation middleware (trigger/keep) |
| Stop condition | 5 `turn/end` reasons; no turn budget | `needs_follow_up`; stop hooks; window rollover | `Stop` (blockable) | base stop + `recursion_limit` |
| Sub-agent | `subagent` package; depth; approval pinned `never` | spawned thread; permission intersection | `SubagentStart`/`SubagentStop` | `task` tool; isolated or fork |
| Steering | durable inbox targets `next-step`/`next-turn` | `TurnSteerParams` + preempt token | `UserPromptSubmit`; `Stop` block | none first-class (runtime interrupts) |

### 1.3 Scope statement

**In scope:** the control structure of the loop; the turn/step machine; how conversation state is held and compacted; how tools are registered and dispatched; how interruption, steering and cancellation reach a running loop; how nested agents are spawned; how streaming is surfaced; how errors and retries are handled; and how the loop terminates. Every claim is a claim about an agent loop.

**Out of scope, deliberately:** the sandbox *implementation* (Docker/seatbelt/landlock internals), the terminal UI, the CLI argument surface, the SDK bindings, the model client's wire protocol, and prompt-engineering content. Where a system's loop touches one of these, it is named only as far as the loop's control flow requires.

**Boundary against the sibling guides.** This guide does not re-derive any taxonomy or landscape. The harness concept and the ETCLOVG layering live in [agent_harness_engineering_guide.md](agent_harness_engineering_guide.md); the scaffolding layer above the loop lives in [agent_scaffolding_guide.md](agent_scaffolding_guide.md); the market and benchmark view of coding agents lives in [coding_agents_research.md](coding_agents_research.md); the operational runbook for running Deep Agents under a CLI lives in [deepagents_copilot_cli_guide.md](deepagents_copilot_cli_guide.md). This guide is the layer those four point at when they say "the loop" and do not open it.

## 2. The Four Projects, Verified

Before any loop is read, the question "can this even be read?" has to be answered per project, because for one of the four the answer changes the whole method.

### 2.1 deepseek-harness — public, and structured for a loop to be replaceable

**What it is.** DeepSeek Harness (DSH), self-described as "DeepSeek Harness: Everything is a Plugin." It is a pnpm/TypeScript monorepo: `packages/`, `apps/`, `native/`, `python/`, `vendor/`, `docs/`, `benchmarks/`. It carries an `AGENTS.md` (17 KB), `SAFETY.md`, and a 24 KB `THIRD_PARTY_NOTICES.md`.

**Language:** TypeScript. **Licence:** MIT (plus third-party notices). **Loop source public?** Yes, and unusually cleanly delimited: the loop is its own package, `packages/core/agent-loop/`, published as `@deepseek-ai/dsh-agent-loop`. **Version read:** commit `5badb15009ae1756c3afe0ae0cef1faafc290ccc` (tag `dsh-v0.2.1-alpha.1`, `master` HEAD).

**Honest consequence.** There is no stable release; the newest tag equals the branch head, so this is alpha code read at a moving point on `master`. The package's own README enumerates "Known Limitations and Deferred Work", several of which are loop-relevant (there is no built-in turn budget, and parallel-safety classification is unary). The guide reads the alpha and says so.

### 2.2 OpenAI Codex — public, but the loop is not one file

**What it is.** "Lightweight coding agent that runs in your terminal." A Rust workspace (`codex-rs/`) plus a TypeScript CLI/SDK (`codex-cli/`, `sdk/`, `docs/`), built with Bazel (`MODULE.bazel`, `BUILD.bazel`).

**Language:** Rust. **Licence:** Apache-2.0 (`LICENSE` ~10.9 KB, `NOTICE` present). **Loop source public?** Yes. **Version read:** commit `0b47040dc9eb08d9c37d51e0824870ce5b27101b` (`main` HEAD at read); latest published release `rust-v0.160.1`.

**Honest consequence.** Codex is the largest and most coupled of the three readable systems: the loop logic is spread across `session/turn.rs` (≈3,200 lines at this commit), `tasks/`, `compact.rs`, `tools/`, and `agent/control/`. A reader cannot point at one function named "the loop"; the loop is an emergent product of a task trait, a session, and a turn driver. This guide therefore describes *where* the loop is assembled and *which* structures carry it, and does not pretend a single file owns it.

### 2.3 Claude Code — the loop source is not public, and this guide will not pretend otherwise

**What it is.** The public repository `anthropics/claude-code` is the *distribution, documentation, plugin, and issue-tracker* repository for a proprietary product. At the commit read, the complete root listing is: `.claude-plugin/`, `.claude/`, `.devcontainer/`, `.github/`, `.vscode/`, `CHANGELOG.md` (≈945 KB), `CLAUDE.md`, `LICENSE.md`, `README.md`, `SECURITY.md`, `Script/`, `demo.gif`, `examples/`, `feed.xml`, `mods/`, `plugins/`, `scripts/`. **There is no `src/` directory and no application source for the agent.**

**Language:** the API reports TypeScript, but that reflects plugin and example content, not the product's loop. **Licence:** proprietary — `LICENSE.md` reads in full, "© Anthropic PBC. All rights reserved. Use is subject to Anthropic's Commercial Terms of Service." The GitHub API returns `license: null` (no OSI licence). **Version read:** commit `fbe20e00e2851fc01506f54f98a8f0b875af3847` (tag `v2.1.292`).

**Public?** No. The loop ships as a compiled binary. The README states installation via a `curl` install script, a Homebrew cask, WinGet, or `npm install -g @anthropic-ai/claude-code` (marked deprecated), and points to `https://code.claude.com/docs/en/overview` — i.e. the loop is *documented*, not *shipped as source*.

**What this guide will and will not claim about Claude Code.** This is the single most important honesty constraint in the study, so it is stated flatly:

- **It will** describe Claude Code's *documented* loop-adjacent behaviour, and label every such statement **documentation-derived**, citing the page it came from (fetched 2026-10-06). The documented hook lifecycle — per-session, per-turn, and per-tool-call events including `PreToolUse`, `PostToolUse`, `PostToolBatch`, `Stop`, `StopFailure`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`, `PermissionRequest`, `PermissionDenied` — is strong evidence *about the shape of the loop's seams*, because those are exactly the boundaries a loop must expose. It uses the repository's own files (`README.md`, `LICENSE.md`, `SECURITY.md`, `CLAUDE.md`, `plugins/README.md` and the plugin directories, `examples/hooks/`, `examples/settings/`) as primary evidence for what the product exposes. It notes one structurally interesting fact: the repository contains a plugin, `plugins/ralph-wiggum/`, whose README describes "interactive self-referential AI loops" implemented by *intercepting the `Stop` event*, with `/ralph-loop` and `/cancel-ralph` commands — loop control expressed entirely through the public hook seam.
- **It will not** describe Claude Code's internal control flow as fact: no file paths, no function names, no class names, no line numbers, no claims about how its loop is written, because none of that is readable. Where the guide needs a mechanism it cannot read, it says what the *documented contract* implies and marks it as the guide's inference, not a source-derived observation.

A useful third-party cross-reference survives here: DeepSeek Harness ships `packages/subagent/subagent-claude-code/` (providing `run.ts`, `process.ts`) and `packages/hooks/hooks-claude-code/`, i.e. a third party writes adapters to Claude Code's sub-agent and hook surfaces. That is independent evidence about the *shape* of those documented contracts — nothing more, and nothing about the loop's internals.

### 2.4 deepagents — the graph is public, the step loop is not in this repository

**What it is.** "The batteries-included agent harness." A monorepo: `libs/deepagents` (Python library), `libs/code` (a Textual TUI, package `deepagents_code`), `libs/acp` (an Agent Client Protocol server, package `deepagents_acp`), plus `examples/` and `action.yml`.

**Language:** Python. **Licence:** MIT (root `LICENSE` ~1,067 bytes; per-package licences under `libs/deepagents/` and `libs/code/`). **Version read:** commit `9a91d79e18dacfe900ac62e59c756e87f3b586a7` (`main` HEAD); release `deepagents==0.7.22` targets commit `dcba42543955cadd63718f64ba0165864e7323ad`.

**Loop source public?** Partly, and the split matters. `libs/deepagents/deepagents/graph.py` imports `from langchain.agents import AgentState, create_agent` and `from langchain.agents.middleware import HumanInTheLoopMiddleware, InterruptOnConfig`. Its own module docstring calls `create_deep_agent` "the main entry point for constructing a fully configured deep agent with planning, filesystem, subagent, and summarization middleware". The repository's own `libs/ARCHITECTURE.md` puts it unambiguously: "Deep Agents sits on top of LangChain and LangGraph … LangChain builds the loop that calls the model, executes tools, and repeats until the model finishes; the runtime layer provides durable execution."

**Honest consequence.** The *step loop primitive* — model call, tool execution, repeat — is provided by the `langchain` package (and LangGraph beneath it), which is **not in this repository**. What deepagents contributes and what this guide therefore reads is the **graph assembly, the middleware stack, the state reducers, and the backends that surround the loop**. The version the loop primitive belongs to is the dependency range pinned in `libs/deepagents/pyproject.toml`: `langchain>=1.4.3,<2.0.0`, with `langchain-core>=1.6.6,<2.0.0`. This guide does not claim to have read LangChain's loop source; it read deepagents' assembly of it, and says so on every relevant claim.

## 3. The Common Shape, Defined Once

Every one of the four loops, however differently written, is an instance of one canonical shape. Stating it once makes the per-system sections comparable, because each system can then be described as *a particular commitment* about each line.

### 3.1 The canonical loop

```
turn:
  append accepted user input to history
  repeat:
    request = derive(history)          # messages + system prompt + tool schemas
    response = call_model(request)     # may stream
    append assistant output to history
    calls = extract_tool_calls(response)
    if calls is empty:
      stop(turn, reason = completed)   # the base stop condition
    for each call in calls:
      result = dispatch_and_execute(call)
      append result to history
    # loop continues
```

The five load-bearing pieces are: **(1)** how `derive(history)` is computed and when the transcript is compacted; **(2)** whether `call_model` can be interrupted or steered mid-flight; **(3)** how `dispatch_and_execute(call)` gates, sandboxes and approves the call; **(4)** how results are ordered when calls run concurrently; and **(5)** every condition beyond "no tool calls" that can end the turn. A loop's character is almost entirely determined by those five.

### 3.2 The documented variants

Across the four systems the canonical shape appears in four recognisable variants:

- **The event-sourced step machine.** The loop is a small state machine whose every transition is appended to a durable log, and each new request is *derived* from that log rather than held in a mutable variable. DSH is this variant in its purest form: its module header says "Every request is derived from the session log", and turns and steps are bracketed by `turn/start`, `step/start`, `step/end`, `turn/end` events.
- **The supervised task turn.** The loop is one method of an async task that a supervisor owns; the turn itself is an inner `loop` whose exit conditions include token budget, pending input, and stop hooks. Codex is this variant: a `SessionTask` trait with a `RegularTask` implementation whose `run` drives `run_turn`, itself a `loop` that can roll the context window over mid-turn.
- **The middleware-wrapped graph step.** The loop is a graph step owned by an external runtime; the harness contributes only the middleware that runs before/around a model call and around tool execution. deepagents is this variant: `create_deep_agent` assembles middleware and hands it to `langchain.agents.create_agent`.
- **The hook-and-plugin loop.** The loop is closed source, and the only places an integrator can *reach* it are lifecycle hooks and plugin commands. Claude Code is this variant *as documented*: the loop is not visible, but its boundaries (`PreToolUse`, `PostToolUse`, `Stop`, `PreCompact`) are.

### 3.3 What is invariant across all four

Three things hold for every system studied:

1. **The base stop condition is "no further tool calls."** No system continues a turn when the model's response requests nothing to execute. Everything else is an *additional* stop condition layered on top.
2. **History is the only state the model sees, and it is append-mostly.** All four append user messages, assistant messages, calls and results, and derive each request from that history; none passes out-of-band state into a model call except through a context section that is itself part of the request.
3. **Compaction is a distinct, named operation with a failure mode.** Every system has a compaction path, and in every system a failed or badly-timed compaction is a correctness risk rather than a cosmetic one — which is why each raises it to a first-class phase (DSH: "surface replacement"; Codex: `CompactionPhase::{PreTurn, MidTurn, PostTurn}`; deepagents: a summarisation middleware with a trigger/keep pair).

The divergences in §9 all sit on top of that invariant substrate.

### 3.4 The canonical loop, traced in one turn

To make the comparison concrete, here is the canonical loop walked once against a single user request ("fix the failing test"), with the *names* each system uses. This trace is the reference the per-system sections annotate.

1. **Admit input.** The user message is accepted and recorded. DSH appends a `user/message` surface event and places the input in an inbox; Codex records it through `run_hooks_and_record_inputs`; deepagents adds it to graph state; Claude Code fires `UserPromptSubmit` (documented).
2. **Open the turn.** DSH appends `turn/start`; Codex has already established a `TurnContext`; deepagents is inside an `invoke()`; Claude Code's turn begins when the prompt is processed.
3. **Derive the request.** Messages, system prompt and tool schemas are assembled from history. DSH calls `session.deriveMessages()` and logs `request/header`; Codex clones history with `for_prompt(...)` under a `StepContext`; deepagents' middleware assembles the system prompt and the tool list; Claude Code's request is not observable.
4. **Call the model, streaming.** Output arrives incrementally. DSH pushes deltas into an `AssistantStreamAttempt` and emits `agent/assistant-stream`; Codex consumes response events and parses assistant text; deepagents relies on LangGraph streaming; Claude Code fires `MessageDisplay` (documented).
5. **Append the assistant message.** DSH appends `assistant/message` (or `assistant/attempt` on failure); Codex records the response items; deepagents appends `AnyMessage` values; Claude Code's persistence is not documented.
6. **Extract tool calls; stop if none.** This is the base stop condition. If the model asked for nothing, the turn ends here: DSH returns `completed`, Codex computes `needs_follow_up = false`, deepagents leaves the tool node, Claude Code reaches `Stop`.
7. **Dispatch the batch.** Calls run in parallel up to a limit, or exclusively. DSH's `runGroup` fills a bounded pool and commits in model order; Codex's `ToolCallRuntime` takes read or write guards on its `RwLock`; deepagents invokes the tools through the graph tool node; Claude Code resolves the batch and fires `PostToolBatch` (documented).
8. **Gate each call.** Approval and sandbox apply. DSH's user-approval subsystem and permission presets; Codex's `request_*_approval`; deepagents' `interrupt` permission → `HumanInTheLoopMiddleware`; Claude Code's `PreToolUse` block and permission rules.
9. **Append results, paired to calls.** DSH appends `tool/result` citing the `tool/call` seq; Codex appends response items with metadata; deepagents appends `ToolMessage`s; Claude Code fires `PostToolUse`/`PostToolUseFailure` (documented).
10. **Continue or compact.** If the token budget is pressing, compaction runs first. DSH shadows older nodes via a surface replacement; Codex rolls over (`PreTurn`/`MidTurn`/`PostTurn`); deepagents' summarisation middleware triggers at its threshold; Claude Code fires `PreCompact`/`PostCompact` (documented). Then back to step 3.

The per-system sections that follow differ only in *how each of these ten moves is implemented, named, and bounded* — which is precisely the point of the study.

## 4. The Comparison Axes

The nine axes below are used verbatim in every per-system section, in this order. Each is defined so a reader knows exactly what is being compared.

- **(a) Where the loop physically lives.** The file or package that owns control, named by path. This axis distinguishes "one file you can read top to bottom" from "an emergent property of several modules" from "not in this repository at all".
- **(b) Control structure.** Which of four shapes the loop takes — a plain imperative `while` loop, recursion, an explicit state machine, or an event stream — and whether the loop is synchronous within a turn boundary or suspended and resumed around asynchronous inputs.
- **(c) Conversation and context state.** Where the transcript is stored (in-memory variable, durable log, graph channel), how a model request is derived from it, and the trigger and mechanism by which it is compacted or truncated.
- **(d) Tool registration, schema, dispatch, sandbox, approval.** How a tool becomes visible to the model (registry), how its arguments are schematised, how a call is routed to an executor, how execution is confined (sandbox), and where a human or policy approval can gate it.
- **(e) Interruption, steering and cancellation.** How a caller reaches a *running* loop: what a cancel does to an in-flight model call, whether new input can be delivered to the current step or only queued to the next turn, and what guarantees hold about already-streamed output.
- **(f) Sub-agents and nested loops.** How a child agent is started, and — the operative question — what it inherits (model, tools, permissions, depth budget, conversation history) and what bounds its depth.
- **(g) Streaming.** How model output is surfaced incrementally, and how streamed frames relate to the durable transcript.
- **(h) Errors and retries.** What happens when a model call fails, a tool fails, or a step fails partway, and which failures are retried versus surfaced versus turned into synthetic results.
- **(i) Termination.** Every condition that ends a turn, a step, or a task — not just "the model stopped asking for tools", but budget ceilings, hook vetoes, depth limits, and operator actions.

Two meta-axes are used only in §9, because they are comparisons *between* systems rather than within one: **what the operator can change without editing the loop** (extension seams), and **what the loop guarantees about its own history** (integrity properties).

## 5. deepseek-harness — the loop as a replaceable package driving a session log

**Version read:** commit `5badb15009ae1756c3afe0ae0cef1faafc290ccc` (tag `dsh-v0.2.1-alpha.1`, `master` HEAD), 2026-10-06. **Licence:** MIT. **Loop source:** public.

**(a) Where the loop physically lives.** In one package and, overwhelmingly, in one file. The plugin entry is `packages/core/agent-loop/src/index.ts` (registers the `AgentLoop` service, the configuration schema, declarative agent startup, and the `AgentFactory` on `ctx.agents`). The driver is `packages/core/agent-loop/src/agent.ts`, whose header comment reads "Default Agent driver over queued turns and step-boundary input. Every request is derived from the session log." The class is `ReactLoopAgent`, and it `implements Agent`. Three sibling files carry the parts that would otherwise bloat the driver: `inbox.ts` (the `ReactLoopInbox`), `tool-calls.ts` (`executeToolCalls`), and `assistant-stream.ts` (`AssistantStreamAttempt`), with `runtime-context.ts` projecting per-step context and `constants.ts` holding `DEFAULT_MAX_PARALLEL_TOOL_CALLS`. The package README describes itself as "the one concrete implementation of the public `Agent` contract" and advises choosing a custom `Agent` "only when the standard 'call model, run tools, repeat' lifecycle is insufficient". This is the most legible "where does the loop live" answer of the four: a named package, a named class, a named trait-like contract (`Agent`) it satisfies.

**(b) Control structure.** An **event-sourced step machine driven by two nested imperative loops**. The `Phase` type in `agent.ts` is a three-way union — `{kind:'idle'} | {kind:'maintenance'} | {kind:'running', turn, step}` — so the *outer* structure is a small state machine; but within the running phase the driver is plain loops. The entry point `kick()` is literally `try { while (await this.turn()) {} } catch { … } finally { … }` — the task loops turns until `turn()` returns false. `turn()` opens with `this.session.append('turn/start', {turn})`, then runs `while (true)` over steps: it computes `step = phase.step + 1`, calls `preStep(...)`, rejects on a `blocked` decision, appends `step/start`, calls `this.step(decision)`, and appends `step/end` in a `finally`. It exits when a step has set `turnEnds` **and** `this.inbox.nextStep.length === 0`, then appends `turn/end` with a `TurnEndReason`. `step()` is itself a `while (true)` loop — a retry loop, not a step loop: each iteration builds a request, streams it, and either continues (on a retry decision), returns `{kind:'max-tokens'}`, returns `{kind:'completed'}` when the assistant produced no tool-call blocks, or calls `executeToolCalls(...)` and returns `completed` if a tool concluded the turn, else `null` (meaning "keep going"). Cancellation does not unwind by exception alone: it is read from `signal.throwIfAborted()` at each boundary, and `Phase` transitions are published through `setPhase`, which emits `agent/status` on change.

**(c) Conversation and context state.** The transcript **is the session log**, and the loop owns no separate copy. Every model request is reconstructed inside `buildRequest(...)` from `session.deriveMessages()`, `session.requestHeader()`, `session.requestContext()`, and `session.toolHistory()`; the loop also *logs* what it sent (`request/header`, `request/context`, and a `request/header {reason:'change'}` when the envelope or tool set changes). The module header's "every request is derived from the session log" is not a slogan — it is what `frozenMessages` and the deep-freeze of each derived message identity enforce, so that a resumed session and a live one derive the same request. Model visibility is restricted: raw stream frames and lifecycle markers are log-only, while user messages, assistant messages, tool calls and results are *surface* messages (`surfaceOp: 'append'`). **Compaction** is expressed as a "surface replacement" that *shadows* older nodes: the README says input "grows with every surface message until a compaction replacement shadows older nodes", and that a replacement "invalidates reuse from the first shadowed history token". The compaction mechanics live in a separate package family: `packages/compaction/compaction-basic/src/summarizer.ts` implements `summarizeWithLlm`, which replays the conversation prefix and appends a compaction instruction as the *final user message* (deliberately, to reuse the provider's warm prefix cache), then `frameSummary` wraps the result in `<compacted-summary>` tags under a checkpoint preamble; `packages/compaction/compaction-basic/src/{config.ts,region.ts}` carry the configuration and the region selection. Sibling compaction packages (`compaction-tool-result-pruner`, `compaction-image-offload`, `command-compact`) show the design intent that compaction is *pluggable and per-region*, not one monolith.

**(d) Tool registration, schema, dispatch, sandbox, approval.** The loop does not own the tool registry; it consumes `ctx.tools` and a scheduler service. Dispatch is the job of `tool-calls.ts`. Its docstring states the contract precisely: "Exclusive calls form barriers; parallel calls use a bounded rolling pool and are reclassified before start. Dispatch may overlap, while policy, results, and result context remain model-ordered." The entry point `executeToolCalls(ctx, turn, step, toolCalls, signal, acceptContext)` walks the calls in model order, asks `ctx.tools.executionMode(first.exec).kind` for the mode, groups a parallel run or isolates a single exclusive call, and calls `runGroup(...)`. `runGroup` implements the rolling pool: `fillPool` starts calls while `inFlight.size < maxParallelToolCalls`, and `commitReady` advances a `committed` cursor only across *contiguous* model-order slots, so results and any "additional contexts" commit in the order the model emitted them even though dispatch overlapped. `maxParallelToolCalls` defaults to `10` (README field table; `DEFAULT_MAX_PARALLEL_TOOL_CALLS` in `constants.ts`) and is re-read per group. Each call goes `prepare` → `dispatch`/`post-result`/`final-result` on `ctx.tools[TOOL_RUNTIME_SCHEDULER]`. **Approval** is a separate subsystem (`packages/interaction/user-approval/`, `packages/interaction/permission-presets/`) and **sandboxing** another (`packages/sandbox/…`), reached through `ctx.get(...)` rather than hard dependencies. One loop-visible safety behaviour is worth naming: when the set of visible tools changes between requests, `buildRequest` appends a `developer/message` listing the tool additions and removals, so the model is told its capabilities moved.

**(e) Interruption, steering and cancellation.** This is where DSH is most explicit, and the vocabulary is clean. `send(message, target, wakeup)` is the primitive; three thin wrappers name the intents: `followup(input)` = `send(input, 'next-turn', true)`, `steer(input)` = `send(input, 'next-step', true)`, and `inject(input)` = `send(input, 'next-step', false)`. The **target** decides where input lands — the next step of the current turn, or the next turn — and **wakeup** decides whether it starts a driver. The inbox is durable and projected: every mutation commits one `agent/inbox/spliced` event, and `inbox.ts` folds it synchronously (targets `next-turn` and `next-step`, with claim-by-deletion and `agent/inbox/{claimed,inserted,discarded}` notifications). **Cancellation** is cooperative through `AbortController`: `cancel(cause, options = {})` clears the inbox unless `keepInbox` is set, and aborts the current phase's signal with an `AgentCancelCause` whose `kind` is one of `user`, `parent`, `disposed`, or `hook` (with `reason` for hooks). `abortedCancelCause` deliberately *copies* only the recorded fields into `turn/end`, because Node's `fetch` may attach a live `stack` to the caller's reason object that the log must not absorb. Two guarantees are stated in the README and visible in `step()`: **"Cancellation preserves streamed text already delivered to the user"** — on an aborted stream the loop settles `live.interruptedBlocks()` as an `assistant/message` with `interrupted: true` — and a cancelled step's undispatched tool calls receive synthetic `tool/call` + `tool/result` pairs with error code `ABORTED_BEFORE_DISPATCH`, so replay stays valid.

**(f) Sub-agents and nested loops.** Delegation is a first-class package, `packages/subagent/`, with a shared composition module at `packages/subagent/subagent/src/child-agent.ts`. Because it is the parent that composes the child, the file is where inheritance is *defined* rather than inferred. `resolveChildDepth(parent, maxDepth)` computes `delegationDepthOf(parent) + 1` and throws `SubagentDepthError` above an optional cap — the persisted parent header is the monotone floor, "so a resumed parent cannot delegate as if it were top-level". `resolveChildAgentOptions` inherits the parent's provider, model, reasoning-effort and `maxTokens` (with the parent's *latest request header* winning over its creation options) and stamps `subagentDepth` on the child. `childSessionMeta` persists `parentSession`, `isSeeded`, `origin: 'subagent'`, and the durable `delegationDepth`, precisely so "a cold read of the child" reconstructs the composition it actually ran under. Most consequential for governance, `captureDelegatedPolicyOverrides` and `appendDelegatedPolicyOverrides` **pin the child's approval policy to `'never'`** and append it to the child's own log as `source: 'delegation'` events: a delegated child "acts only within the sandbox scope fixed at delegation, so its asks are rejected deterministically". `applyChildComposition` joins the child to the parent's preset *and* registers the model-facing `SUBAGENT_DELEGATION_CONTEXT` string, and the multi-backend roster (`.claude-code`, `.codex`, `.acp`, `.dsh-sdk`, in-process drivers) shows sub-agents are a seam, not a hardcoded call.

**(g) Streaming.** Streaming is surfaced as its own object and event family. `AssistantStreamAttempt` (in `assistant-stream.ts`) is constructed per attempt with a revision counter and an emit callback that publishes `agent/assistant-stream` frames; the driver pushes each streamed delta into the attempt as it arrives. The README pins the ordering guarantee — one process-local `start`, streamed deltas emitted only after the matching durable assistant-frame settlement, and exactly one terminal `end` — with `committed` following the durable `assistant/message` and `aborted` following a failed final append. The durable transcript and the stream are therefore kept consistent: nothing is shown as streamed that was not also settled.

**(h) Errors and retries.** Failures are structured, not stringly-typed. In `step()`, a terminal stream finish with `kind: 'error' | 'aborted'` enters the `agent/request-error` waterfall; a listener may return `{kind:'retry'}`, in which case the `while (true)` continues and re-streams — otherwise the failure throws as an `LlmError` carrying a `.failure` with a code. In `turn()`, a step failure triggers *recovery*: the driver replays `toolRecovery.results()` (collected by observing `session/event` through a `ToolCallRecovery`) as `tool/result` events, and if that itself fails it throws an `AggregateError` rather than silently losing the tool results. Unanswered calls likewise receive deterministic synthetic results so that the log never holds a call without a result; the specific code-name constants on that path could **not** be located in any of the seven files of `packages/core/agent-loop/src/`, so none is named here (§15 row 39, §16.1 item 12). The turn's ending is resolved by inspecting the abort signal: "a cause is present exactly while the signal is aborted", so an abort becomes `{kind:'aborted', reason: cause}` and anything else becomes `{kind:'error', error: {message, code}}`. Plugin, middleware and result-processing failures are thrown and close the turn — the README's framing is deliberate: "plugin failure ends the turn, not the loop".

**(i) Termination.** Three levels. A **step** returns when the assistant produced no tool-call blocks, or when a tool result carried `concludesTurn`, or on max-tokens, or when a retry waterfall declines to retry. A **turn** ends when `turnEnds` is set and no `next-step` input remains, with exactly one of five reasons appended to `turn/end`: `completed`, `max-tokens` (sticky — a later completed step cannot downgrade it), `aborted` (carrying the cancel cause), `error`, or `blocked` (a `reject`ing `agent/pre-step`). A **task** ends when `turn()` returns false, i.e. no pending inbox work. Notably, there is **no built-in turn budget**: the README lists it as a known limitation and says a policy bounding runaway turns "must cancel from an existing lifecycle extension point such as `agent/turn-stopping`". So DSH's termination guarantee is structural (no pending work ⇒ stop) plus whatever the operator attaches at `agent/turn-stopping`.

**What is distinctive about this implementation.** DSH is the only one of the four whose loop is *a self-contained, replaceable package that treats the session log as the single source of truth and reconstructs every request from it*. That choice cascades: because the transcript is a durable log, steering can be modelled as durable inbox splices with two named targets; because compaction is a *surface replacement* that shadows nodes rather than a mutation, the log stays append-only; because every effect "happens through session events and the `agent/*` taxonomy", a plugin can observe, intercept (`agent/pre-step`, `agent/request`, `agent/request-error` waterfalls) or veto without touching the loop. The cost of that purity is visible too: the README itself admits there is no turn budget and that parallel-safety classification is unary, so the clean seam set is not yet a complete control set.

### 5.1 The loop's extension seams, in one list

Because the guide argues that DSH's distinctiveness is its seam set, the seams are worth naming together. Read from `agent.ts`, the driver's own README, and `inbox.ts`:

- **`agent/pre-step`** (waterfall) — runs before each step; may return `enter` (optionally rewriting the message batch) or `reject`, which ends the turn as `blocked`.
- **`agent/request`** (waterfall) — proposes the `LlmCallConfig` for the next model call after adapter defaults are stripped.
- **`agent/request-error`** (waterfall) — receives a terminal stream failure and may return `{kind:'retry'}`.
- **`agent/turn-stopping`** (serial) — fires when a step has set a turn end and no `next-step` input remains; the documented place to attach a runaway-turn policy.
- **`agent/status`, `agent/error`, `agent/assistant-stream`** (emitted) — external state transitions, failures, and streamed frames.
- **`agent/created`** and the **`agent/inbox/*`** family — creation listeners and the durable inbox notifications (`inserted`, `claimed`, `discarded`, and the `agent/inbox/spliced` fold).

A builder can therefore intercept the loop *before a step*, *before a request*, *after a request failure*, and *at the moment it is about to stop*, plus observe its status and stream — all without editing the driver. That is a materially larger set of pre-action and pre-stop seams than any of the other three exposes at loop level.

## 6. OpenAI Codex — the loop as a task supervisor over a session

**Version read:** commit `0b47040dc9eb08d9c37d51e0824870ce5b27101b` (`main` HEAD at read), 2026-10-06; latest release `rust-v0.160.1`. **Licence:** Apache-2.0. **Loop source:** public, but distributed.

**(a) Where the loop physically lives.** There is no single "loop" file; control is assembled from four layers inside `codex-rs/core/src/`. The **task contract** is `tasks/mod.rs`, whose docstring is the clearest map: "Async task that drives a [`Session`] turn. Implementations encapsulate a specific Codex workflow (regular chat, reviews, ghost snapshots, etc.). Each task instance is owned by a [`Session`] and executed on a background Tokio task." The trait there is `SessionTask`, with `kind()`, `span_name()`, `run(self: Arc<Self>, session, ctx, input, cancellation_token)`, and `abort(...)`. Its declared submodules — `compact`, `lifecycle`, `regular`, `review`, `user_shell` — are the task *kinds*. The ordinary chat path is `tasks/regular.rs` (`RegularTask`), which calls into `session/turn.rs` (`run_turn`). The state that carries a turn lives in `session/turn_context.rs` (`TurnContext`) and `state/mod.rs` (which re-exports `RunningTask`, `TaskKind`, `TurnState`, `ActiveTurn`, `SessionState`, `SessionServices`, `AutoCompactWindowIds` and `TurnTokenUsage` from `state/turn.rs`, `state/session.rs`, `state/service.rs` and `state/turn_token_usage.rs`). The turn's *protocol* surface is mirrored in `codex-rs/app-server-protocol/schema/json/v2/`: `TurnStartParams.json`, `TurnStartedNotification.json`, `TurnCompletedNotification.json`, `TurnInterruptParams.json`, and `TurnSteerParams.json`.

**(b) Control structure.** A **supervised, multi-loop async structure** — no recursion, no explicit state-machine enum, but three nested imperative loops each with a distinct responsibility. The outer loop is in `RegularTask::run`: after per-turn lifecycle setup it enters `loop { let last_agent_message = run_turn(...).await?; if ctx.terminal_error.lock().await.is_some() { return Ok(…) } if !sess.input_queue.has_pending_input(&sess.active_turn).await { return Ok(…) } next_input = Vec::new(); }`. So a single task keeps re-entering `run_turn` while steered input keeps arriving. The middle loop is inside `run_turn` (a `loop` beginning in `session/turn.rs`): each iteration captures a `StepContext`, records pending input, computes a sampling-request input slice, calls `run_sampling_request(...)`, then branches on `model_needs_follow_up`, `has_pending_input`, `token_limit_reached`, and `should_roll_over` — a decision that may trigger auto-compaction and `continue`, or call stop hooks and `break`. The innermost loop is `run_sampling_request`, which re-issues the request while retries remain (`loop { … handle_response_stream_error(&mut retry_state, max_retries, …) }`) and returns a `SamplingRequestResult { needs_follow_up, last_agent_message }`; beneath it `try_run_sampling_request` owns a fourth loop that consumes the response stream. The overall shape is therefore *a supervisor over a turn loop over a retry loop over a stream loop* — control expressed by nesting, not by a state enum.

**(c) Conversation and context state.** The conversation lives in the `Session`, and each model request is a fresh derivation: `run_turn` builds `sess.clone_history().await.for_prompt(&step_context.settings.model_info.input_modalities)`. Per-step configuration is captured in a `StepContext` (via `capture_step_context_with_required_mcp_servers`) that "capture[s] once so context, advertised tools, and tool calls share one request view". **Compaction** is the most elaborated of the four. `session/context_window.rs` computes `context_window_token_status`, including `token_limit_reached` and `turn_end_compaction_threshold_reached`; `compact.rs` provides `run_compact_task`, `run_inline_auto_compact_task`, `build_compaction_replacement_history` and `build_compacted_history`, and exposes the prompt material `SUMMARIZATION_PROMPT` and `SUMMARY_PREFIX`. Compaction is *phased*: `CompactionPhase::{PreTurn, MidTurn, PostTurn}` with `CompactionReason::ContextLimit`. The turn loop calls `run_pre_sampling_compact` before recording new input (so that a failure can preserve the input), calls `run_auto_compact` mid-turn when `should_roll_over` is set, and calls it again post-turn when `model_post_turn_compact_threshold_percent > 0`. There is a distinctive safety comment on the roll-over path: "as long as compaction works well in getting us way below the token limit, we shouldn't worry about being in an infinite loop" — i.e. the loop trusts compaction to terminate the roll-over. Separate packages (`compact_token_budget.rs`, `compact_remote_v2.rs`, `compact_model_fallback.rs`, `state/auto_compact_window.rs`) show that, as in DSH, compaction is plural.

**(d) Tool registration, schema, dispatch, sandbox, approval.** Tools are typed runtimes behind a trait: `tools/registry.rs` declares `CoreToolRuntime: ToolExecutor<ToolInvocation>` and carries the hook integration (`run_pre_tool_use_hooks`, `run_post_tool_use_hooks`), with `AnyToolResult` as the boxed outcome. Routing is `tools/router.rs` (`ToolRouter`, re-exported from `tools/mod.rs`). Dispatch and concurrency are in `tools/parallel.rs`: `ToolCallRuntime` holds `parallel_execution: Arc<RwLock<()>>` and exposes `handle_tool_call(call, cancellation_token)`, which prepares a recorded call via `sess.services.executed_tool_calls`, runs it, and attaches result metadata. The `RwLock` is the key structural fact: read-guards allow parallel tool execution while a write-guard is the exclusive barrier — the same parallel-versus-exclusive idea as DSH's `executionMode`, implemented with an async reader/writer lock rather than a scheduler pool. **Sandbox** and **approval** are explicit subsystems: `tools/sandboxing.rs` defines `ApprovalStore`, `ExecApprovalRequirement`, `SandboxOverride`, `SandboxAttempt`, `ToolCtx`, and `default_exec_approval_requirement`, plus `sandbox_override_for_first_attempt` (escalation after a sandboxed failure that `escalate_on_failure` permits); `tools/approvals.rs` defines `ApprovalContext`, `ApprovalAction`, and the three approval paths `request_user_approval`, `request_guardian_approval`, `request_reviewer_approval`. Execution policy is a large, separate module (`exec_policy.rs`).

**(e) Interruption, steering and cancellation.** Codex models steering as *input preemption of an in-flight stream*, and it is unusually concrete. `TurnSteerParams.json` is a first-class app-server request; `TurnInterruptParams.json` requires exactly `{threadId, turnId}`. Inside `run_sampling_request` the driver reads `step_context.preempt` (a `CancellationToken`) and, if present, arms `sess.input_queue.watch_user_input(&sess.active_turn, &turn_context.sub_id, preempt.clone())` so that user input arriving mid-stream cancels the preempt token rather than the whole turn; `.or_cancel(&preempt)` then races the retry/sleep against that token, and when it fires the function returns `SamplingRequestResult { needs_follow_up: true, last_agent_message: None }` — the stream is abandoned and the next turn-loop iteration samples again with the pending input. Steered input is recorded with its own persist context, `PersistContext::SteeredUserInput`, and mid-turn drains are gated by `can_drain_pending_input` so that the *first* user input of a turn is sampled before any later steer is folded in. Cancellation proper is a `CancellationToken` throughout (`or_cancel`, `cancellation_token.child_token()`), surfacing as `CodexErr::TurnAborted`; the driver records aborted turns with an `InterruptedTurnHistoryMarker` (`Disabled | ContextualUser | Developer`, chosen by config and multi-agent version) so that a resumed transcript shows *that* it was interrupted. `run_turn_interrupt_hooks` (referenced from `tasks/mod.rs`) runs hooks on abort, and `GRACEFULL_INTERRUPTION_TIMEOUT_MS = 100` bounds the graceful path.

**(f) Sub-agents and nested loops.** Nested agents are *spawned threads*, coordinated by an agent-control subsystem under `agent/control/`. `spawn.rs` carries the spawn path (`SpawnAgentOptions`, `build_agent_resume_config`, `apply_role_to_config`, and a `SpawnInitialInput` enum that distinguishes plain user input from inter-agent communication). `interrupt.rs` implements `interrupt_spawned_agent`, whose rules are instructive: root and self targets are rejected ("an agent cannot interrupt itself; return your result and let the parent interrupt you if needed"), and an unloaded or already-dead runtime counts as a *successful* interruption. Inheritance is explicit and permission-narrowing: the spawn path intersects permission profiles (`intersect_effective_permission_profiles`) and can inherit the parent's exec policy and environments (`SpawnAgentThreadInheritance`). Concurrency across children is governed by config (`max_concurrent_threads_per_session`) and surfaced to the model through role/usage hints resolved in `session/multi_agents.rs` (`usage_hint_text`, `resolve_usage_hints`), which branch on whether the session is a root or a `SubAgentSource::ThreadSpawn`. The multi-agent *version* (`MultiAgentVersion::{V1, V2}`) is threaded through events and prompts, so the child-facing behaviour differs by version.

**(g) Streaming.** Streaming is the response-event stream consumed by `try_run_sampling_request`, whose inner loop handles deltas as they arrive. Assistant text is parsed by an `AssistantTextStreamParser` (in `session/turn.rs`) through `seed_item_text`, `parse_delta`, `finish_item`, and `drain_finished`, then emitted by `emit_streamed_assistant_text_delta`; plan-mode items get their own handling (`handle_plan_segments`, `emit_agent_message_in_plan_mode`). On the protocol side, `AgentMessageDeltaNotification.json` is the app-server notification that carries assistant deltas to a client, so streaming is a *protocol-level* contract, not merely a UI convenience.

**(h) Errors and retries.** Errors are a typed enum (`CodexErr` with `CodexErrorDetails`), and retries are explicit and bounded. `run_sampling_request` reads `turn_context.provider.info().stream_max_retries()` into `max_retries` and keeps a `ResponsesStreamRetryState`; each failure goes through `handle_response_stream_error(...)`, which decides whether to back off and retry (the module imports `util::backoff`) or to rethrow. Terminal details are handled by name: `ContextWindowExceeded` exits to the compaction path; `UsageLimitReached` updates rate limits before exiting; `TurnAborted` propagates; `InvalidImageRequest` emits a specific user-facing error and breaks. Two retry guards are notable: auto-compaction on a context overflow for a budget-exhausted reviewer is allowed **once per model step** (a boolean `guardian_budget_compacted` prevents "ineffective compaction" from looping), and a tool call that fails non-fatally becomes a *failure response* appended to history rather than aborting the turn (`ToolCallRuntime::handle_tool_call` maps `FunctionCallError` to a `ResponseItemEnvelope` unless it is `Fatal`).

**(i) Termination.** A turn's follow-up decision is `needs_follow_up = model_needs_follow_up || has_pending_input`. When `!needs_follow_up`, the loop runs `run_turn_stop_hooks(...)`, whose `StopHookOutcome` can set `should_block` (a hook injects a continuation prompt and the loop `continue`s) or `should_stop` (the loop `break`s); if neither, an optional post-turn compaction runs and the loop breaks. Mid-turn, `should_roll_over` forces a compaction `continue` rather than a stop. The *task* terminates when `run_turn` returns and either a terminal error is recorded or the input queue has no pending input. On top of the loop's own conditions, the session carries a `terminal_error` that short-circuits the outer task loop.

**What is distinctive about this implementation.** Codex is the only one of the four where the loop is *an async task owned by a session and supervised by a set of exit conditions* rather than a self-contained function. That produces three signatures you do not see elsewhere in quite this form: **(1)** steering is implemented by racing a *preempt token* against an in-flight model stream, so user input can preempt a response mid-flight and the interim result is explicitly `needs_follow_up: true`; **(2)** interruption is *hooked and marked* — aborted turns are tagged in history (`InterruptedTurnHistoryMarker`) and interrupt hooks run, so a resumed conversation knows it was interrupted; **(3)** compaction is *phased and trusted to terminate* — the same turn loop can compact before, during, or after sampling, and the code states that it relies on compaction being effective to avoid an unbounded roll-over. The cost is legibility: the loop is a product of `tasks/` + `session/` + `state/` + `tools/`, and no single file can be read to see it whole.

### 6.1 The four loops, in one place

Because the guide's claim is that Codex expresses control by nesting, the nesting is worth laying out explicitly, with each loop's exit:

1. **The task loop** — `RegularTask::run` in `codex-rs/core/src/tasks/regular.rs`. Re-enters `run_turn` while steered input remains. Exits when a terminal error is set or `input_queue.has_pending_input(&sess.active_turn)` is false.
2. **The turn loop** — inside `run_turn` in `codex-rs/core/src/session/turn.rs`. Per iteration: drain pending input, capture a `StepContext`, build the sampling input, call `run_sampling_request`, then branch. Exits via `break` when `!needs_follow_up` and stop hooks do not block/stop, or `continue`s after a mid-turn compaction roll-over.
3. **The retry loop** — in `run_sampling_request` (same file). Re-issues the request while `handle_response_stream_error(...)` says to retry, bounded by `stream_max_retries()`. Exits by returning a `SamplingRequestResult`.
4. **The stream loop** — in `try_run_sampling_request` (same file). Consumes the response-event stream and dispatches tool calls.

Mapping this to the canonical loop of §3.1: loop 2 is the canonical "step" cycle, loop 3 is the model-call retry, loop 4 is the streaming body, and loop 1 is the outer "turn" re-entry that DSH expresses as `while (await this.turn())`. The two systems implement the same shape with very different decomposition — which is exactly the finding of §9.

## 7. Claude Code — the loop that is not public

**Version read:** commit `fbe20e00e2851fc01506f54f98a8f0b875af3847` (tag `v2.1.292`), 2026-10-06. **Licence:** proprietary ("© Anthropic PBC. All rights reserved."). **Loop source:** **not public.** Every claim in this section is either (i) read from a file that *is* in the public repository, or (ii) taken from the product's published documentation and labelled **documentation-derived**. Nothing here describes Claude Code's internal code, because none is available. Where this guide draws an inference from the documented seams, it says so.

**(a) Where the loop physically lives.** It is not in the repository. The complete root listing at the commit read contains no `src/`: `.claude-plugin/`, `.claude/`, `.devcontainer/`, `.github/`, `.vscode/`, `CHANGELOG.md`, `CLAUDE.md`, `LICENSE.md`, `README.md`, `SECURITY.md`, `Script/`, `demo.gif`, `examples/`, `feed.xml`, `mods/`, `plugins/`, `scripts/`. The README describes a tool that "lives in your terminal" and installs via `curl -fsSL https://claude.ai/install.sh | bash`, a Homebrew cask, WinGet, or the deprecated `@anthropic-ai/claude-code` npm package. The loop therefore ships as a compiled binary. This is the first fact and the load-bearing one: **there is no file path to cite for Claude Code's control flow, and this guide will not invent one.**

**(b) Control structure.** Unknown as source. What the *documentation* exposes is the shape of the loop's boundaries, and that shape is unmistakably two nested loops. The hooks reference (fetched 2026-10-06, **documentation-derived**) describes three cadences — "per session", "per turn", and "on every tool call inside the agentic loop" — and its lifecycle diagram places a **nested agentic loop** (with `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `SubagentStart`/`SubagentStop`, `TaskCreated`, `TaskCompleted`) *inside* a per-turn loop (with `UserPromptSubmit` at the top and `Stop`/`StopFailure` at the bottom). The documented `PostToolBatch` event fires "after a full batch of parallel tool calls resolves, before the next model call" — a direct statement that tool calls can run as a parallel batch, and that the batch is a boundary before the next model call. That is precisely the canonical loop's step structure (§3.1), externalised as named events rather than as code. The inference — that Claude Code runs a step loop over tool batches bracketed by per-turn `Stop`/`StopFailure` — is the guide's reading of the documented seams, marked as such; the *events themselves* are documented facts.

**(c) Conversation and context state.** Not readable. Documented evidence marks compaction as a first-class, hookable phase: the hooks reference lists `PreCompact` ("Before context compaction") and `PostCompact` ("After context compaction completes"), and a `SessionStart` event that fires "when a session begins **or resumes**" — resume semantics, stated as a contract. Context is also shaped by instruction files: an `InstructionsLoaded` event fires "when a CLAUDE.md or `.claude/rules/*.md` file is loaded into context … at session start and when files are lazily loaded during a session", which is documented evidence that the context is *lazily extended* during a run rather than fixed at start. How history is stored, how a request is derived from it, and how compaction shrinks it are **not observable** from the public surface, and this guide does not claim them.

**(d) Tool registration, schema, dispatch, sandbox, approval.** The tool boundary is the most thoroughly documented part of the surface, and it is documented *as a policy surface*. The repository's `plugins/README.md` and the plugin directory structure (`commands/`, `agents/`, `skills/`, `hooks/`, `.mcp.json`) show that tools arrive from plugins, skills and MCP servers. The published docs (**documentation-derived**) define permission configuration as `allow`, `ask`, and `deny` rules, and — importantly for an enterprise reader — a four-scope settings model with a **managed** file (`managed-settings.json`, MDM, or server-managed settings) whose values "nothing you set overrides … apart from a few security-sensitive exceptions". The hook reference documents `PreToolUse` ("Before a tool call executes. **Can block it**"), `PermissionRequest`, `PermissionDenied`, `PostToolUse`, and `PostToolUseFailure`. A tool-level example in the repository, `examples/hooks/bash_command_validator_example.py`, is a concrete, readable illustration of the `PreToolUse` blocking contract. What is *not* observable: how a tool is schematised, how a call is dispatched to an executor, and how the sandbox is enforced. Those are claimed nowhere.

**(e) Interruption, steering and cancellation.** Partially documented. `Stop` is documented as the event "when Claude finishes responding", and `StopFailure` as "when the turn ends due to an API error" — so the *end of a turn* is an externally observable event with a failure variant. Steering is documented at the boundary rather than through the running loop: `UserPromptSubmit` fires "when a prompt is submitted, before Claude processes it", and the hooks reference explicitly notes that a `Stop` hook can *block* termination (the guide treats this as documentation-derived). The strongest evidence that cancellation and loop control are reachable through the public seam is a plugin shipped *in this very repository*: `plugins/ralph-wiggum/`, whose README describes "interactive self-referential AI loops for iterative development. Claude works on the same task repeatedly until completion", implemented through a `Stop` hook that "intercepts exit attempts to continue iteration", with `/ralph-loop` and `/cancel-ralph` commands. A loop expressed as a plugin on top of a `Stop` hook is a meaningful statement about where loop control is exposed — and it is a statement the repository itself makes. Whether a cancel aborts an in-flight model stream, and what happens to already-streamed text, is **not documented and not claimed**.

**(f) Sub-agents and nested loops.** Documented at the lifecycle level. The hooks reference lists `SubagentStart` ("When a subagent is spawned") and `SubagentStop` ("When a subagent finishes"), and an agent-team teammate event `TeammateIdle`. Plugins ship agents as first-class artifacts — the repository's own `plugins/code-review/` describes "5 parallel Sonnet agents", and `plugins/pr-review-toolkit/` lists six specialised review agents — evidence that sub-agents are a normal composition unit and can run in parallel. A sub-agent's isolation mode is documented as configurable (one documented hook, `WorktreeCreate`, is described as running on worktree creation "via `--worktree`, `isolation: \"worktree\"`, or for a background session"). Independent corroboration of the *shape* of the sub-agent contract: DeepSeek Harness ships `packages/subagent/subagent-claude-code/` (`run.ts`, `process.ts`) as an adapter to it, and `packages/hooks/hooks-claude-code/` as a hook adapter. What a sub-agent *inherits* — model, tools, permissions, depth budget — is not documented in the sources read, and is not claimed.

**(g) Streaming.** Documented as a display surface: the hooks reference includes a `MessageDisplay` event that "runs while assistant message text streams", alongside `Stop` and per-tool events. So streaming is a first-class, observable boundary in Claude Code — but how streamed text relates to the durable transcript (whether partial output is finalised on interruption, as DSH guarantees, or discarded) is **not documented**, and this guide does not assert it.

**(h) Errors and retries.** Documented at the event level, not at the policy level. `StopFailure` marks a turn ending on an API error; `PostToolUseFailure` fires "after a tool call fails"; and `PermissionDenied` supports a JSON field (`hookSpecificOutput.retry: true`) that tells the model it *may* retry a denied tool call — with the documented caveat that Claude Code ignores `retry` "when the classifier produced no verdict". That is real, readable evidence about the error taxonomy and about how a permission denial is fed back to the model. Retry and backoff policy for model calls is **not observable** and is not claimed.

**(i) Termination.** The documented stop condition is *author-extensible*, and that is the single most interesting fact about Claude Code's loop surface. `Stop` fires "when Claude finishes responding" and a `Stop` hook can block the exit — which is exactly the mechanism `plugins/ralph-wiggum/` uses to convert a completing turn back into a continuing one. At the session level, `SessionEnd` fires "when a session terminates". So while the loop's internal termination logic is unreadable, its *termination seam* is documented and demonstrably powerful enough to implement a different loop policy on top. There is an honest limit here: because the seam can only be exercised, not read, this guide cannot compare Claude Code's termination logic to the other three at the code level.

**What is distinctive about this implementation.** Claude Code is the only system in the study whose loop is *unreadable*, and yet it is the system that externalises loop *control* most aggressively: `PreToolUse` can block a tool, `Stop` can block the end of a turn, `PreCompact`/`PostCompact` bracket compaction, and a plugin shipped in the repository uses that `Stop` seam to implement a whole alternative loop. The design statement is counter-intuitive but clear — the internal loop is proprietary, while the *decisions that steer it* are public contracts. For this guide's purposes the asymmetry is the finding: the three readable systems show you how a loop is written; Claude Code shows you the seams through which a loop is *governed* without being visible.

### 7.1 What the documented hook cadences imply

The three documented cadences (all **documentation-derived**, `code.claude.com/docs/en/hooks`, fetched 2026-10-06) map cleanly onto the canonical loop's boundaries, which is why they are usable evidence even without source:

- **Per session** — `SessionStart` ("when a session begins **or resumes**") and `SessionEnd`. Implies sessions are durable and resumable.
- **Per turn** — `UserPromptSubmit` ("when a prompt is submitted, before Claude processes it", and also "on turns Claude Code starts on its own"), `Stop` ("when Claude finishes responding"), and `StopFailure` ("when the turn ends due to an API error"). Implies a turn boundary with a distinct success and failure exit, and that a turn can be initiated without a user prompt.
- **Per tool call, inside the agentic loop** — `PreToolUse` ("can block it"), `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, and `PostToolBatch` ("after a full batch of parallel tool calls resolves, before the next model call"). Implies a step containing a tool batch, with pre-call gating and a batch boundary before the next model call.

Two further documented events are loop-adjacent and worth recording: `PreCompact`/`PostCompact` bracket compaction, and `SubagentStart`/`SubagentStop` mark nested-agent lifecycle. The implication this guide draws — a per-turn loop containing a per-tool-call step loop, with compaction and sub-agents as distinct phases — is an *inference from the seams*, and is labelled as such; the events themselves are documented facts.

## 8. deepagents — the loop delegated to an external library

**Version read:** commit `9a91d79e18dacfe900ac62e59c756e87f3b586a7` (`main` HEAD), 2026-10-06; release `deepagents==0.7.22`. **Licence:** MIT. **Loop source:** partly public — the *graph assembly and middleware* are here; the *step loop* is in `langchain` (pinned `>=1.4.3,<2.0.0` in `libs/deepagents/pyproject.toml`), with `langgraph` beneath it. This section reads deepagents' assembly of the loop and does **not** claim to have read LangChain's or LangGraph's loop source.

**(a) Where the loop physically lives.** Not in this repository, by design. `libs/deepagents/deepagents/graph.py` imports `from langchain.agents import AgentState, create_agent`, and `create_deep_agent(...)` ends by calling `create_agent(model, system_prompt=…, tools=…, middleware=deepagent_middleware, …)` and then `.with_config({"recursion_limit": 9_999, "metadata": {…}})`. The repository's own `libs/ARCHITECTURE.md` states the layering explicitly: "Deep Agents sits on top of LangChain and LangGraph … LangChain builds the loop that calls the model, executes tools, and repeats until the model finishes; the runtime layer provides durable execution." What *is* in the repository is the assembly: `graph.py` builds the middleware stack and the sub-agent specs; `libs/deepagents/deepagents/middleware/` holds the behaviour that runs around the loop; `backends/` decides where files and execution live. So the answer to "where does the loop live" for deepagents is: *in a dependency, configured here*.

**(b) Control structure.** A **middleware-wrapped graph step, owned by the external runtime**. `create_deep_agent` returns a `CompiledStateGraph`; there is no imperative loop in the repository. The loop's behaviour is shaped entirely through the middleware stack the assembly produces, in a documented order: base scaffolding (`FilesystemMiddleware`, `SubAgentMiddleware`, `SummarizationMiddleware`, `PatchToolCallsMiddleware`, optional `AsyncSubAgentMiddleware`), then caller middleware, then a tail (profile middleware, `SkillsMiddleware`, prompt-caching middleware, `MemoryMiddleware`, `HumanInTheLoopMiddleware`, `UnsupportedContentMiddleware`, `_ToolExclusionMiddleware`). The `ARCHITECTURE.md` description of *when* middleware runs is the control structure in prose: middleware "can run before a model call, around a model call, around tool execution, or while state is being prepared". The only loop-shaped parameter deepagents itself sets is `recursion_limit: 9_999` — a very high runtime guard, not a behavioural loop. The guide is explicit that the *step repetition* itself is LangGraph's.

**(c) Conversation and context state.** State lives in LangGraph; deepagents extends the schema and the reducer. `DeepAgentState(AgentState)` overrides the `messages` field with a `DeltaChannel(_messages_delta_reducer, snapshot_frequency=50)`, and the docstring says why: to reduce "checkpoint growth from O(N²) to O(N)". That is a state-representation decision unique among the four — a *delta channel* with periodic snapshots, rather than an append-only log (DSH) or an in-session history (`codex`). Compaction is a middleware: `create_summarization_middleware(model, backend)` builds a `_DeepAgentsSummarizationMiddleware`, and `compute_summarization_defaults(model)` chooses the trigger/keep pair from the model's profile — `("fraction", 0.85)` trigger with `("fraction", 0.10)` keep when the model advertises `max_input_tokens`, otherwise a fixed `("tokens", 170000)` trigger with `("messages", 6)` keep (and a separate argument-truncation setting at `("messages", 20)`/`("messages", 20)`). The same middleware also handles context-overflow exceptions (`_is_context_overflow`) and offloads data-URL media. The middleware is inserted in both the main stack and every sub-agent stack (`create_summarization_middleware` appears in the main stack, the general-purpose sub-agent stack, and each declarative sub-agent's stack), so compaction is a *per-agent* policy, not a global one.

**(d) Tool registration, schema, dispatch, sandbox, approval.** Tools arrive three ways: built-ins contributed by middleware (`ls`, `read_file`, `write_file`, `edit_file`, `glob`, `grep`, `execute`, `task`), caller-supplied `tools=`, and tools injected by middleware. `SubAgentMiddleware` "backs the `task` tool handler", and `FilesystemMiddleware` "backs every built-in file tool and now also enforces `permissions` rules (a security guarantee)". **Permissions** are declarative `FilesystemPermission` rules evaluated "in declaration order; the first match wins. If no rule matches, the call is allowed", with three modes — `allow`, `deny`, and `interrupt`. An `interrupt`-mode rule auto-installs a `HumanInTheLoopMiddleware` via `_build_interrupt_on_from_permissions`, merging generated interrupts with any caller-supplied `interrupt_on` (user entries win per tool name). **Sandboxing is a backend property, not a loop property**: `execute` availability is decided by whether the resolved backend implements `SandboxBackendProtocol`; for non-sandbox backends "the `execute` tool will return an error message". Tool *visibility* is manipulated by `_ToolExclusionMiddleware` and by harness profiles' `excluded_tools`. Two structural details matter for the loop: tool exclusion "runs last so excluded tool names are stripped after all tool-injecting middleware has run", and `FilesystemMiddleware` and `SubAgentMiddleware` are declared a protected scaffolding set that `HarnessProfile.excluded_middleware` *cannot* remove (attempting to raises `ValueError`).

**(e) Interruption, steering and cancellation.** This is the axis where deepagents is thinnest, and honesty requires saying so. deepagents does **not** implement a loop-level interrupt, steer or cancel of its own; those are LangGraph's `interrupts` and the `Checkpointer` resumability the `ARCHITECTURE.md` names as runtime facilities. What deepagents contributes is the *approval* form of interruption: `interrupt_on` and the permission-derived `HumanInTheLoopMiddleware` pause the run at specified tool calls "for human approval or modification". The file `libs/deepagents/deepagents/middleware/_fs_interrupt.py` (with `_build_interrupt_on_from_permissions`) is the bridge from filesystem policy to that human-in-the-loop interruption. Because the assembly is declarative, inheritance is spelled out in the `create_deep_agent` docstring: declarative `SubAgent` specs inherit top-level `interrupt_on` by default and may override it; `CompiledSubAgent` runnables and remote `AsyncSubAgent` specs do **not** inherit it. But whether new input can be delivered into a *running* step, and what a cancel does to an in-flight model stream, is a LangGraph behaviour this guide did not read and does not assert.

**(f) Sub-agents and nested loops.** Sub-agents are the axis deepagents invests in most. The delegation tool is `task`, built by `_build_task_tool(...)` in `libs/deepagents/deepagents/middleware/subagents.py` from a `TaskToolSchema` and the set of registered specs. There are three spec kinds — declarative `SubAgent`, pre-compiled `CompiledSubAgent`, and remote/background `AsyncSubAgent` (routed to `AsyncSubAgentMiddleware` and described as "agents deployed via LangSmith deployments") — plus an experimental `mode="fork"`. The inheritance model is explicit: a sub-agent is **isolated by default** ("the subagent only sees the delegated task"), while a **fork** "continues the parent's conversation and rebuilds its system prompt instead of starting isolated", inheriting the parent's skills (and forbidden to define its own) and mirroring the parent's prompt-producing middleware `_fork_messages(...)`. Tools are inherited "unless the subagent declares its own"; permissions are inherited unless the sub-agent specifies its own (which "replaces the parent's rules entirely"). Recursion is *guarded at the tool*, not by a depth counter: the middleware refuses recursive delegation with the message, recorded in the source, "You are a subagent and cannot delegate to another subagent. Complete this task yourself instead of calling this tool again." If no `general-purpose` sub-agent is supplied, one is auto-added (unless disabled via profile), and the sub-agent's own compiled graph is created through a nested `create_agent` call.

**(g) Streaming.** Not implemented in this repository. `ARCHITECTURE.md` attributes streaming to the runtime — LangGraph "exposes streaming APIs for observing a run as it happens" — and deepagents adds nothing of its own. The guide therefore makes no claim about how deepagents surfaces deltas; the honest statement is that streaming is entirely the external runtime's contract.

**(h) Errors and retries.** Also largely external. deepagents contributes *request cleanup* middleware rather than retry logic: `PatchToolCallsMiddleware` runs in every stack ("request cleanup" in the architecture's own words) and exists to repair malformed tool-call payloads before/around the model boundary, and `UnsupportedContentMiddleware` sits at the tail. The summarisation middleware is the one place deepagents reasons about failure, recognising context-overflow exceptions (`_is_context_overflow`) so that compaction can respond to them. The model-call retry policy, backoff, and stream-error handling observed in Codex have **no counterpart in deepagents' own code** — they belong to the model client and the runtime, and are not claimed here.

**(i) Termination.** The base stop condition is the canonical one — the loop continues while the model requests tools and ends when it does not. deepagents adds three guards, all visible in the assembly: the **runtime `recursion_limit: 9_999`** passed via `.with_config(...)`; the **summarisation trigger** (a fraction or token/message threshold above which the run compacts rather than continuing to grow); and the **sub-agent recursion refusal** in the `task` tool, which prevents a child from spawning a child and thereby bounds nested-loop depth at one level for the declarative path. Human-in-the-loop interruption can *pause* the run, but pausing is not terminating; resumption is the checkpointer's job.

**What is distinctive about this implementation.** deepagents is the clearest illustration among the four of a *separation of concerns between loop and assembly*: the loop is somebody else's, and deepagents' entire contribution is a declarative middleware stack plus a state reducer plus a sub-agent model. That makes it the most configurable and the least self-contained: you can reorder middleware, exclude tools, add profiles, and change compaction policy without touching a loop — because there is no loop here to touch — but you also cannot read the loop's interruption or retry behaviour from this repository at all. Its two genuinely novel loop-adjacent choices are the `DeltaChannel` message reducer (checkpoint growth O(N²) → O(N)) and an explicit *fork* sub-agent mode that continues the parent's conversation rather than starting isolated.

### 8.1 The middleware stack, read as control flow

Since deepagents has no loop code, its middleware order *is* its statement about the loop's phases. The main-agent stack assembled at the end of `create_deep_agent` (`graph.py`), in order, is:

1. `FilesystemMiddleware` — built-in file tools; enforces `permissions` at the tool level (a protected scaffolding member).
2. `SubAgentMiddleware` — provides the `task` tool (a protected scaffolding member).
3. `SummarizationMiddleware` — compaction, triggered by the model-profile threshold.
4. `PatchToolCallsMiddleware` — tool-call repair at the request boundary.
5. `AsyncSubAgentMiddleware` — present only when async sub-agents are supplied.
6. *(caller middleware is inserted here)*
7. Harness-profile `extra_middleware`, then `SkillsMiddleware` (when skills are given), then the prompt-caching middleware.
8. `MemoryMiddleware` (when memory is given), then `HumanInTheLoopMiddleware` (when any interrupt is configured), then `UnsupportedContentMiddleware`, then `_ToolExclusionMiddleware`.

The ordering is itself a set of decisions: tool exclusion runs **last** "so excluded tool names are stripped after all tool-injecting middleware has run"; memory sits after prompt caching so that "memory updates … don't invalidate the Anthropic prompt cache prefix"; and `SkillsMiddleware` sits after user and profile middleware so "skill tool disclosure sees the compacted conversation". A reader who wants to know where deepagents intervenes in the loop can read this list top to bottom — it is the closest thing the repository has to a control-flow diagram, and the `ARCHITECTURE.md` three-layer diagram (Deep Agents harness → LangChain agent loop → LangGraph runtime) is its companion.

### 9.2 What is convergent

Testing the candidate convergences against the source, four hold for all four systems:

1. **"No further tool calls" is the base stop condition, everywhere.** DSH returns `completed` when `toolCalls.length === 0`; Codex computes `needs_follow_up` from the model's request for tools; deepagents' loop ends when the model produces a final response; Claude Code documents `Stop` as firing "when Claude finishes responding". Every *extra* stop condition is layered on top of this one.
2. **Tool calls are executed as a batch and their results are kept in the model's order.** DSH's `commitReady` advances a `committed` cursor "only across contiguous model-order slots" while dispatch overlaps; Codex records calls through `executed_tool_calls` and gates exclusivity with an `RwLock`; Claude Code documents `PostToolBatch` firing "after a full batch of parallel tool calls resolves"; deepagents inherits LangGraph's tool node. Parallel *dispatch* with ordered *commit* is the shared design.
3. **Compaction is a first-class, named, phased operation, not an ad-hoc truncation.** DSH: "surface replacement" + dedicated compaction packages. Codex: `CompactionPhase::{PreTurn, MidTurn, PostTurn}`. deepagents: a summarisation middleware with an explicit trigger/keep pair, installed per agent. Claude Code: `PreCompact`/`PostCompact` hook events. A loop that cannot compact cannot survive a long task, and all four treat it as architecture.
4. **Nested agents are narrowed, never widened.** DSH pins a child's approval policy to `'never'`; Codex intersects permission profiles and forbids self-interrupt; deepagents refuses recursive delegation at the `task` tool and only inherits permissions the parent already had; Claude Code documents sub-agent start/stop as distinct lifecycle events. Delegation widens *scope of work*, not *scope of permission*.

### 9.3 What is genuinely divergent — and the design reason visible in the code

The spine of this study holds: **the four systems differ most sharply in where loop control lives, and each location is justified by something readable in the code.**

- **Dedicated package vs distributed supervisor vs external library vs invisible loop.** DSH can make the loop a package because it makes the *session log* the source of truth and reconstructs every request from it ("Every request is derived from the session log"), so the loop needs almost no private state and can be swapped via the `Agent` contract. Codex cannot, because its task supervisor must own many task kinds (`RegularTask`, `CompactTask`, `ReviewTask`, `UserShellCommandTask`) over one long-lived `Session` — control is consequently a trait (`SessionTask`) and the turn logic its largest implementation. deepagents cannot, because it chose to sit on a runtime it does not own ("Deep Agents … does not introduce a new runtime"). Claude Code does not expose a loop at all, and instead publishes the seams that *govern* it. The reason for each choice is written down in each codebase.
- **Steering implemented three different ways, from three different substrates.** DSH models steering as durable inbox *splices* with two explicit targets (`next-step`, `next-turn`) — the natural representation when the transcript is a log. Codex models steering as a *preempt token* raced against an in-flight stream — the natural representation when the loop owns a live async stream and must not lose the partial response. deepagents has no steering primitive because its loop is elsewhere. Claude Code documents `UserPromptSubmit` and a blockable `Stop` but not a mid-stream steer. Same intent, three substrates.
- **Termination is written at four different layers — this is the study's headline divergence.** DSH deliberately has **no turn budget** and defers any bound to a lifecycle extension point (`agent/turn-stopping`) — the stop contract is treated as *policy*. Codex writes the bound as a **context-window property**: roll over and compact, trusting compaction ("as long as compaction works well … we shouldn't worry about being in an infinite loop"). deepagents writes it as a **runtime guard** (`recursion_limit: 9_999`, high by intent) plus a summarisation threshold. Claude Code writes it as an **extension point**: `Stop` can be blocked, and a plugin in the repository uses exactly that to replace the stop policy. Four systems, four layers — policy, window, runtime, seam.
- **Stop semantics differ in a way that matters operationally.** DSH's `max-tokens` is *sticky* — once a step hits the ceiling, a later completed step cannot downgrade the turn outcome. Codex's turn can *roll over* mid-turn and continue after compaction, so a "turn" can contain more than one context window. deepagents' turn is one `invoke()`. Claude Code's turn boundary is the documented `Stop`/`StopFailure` pair. Three of these are readable; the fourth is a contract.
- **Context representation diverges at the data-structure level.** Append-only durable log (DSH), in-session cloned history (Codex), delta-channel state with periodic snapshots (deepagents), undocumented but hookable (Claude Code). This is the deepest divergence because it is the hardest to change later: an append-only log makes replay free but compaction must "shadow" (never mutate); a delta channel makes long threads linear but changes what a "snapshot" is.

### 9.4 Two meta-axes

**Extension seams — what an operator can change without editing the loop.** DSH: `agent/*` events plus the `agent/pre-step`, `agent/request` and `agent/request-error` waterfalls, the tool registry, swappable compaction packages, and swappable sub-agent backends. Codex: task kinds, the tool-hook surface (`run_pre_tool_use_hooks`/`run_post_tool_use_hooks`), stop hooks, exec policy, and feature flags. deepagents: the middleware list, harness profiles (`extra_middleware`, `excluded_tools`, `excluded_middleware`), backends, and declarative permissions. Claude Code: hooks, plugins, MCP servers, and managed settings. Every system treats the loop as something an integrator parameterises rather than rewrites.

**History integrity — what the loop guarantees about its own transcript.** DSH is the most explicit: an aborted or failed step still produces paired `tool/call` + `tool/result` events (synthetic `ABORTED_BEFORE_DISPATCH`), so the log never contains a call without a result. Codex appends a *failure response* for a non-fatal tool error and records an interrupted-turn marker, keeping the sequence well-formed. deepagents repairs malformed tool calls in middleware (`PatchToolCallsMiddleware`) right at the request boundary. Claude Code documents `PostToolUseFailure` as an event but not what it appends, so no guarantee is claimed. In all three readable systems, "a tool call always has a matching result" is enforced by the loop — a property a regulated operator will care about more than any benchmark number.

### 9.5 Where the spine could be wrong

The spine — "the four differ most in where loop control lives" — was tested against the source, not assumed (§5–§8). Three caveats keep it honest. First, the *observable* difference between DSH's dedicated package and Codex's distributed supervisor is partly a difference of code organisation rather than of behaviour: both loop turns and steps with a base stop condition and both compact by phase. Second, deepagents and Claude Code are not comparable at the same level of evidence — deepagents exposes its *assembly* but not its loop, and Claude Code exposes neither — so the spread in §9.1 is a spread in *readability and seam placement* as much as in control flow. Third, the claim "children are narrower than parents" (§9.2, item 4) is verified in DSH, Codex and deepagents but is only *documented* for Claude Code, and documentation is not code. The thesis survives all three caveats; what it does not survive is any claim that the four loops *behave* as differently as they *read*.

## 10. Context and State Management Across the Four

The four systems differ in context management not because they solve different problems but because they chose different *representations of history*, and the representation constrains everything else. Depth on context engineering generally lives in [context_engineering_guide.md](context_engineering_guide.md); this section compares only what the loop does.

**The four representations.** DSH keeps an **append-only durable session log** and derives each request from it; the loop holds almost no private state, and "surface" messages (model-visible) are distinguished from "log-only" events (stream frames, lifecycle markers). Codex keeps the history **in the `Session`** and clones it per request through `clone_history().for_prompt(...)`, with per-step configuration captured separately in a `StepContext`. deepagents keeps history in **LangGraph state**, with the `messages` field using a `DeltaChannel(_messages_delta_reducer, snapshot_frequency=50)` so checkpoint growth is linear rather than quadratic. Claude Code's storage is undocumented; only the compaction hooks (`PreCompact`/`PostCompact`) and lazy instruction loading (`InstructionsLoaded`) are observable.

**Why the representation matters.** An append-only log makes *replay* free — DSH can rebuild the exact request from the persisted events, which is why its loop can be a swappable package. But it forces compaction to be *non-destructive*: DSH compacts by "shadowing" older nodes with a surface replacement, never by mutating them, and the README notes that a replacement "invalidates reuse from the first shadowed history token". A delta channel, by contrast, optimises for long threads (deepagents' O(N²)→O(N)) at the cost of a more complex notion of "a snapshot". Codex's in-session history sits between them: cheap to clone, but the loop must explicitly *record* what it sent so that a resumed session reconstructs context (hence `record_context_updates_and_set_reference_context_item`, and the `request/header`/`request/context` logging DSH does the same way).

**Compaction triggers compared.** DSH's compaction is expressed as a *region* operation (`packages/compaction/compaction-basic/src/{config.ts,region.ts}`) with a summariser that injects the compaction directive as the *final user message* to reuse the provider's warm prefix cache — a cache-aware choice. Codex triggers compaction on token-window pressure (`context_window_token_status`, `turn_end_compaction_threshold_reached`) and phases it (`PreTurn`/`MidTurn`/`PostTurn`); its mid-turn roll-over is what lets a single "turn" span more than one context window. deepagents triggers on a configurable fraction (`0.85`) or absolute size (`170_000` tokens) with a keep window (`0.10` fraction or `6` messages), computed per model profile — and, notably, **per agent**, because the summarisation middleware is installed in the main stack *and* in every sub-agent stack. Claude Code exposes the *moments* (`PreCompact`/`PostCompact`) but not the mechanism.

| Aspect | DSH | Codex | Claude Code | deepagents |
|---|---|---|---|---|
| Trigger | Region/policy driven; surface replacement | Token-window status (`turn_end_compaction_threshold_reached`) | Undocumented; `PreCompact` hook | Fraction 0.85 or 170k tokens |
| Keep window | Region selection | Compaction scope limits | Undocumented | Fraction 0.10 or 6 messages |
| When | Before/around a request, as a replacement | `PreTurn` / `MidTurn` / `PostTurn` | Before/after compaction event | Inside the summarisation middleware |
| Scope | Per region (packages per target: tool results, images, command) | Per turn, with a roll-over that continues the turn | Undocumented | Per agent (main + each sub-agent stack) |
| Pairing safety | `compaction-tool-pairing` | `build_compacted_history` | Undocumented | messages reducer keeps the sequence |

The **pairing-safety** row is the one that matters most for replay: every readable system has a specific mechanism to avoid leaving a tool call orphaned by compaction, which is the same integrity invariant §9.4 highlights.

**Shared invariants worth naming.** All four (three readable plus one documented) treat compaction as a distinct phase rather than a silent truncation; all four keep the *system prompt* out of the compaction target in some way (DSH separates system nodes from history; deepagents' prompt assembly is `USER`→`BASE`→`SUFFIX` and its compaction targets messages); and all four preserve tool-call/result pairing across compaction — DSH's `compaction-tool-pairing` concept (packages `compaction/compaction/src/tool-pairing.ts`) and Codex's `build_compacted_history` both exist precisely to avoid leaving an orphaned call in the compacted transcript. That last invariant is the one an auditor should look for first: **a transcript in which every tool call has a matching result is a precondition for replaying an agent's actions.**

## 11. Tool Dispatch and Safety Across the Four

This section compares only loop-level dispatch and approval; sandbox *implementation* is owned by [agent_sandboxing_strategies_guide.md](agent_sandboxing_strategies_guide.md).

**Concurrency model.** All four dispatch tool calls in batches and must reconcile "dispatch may overlap" with "results are model-ordered". DSH does it with an explicit scheduler: `runGroup` maintains a bounded rolling pool (`inFlight.size < maxParallelToolCalls`) and a `committed` cursor that advances "only across contiguous model-order slots", with exclusive calls acting as ordering barriers re-evaluated before start. Codex does it with an `RwLock`: `ToolCallRuntime.parallel_execution` is read-guarded for parallel calls and write-guarded for exclusive ones, and each call is recorded through `sess.services.executed_tool_calls` so results carry their provenance. Claude Code documents the boundary (`PostToolBatch` fires "after a full batch of parallel tool calls resolves, before the next model call") without exposing the mechanism. deepagents inherits the batch behaviour from LangGraph's tool node.

**Approval points.** The approval point is where each system allows a human or policy to interpose, and the four place it differently. DSH: a separate `interaction/user-approval` subsystem plus permission presets, reached via `ctx.get(...)`; the loop itself just dispatches. Codex: `ApprovalContext` with three distinct request paths — `request_user_approval`, `request_guardian_approval`, `request_reviewer_approval` — and an `ApprovalStore` that caches decisions by key (`ApprovalCacheKey`), so a repeated action is not re-prompted. deepagents: declarative — a `FilesystemPermission` with mode `interrupt` auto-installs `HumanInTheLoopMiddleware`, and `interrupt_on` names the tools that pause; the tool *still visible* but the call can be denied or interrupted (the assembly docstring is explicit that "permissions are not a visibility mechanism"). Claude Code: `PreToolUse` "can block it", `PermissionRequest`/`PermissionDenied` are events, and allow/ask/deny rules live in settings with a managed file that overrides user settings.

**A shared safety design.** All four separate *what the model can see* from *what the call may do*: DSH appends a `developer/message` when the visible tool set changes; Codex has `ToolExposure` and a `HostedSpec`/`SpecPlan` layer; deepagents uses `_ToolExclusionMiddleware` and profile `excluded_tools`; Claude Code allows a tool to be visible while its call is denied. Visibility is not permission, in every system.

**The escalation pattern.** Codex and DSH both implement "try sandboxed, escalate on failure": Codex via `sandbox_override_for_first_attempt` and `escalate_on_failure`, DSH via `packages/sandbox/sandbox/src/escalation.ts` and the `sandbox-policy` session mode. deepagents places the equivalent at the backend boundary (a non-sandbox backend simply fails `execute`), and Claude Code's documented permission model implies a prompt-then-allow flow without exposing the escalation mechanics.

**The gate at a glance.** Reading the four along the single dimension "where can a call be stopped before it runs", the placement differs but the *existence* of a gate does not:

| Question | DSH | Codex | Claude Code | deepagents |
|---|---|---|---|---|
| Who decides? | user-approval subsystem + permission presets | `ApprovalContext` (user/guardian/reviewer) | allow/ask/deny rules + managed settings | `FilesystemPermission` + `interrupt_on` |
| Cached? | Presets | Yes — `ApprovalStore` by `ApprovalCacheKey` | Standing approvals in settings files | Declarative rules, first-match-wins |
| Default when unconfigured | Deployment preset | Policy-dependent (`default_exec_approval_requirement`) | Project/user rules; managed overrides | **allow** (no match ⇒ allowed) |
| Can a call be paused rather than denied? | Approval request | Approval request | `PermissionRequest` event | Yes — `interrupt` mode → HITL |
| Visibility ≠ permission? | Yes (`developer/message` on tool-set change) | Yes (`ToolExposure` vs policy) | Yes (visible tool, denied call) | Yes (stated explicitly in the API docstring) |

The **default-when-unconfigured** row is the one to read twice: deepagents' documented default is to allow a call that matches no rule, which means a deployment's protection is exactly the set of rules it remembered to write.

## 12. Sub-Agents and Nested Loops Across the Four

Sub-agents are where the loop becomes recursive, and the four systems bound that recursion in four different currencies. Broader multi-agent topologies are covered by [hierarchical_multi_agent_frameworks_guide.md](hierarchical_multi_agent_frameworks_guide.md) and [multi_agent_banking_guide.md](multi_agent_banking_guide.md); here the subject is only the nested loop.

**The four recursion bounds.** DSH bounds by **depth**: `resolveChildDepth` computes `delegationDepthOf(parent) + 1` and throws `SubagentDepthError` above an optional `maxDepth`, and the depth is persisted in the child's session metadata so "a resumed parent cannot delegate as if it were top-level". Codex bounds by **identity and permission**: `interrupt_spawned_agent` rejects root and self targets, and spawned threads inherit an *intersection* of permission profiles plus the parent's exec policy. deepagents bounds by **refusal**: the `task` tool will not let a sub-agent delegate further — the recorded refusal message is "You are a subagent and cannot delegate to another subagent" — so the declarative tree is one level deep. Claude Code bounds by **documented lifecycle**: `SubagentStart`/`SubagentStop` mark spawn and finish, and `isolation: "worktree"` is available for filesystem isolation, but the depth policy is not documented.

| Bound | DSH | Codex | Claude Code | deepagents |
|---|---|---|---|---|
| Mechanism | Depth counter (`delegationDepthOf + 1`) | Permission intersection + identity checks | Documented lifecycle only | Tool-level recursion refusal |
| Enforced at | `resolveChildDepth` / `SubagentDepthError` | `interrupt_spawned_agent`; spawn permission intersect | Not documented | `_build_task_tool` refusal |
| Persisted? | Yes (`delegationDepth` in child meta) | Via thread/agent state | Not documented | In state, but the bound is static |
| Failure mode | Explicit error on cap exceeded | `UnsupportedOperation` on root/self | Not documented | Tool call refused with a fixed message |

**What a child inherits — the operative question.** DSH composes the child explicitly in `child-agent.ts`: route (provider/model/reasoning-effort), `maxTokens`, sandbox override, and permission preset are inherited, while the **approval policy is pinned to `'never'`** and the child gets a fixed model-facing delegation statement ("your permission scope was fixed when you were started and cannot be widened from inside this session"). Codex inherits environments and exec policy by construction and narrows permissions by intersection. deepagents' spec-level rules are documented in `create_deep_agent`: tools inherited "unless the subagent declares its own"; permissions inherited unless the sub-agent supplies its own (which "replaces the parent's rules entirely"); `interrupt_on` inherited by declarative sub-agents but *not* by compiled or remote ones; and a `mode="fork"` sub-agent "continues the parent's conversation and rebuilds its system prompt". Claude Code's inheritance is not documented in the sources read.

**The convergence worth stating plainly.** In every system that exposes the rule, **a child's authority is a subset of its parent's**. DSH narrows to `'never'` approval; Codex intersects; deepagents inherits-unless-overridden and refuses grandchild delegation. None of the four widens a child's permissions, and none lets a sub-agent grant itself a capability its parent lacked. For a delegated-work architecture this is the single most important property to verify in code, because it is the property that makes a nested loop safe to run at depth.

**A note on backend pluralism.** DSH's sub-agent roster (`subagent-claude-code`, `subagent-codex`, `subagent-acp`, `subagent-dsh-sdk`, `subagent-fork-in-process`, `subagent-in-process-driver`, `subagent-spawn-in-process`) and deepagents' three spec kinds are the same idea expressed twice: the *child loop* can be a different implementation (even a different product's agent) behind the same delegation tool. That is where the four systems are most convergent architecturally and most divergent in code — they agree the sub-agent is a seam, and disagree about how to write one.

## 13. What Is Worth Stealing

Each pattern below is stated with the system it came from and the file it was read at, so a builder can go to the source. These are observations, not recommendations to adopt any one system wholesale.

1. **Derive every model request from a durable log, not from mutable state.** DSH (`packages/core/agent-loop/src/agent.ts`; package README) appends `turn/start`, `step/start`, `user/message`, `assistant/message`, `tool/call`, `tool/result`, `step/end`, `turn/end` and rebuilds each request from `session.deriveMessages()`. The payoff is that a resumed session and a live one produce the same request, which is what allows the loop to be a swappable package. This is the single most reusable structural idea in the study.
2. **Make the loop a replaceable contract.** DSH's `ReactLoopAgent implements Agent`, and the README frames the standard lifecycle as replaceable "only when the standard 'call model, run tools, repeat' lifecycle is insufficient". Naming the loop's contract (rather than its code) is what let DSH offer custom `Agent` implementations without forking.
3. **Give steering two explicit destinations, not one.** DSH's `steer()` → `next-step` and `followup()` → `next-turn` (`inbox.ts`), with `inject()` as a non-waking step input, encode *where* input lands as data. Most systems conflate "new input" with "new turn"; separating them is cheap and prevents a steer from silently becoming a new turn.
4. **Persist steering as durable inbox splices.** DSH commits every inbox mutation as one `agent/inbox/spliced` event with a deterministic fold (`inboxProjectionDefinition`), so pending input survives a restart and a replay rejects an invalid splice rather than guessing. If input can be queued, queueing it durably removes a whole class of crash-recovery bugs.
5. **Preserve already-streamed text on cancellation.** DSH's README guarantees "Cancellation preserves streamed text already delivered to the user", and `assistant-stream.ts`/`agent.ts` settle `live.interruptedBlocks()` as an `assistant/message` with `interrupted: true`. Discarding partial output that a user already saw is a correctness failure, not a UX preference.
6. **Record synthetic results for tool calls that were skipped or unanswered.** DSH's `tool-calls.ts` appends paired `tool/call` + `tool/result` for calls aborted before dispatch (`ABORTED_BEFORE_DISPATCH`), and `turn()`'s recovery path records synthetic results for unanswered calls. The invariant "every tool call has a matching result" is what keeps a transcript replayable.
7. **Bounded rolling pool with model-order commit.** DSH's `runGroup` overlaps dispatch up to `maxParallelToolCalls` but advances `committed` "only across contiguous model-order slots"; Codex achieves the same with `ToolCallRuntime`'s `RwLock`. Parallelism should never reorder what the model sees.
8. **Reclassify an exclusive call before it starts.** DSH re-reads `executionMode` for later calls so a registry change can introduce a barrier mid-batch (`tool-calls.ts`). Deciding exclusivity at emit time is not enough if the tool set can change during a step.
9. **Race a preempt token against an in-flight stream to steer.** Codex (`session/turn.rs`, `run_sampling_request`) cancels a `preempt` token via `watch_user_input` and returns `needs_follow_up: true` with the partial response abandoned-but-ordered. It separates "stop this response because new input arrived" from "abort the turn", which are different operations that deserve different tokens.
10. **Mark an interrupted turn in history.** Codex's `InterruptedTurnHistoryMarker` (`tasks/mod.rs`) records `Disabled`, `ContextualUser`, or `Developer` so a resumed transcript shows *that* and *how* a turn was interrupted. A transcript that cannot distinguish "finished" from "was stopped" is a weak audit artifact.
11. **Phase compaction, and name the phases.** Codex's `CompactionPhase::{PreTurn, MidTurn, PostTurn}` (`compact.rs`) makes "when did we compact" a first-class fact; DSH's surface-replacement model achieves the same separation by keeping compaction out of the live mutation path. Compaction that can happen at several points should say which point it took.
12. **Compact with the provider's cache in mind.** DSH's summariser (`packages/compaction/compaction-basic/src/summarizer.ts`) replays the conversation prefix and appends the compaction directive as the *final user message* so "the provider's KV cache is reused instead of invalidated". A compaction strategy that ignores prefix caching silently doubles its own cost.
13. **Pin a sub-agent's authority to a subset of its parent's, and persist it.** DSH's `child-agent.ts` pins the child's approval policy to `'never'`, inherits the parent's sandbox mode, and appends the decision to the child's own log as `source: 'delegation'` events "so the child's effective policy is reconstructable from its log alone". Persisting the *authority* a sub-agent ran under is what makes delegated work auditable.
14. **Refuse recursive delegation at the tool.** deepagents' `task` tool (`middleware/subagents.py`) refuses grandchild delegation with the recorded message "You are a subagent and cannot delegate to another subagent". A one-level declarative tree is a simple, checkable bound; if deeper nesting is needed, make it explicit rather than emergent.
15. **Offer a fork mode that continues the parent's conversation.** deepagents' `mode="fork"` (`graph.py`; `_fork_messages` in `subagents.py`) inherits the parent's conversation and mirrors its prompt-producing middleware rather than starting isolated. This is the clean way to get "a second pair of hands on the same context" without copying state by hand.
16. **Use a delta channel for long conversation state.** deepagents' `DeepAgentState(AgentState)` overrides `messages` with `DeltaChannel(_messages_delta_reducer, snapshot_frequency=50)` to reduce checkpoint growth "from O(N²) to O(N)" (`graph.py`). If a transcript can run for hundreds of steps, the state representation, not the loop, is the scalability bottleneck.
17. **Protect the scaffolding middleware that other features depend on.** deepagents declares `FilesystemMiddleware` and `SubAgentMiddleware` a protected set that a profile cannot exclude, and raises `ValueError` rather than proceeding "with a silently degraded agent" (`graph.py`, `_REQUIRED_MIDDLEWARE`). Making an unsafe configuration *unrepresentable* beats documenting that it is unsafe.
18. **Let a permission rule pause for human approval, not just deny.** deepagents' `interrupt` mode auto-installs `HumanInTheLoopMiddleware` via `_build_interrupt_on_from_permissions` (`middleware/_fs_interrupt.py`). A three-valued permission model — allow / deny / ask — maps to real operational reality better than a binary one.
19. **Treat the stop condition as a seam, not a constant.** Claude Code documents `Stop` as firing "when Claude finishes responding" *and* as blockable, and the repository ships `plugins/ralph-wiggum/` — "interactive self-referential AI loops … a `Stop` hook that intercepts exit attempts to continue iteration". Whether or not one wants a loop that refuses to stop, making the stop decision governable is a design choice worth copying.
20. **Separate log-only events from model-visible ones.** DSH's `surfaceOp: 'append'` marks the messages that become history while raw stream frames and lifecycle markers persist without ever entering the model's context. Persisting everything but sending only what belongs in the prompt keeps the transcript rich and the context clean.
21. **Log the request you built, not only the response you got.** DSH records `request/header` (with reason `initial`/`resume`/`change`/`series`) and `request/context`; Codex records context updates per step. When an answer is wrong, the first question is always "what exactly did the model see?", and a request log answers it.
22. **Bound retries per model step.** Codex sets `max_retries` from `stream_max_retries()` and guards reviewer re-compaction with a single `guardian_budget_compacted` flag "so ineffective compaction cannot loop". A retry budget that is global rather than per-step can mask a permanent failure as a slow one.
23. **Escalate the sandbox on failure rather than pre-authorising broad access.** Codex's `sandbox_override_for_first_attempt`/`escalate_on_failure` and DSH's `packages/sandbox/sandbox/src/escalation.ts` both start confined and widen only after a specific failure, with an approval. This gives a smaller default blast radius for the same task success.
24. **Keep the sub-agent backend a seam.** DSH ships adapters to Claude Code, Codex, ACP and its own SDK behind one delegation surface (`packages/subagent/`), and deepagents offers declarative, compiled and remote spec kinds. Nested loops are more future-proof when the child implementation is swappable.
25. **Let compaction use its own model route.** DSH's summariser resolves a summarisation provider/model and falls back to the routed model, and marks the call `purpose: 'compaction'` (`summarizer.ts`). A cheaper or faster model for summarisation is a straightforward cost control that required no loop change.
26. **Make an empty step cost nothing.** DSH opens no step when a `pre-step` decision is rejected or the first input batch is empty ("A rejected decision or empty first batch opens no step"). A loop that can decline to call the model avoids spending tokens on turns that have no work.

## 14. What a Regulated Enterprise Should Take From This

This section draws **controls-relevant observations only** — the loop's approval point, its termination guarantees, and its audit surface — and maps them to controls this repo has already catalogued rather than re-deriving them. The control catalogue lives in [banking/ai_risk_register_guide.md](../../banking/ai_risk_register_guide.md); the governance frame in [ai_governance_framework_guide.md](ai_governance_framework_guide.md); frontier-risk framing in [frontier_ai_risk_guide.md](frontier_ai_risk_guide.md); operational telemetry in [agentops_guide.md](agentops_guide.md). Read this section as a *mapping*, not a new framework.

### 14.1 The approval point is the loop's only pre-action control

Every system studied interposes a human or policy decision at a specific, nameable place, and that place is the loop's only opportunity to stop an action *before* it happens:

- DSH exposes `agent/pre-step`, which can return a `reject` and end the turn as `blocked`, alongside a separate user-approval subsystem.
- Codex has three approval request paths (`request_user_approval`, `request_guardian_approval`, `request_reviewer_approval`) behind an `ApprovalStore` that caches decisions by key.
- deepagents turns a `FilesystemPermission` of mode `interrupt` into an installed `HumanInTheLoopMiddleware` at named tools.
- Claude Code documents `PreToolUse` as able to block a call, with allow/ask/deny rules and a managed-settings file that overrides user settings.

**Observation for the risk register.** A deployment's approval-point inventory should be *per-tool and per-loop*, because all four systems make approval a property of the tool boundary, not a global switch. Where a tool is auto-approved by policy (Codex's `ApprovalStore` cache; deepagents' default-allow when no rule matches; DSH's permission presets), the register should record the *cache key* and the *default*, not merely "approval enabled".

### 14.2 Termination is written at four different layers — so it must be pinned per deployment

The study's headline divergence is directly a control fact: **the loop itself may not bound itself.**

- DSH has **no built-in turn budget** and says so; a bound "must cancel from an existing lifecycle extension point such as `agent/turn-stopping`". A deployment that assumes the loop bounds itself is wrong on this system by construction.
- Codex bounds via context-window rollover and trusts compaction to terminate, and guards reviewer auto-compaction to once per step (`guardian_budget_compacted`).
- deepagents sets a runtime `recursion_limit: 9_999` — high by intent — plus a summarisation trigger and a one-level sub-agent bound.
- Claude Code exposes `Stop` as blockable and therefore as an author-configurable stop policy.

**Observation for the risk register.** "Maximum loop length", "maximum spend per turn", and "maximum sub-agent depth" are *deployment* parameters, not product constants, in three of the four systems and a seam in the fourth. Each should be an explicit, recorded per-deployment setting with an owner, and each should be exercised in a test that shows the bound actually fires. On DSH specifically, the absence of a turn budget is a documented gap that the deployment must close at `agent/turn-stopping`.

| Bound you must pin | DSH | Codex | Claude Code | deepagents |
|---|---|---|---|---|
| Turn length / cost | **None built in** — add at `agent/turn-stopping` | Context-window rollover; stop hooks | Author-configurable via blockable `Stop` | Summarisation threshold; `recursion_limit` |
| Sub-agent depth | `maxDepth` via `SubagentDepthError` | Permission intersection; no self-interrupt | Not documented | One level (tool refuses nesting) |
| Model-call retries | `agent/request-error` decides `retry` | `stream_max_retries()`; per-step re-compact guard | Not observable | Runtime-owned |
| What ends a turn | 5 recorded reasons | `needs_follow_up` + stop hooks | `Stop` / `StopFailure` | Base stop + limits |

A deployment that records only "the agent has a loop" has recorded nothing checkable. The four rows above are the checkable bounds, and each maps to a control entry in the risk register.

### 14.3 The audit surface is the transcript's integrity, plus the stop reason

Across the three readable systems the loop enforces one invariant that matters more than any log volume metric: **a tool call always has a matching result.** DSH synthesises paired results for skipped calls; Codex records executed calls through `executed_tool_calls` and appends failure responses for non-fatal tool errors; deepagents repairs malformed calls at the request boundary. This invariant is what makes a transcript replayable — and replayability is what lets an investigator reconstruct *what the agent actually did*, not just what it said.

**Observation for the risk register.** The minimum audit record for an agent loop action should be: the approval decision and its policy version, the tool call, the matching tool result, and the turn's stop reason (DSH makes this a first-class field with five values; Codex exposes a `TurnCompletedNotification`/abort surface). Where a loop's stop reason is not recorded — Claude Code's `Stop`/`StopFailure` events are observable but their persistence is not documented — the deployment should capture it through the public seam rather than assume it is retained. This maps onto the per-action and trajectory-level detection already catalogued in the governance and agentops guides and does not need re-deriving here.

### 14.4 A Cymbal Bank illustration

Consider a Cymbal Bank back-office agent that reconciles exceptions and, on some paths, initiates a state-changing action (a payment repair, a limit adjustment). Reading the four loops gives the deployment three controls to pin, and only three:

1. **The approval point.** Name the exact tool(s) that can change state, and verify the loop gates them at its pre-action seam — DSH's `agent/pre-step` reject, Codex's approval request, deepagents' `interrupt` permission, or Claude Code's `PreToolUse` block.
2. **The termination bound.** Set an explicit per-turn budget and a sub-agent depth cap *at deployment*, because the loop may not have one (DSH) or may set it very high (deepagents' `9_999`), and record both in the risk register with an owner.
3. **The paired audit record.** Require that the retained transcript pairs every action with its result and records the stop reason, so that a later reconstruction shows what was attempted, what was approved, and why the turn ended.

Everything else about the loop — concurrency model, streaming surface, compaction policy — is an engineering choice that the deployment can adopt or change without changing those three controls. The point of reading four loops is that the controls are the same three even though the code that guards them is written four different ways.

### 16.2 Glossary

| Term | Meaning as used in this guide |
|---|---|
| **Agent loop** | The repeated cycle model-request → response → tool execution → result-appended → repeat, until a stop condition. The subject of this guide. |
| **Turn** | One user-initiated unit of work; may span many model calls. Bounded by `turn/start`…`turn/end` (DSH), `TurnContext`/`TurnState` (Codex), `Stop` (Claude Code docs), one `invoke()` (deepagents). |
| **Step** | One model call plus the tool execution that follows it, inside a turn. DSH names it explicitly (`step/start`…`step/end`). |
| **Tool call** | A structured model request to run a named capability with arguments. |
| **Tool result** | The value produced by a tool call, appended to history so the next request can see it. |
| **Transcript** | The ordered model-visible history (user/assistant messages, calls, results), as distinct from log-only events. |
| **Surface message / log-only event** | DSH's distinction: surface messages are model-visible and re-derived; log-only events (stream frames, lifecycle markers) are persisted but never sent. |
| **Compaction** | Any operation that shrinks the transcript so the loop can continue past the context window. |
| **Surface replacement / shadowing** | DSH's non-destructive compaction: a newer node shadows older ones rather than mutating or deleting them. |
| **Stop condition** | The predicate that ends a turn. Base form in all four: "no further tool calls". |
| **Steering** | Input delivered into an *already-running* turn or step (as opposed to input that starts a new turn). |
| **Inbox** | DSH's durable queue of pending input, with targets `next-step` and `next-turn`, persisted as `agent/inbox/spliced` events. |
| **Preempt token** | Codex's `CancellationToken` that cancels an in-flight model stream when new user input arrives, without aborting the turn. |
| **Waterfall** | DSH's middleware dispatch that lets a listener intercept and rewrite a decision (`agent/pre-step`, `agent/request`, `agent/request-error`). |
| **Delegation depth** | DSH's persisted counter ensuring a resumed parent cannot delegate as if top-level; bounded by an optional `maxDepth`. |
| **Fork sub-agent** | A deepagents sub-agent (`mode="fork"`) that continues the parent's conversation instead of starting isolated. |
| **Recursion limit** | The runtime guard deepagents passes to LangGraph (`9_999`); a ceiling, not a behavioural loop bound. |
| **Delta channel** | deepagents' `messages` state representation: deltas with periodic snapshots, keeping checkpoint growth linear. |
| **Approval point** | The loop's pre-action place where a human or policy can allow, deny, or pause a tool call. |
| **Session log** | DSH's append-only durable event log, from which every model request is derived. |
| **Middleware** | deepagents' pre/post hooks around model calls and tool execution; where its harness behaviour lives. |
| **Interrupt** | deepagents/LangGraph's pause-for-approval mechanism; distinct from a cancel. |
| **Checkpointer** | The LangGraph facility that persists state and enables resume after an interrupt. |
| **Harness profile** | deepagents' per-model configuration of extra middleware, excluded tools, and protected-stack validation. |
| **Turn budget** | A bound on loop length/cost. DSH has none built in; a deployment must add one. |

### 16.5 Closing summary

Four systems, four answers to one question. DeepSeek Harness makes the loop a replaceable package and hands it a durable log to derive from, and pays for that purity by leaving the turn budget to policy. Codex makes the loop a supervised task with a preemptive steering token and a phased, trusted compaction, and pays for its power with legibility. deepagents delegates the loop to a library and wraps it in middleware, gaining configurability and losing ownership of interruption and retry. Claude Code keeps the loop closed and publishes the seams that govern it, so the stop decision itself becomes an extension point. Running the same nine axes over all four, the convergences are the boring, load-bearing ones — no-tools-means-stop, ordered batch results, compaction as architecture, children narrower than parents — and the divergences are all instances of one choice: where control lives, and therefore what a *stop* is made of. That is why the four systems cannot be ranked by their loops, only read.

a loop is a contract about when to stop, and the four of them write that contract differently.
