## 1. How this guide relates to the repository, the target role and the decoder

### 1.1 The series convention, and what this guide does that its predecessors do not

This is the fourth guide in this repository's personalized role-analysis series. It keeps the convention set by the first three: a blockquote header addressed to the subject, a numbered table of contents, an explicit statement of source material, an evidence-graded treatment of anything external, a glossary, a claims audit, and a closing note that says where the repository is silent. It is written to be read alongside its predecessors, not instead of them.

The three predecessors were architect-to-architect moves. `../data_architect_skillgaps_guide.md` (715 lines, August 2026) analyses Solution Architect → **Data Architect**, across ten assessment axes and a digital-profile heatmap. `../architecture/skill_gaps_enterprise_architect_guide.md` (316 lines, July 2026) analyses Solution Architect → **Enterprise Architect**, with a banking-domain gap list. `../senior_data_platform_architect_guide.md` (731 lines, September 2026) analyses Solution Architect → **Senior Data Platform Architect** and adds the seniority axis the first two lacked. All three asked the same kind of question — *which architecture role fits this profile best, and how much of it does the profile already evidence?* — and all three answered it with a percentage and a study plan.

Three things are genuinely new here.

**(i) A DIFFERENT DIRECTION, NOT A DIFFERENT DOMAIN.** The predecessors compared architecture roles to each other and moved the subject laterally within one track: from solution architecture to data architecture, enterprise architecture, or platform architecture. This guide asks a different question. It asks whether the next move should remain inside the architecture track at all, or should leave it for a role where the deliverable is a running system rather than a design for one. That is not a lateral step between domains; it is a step out of the category. The target role is hired to **build** — to own components of an agent runtime and be answerable for whether the agent completes real tasks — while the subject's current role is hired to **design** and to govern other people's design. The assessment frame therefore has to be different: the question is not "how much of this domain does he know" but "what has he shipped, and can it be inspected", which is a question about artefacts rather than about knowledge. This distinction is the structural insight of the guide and it drives §5, §7 and §9.

**(ii) A NEW KIND OF EVIDENCE SOURCE: THE REPOSITORY ITSELF.** The predecessors measured the subject's knowledge by reading what he had written. This guide can do something they could not do cleanly, because the body of work is now large enough to be treated as an object of study in its own right: a 629-file public research repository, a 193-post technical site, a 197-post blog spanning 2007–2024, 166 public GitHub repositories, and a topic distribution that can be counted. §4 reads that repository as evidence — the first time in this series that the repository is the evidence rather than merely the instrument — using its own topic distribution as data, with the file counts printed and the measurement date attached. The case for doing so is that the target role's nice-to-have list explicitly names open-source work or technical writing, so the repository is not a proxy for the relevant evidence; it is a candidate instance of it. The honest limit of that move is stated as the guide's integrity rule in §1.4, and it is not a disclaimer: writing a guide about a system is evidence of understanding, not of having built or operated one, and every section below respects that boundary.

**(iii) A GAP OF A DIFFERENT KIND.** The predecessors' gaps were knowledge gaps: learn another domain, learn another framework, learn the seniority standard. They were closable by study, and the series' learning plans said so. The gaps this guide finds are largely **artefact gaps** — the distance between being able to specify a system and having shipped, tested, instrumented and operated one. An artefact gap is not closed by reading. It is closed by producing artefacts that a hiring team can inspect: a repository with a task queue in it, a sandboxed code-execution service, an evaluation harness wired into CI, a merged contribution to somebody else's runtime. §4 proves the gap with counts, §5 names it requirement by requirement, §7 attaches an inspectable artefact to every gap it names, and §9 sequences those artefacts. The guide is built so that its conclusion would survive being read by the hiring team, not only by the candidate.

Everything else is deliberately built on the predecessors rather than re-derived. The **L1–L5 proficiency rubric** is owned by the first guide (§1.11 of `../data_architect_skillgaps_guide.md`: L1 Absent/gap → L2 Familiar/thin → L3 Working/thin → L4 Strong/DENSE → L5 Expert/DENSE), together with the evidence rules that a dedicated guide is the primary evidence unit, that section-level coverage counts only when verified, and that keyword mentions never constitute coverage on their own. That rubric is not re-derived here, no axis is rescored, and no new heatmap or ranked gap list is produced — two versions of the same instrument would only produce two inconsistent assessments. Where the first guide's ten axes apply, this guide names them and points at them. Where the second guide's banking-domain gap list applies, this guide names it. Where the third guide's seniority model applies, this guide names it and adds only what changes when the target is an individual-contributor engineering role at a startup rather than a senior architect in an enterprise.

### 1.2 The one-paragraph definition, in the job description's own terms

**An Agent Runtime / Control-Layer Engineer builds the core systems of an agent runtime and its control layer — context and memory, model and tool orchestration, task planning and execution, tool and MCP integrations, evaluation and quality feedback — owns the design and delivery of complex components within that runtime, and is accountable for making an agent more reliable on real-world tasks.** The company's product takes on complex work — deep research, data analysis, software development — and carries it through to a finished result; the runtime is the machinery that makes the words "carries it through" true rather than aspirational. The role's stated measures are task success, reliability, latency and cost, and its stated method is context engineering, prompt design, retrieval, tooling and architecture — improved iteratively, from real tasks and production failures, against a reproducible evaluation suite with regression tests and end-to-end observability. The role is also stated to work on problems where the requirements and the approach are not yet clear, which means the engineer is expected to define the problem and its success criteria and then drive design, implementation, rollout and improvement. The organising idea, stated once and used throughout this guide: **the runtime's product is completion.** Everything the role owns exists to make completion rate high, repeatable, affordable and explicable; everything the role does not own is a constraint on that product rather than a part of it.

### 1.3 The distinction that gives the role its identity

Three claims define the boundary. Each is stated against the role the market most often conflates with it.

1. **It is a role measured on a system's behaviour, not on a design's quality.** There is no artefact in this role that is complete when written. A context-management component is finished when the agent's task success rate on a held-out task set goes up and the cost per task does not; a tool integration is finished when it survives malformed arguments, timeouts, partial failures and a hostile input without taking the run down; a sandbox is finished when untrusted generated code has run inside it and could not reach what it was not allowed to reach. The judgement is empirical and attributable. A solutions architect's design can be correct and unadopted and it remains a correct design; a runtime component that does not improve completion is simply broken.
2. **The unit of work is a component with an owner, not a document with an audience.** The job description says "owning design and delivery of complex components". The word *delivery* is the load-bearing one. Inside a small company there is usually nobody downstream waiting to be handed a specification — there is a codebase, a deploy pipeline, a set of failing runs and a cohort of users. The engineering manager and the existing engineers will judge the component by whether it exists, whether it is tested, whether it is instrumented and whether it survives being paged about.
3. **The measures are the job description's measures, and they are all runtime measures.** Task success, reliability, latency, cost. Note what is absent from that list: standards conformance, architectural alignment, stakeholder sign-off, roadmap adherence. Those are real in the subject's current environment and are close to invisible here. An architect is measured on whether the design was right and whether it was followed; this role is measured on whether the thing works, at what rate, at what price, and how long it takes. When a component is excellent and the completion rate does not move, the component is wrong.

Why this matters and is not wordplay: the predecessor series established that the subject's public evidence is dense in **summary and synthesis** and thin in **operation**. The third guide's seniority model made a related point — titles are not portable and the work is. This role makes the same point in its sharpest form. Everything in §4, §5 and §7 follows from the three claims above.

### 1.4 The integrity rule, and the decoder for the job description's vocabulary

**The integrity rule.** This guide's evidence base is a body of writing. The repository holds 629 markdown files as of 2026-09-28, the personal site holds 193+ tech-tagged posts, the older blog holds 197+ posts, and GitHub holds 166 public repositories. That is a substantial public body of technical work and it is a genuine asset — treated as an asset in §6 rather than dismissed. But it is a body of **description**. A guide that analyses a system, however carefully, is a data point about the author's understanding of that system. It is not a data point about whether the author has built the system, tested it under load, been paged at three in the morning because of it, or carried the consequence of it failing for a customer. This is not a hedge to be set aside once the analysis gets interesting. It is the measurement instrument's stated level of precision, and where the job description asks for a record of shipping, the honest answer is that the repository cannot testify either way. Every count in §4 and every row in §5 is subordinate to that limit. In particular, **no guide in this repository is treated as evidence that its author has built or operated the thing it describes** — not the sandboxing guide, not the evaluation guides, not the workflow guide, not the 971-line runtime cache guide.

**The decoder.** The job description has an unusual density of compound nouns — context engineering, model routing, execution isolation, task queue, control layer. Compound nouns are where job descriptions do their hiding: each one bundles an operational demand and a conceptual one under a single phrase that reads as a skill. The decoder below takes each in turn and separates the two, because the difference between them is precisely the difference this guide exists to make. ## 2. What the role owns, and what it does not

### 2.1 The ownership map

The job description names five areas of ownership — context and memory, model and tool orchestration, task planning and execution, tool and MCP integrations, evaluation and quality feedback — and frames the whole role as owning "design and delivery of complex components" across them. Two further areas are implied by the text rather than named as bullets: **safety boundaries** ("context, tools, execution, feedback and safety boundaries") and **observability and reproducibility** ("build reproducible agent evaluations, regression tests and end-to-end observability"). Both are treated below as owned, because the sentence structure puts them inside the role's scope. What "owning" means in each case is stated concretely, because in this role ownership is an operational fact rather than a title.

| Owned | What owning it means concretely | The artefact that proves ownership | Whose work it constrains |
|---|---|---|---|
| **Context and memory** | Deciding what enters the model's context, in what order, under what budget, and what leaves it — assembly, retrieval injection, tool-result handling, compaction across turns, summarisation policy, and the persistence layer that makes memory survive a session | The context-assembly component itself, its tests, and the measured effect on task success and token cost per task | Every agent capability that needs more context than fits, and the cost line |
| **Model and tool orchestration** | The layer that calls models and tools, sequences them, handles streaming, retries and partial results, enforces timeouts, and routes each request to a model — with the routing and fallback policy explicit and versioned | The orchestration layer, its retry and fallback semantics, and a per-route cost/latency report that someone actually reads | Latency, cost and reliability of every run; the choice of models available to the product |
| **Task planning and execution** | Turning a stated goal into an ordered, resumable, observable sequence of steps; deciding what is planned up front and what is decided as the run proceeds; making a long run survive a process restart | The planner and its execution model, plus the durable state that makes a 40-minute task resumable rather than restartable | Whether the product's central promise — carrying complex work through to a result — holds on tasks longer than one context window |
| **Tool and MCP integrations** | The tool surface: schemas, argument validation, auth and scoping per tool, error semantics that the model can act on, capability discovery, timeouts, and versioning of a surface other people build against | The integration layer and its contract; the registry of what the agent can do; the failure tests that prove it degrades rather than collapses | Every capability the product offers and every third-party MCP server relied on |
| **Evaluation and quality feedback** | The harness that defines what "better" means: real-task suites, scoring, regression gates in CI, failure triage, and a feedback loop from production failures back into the suite | A runnable evaluation suite and its CI gate; a failure taxonomy derived from real runs | Every change anyone makes to the runtime, prompt or context policy |
| **Safety boundaries and execution isolation** | The policy and enforcement plane: what the agent may do, to which resources, under whose credentials, with what approvals, with what limits, and with what the agent cannot do at all — including the sandbox in which generated or untrusted code executes | The policy layer and the sandbox, plus an escape or boundary test that fails loudly when the isolation is wrong | The company's blast radius; every customer's data; whether the product can be sold to any regulated buyer |
| **Observability and reproducibility** | Traces for a single run across model calls, tool calls, retries and sub-agents; per-step token, latency and cost attribution; enough structure to replay a failed run and reconstruct what it did and on whose authority | The trace schema, the instrumentation, the replay path, and the dashboards or queries the team uses daily | The team's ability to diagnose rather than speculate — which is the difference between a two-hour and a two-week fix |

### 2.2 What the role does not own

Stated from the text of the description and its silences, both of which are informative.

- **The model itself.** The role orchestrates models, routes to them, budgets for them and measures them. It does not pre-train them, fine-tune them at the research frontier, own their weights, or own the research programme that produces them. The description separates this role from research explicitly by naming "product, research, infrastructure and security teams" as collaborators — which means research exists as a distinct function the incumbent works with rather than is part of.
- **Product definition.** The role owns "defining the problem and success criteria when the requirements and approaches are unclear" — but that is problem definition within a component, not ownership of what the product is for. The product exists; the description's first line states what it does. A runtime engineer who starts redefining the product's value proposition has moved into somebody else's job.
- **The research agenda.** Where the product needs a capability that does not yet exist (a better planner, a new memory mechanism, a new reward signal), the runtime engineer consumes the result and engineers the operational version. Telling the difference between "this is a research problem" and "this is an engineering problem with a bad interface" is itself a senior skill in this role; owning the research is not.
- **Data-centre and hardware infrastructure.** Compute procurement, GPU capacity, cluster operations: the description names infrastructure as a collaborating team. The runtime engineer owns what runs *on* the substrate, not the substrate.
- **The customer's governance obligations.** The role owns safety boundaries inside the product. It does not own the customer's regulatory position, the customer's data-residency obligations, or the customer's audit relationship — those constrain the runtime, through the security team the description names, rather than being owned by it.
- **Front-end product experience.** How the agent's work is presented to a user is a product and design concern. The runtime engineer owns whether the work happened and can be explained, not how it is surfaced.
- **Pricing and commercial terms.** Cost is owned as an engineering property (cost per task, cost per successful completion, cost attribution). Whether the product is priced on that basis is not.

### 2.3 The boundaries are contested, and at a small company the contest has an unusual arbiter

Three patterns recur in this family of roles, and all three will be present at a small company, accelerated.

1. **Ownership claimed without authority.** The description measures the role on latency and cost while model choice, provider contracts and compute allocation sit with research or infrastructure. This is the same structural defect the third guide identified (§2.3 of `../senior_data_platform_architect_guide.md`): accountability without control. It is worth naming early in any hiring conversation, because at a startup it is usually the *reason* the role is open — the runtime is slow or expensive and nobody has been made responsible for it.
2. **The vacuum fill, in both directions.** At a small company there is no platform team, no SRE function and often no QA function; the runtime engineer absorbs whatever nobody else claims, up to and including the CI pipeline and the on-call rota. Equally, the runtime engineer will be tempted to absorb the parts of research and product that are adjacent and interesting. The first is a job; the second is a schedule slip.
3. **The arbiter is different from the one the subject is used to.** In a large corporate and investment bank in Singapore, boundary disputes are resolved by governance: a forum, a standard, a RACI, an architecture board. At a small company, boundaries are established by whoever is willing to be paged when the thing breaks. This is not a figure of speech. The person who owns production owns the boundary, and an engineer who wants the boundary without the pager will lose it to one who takes the pager. §11 treats this as a failure mode rather than an observation, because it is where the architect's instinct does the most damage.

### 3.2 Where the existing rubric stops applying, and why that is the finding

The first guide's rubric scores an axis by the density of **dedicated guides** about it. That instrument was right for the roles it was built for — data architect, enterprise architect — because in those roles the practitioner's first deliverable is a design, and a body of design knowledge is a reasonable proxy for the ability to produce one. The job description assessed here measures something the rubric cannot see. Its central requirement is "a record of shipping maintainable, testable production systems", and the repository's evidence unit — a guide, a README, a post — is exactly the artefact class that a record of shipping is not. Applying the rubric to this role would produce a high number and a wrong conclusion: the subject would score strongly on the rows where the repository is dense, and the dense rows are not the ones the job description weights most heavily. §4 states the weighting difference as a measurement; §5 walks the requirements one by one.

The practical consequence for a reader of this series is a change of target state. The predecessor guides defined a target such as "L4 on all ten axes, with L5 on three". The equivalent target here is not expressed in levels at all: **design-level competence across every row above, and demonstrable operational competence in the rows that carry the four measures — task success, reliability, latency and cost.** That is a smaller knowledge requirement and a much larger artefact requirement. The third guide's §6.2 list of what changes between mid-level and senior is the nearest existing instrument; on its terms, the binding constraint for this role is not the sixth of its dimensions (breadth of knowledge) but the third, the one about consequence actually carried.

### 4.5 The integrity rule, restated as a finding rather than a disclaimer

The rule stated in §1.4 was: writing about a system is evidence of understanding, not of having built or operated one. The audit above converts it from a warning into a measured result, and the result has three parts.

First, the repository's density is not uniform across the job description's requirements; it is concentrated in the requirements that can be documented and sparse in the requirements that can only be demonstrated. That is not an accident of this repository. It is a property of the artefact class: anything that can be learned by reading can be written up, and anything that can only be learned by operating is invisible to a keyword count.

Second, the mismatch operates in the direction the job description cares about. The description's "what they bring" section is not a wish list; it is the hiring bar, and it is dominated by substrate requirements and a shipping record. On those, the audit returns thin counts and silence. On the nice-to-haves, it returns genuine depth. A hiring team reading this repository would find a candidate whose documented understanding exceeds the bar in one dimension and whose evidence falls short of it in another, and would have no way to tell from the public record which one predicts the job.

Third, and this is the only place in the guide where a recommendation is stated before it is earned: the correct response to an artefact gap is an artefact, not another guide. A 900-line treatment of durable execution adds nothing to the evidence class this job description is screening on. A repository containing a queue with idempotent consumers and a dead-letter path adds something that cannot be argued away. §9 sequences that work; §5 names the artefact attached to each requirement; §7 does the same for each gap.

### 5.3 The two lines that decide the application

Everything above reduces to two sentences in the description, and they pull in opposite directions.

**The bar:** "5+ years software engineering or equivalent ability, with a record of shipping maintainable, testable production systems." The subject clears the first clause by a wide margin — the profile's own timeline puts the career from around 2003, and the second predecessor's assessment already treated the breadth of domain experience as unusual. The second clause is where the evidence stops. There is no production service in the public record, no test suite with users who depend on it, no release history, no changelog attached to a system that someone else operated. The 166 public repositories, read in the profile's own words as learning projects, samples, proofs-of-concept and forks, are not that record. This is not a disqualification — a hiring team assesses a candidate, not a GitHub profile, and an interview can surface delivery history that no repository shows. It is a statement that **the public evidence cannot be used to argue the case, and must not be presented as if it could.** The most common failure at this point in an application is confident over-claiming; the second most common is apologising for a gap that may not exist. The correct posture is to state the delivery history that does exist, precisely and in the past tense, and to leave the judgement to the interviewer.

**The foundation:** "strong backend or distributed-systems foundations — concurrency, task queues, persistence, idempotency, failure recovery, observability". Here the subject is genuinely strong at the level of understanding and genuinely unexercised at the level of operation, and the asymmetry is unusual: most candidates who can talk about idempotency have met it in code, and most candidates who have met it in code cannot explain it as clearly. This profile inverts that. The repository's treatment of durable execution, workflow engines and failure semantics is more systematic than what most working backend engineers produce — and it is produced by someone who has not, on the public record, debugged a duplicate write at two in the morning. §11 treats "I already know this" as a failure mode for exactly this reason; the interview advice in §8 is to answer these questions from the conceptual depth honestly and to concede the operational limit in the same breath, because a good interviewer will test the second part and will respect a candidate who volunteers it.

## 8. The interview and the assessment

### 8.1 What this loop will actually probe, read off the description

The description is unusually explicit about what it will test, which is a rare advantage for a candidate. Three things are named as abilities rather than as skills.

1. **Distributed-systems foundations.** Named in the first "what they bring" bullet in exactly the vocabulary to expect: concurrency, task queues, persistence, idempotency, failure recovery, observability. This is likely to be probed in a systems conversation and, because the role is at a small company, probably also in code.
2. **Independent ownership of complex systems and responsibility for delivery quality.** Not a skill question. This is probed with narrative questions about what the candidate has owned, what went wrong, and what happened afterwards.
3. **Defining the problem when requirements and approaches are unclear.** Also not a skill question, in the usual sense. It is probed with an open-ended scenario — an agent that fails on some class of tasks, with no stated cause — and evaluated on whether the candidate asks for the right facts or reaches for a solution.

A realistic loop shape, inferred from the description and from the role class rather than from any specific employer: a practical session on the runtime substrate (concurrency, queues, failure handling, or a debugging exercise on a failing run); a design conversation on one component from §2.1 with an emphasis on failure modes, isolation and cost; a discussion of ownership and pace with the founders or the engineering lead; and, at a company of this size, an explicit conversation about AI-tool use, because the description makes it a requirement rather than a preference (§13.4).

### 8.2 How to answer using genuine evidence rather than aspiration

Three rules, in order of importance.

**Rule 1: claim the documented depth as documented depth.** The repository's agent, retrieval, evaluation and security material is genuinely strong, and it can be described as what it is — "I have studied this systematically; here is my treatment of failure taxonomy; here is the evaluation material" — without any embellishment. This is a real answer and interviewers respect a precise claim more than an inflated one. What must not happen is the claim sliding from "I know how this works" to "I have built this". That slide is detectable, and it is fatal in a role where the interviewer's own job is to find the person who can be trusted with production.

**Rule 2: for operational questions, answer from the closest real analogue and label it.** Most operational questions have a conceptual core and an empirical shell. The conceptual core should be answered fully and confidently; the empirical shell should be answered by naming the nearest experience that exists and saying exactly what it is. A worked example: *"What happens when a consumer dies between dequeue and ack?"* — answer the mechanism precisely (the message returns to the queue after the visibility timeout, so the consumer must be idempotent, and the idempotency key should be the message id plus the operation, not a timestamp), then name the limit: *"I have not run that at scale — the closest I have is deduplicating loads in data integration, which is the same problem at a lower rate."* That answer is stronger than a fabricated war story and it is the only one that survives a follow-up question.

**Rule 3: where the answer is unknown, say unknown and describe how it would be found out.** "I don't know, and here is how I would find out in the first week" is the correct answer to a surprising fraction of questions in an interview for a role whose specification is partly undefined. It is also, literally, the behaviour the description asks for — define the problem, then drive improvement. A candidate who answers confidently and wrongly on a substrate question is worse than one who says so.

### 8.3 The questions that would expose a design-only background, and the honest way to answer them

Then describe how you would instrument this one — the trace schema, the four measures from the description — because that is answerable from knowledge and is genuinely wanted |
| "Tell me about a production incident you caused." | Whether failure has ever had a name attached to it | Do not invent one. Say that production ownership has not been part of the role, then demonstrate the thing the question is actually testing — a failure taxonomy — by naming the classes from `llm_agents_failures_production_guide.md` and stating which the candidate would expect first in a runtime like theirs. Then name the operational discipline they would need: trace-first debugging, cheap rollback, a blameless note |
| "Here is a trace of a failing run. Where do you look first?" (an exercise, not a question) | Whether the candidate can read telemetry rather than read source | This one is answerable and should be answered well: the trace structure (model calls, tool calls, retries, token counts per step) is documented in the repository, and `agentops_guide.md` addresses it. This is the place to be visibly strong, and the place where the documented depth converts directly into interview performance |
| "How would you size this queue, and when would you shard it?" | Whether the answer comes from a book or from running one | Give the conceptual model — depth, age, consumer throughput, the delay-vs-cost trade-off, the point at which lock contention or a single broker's throughput becomes the limit — then say which parts of that reasoning you have not validated empirically. Naming the boundary of your own knowledge is the answer to this question, not a weakness in it |
| "You have an agent at 60% task success. What do you do in the first week?" | Whether the candidate reaches for a component or for a measurement | This is the strongest question in the set for this candidate, because it rewards the thing the repository proves: build the eval first (is 60% stable, or is the task distribution bimodal?), triage the failures into classes, and only then pick a lever — context, retrieval, tool reliability, or planning. Answering this with a method rather than a preference is the single best opportunity in the loop |
| "How many pull requests do you review in a week, and how do you handle a 2,000-line one?" | Code review at scale — a requirement the public record cannot evidence (§3.3) | Answer from what is true. If the answer is "review has mostly been mine to request rather than to give", say so, and describe the review standard actually held: tests for behaviour, one concern per change, an explicit failure mode per change. Then ask what their review cadence is, because at a small company that question is welcome |
| "What did you cut to ship on time?" | Whether the candidate has ever had to trade scope against a date under real pressure | Design work often ends before the cut is made — the trade-off is documented instead of experienced (§11.4). Say that, then demonstrate the reasoning: what is safely cuttable, what is not, and why the cut should be recorded |
| "The design is wrong and we have customers. Do you fix it or ship it?" | Whether the architect's instinct to get the design right before shipping will survive contact with a startup | The honest answer is that the instinct runs the other way and the discipline has to be deliberate: ship the narrow correct version, write down what is deliberately deferred, and schedule the fix against evidence rather than against principle. This is §12's whole subject, and naming the bias instead of denying it is the credible move |
| "You have read a lot about this. What have you run?" | The single question this profile has to have a prepared answer for | Give the artefacts (§9) or give the truth. There is no third option and no phrasing that improves on either |

### 8.4 What to bring, and what to prepare

- **The artefacts, listed with their numbers** — repository URLs, the CI badge, the measured before/after, the cost per task. A candidate who can be checked in click is a candidate whose claims are cheap to believe.
- **One component design, written to two pages, on a real question from the description** — for example, how to instrument a single agent run so that a failure can be replayed from its trace. This is a genuine strength area and a written artefact demonstrates the ability the description names under "define the problem".
- **A failure taxonomy** prepared from the repository's own material, with the classes the candidate would expect in this product and the first detector for each. This converts the documented depth into something that looks like experience-adjacent judgement, without claiming it.
- **The two clock questions answered before the interview** — what the team's release cadence is, and what the on-call arrangement will be. Not asked defensively; asked because §11 and §12 both hinge on the answer. A runtime role at a five-person company with no on-call rota is a different job from the same title with one.
- **Do not bring the repository as the answer to everything.** "I wrote a guide on that" is a sentence that ends interviews in this role class. The guide is the credential; the artefact is the evidence.

### 8.5 The preparation protocol, repeatable

1. Re-read the description and mark every line that names a **measure** or a **delivery** as a question the loop will ask. Those are the ones this profile cannot answer from the public record.
2. For each of those lines, write the honest answer down. The exercise's value is not rehearsal; it is discovering which lines have no honest answer yet, because those are the ones §9's artefacts must create one for.
3. Do one full exercise-style session on the substrate: a queue with a failing consumer, a sandbox with a boundary violation, a trace with a bad tool call. Being able to read the artefact is most of what the practical session tests.
4. Prepare the two-page component design and one measured result. Between them, they answer the two most likely probing questions — "can you define a problem" and "can you measure an outcome".
5. Re-run this self-assessment after the artefacts exist, using §5's verdict table. Several rows should move from PARTIAL to MET, and the rows that do not move are the answer to give if asked what you are working on next.

## 9. The 90-day evidence plan

Ordered so that each artefact makes the next one cheaper, and so that the earliest artefact is the one that makes everything after it measurable. Effort estimates assume part-time work alongside a full-time role, which is the realistic condition.

| Window | Artefact | What it proves | Effort | The inspectable property |
|---|---|---|---|---|
| **Days 1–14** | **An evaluation harness.** 30 tasks drawn from real work types (a retrieval question, a data question, a code change), a scorer, a stored baseline, and a CI job that fails on regression | That the candidate's first instinct is measurement rather than construction — which is the behaviour behind the description's task-success/latency/cost line | ~25–35 hours. The repository's four evaluation guides and the `rag/` evaluation material make this the fastest artefact on the list | `make eval` runs locally and in CI; the baseline is committed; a deliberately degraded change makes the check fail |

### 9.1 The plan's central claim, stated plainly

**Three inspectable artefacts outweigh three more guides.** The repository already contains more than six hundred documents, including 775 lines on sandboxing strategies and 971 on runtime cache design. Adding a 900-line treatment of durable execution would change no answer in §5's verdict column, because every "NOT EVIDENCED" verdict in that table is a verdict about an absent artefact rather than about absent knowledge. The plan above adds 629 → 629 files of prose and roughly five new repositories or contributions, and it is the second number that moves.

This is not a rejection of writing. §6.1 established that the writing is a genuine asset and that the description names it as a nice-to-have. The point is narrower: in this role, writing is evidence when it is attached to an artefact. A README that documents a running queue is a different artefact class from a guide that surveys queue design, and both the hiring team and the reader of this series should be able to see the difference without being told.

### 9.2 What not to do in the 90 days

- **Do not commission new guides on the runtime substrate.** The mapping in §3 already identifies where the repository is dense; adding to the dense areas changes nothing that the job description measures.
- **Do not start with the sandbox because it is the most interesting problem.** Start with the harness, because without it nothing else produces a number, and the description's measures are the point.
- **Do not build four things in parallel.** One running service with users (or with a load test that stands in for users) beats four half-built components, and it is the only shape that produces a delivery record.
- **Do not publish anything that touches the current employer's systems, data or designs.** The artefacts above are all synthetic by construction. Where the honest delivery account requires material that cannot be published, it stays a verbal, reference-checkable account (§7.1).

### 9.3 The kill criterion

If the 90 days produce no running artefact — not a partial one, not a design, not a document about one — then the diagnosis in §7.6 is confirmed and the constraint is not knowledge. The correct response is not a longer plan. It is to say so, to work out whether the constraint is time, cadence or appetite, and to treat that answer as the most important finding of the entire analysis. A candidate who cannot finish a small service in ninety days alongside a job should not accept an offer from a company whose product *is* a small service, and should not let a hiring team discover this after joining.

## 10. The routes in and the transition

### 10.1 The realistic mechanism, which is not a cold application

A CV that reads "Solution Architect, GenAI" at a large corporate and investment bank will be read by a five-person startup as the wrong shape before it is read as too senior: the applicant appears to be someone who designs for a living, applying for a job that is entirely implementation. Nothing in the CV can overcome that early read. What can overcome it is the thing this profile has and most candidates do not — a public, inspectable body of work that includes the runtime substrate. The mechanism is therefore: **let the artefacts arrive before the application**. Specifically:

1. Build the §9 artefacts and make them trivially inspectable — one repository, a README with four numbers, a CI badge, a reproduction command.
2. Contribute the merged pull request first (§7.5). A contribution that lands in an agent-tooling project puts the subject in front of maintainers as an engineer rather than as an architect, and it creates a third-party judgement that no self-description can match.
3. Write about the artefacts, not about the category — one detailed post on the queue's failure modes, or the sandbox's boundary tests. The writing habit is an asset; the writing has to be attached to the thing (§9.1).
4. Then apply, through a referral or through the maintainers met in step 2. At companies of this size, referral is not a preference; it is generally how engineering hires happen, and the public work is precisely what makes a referral easy for someone else to make.

The order matters. Applying first produces a rejection on shape, and a rejection is not re-opened by a later artefact.

### 10.2 What the hiring team will worry about, and what to pre-empt

- **"He is an architect; he will not write code."** Pre-empted by code in the public record that is not a tutorial: the queue, the sandbox, the harness. Not by a statement of willingness.
- **"He will want architect money and architect title."** A real risk, and unfixable with words. The honest handling is to decide, before applying, whether a non-architect title and a startup package are acceptable. **No compensation figure is printed anywhere in this guide** — §13.6 and §16.1 record why — so this decision has to be made on the candidate's own information rather than on a published band.
- **"He is used to a platform team, a change board and a testing function."** Pre-empted by the artefacts being built without any of those, and by being able to say what was consciously not built.
- **"He will slow us down with governance."** Pre-empted in the interview by the answer to §8.3's last question: naming the bias, not denying it.
- **"His agent knowledge is reading, not building."** Pre-empted only by the artefacts. There is no other move.

### 10.3 The alternative entry points, if the IC route is closed

The IC route is not the only way in, and the alternatives have different benefits and different costs. The discipline is to be explicit about which gap each one closes and which it does not.

| Route | What it actually is | Which gap it closes | Which gap it leaves open | Repository material |
|---|---|---|---|---|
| **Agent runtime IC** (the primary route) | Building components of the runtime | Everything, if it works | None, if it works — but it requires the artefacts to exist first and it is the most competitive entry | `agent_sandboxing_strategies_guide.md`; `agentops_guide.md`; `../durable_ai_agent_workflows_guide.md` |
| **Forward-deployed / field engineering** | Sitting with customers, building and shipping integrations and prototypes inside their environments | Shipping under time pressure, autonomy, real users, delivery cadence — the strongest closure of §7.1 and §7.6 available without changing role family | Core runtime ownership; isolation internals; the substrate | `../../management/forward_deployed_engineering_guide.md` |
| **Platform / infrastructure-adjacent engineering** | Building internal or product infrastructure rather than agent components | Concurrency, queues, persistence and operability at the level a platform team requires | The agent-specific rows — context, evaluation, planning; and it is the easy lateral move, so it risks repeating the architecture-track pattern | `../ai_platform_engineering_guide.md`; `../distributed_systems_engineering_guide.md` |
| **Developer tooling / DX** | Building the tools other engineers run — runners, CLIs, local development infrastructure | Delivery record and external users, at lower stakes; matches a documented instinct for tool-building | The runtime's evaluation and memory rows entirely | `../ai_native_companies_guide.md` for the company class |
| **Solutions architecture at an AI-native company** | The same role in a faster company, closer to the product | Proximity to a runtime, exposure to its failures, much higher shipping tempo | It is a lateral move inside the architecture track, exactly the pattern the first three guides analysed. It improves §12's translation question without closing the artefact gap | `../ai_native_companies_guide.md`; `../enterprise_ai_gateway_guide.md` |
| **Consulting-to-product** | A vendor- or consultancy-side role that converts into a product team, or a technical product role | Commercial context, breadth, a route into product organisations | Hands-on ownership; and it moves further from the code in the medium term | `../../management/consulting_advisory_experience_guide.md`; `../../management/product_management_frameworks_guide.md` |
| **Open-source first** | Becoming a maintainer, then being hired by someone who depends on the project | Everything, with the strongest possible evidence class: third-party dependency | Slower, and not fully within the candidate's control | — |

Two observations about the table. First, **forward-deployed engineering is the closest thing to an honest middle route**: it is the only entry point that closes the shipping and cadence gaps without requiring the substrate artefacts to be built first, and it is a role where two decades of enterprise and regulated-industry experience is an asset rather than a liability. Second, **the platform-infrastructure route is a trap in this specific case**: it is the lateral move that looks like progress, it uses the subject's existing strengths, and it leaves the binding constraint untouched. It is the move the first three guides in this series would have recommended. This guide's whole argument is that the binding constraint has changed.

### 10.4 The transition itself

- **Sequence:** artefacts first, contribution second, visibility third, application fourth (§10.1). Applying before the artefacts exist spends the one introduction the candidate gets at a startup.
- **Run the search as a process, not as a series of applications.** The repository's `../../management/reverse_job_search_guide.md` is the method already documented; it does not need re-deriving here.
- **Onboarding materials exist and are not the bottleneck.** `../../management/the_first_90_days_guide.md` covers the first-ninety-days method; the constraint is not knowing how to onboard, it is having something to onboard into.
- **Decide the title and package question before the first conversation**, because it is the question that ends more senior-candidate processes than any technical one.
- **If the IC route fails twice for the same stated reason, believe it.** Two rejections on shape mean the artefacts are not yet convincing, or that the role family genuinely does not hire from this profile without a prior step. The second case is what §10.3 exists for.

## 11. The failure modes of the move

Five ways this transition goes wrong. Each is stated as a symptom, a cause and a guardrail, because a failure mode without a guardrail is just a warning.

### 11.1 Design instinct as shipping avoidance

**Symptom.** Three design documents before the first commit. A component-shaped proposal for a task-sized problem. The phrase "we should decide the interface first" used more than once in a week. In its most dangerous form: a design review scheduled for something that would take an afternoon to try.

**Cause.** This is not laziness; it is a trained response with a real history behind it. Two decades of an environment where the design was the deliverable, where a design that got implemented badly was still a correct design, and where the review was the moment of value. The instinct also has a defensive function: writing a design is comfortable, and committing code that might be wrong is not.

**Guardrail.** A timebox per component with a public artefact at the end of it — a branch, a failing test, a deployed prototype — and a written "what I am deliberately not designing yet" section at the top of the work rather than in the appendix. The test to apply: *if a design document exists and no code does, the work has not started.* The repository's own habit is the risk here, because it is a habit of producing excellent documents quickly and stopping there.

### 11.2 The seniority inversion

**Symptom.** The most experienced person in the room writing the least code and saying the most in review. Opinions about naming, standards, layering and process offered before the substrate is understood. A growing sense of being personally accountable for quality that is not attached to anything being built.

**Cause.** The title travels and the context does not. An architect with a 20-year CV joining a five-person team arrives, structurally, as the most senior person there — and the environment will treat him that way, which is exactly the condition under which the habit of directing rather than doing is reinforced.

**Guardrail.** Accept the inversion deliberately: ask for a title that matches the work being done rather than the CV, take the on-call, own one component end to end including its bugs, and let other people's review comments change the code without argument. The concrete test: *is the code review of a change I wrote being done by somebody with less experience than me, and am I taking the comments?* If the answer is no, the inversion has already happened.

### 11.3 The "I already know this" trap

**Symptom.** Confident design decisions in a domain that has been read exhaustively and built never. The sandbox boundary chosen from the survey of strategies rather than from an attempt. A queue configured the way the durable-execution guides say before anything has been run. Correction received with a reference.

**Cause.** This is the specific hazard of an evidence base made of writing, and it is §4's finding applied to behaviour. `agent_sandboxing_strategies_guide.md` is 775 lines of good material; it is also 775 lines that can create the sensation of having solved the problem. The trap is not that the knowledge is wrong — it is largely right — it is that the confidence appropriate to reading is not the confidence appropriate to building.

**Guardrail.** Keep a written **known-unknowns log** per component: the things the design assumes and nothing has verified. Run the experiment even when the answer seems certain — especially then, because the surprises live exactly there. And apply a stated rule: *no component is described as done until something has failed inside it.*

### 11.4 The loss of scaffolding

**Symptom.** Stalling when there is no platform team to ask, no pipeline to deploy into, no observability stack to instrument against and no process to appeal to. Or the mirror image: rebuilding the scaffolding — governance, standards, a review process, a design template — before shipping anything.

**Cause.** The profile's real but unquantified dependency. The effectiveness of an architect in a large bank is partly a property of the institution: the pipelines, the compliance machinery, the review forums, the vendor processes, and colleagues who handle deployment, testing and operations. None of that will exist at the target company. Note carefully what this claim is and is not — it is a statement about the environment, not about the person, and the evidence for it is the description of the environment rather than any failure of the subject.

**Guardrail.** Name the dependency out loud, in a list, before joining: which parts of what I do are mine and which are the institution's. Then build the minimum substitute deliberately and fast — a deploy script, a CI job, an alerting rule, a log query — treating them as part of the job rather than as missing infrastructure. The version of this failure that is harder to see is over-compensating: importing the institution's processes to feel effective again. The test is whether the scaffolding ships something inside a week of being built.

### 11.5 The translated standard

**Symptom.** Pushing for the standards of the previous environment in a company that cannot support them yet: change control, sign-off, a formal architecture review for a two-day change, a vendor evaluation process. Frequently delivered with the best possible justification and the worst possible effect.

**Cause.** Genuine professional conviction — the belief, earned over two decades in regulated systems, that skipping these steps causes harm. The problem is not that the belief is wrong in general; it is that the steps are calibrated to a blast radius that does not exist yet, and a five-person company that adopts them before it has a product will be slowed to a stop by the right practices at the wrong time.

**Guardrail.** A rule for the first year: **propose the control, and propose the thing it protects against.** If the answer to "what specifically has gone wrong that this prevents" is "nothing yet", the control waits until it does — and instead of the control, write the detector. The detector is cheap, it is the part that catches a real incident, and it is the part a startup will accept. This is the same discipline as §12's translation rule, applied to the candidate's own instincts rather than to a fictional reviewer's.

## 12. The banking-to-startup translation

### 12.1 The evidence position, stated before the analysis

Neither profile file describes a working environment: both are OSINT compilations of public traces — repositories, posts, certifications, profile pages — and neither records the internal stack, team structure, release process, on-call arrangement or engineering standards of the current employer. Nothing in this section is attributed to any employer, and no claim here rests on a fact about one. **Why this section is still worth writing:** the environment *class* is public and material. Two decades of regulated-enterprise and system-integrator engineering selects for habits, and this guide's job is to say which of those habits the target role rewards and which it punishes. That is a claim about a category of environment and about an 18-year career history, both of which the profile files do support.

### 12.2 What transfers

**Rigour in the face of incomplete evidence.** The most valuable transferable habit, and the one the target role needs most. Structured practice at stating assumptions, naming the evidence class, defining what would change the decision, handling a problem by taking the assumptions apart. A startup's hard decisions — which model, which sandbox boundary, where the failure domains are — are made with exactly this quality of evidence, and most engineers make them by instinct.

**Safety framing.** Asking "what is the worst thing this component can do, who is harmed, and what is the audit record" before the design settles. The job description's first sentence names safety boundaries as part of the runtime. In agent engineering this habit arrives late and badly for most practitioners, because the standard failure ("the agent was helpful in an unhelpful direction") does not feel dangerous until it is.

**The habit of naming failure modes.** Writing the failure taxonomy down before implementation rather than discovering it in production. The repository does this at length, and the target role's own measures are reliability measures. Related: tolerating complexity without simplifying it away.

**Communicating cost and risk to people who are not engineers.** The ability to explain the cost of a design choice in a form a founder or a customer can act on. Rare in the IC population at this company size, and directly relevant, since cost per task is one of the four stated measures.

**Written communication.** 629 files of it. At a small company, written clarity is scarce and high-leverage: decision records, incident notes, component READMEs and candidate-visible documentation are all immediately useful.

### 12.3 What does not transfer

| Does not transfer | Why it fails at the target | What replaces it |
|---|---|---|
| **Governance scaffolding** — change advisory, sign-off chains, architecture review boards, formal exception processes | There is nobody to convene them and no volume of change that justifies them; the mechanism is calibrated to blast radius the company has not yet accumulated | Code review by the people who will be paged; a written record for expensive-to-reverse decisions only; deploy and roll back fast enough that review happens after the fact |
| **Vendor and procurement processes** — RFPs, due diligence, multi-quarter evaluation cycles | Tools are adopted in an afternoon and dropped in a week | An afternoon trial with a fixed evaluation question, and a cost cap |
| **The assumption of a platform team** — deployment, CI, observability, testing, on-call all exist and belong to someone else | None of it exists. The runtime engineer is the platform team | Build the minimum substitute deliberately (§11.4). This is the single largest practical difference between the two environments |
| **An established target state and a roadmap to align to** | The description says the opposite: the role defines the problem when requirements and approaches are unclear | Tolerating ambiguity as a working condition rather than as a phase before the work |
| **Regulatory constraints treated as given inputs** | The company is not a bank. Its constraints come from its customers' regulators, indirectly and later | Anticipating which constraints will arrive with the first regulated customer, and designing the isolation and audit trail before someone asks |
| **Decision by committee and by consensus** | A five-person team cannot run a decision process per change; unresolved questions get decided by whoever ships | Deciding, recording, and reversing cheaply. Reversibility replaces consensus as the safety mechanism |
| **The inverse-complexity reflex** — two-decade habits of structuring large systems | A five-hundred-line service does not need four layers, a plugin system or an abstraction for the second case | Building the smallest correct thing; adding structure when the second case actually arrives |

### 12.4 The real risk, stated in the form it will actually be experienced

**An architect's instinct to design can read as an inability to ship.** This is the guide's most uncomfortable claim and the one most likely to be true. It is worth being precise about how the misreading happens, because it is not a failure of character and it is not cured by intention.

A hiring team at a small company reads for one signal above all others: *has this person made something work that somebody else used?* A candidate whose public output is 629 documents, of which the most substantial are analyses of systems he did not build, supplies a very strong signal for the opposite: *this person is extremely good at describing.* The documents being excellent makes the read worse, not better — the better the design, the more clearly it demonstrates that the candidate's best work product is a document about shipping rather than a shipment. At a startup, where the cost of a wrong hire is measured in months of runway, that reading is rational.

Three honest consequences follow, and none of them is a reassurance:

1. **The misreading cannot be argued away, only displaced.** A statement of willingness to code is worth nothing; a running service in a public repository is worth a great deal (§9). The artefacts have to exist before the application, not after (§10.1).
2. **The first ninety days either confirm or destroy the read, and the confirmation is fast.** In a small team, the first component is visible to everyone and either it works or it does not. A candidate who is genuinely strong at building will prove it in weeks; a candidate who is not will be discovered in the same period, which is exactly why the honest assessment in §7.1 matters more than the application strategy.
3. **The asymmetry is not fair and it is not fixable by the candidate alone.** Two decades of design work is a genuine achievement and it does not count as evidence of shipping. The response is not to devalue the career; it is to stop expecting the CV to make the case.

### 12.5 What the version that works in both environments looks like

Stated as a short list, because this is the practical payload of the section.

- Keep the rigour, drop the ceremony: record assumptions and reversal costs in an ADR for expensive decisions, and skip the process around everything that is cheap to undo.
- Keep the safety framing, make it code: a boundary the design claims should have a test that attempts to violate it. §7.3's escape tests are the model.
- Keep the failure discipline, move it earlier: write the failure taxonomy, then instrument for it in the first version rather than after the first incident.
- Keep the written communication, attach it to artefacts: a README with numbers is worth more than a design note, and it is the same skill.
- Drop the inverse-complexity reflex and the assumption of scaffolding consciously, and treat both as things to notice in the first week rather than to import.

## 13. The AI-era effect on the role, evidence-graded

### 13.1 The grading scheme

Every claim below carries one of five grades, and the grade is part of the claim:

- **Measured** — a study with a stated method, sample and result, read from the primary source.
- **Surveyed** — self-reported data collected at scale, with a stated methodology.
- **Vendor-sourced** — research published by a party with a commercial interest in the finding.
- **Self-reported** — a claim by an individual about their own work or effect.
- **Projected** — a forecast or opinion with no measurement behind it.

**Method and tool limitation.** `web_search` was not used for any claim in this section; every external source was retrieved with `web_extract` directly from a primary URL on **2026-09-28**, and the retrieval date is recorded with each claim. Where a search would have been needed to establish something and the only path available was a primary URL that did not exist, no claim was made. **An empty or unavailable search is a limitation of the research path, not evidence of absence**, and the small number of cited studies reflects that limitation rather than the state of the literature.

### 13.2 The graded claims

### 13.3 What follows for this role, reasoned only from the graded claims

Three inferences, each tied to a claim above.

1. **If the time-horizon trend is real, the binding constraint on agent products is reliability over longer runs, which is exactly what this job description is built around.** The paper does not attribute progress to better reasoning alone but to reliability and mistake-adaptation — retries, recovery, error handling, not losing state. That is a description of a control layer. It is the strongest available argument that this role is where the product risk sits, and it is a measured argument rather than a projected one.
2. **Evaluation and cost attribution appreciate as run length grows.** A 50-minute horizon at 50% success means most long runs fail, which makes failure triage and cost-per-completed-task more valuable than cost-per-token. The description's four measures map onto this directly, and the candidate's documented depth in evaluation is the asset that appreciates.
3. **The productivity claim is the one to be careful with.** The METR result is a caution against citing AI-tool speed-ups as evidence of anything, because the developers in that study were wrong about their own direction of travel. A candidate whose public output is large and AI-tool-mediated should expect a sharp interviewer to ask whether the volume is productivity or whether it is the volume that AI tools make cheap. There is no good prepared answer to that question; there is only the artefacts.

### 13.4 The requirement worth remarking on

The description lists **"effective use of AI tools while keeping their own judgement"** among "what they bring" — the same section that carries the five-year floor and the distributed-systems foundations. That is a hiring requirement rather than a preference, and it is unusual enough to note: most descriptions in this period treat AI-tool fluency as a soft preference, a culture fit, or an omission. Two consequences.

First, it is the one requirement in the entire description that this profile meets without qualification, and it should be the first thing an application leads with — with the qualifier that "effective use" and "keeping judgement" are separate demands, and the second one is the hard half. The METR result is the substantive knowledge to bring to that conversation, because it is precisely a case in which judgement about an AI tool would have contradicted the users' own sense of it.

Second, the requirement cuts both ways for this candidate. A repository produced with heavy AI-tool assistance demonstrates fluency, and it also invites the question of whether the volume would exist without it. The repository's own framing — a documented learning method of writing down, practising, and choosing carefully after hands-on exploration — is the honest answer, and it is verifiable from the corpus. What is not available is an answer that claims the tool amplified an otherwise-shipped record, because there is no such record to amplify.

### 13.5 What the AI era does not change here

- The four measures. Task success, reliability, latency and cost are unaffected by the tooling debate; if anything, tooling makes cost attribution harder by adding indirection.
- The artefact gap. No AI tool closes §7's gaps, because the gaps are about having shipped rather than about the effort shipping costs — and the METR result is the specific reason to distrust the intuition that it does.
- Accountability. A runtime engineer is answerable for what the component did to a customer, whoever or whatever wrote it. That is the part of the role the graded evidence leaves entirely untouched.

## 14. The Cymbal Bank worked example (fictional, illustrative)

**This entire section is fictional.** Cymbal Bank is this repository's standard fictional persona. No person, team, system, figure, incident or document in this section is real, none is derived from any employer, and none should be read as a description of any organisation's practice. Its purpose is to put the guide's translation argument (§12) into a concrete scene and to show where the habits the profile evidences are exactly right and where they would cost a small company time. It is the same device the third guide used in its §13 worked example (`../senior_data_platform_architect_guide.md`); here the scene is tuned to this role, and the subject's position is deliberately the one that exposes the risk — he is the **reviewer**, not the builder.

### 14.1 The scene

Cymbal Bank, Singapore. An internal platform team has spent eleven weeks building **Meridian**, an internal agent runtime that performs two kinds of work: it investigates reconciliation breaks between two systems and drafts a case note for operations staff, and it answers policy questions from the bank's internal documentation with citations.

Meridian's architecture, as presented: a planner that decomposes the request into steps; a retrieval layer over an internal document store; a tool layer exposing four tools — a read-only query tool against a reporting replica, a document search tool, a ticketing tool that can comment on and close cases, and a **notification tool that can email the operations distribution list**; a context assembler; and an evaluation suite that currently has nine hand-written examples. It runs on one Kubernetes cluster, uses two models (a frontier model for planning and a cheaper model for extraction), and is used by about forty operations staff in a pilot. There is no sandbox in the architecture, because the agent does not execute user code. Model credentials are held in one service account shared by both workloads.

Jack Liu Shurui sits on the bank's design authority as the GenAI architecture reviewer. He has thirty minutes on the agenda. Everything below is what he would say, and — separately — what the same review would cost if he said all of it at a company of five.

### 14.2 Where the reviewer's instinct is exactly right

Six findings, all of which a small company would benefit from hearing and most of which its engineers would not have raised unprompted.

1. **The irreversible action is the risk, and it is in the notification tool.** Queries are read-only, case comments are reversible, and closing a case is recoverable in a ticketing system. The notification tool can email forty operations staff, and that cannot be taken back. The review finding is specific: the tool that can act on the world outside the system should sit behind an approval gate, or be scoped so that the agent can draft and a human can send. This is the instinct that arrives late in agent engineering and it is the one that prevents the incident nobody wants to explain.
2. **Retrieved content is attacker-influenced.** Meridian's retrieval corpus contains documents written by people, and among them are emails, ticket comments and external correspondence. Any of it can contain instructions. This is the trust-boundary question, and it is the one area where the profile's public evidence is unusually strong — 62 files and a 679-line guide on exactly this. The finding: the agent's plan should not be able to call the notification tool as a consequence of text that arrived through retrieval, and the boundary should be enforced in code rather than in a prompt instruction.
3. **The service account is the privilege problem, and the audit evidence depends on it.** One service account shared by two workloads means the run cannot be attributed to a requestor, the credentials cannot be scoped to the task, and the audit trail cannot answer "who authorised this". The finding: mint credentials per run with the narrowest scope the task needs and a fixed expiry. This is §7.4's gap, and it is the finding a banker's instinct produces fastest.
4. **The evaluation suite cannot support the pilot it is being asked to support.** Nine hand-written examples is a demonstration, not a regression suite. The finding is not "more examples" but "the suite must be representative of the forty users' actual task distribution, must have a stored baseline, and must block a change": the failure modes of a retrieval-and-planning system are distributional, and a nine-item suite produces false confidence.
5. **Cost per completed task is unbudgeted and unattributed.** Two models, no per-run cap, no attribution to a requestor, no reporting. The finding: a budget per run and a metric per completed task, not per token — because the interesting cost is the cost of the runs that failed and were retried.
6. **The design authority is being asked to approve an architecture that has no rollback path for a behaviour change.** No versioned prompt or policy artefact, no way to route a class of requests to the previous behaviour, no drift detection. The finding: behaviour is code and needs the same versioning and rollback story.

Every one of those six is a correct finding. None of them requires knowing anything a twenty-year architecture career does not supply, and four of the six are safety or audit findings — the area where this profile is strongest.

### 14.3 Where the same review would slow a startup down

Now the honest half, and it is not a small half. Six ways the same reviewer, with the same instincts and no adjustment, costs a five-person company time.

1. **Asking for the target-state design before the prototype.** "What is the two-year architecture here?" is a reasonable question in a bank and a schedule-ender at a startup whose product is three months old. The finding to keep is the boundary, not the roadmap.
2. **Requiring a change process for prompt and policy changes.** A change advisory for a prompt edit is proportionate when the change affects forty operations staff in a regulated entity and is not proportionate when it affects a product's first twelve customers — where the proportionate control is a regression gate and a fast rollback.
3. **Insisting on dual-model redundancy before the first paying customer.** Resilience engineering a system before it has traffic spends the scarce engineering capacity on a failure that is not yet the binding one. Correct at year three; a distraction at month two.
4. **Asking for a business case before approving a spike.** "What is the expected value of this change" is the right question in a bank with a portfolio of competing initiatives and the wrong question about a two-day experiment whose entire purpose is to find out whether the value exists. Cost-benefit analysis is how you choose between options you understand, not how you explore an option you do not.
5. **Treating the review's sign-off as the safety mechanism.** This is the deepest difference and the hardest to see from inside a bank. In a regulated institution, the control is often the review; the design authority's approval is the artefact that demonstrates diligence. At a startup, the control is a test, a boundary, a budget cap and a rollback, because there is no review to convene when something goes wrong at two in the morning. A review finding that ends in a decision is worth less than the same finding expressed as a failing test.
6. **Asking for a platform team's deliverable.** "Which team will operate this?" is a correct governance question in an organisation of thousands and a category error in one that has six engineers, all of whom operate what they build. The right version of the question is: "who gets paged, and what does the runbook say?"

### 14.4 The same review, run at startup pace

The same six findings, delivered in a way that helps rather than stalls — this is the translation §12 argues for, made concrete:

- Send the six findings **before** the meeting, in one page, with the reversible ones marked.
- Nominate **two** as blocking: the irreversible tool action and the per-run credential scoping. Block on those and only those.
- Convert the rest into tests rather than decisions: a tool-boundary test, a prompt-injection data path test, a baseline-plus-regression gate, a per-run cost cap assertion. Four tests, one afternoon of combined work, and each one survives the reviewer's departure in a way a review minute does not.
- Ask the questions that produce information rather than compliance: *what is the worst thing the sender tool can do? what does the trace look like when it does? who gets paged? how do we roll back a behaviour change?* Each of these has an engineering answer, and the answers are the control.
- Say the quiet part: "if we were a bank I would ask for four more things; we are not, so I am asking for two and a test." Naming the standard and the reason for departing from it is what makes a reviewer trusted rather than resisted.

### 14.5 What the example is for

The scene is fictional and the lesson is not. The content of the review above is where this profile is genuinely strong, and the profile's public evidence supports it: the safety framing, the failure-mode discipline, the prompt-injection depth, the audit question and the cost question are all real strengths, and none of them is a paper credential.

What the example demonstrates is that the difference between an asset and a liability here is **the form the finding takes**, not its content. A finding that ends in a decision requires a governance mechanism to have force, and there is none at the target company. A finding that ends in a test has force immediately, needs nobody's sign-off, and is exactly the artefact class this job description screens on. The same applies to the candidate's own evidence: the analysis is not the deliverable, in this role or in this interview. **A finding that ends in a test is a contribution; a finding that ends in a document is a description.** That sentence is this guide's practical summary of §12, and §15's action list is its execution.

## 15. One-page summary and action list, then the claims audit

### 15.1 The one-page summary

**The role (§1–§2).** An Agent Runtime / Control-Layer Engineer builds the machinery that makes an agent's promise — taking complex work through to a finished result — true: context and memory, model and tool orchestration, planning and execution, tool and MCP integrations, evaluation and quality feedback, safety boundaries, observability. It is measured on task success, reliability, latency and cost. It owns components and their delivery; it does not own the model, the product, the research agenda, the data-centre substrate, the customer's governance obligations or pricing. Its identity, stated once: **the runtime's product is completion.**

**What is new about this assessment (§1.1).** Three things. A different **direction** rather than a different domain — this is a step out of the architecture track, so the question changes from "how much of this domain does he know" to "what has he shipped and can it be inspected". A new **evidence source** — a 629-file public body of work now large enough to audit as an object, which is possible only because the work exists. And a gap of a different **kind** — an artefact gap rather than a knowledge gap, closable by shipping, not by reading.

**The integrity rule, as a finding rather than a disclaimer (§1.4, §4.5).** The repository's evidence is writing, and writing is evidence of understanding rather than of having built or operated a system. Audit §4 converts this from a caution into a measurement: the repository is dense where knowledge can be documented and thin or silent where competence must be demonstrated.

**The measurement (§4).** Against 629 markdown files, measured 2026-09-28: `prompt.injection` in 62 files, `\bMCP\b` in 65, `idempot` in 112, `agent runtime` in 26, `model routing` in 18, `control layer` in 20 (most generically used, only 4 in the agent shelf), `context engineering` in 11, `browser automation` in 9, `task queue` in 8, `long.term memory` in 8, and **`execution isolation` in exactly 1 file, incidentally**, in a cloud-function security checklist. **The requirement map (§5).** Of seventeen description lines: one met without qualification — effective AI-tool use. Five met as documented depth. Six partial. Three not evidenced. Two unknown. Every requirement satisfiable by knowing is met or partial; every requirement satisfiable only by having done is unproven. The two decisive lines are the shipping record and the distributed-systems foundations: the years are met with room to spare, the shipping record is invisible, and the conceptual strength is broad while the operational experience is absent.

**The interview (§8).** The loop will probe the substrate, ownership and ambiguity tolerance. Answer from what is documented as what is documented; answer operational questions from the nearest real analogue and name it; say unknown where it is unknown. Do not answer "I wrote a guide on that" — in this role class it ends interviews.

**The plan (§9).** Ninety days: an evaluation harness with a baseline and a CI gate; a durable queue with idempotent consumers and a dead-letter path; a sandboxed code-execution service with boundary tests; the three wired into one agent runtime with four published numbers; tenancy plus one merged external contribution; and a dated release history. **Three inspectable artefacts outweigh three more guides** — and if ninety days produces no running artefact, the constraint is cadence rather than knowledge, which is the most important thing either party can learn.

**The translation (§12).** The real risk, stated once: an architect's instinct to design can read as an inability to ship, and the better the design work, the stronger that read. What transfers is rigour, safety framing, failure-mode discipline and written clarity. What does not transfer is governance scaffolding, vendor processes, the assumption of a platform team, an established target state, decision by committee, and the inverse-complexity reflex. What the worked example (§14) adds: the review's content is right, and its **form** is the problem — a finding that ends in a decision needs governance, a finding that ends in a test has force immediately.

### 15.5 Running this analysis again

The role moves faster than the framework, and the evidence base grows. Re-run in six steps, mirroring the predecessors' protocols:

1. **Re-measure §4.** Re-run the same greps with the same command form and date the results. What matters is the *shape* — architecture vocabulary dense, substrate vocabulary thin — and the shape is worth re-checking more often than the numbers are.
2. **Re-check §7's artefacts.** If the queue, the sandbox and the harness now exist, the §5 verdict table must be re-scored, and several PARTIAL rows should become MET. A guide describing a gap that has since closed is a stale assessment wearing a confident voice.
3. **Re-test the compensation absence (§13.6).** It is a finding, not an assumption. If a named source with a date, geography and methodology now publishes a figure, print it with those attributes; if the only new material is another recruitment guide or gated survey, the absence stands.
4. **Re-read the description.** §5's map is a line-by-line reading of a specific document. If the description changes, the map is invalid and must be rebuilt from the new text rather than edited.
5. **Re-grade §13's claims.** The METR material states that its own results age quickly; the discipline is to re-read the current version of each source rather than to accumulate stale citations. Add sources only when they can be read from a primary URL and dated.
6. **Re-run §9's kill criterion.** If ninety days passed and no artefact shipped, that finding outranks everything else in this guide.

**Stopping rule.** The analysis is current when §4's shape still holds on a fresh measurement, §5's verdicts match the artefacts that now exist, §13's citations are within their own stated currency, and §15.3's absences have been re-tested rather than assumed.

### 16.4 Closing

This guide set out to do something the three predecessors could not. They compared architecture roles and asked how much of a domain the subject already knew; this one asks a different question — whether the next move leaves the architecture track altogether, and what happens to an assessment when the thing being hired for is a running system rather than a design for one. That reframing produced the guide's three contributions: the direction change as the structural insight (§1.1(i)), the repository audited as an evidence artefact in its own right (§4), and the finding that the gap here is an artefact gap rather than a knowledge gap (§1.1(iii)).

It also produced the guide's least comfortable conclusion, which is why §4 ends as it does and why §5 marks the two load-bearing lines the way it marks them. The repository is a substantial public body of technical writing — 629 files, 193 site posts, 197 blog posts, 166 public repositories — and the job description names open-source work or technical writing as something it wants. That is real, and §6 states its value without inflating it. But the description's hard requirements are a shipping record and distributed-systems foundations, and on those the measurement returns thin counts and silence: one incidental mention of execution isolation, eight files mentioning task queues and none of them a queue, no trace schema, no CI-gated evaluation harness, no measured task-success or cost figure anywhere in the corpus. The counts in §4 are not there to embarrass the evidence; they are there to say precisely which parts of it are load-bearing for this role and which parts are not.

What follows is therefore unsentimental, and it is the same conclusion the third guide reached in a different key. Ninety days producing an evaluation harness with a baseline, a durable queue with idempotent consumers and a dead-letter triage, and a sandboxed code-execution service with boundary tests — wired into one minimal runtime with four published numbers — would do more for this application than any further reading, and would also answer the question the interview cannot answer from a CV (§9, §8.1). Three inspectable artefacts outweigh three more guides. If ninety days produce no running artefact, that is a finding about cadence rather than about knowledge, and it is the most important thing either party could learn from this analysis.

The integrity rule this guide has applied throughout is now stated as a finding rather than a caution, and it is where a body of writing stops being able to testify: everything in §4 and §5 is subordinate to it, and no guide in this repository — not the sandboxing survey, not the evaluation shelf, not the 971-line runtime cache treatment — is treated as evidence that its author has built or operated the thing it describes. That is not a hedge. It is the precision of the instrument, and the whole analysis is calibrated to it. **Writing about a system is evidence of understanding, not of building one.**
