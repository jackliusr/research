## 1. The Overview

### 1.1 The Short Answer

**Threat modelling is the structured activity of working out what can go wrong with a specific system before it is built — and turning the answer into an owned, tracked, verifiable set of mitigations.** It is not a brainstorm about "hackers", and it is not a compliance checkbox: it is an engineering discipline with a defined notation (the data-flow diagram), a defined analysis mechanism (STRIDE applied per element), a defined knowledge base (the threat libraries), and a defined output contract (the risk register). The canonical framing that holds the whole discipline together is Shostack's Four Questions (2014, ✅-canon, §2): **What are we building? What can go wrong? What are we going to do about it? Did we do a good job?** Every method, every tool and every table in this guide exists to answer one of those four questions. The one-line essence: **a threat model is the system's design seen through the adversary's eyes, written down before the adversary gets to read it** (§10).

### 1.2 The Definition — the Structured Activity

The definition to hold in an interview, in a review, and in the glossary: **threat modelling is the systematic, structured activity of identifying, enumerating and prioritising the threats to a specific system — and of deciding, documenting and tracking the mitigations** — as opposed to the informal activity of "thinking about security". The verified anchors:

- **The MITRE-adjacent and OWASP definitions:** OWASP's community page (✅ verified live this pass) defines a **threat model** as "a structured representation of all the information that affects the security of an application. In essence, it is a view of the application and its environment through the lens of security," and threat modelling as "a process for capturing, organizing, and analyzing all of this information." The Wikipedia threat-model article (✅ verified live) describes threat modelling as "a process by which potential threats... can be identified and enumerated, and countermeasures prioritized." Both say the same thing: **structured, not spontaneous**.
- **The Manifesto's definition (2020, ✅ verified live):** "Threat modeling is analyzing representations of a system to highlight concerns about security and privacy characteristics." Note the word *representations* — the discipline works on a model of the system (the DFD of §3), not on the system itself. That is what makes it design-time: you analyse the drawing before the implementation exists.
- **The Microsoft definition (MSDN 2006, ✅ verified live):** "the methodical review of a system design or architecture to discover and correct design-level security problems," and — the honest part — "There aren't any well-established ways to measure the quality of a threat model." That 2006 caveat is exactly why §8 (metrics and maturity) exists: the discipline has spent two decades building the measurement the founders admitted they lacked.

**What the structured activity consists of** — the five movements that every credible method shares, in order: **(1) model** (draw the system — the DFD, §3); **(2) decompose** (cut the model into elements — processes, data stores, flows, entities — and name the trust boundaries); **(3) analyse** (apply a discovery mechanism per element — STRIDE-per-element, §4 — and enrich it from the libraries, §5); **(4) decide** (score, prioritise, and assign mitigations or explicit risk acceptance — the register); **(5) verify** (check the model's coverage and the mitigations' reality — §8). The sibling's [security_by_design_guide.md](security_by_design_guide.md) §2 covers the *method* layer (STRIDE/DREAD/PASTA/attack trees); this guide covers the *execution* layer underneath it.

### 1.5 The Canon — Where the Discipline Comes From

The methodology has a documented lineage, and the dates are worth holding because they explain why the discipline looks the way it does (each ✅-verified this pass unless marked):

- **1970s — the DFD is born (the notation layer):** Larry Constantine proposes the data-flow diagram; Edward Yourdon, Tom DeMarco, Chris Gane and Trish Sarson popularise it within structured analysis (✅ Wikipedia) — DeMarco's *Structured Analysis and System Specification* (Yourdon Press, 1979) and Gane & Sarson's *Structured Systems Analysis* (1977) are the canonical texts. The notation arrives *before* the security discipline: threat modelling will inherit a ready-made vocabulary.
- **1999 — STRIDE (the classification layer):** Loren Kohnfelder and Praerit Garg develop the STRIDE model at Microsoft (✅-cross-ref, the sibling's §2.2 ledger); Schneier's attack trees appear the same year (sibling §2.5). The threat-modelling canon is born.
- **2004 — the first book (the process layer):** Frank Swiderski and Window Snyder write *Threat Modeling* (Microsoft Press, 2004), developing "the concept of using threat models to create secure applications" (✅ Wikipedia).
- **early 2000s — the trust boundary (the security layer):** the DFD's fifth element, the trust boundary, is added to DFDs specifically for threat modelling (✅ Wikipedia) — the moment the systems diagram becomes a security diagram.
- **2006 — the per-element mechanics (the execution layer):** the MSDN Magazine STRIDE article (Hernan, Lambert, Ostwald & Shostack) publishes the *Threats Affecting Elements* matrix — the per-element application becomes a documented, teachable mechanism (✅ this pass, §4.1).
- **2014 — the Four Questions (the framing layer):** Shostack's *Threat Modeling: Designing for Security* (Wiley) makes the practice approachable by framing it as four questions (✅-cross-ref, §2.1).
- **2020 — the Manifesto (the community layer):** the Threat Modeling Manifesto — values, principles, patterns and anti-patterns, written by a working group including Shostack, de Vries (IriusRisk) and Wuyts (LINDDUN) (✅ this pass) — followed in 2024 by the Threat Modeling Capabilities document (⚠-mentioned via Wikipedia, not extracted this pass).
- **2020s — the tooling and the as-code layer:** pyTM ("the first Threat-Model-as-Code tool", ✅ Wikipedia), Threat Dragon's rule engine (✅), and the platform tools industrialise the practice (§6–§7).

**The pattern:** each decade added a layer — notation (1970s), classification (1999), process (2004), execution mechanics (2006), framing (2014), community (2020), automation (2020s). A modern practice contains all of them; that is what this guide assembles, and the layers' dates are the interview-ready story of why the discipline has the shape it does.

## 2. The Four Questions

### 2.1 The Shostack 2014 Framework

The Four Questions are Adam Shostack's framing from *Threat Modeling: Designing for Security* (Wiley, 2014) — ✅-canon, verified in the sibling's ledger, with the book itself cited by Wikipedia's threat-model article (✅ verified live). The framework, in the sibling's verified wording (§2.1):

1. **What are we building?** — the scoping question: the model of the system, its elements, its boundaries, its data.
2. **What can go wrong?** — the discovery question: the threats, enumerated per element with the help of the libraries.
3. **What are we going to do about it?** — the decision question: mitigations, risk acceptance, ownership.
4. **Did we do a good job?** — the verification question: coverage, measurement, and the honest "have we looked at the right things?"

The framework has been re-stated twice since, and both re-statements are worth knowing because they show the lineage moving: the **OWASP Threat Modeling community page** (✅ verified live) uses the same four with "What are we working on?" as Q1, and the **Threat Modeling Manifesto** (2020 — Shostack is an author; ✅ verified live) sharpens Q4 to "Did we do a good enough job?" The *2014 book* wording ("What are we building? / What can go wrong? / What are we going to do about it? / Did we do a good job?") is the canonical interview answer; the *manifesto* wording ("What are we working on? / What can go wrong? / What are we going to do about it? / Did we do a good enough job?") is the current community restatement. The four questions are **method-agnostic**: STRIDE, PASTA, attack trees, LINDDUN, kill chains — all of them are different engines for answering Q2 (and partly Q1); DREAD and the scoring heuristics answer Q3's prioritisation; the metrics of §8 answer Q4. That is the elegant part of the framework: the questions never change, so the methods underneath them can evolve without the discipline losing its shape.

### 2.3 Q1 — What Are We Building? (the Scoping Question)

The first question is the one most teams rush, and the one the Microsoft canon warns about most explicitly: "Getting the DFD right is key to getting the threat model right" (MSDN 2006, ✅ verified live). Q1's output is **not** a paragraph — it is a diagram and three inventories: **(a) the DFD** (all five element types of §3, with every trust boundary drawn); **(b) the element inventory** (every process, data store, external entity and data flow named and typed — the naming discipline is what makes the later analysis auditable); **(c) the flow register** (every data flow with its source, destination, the trust boundaries it crosses, what it carries, and how it is protected — TLS, signing, mTLS — because a flow's protection state determines half of its STRIDE profile). Two scoping disciplines belong here. **First, scope is a security decision:** the MSDN article's rule is to beware of "magic data sources or sinks" — data is not created out of thin air, every data store needs a named reader and writer, and if the analyst finds themselves modelling "details on either side of a trust boundary", the answer is a **context diagram** (the whole system, one process, all external entities) plus **breakout diagrams** per zone (the MSDN "good practice" — ✅ verified). **Second, the scope must include the system's environment, not just its code:** identity providers, schedulers, the core-banking host, the vendor APIs — the threat model of a Cymbal Bank system that stops at the application boundary misses the boundary that matters most (§9's worked example draws the core-banking zone for exactly this reason). Cross-ref the sibling's §9.1 for the same scenario seen from the review angle; this guide's §9.2 shows the Q1 artifacts in full.

### 2.4 Q2 — What Can Go Wrong? (the Discovery Question)

Q2 is where the method lives, and the method this guide deep-dives is **STRIDE-per-element** (§4): for each element of the DFD, ask which of the six categories apply, record what you find, and let the threat libraries (§5) enrich the search. The MSDN 2006 article's framing of the mechanism (✅ verified live): "To follow STRIDE, you decompose your system into relevant components, analyze each component for susceptibility to the threats, and mitigate the threats. Then you repeat the process until you are comfortable with any remaining threats." Two structural warnings from the same article belong in every session: **(1) the attacker does not respect your model** — "the attacker doesn't have to respect your protocol or use your tools," and "you not only have to think like an attacker, you have to think like all attackers. Simultaneously" — which is why the per-element matrix exists: it replaces the team's memory with a checklist; **(2) threats chain** — "If you can pretend to be the administrator (spoofing), you can shut down the system (a denial of service threat)" — so the Q2 output should note follow-on effects without chasing every permutation (the article's own advice: "Don't get too caught up in trying to track down all the follow-up consequences"). Q2 also has a *depth* dimension: STRIDE-per-element finds the category, the **attack trees** (sibling §2.5) find the exact path, and the **libraries** (CAPEC — "here are the 559 known ways") find what the team has never seen. A session that does all three on its top two goals is doing Q2 properly.

### 2.5 Q3 — What Are We Going to Do About It? (the Decision Question)

Q3 is where threat modelling stops being analysis and becomes engineering. The decision per threat is one of four responses, and the discipline's rule — from the sibling's §2.8 and this guide's §9.4 — is that **the response must be written down with an owner and a date, or it is not a response**: **(1) mitigate** — design the control (the sibling's §3 principles are the design language: least privilege, defence-in-depth, fail-secure...); **(2) transfer** — insurance or a shared-responsibility boundary (the cloud provider's controls, the vendor's contractual controls — cross-ref the sibling's §7.1); **(3) avoid** — change the design so the threat no longer exists (remove the endpoint, drop the feature, move the data); **(4) accept** — a written, dated, owned risk-acceptance decision, never a silent drop. The scoring that orders the decisions is DREAD or a calibrated variant (sibling §2.3 — cross-ref, do not re-derive); the artifact is the **risk register** (sibling §2.8 gives the canonical column shape: ID, threat, category, affected assets, score, mitigation, owner, status, due/verified date). This guide's contribution to Q3 is the *quality bar for mitigations*: a mitigation row is only "done" when it names the control, the layer it lives in (design / code / pipeline / runtime), and the evidence that will prove it (the test, the gate, the review — the sibling's §5–§6 mapping). The worked example's register (§9.4) shows the bar in practice.

### 2.6 Q4 — Did We Do a Good Job? (the Verification Question)

Q4 is the question the discipline was historically weakest at — MSDN 2006's "There aren't any well-established ways to measure the quality of a threat model" (✅ verified live) is the honest admission — and the 2020s answer has three parts (all in §8): **(1) coverage** — did we ask the question of every element × every applicable category, and did we examine every trust-boundary crossing? (the SAMM M3 objective literally says "proactive improvement of threat coverage" — ✅ verified, §8.3); **(2) register health** — are the top rows owned, are mitigations landing, is the accepted-risk list reviewed? (§8.4); **(3) currency** — is the model re-opened on every material design change, because "a threat model that is not updated when the design changes is a historical document" (the sibling's §2.7 — cross-ref). Q4 also has an *honesty* component: the answer "we don't know what we missed" is a legitimate, recorded answer — the verification question is about making the *known* gaps explicit, not about pretending to certainty. The Manifesto's principle (✅ verified live) that "documents record those understandings, and enable measurement" is the Q4 thesis: you cannot measure what you did not write down, which is why Q1's artifacts and Q2's registers are not bureaucracy — they are the instrument panel Q4 reads.

### 2.7 The Four Questions in the Bank — the Cymbal Bank Reading

The four questions are method-agnostic, but a bank answers them with bank-shaped weight on each (⚠-structural — synthesis over the verified framework and the cluster's verified material; cross-ref the sibling's §1.6 for the estate-side framing): **(Q1) "What are we building?" carries the estate's shape** — a Cymbal Bank system is never one application: it is a federation of the very old (core banking hosts — the §9 diagram's CBH, cross-ref [ibm_as400_guide.md](ibm_as400_guide.md) for the AS/400-era platforms) and the very new (APIs, cloud, GenAI — cross-ref [api_governance_guide.md](api_governance_guide.md) and the adversarial-ML guides), so the DFD must be drawn *per trust zone* and the scope must include the core and the vendor boundaries explicitly — the §9 example draws both (TB3, TB4). **(Q2) "What can go wrong?" carries the money and the regulation** — in a bank, the T and R categories are *priced* (a tampered payment message, a repudiated instruction — cross-ref the sibling's §1.6 and the [../banking/nets_software_systems_guide.md](../banking/nets_software_systems_guide.md) payments-switch estate), the I category is a PDPA/GDPR *event* rather than a bug (cross-ref the data-governance guides), and the library layer (§5) must include the bank-specific attack families: payment-fraud patterns, synthetic identity, insider paths. **(Q3) "What are we going to do about it?" carries the control environment** — separation of duties is a supervisory expectation, not a design preference (the maker-checker of the §9 register, cross-ref the sibling's §3.6), and every acceptance decision is a written, dated risk decision because the audit trail must survive an examination (the sibling's §8 — DORA, FSM-N05). **(Q4) "Did we do a good job?" carries the evidence burden** — in a bank, the answer is audited: the model's currency, the register's ownership, and the pipeline's history are the evidence an examiner samples (§7.6, §8.4). The four questions do not change in a bank; the cost of answering them badly does.

## 3. The DFD Notation

### 3.1 The Lineage — Yourdon and DeMarco

The data-flow diagram is not a security invention — it is a 1970s software-engineering notation that threat modelling adopted, and the lineage is worth knowing because it explains *why the notation is what it is*. ✅ Verified live this pass (Wikipedia's data-flow-diagram article, which this section follows): the DFD "originated from the structured analysis and design technique methodology in the middle of the 1970s. It was first proposed by Larry Constantine, and popularized by Edward Yourdon, Tom DeMarco, Chris Gane and Trish Sarson." The canonical texts: Tom DeMarco's *Structured Analysis and System Specification* (Yourdon Press, 1979) and Edward Yourdon's *Structured Design* (1979) and *Modern Structured Analysis* (1988) — the **Yourdon–DeMarco notation** — with the parallel **Gane–Sarson** variant (1977) using rounded rectangles where Yourdon–DeMarco uses circles. ✅ The threat-modelling adoption is documented too: the Wikipedia threat-model article (✅ verified live) records that "DFDs were developed in the 1970s as tool for system engineers to communicate... Traditionally, DFDs utilize only four unique symbols: data flows, data stores, processes, and interactors. In the early 2000s, an additional symbol, trust boundaries, were added to improve the usefulness of DFDs for threat modeling." So the five-element DFD of this section is: four classic structured-analysis symbols, plus one security-specific addition. Microsoft's canonical 2006 description (✅ verified live) matches: "DFDs use a standard set of symbols consisting of four elements: data flows, data stores, processes, and interactors, and for threat modeling we add one more — trust boundaries."

### 3.2 The Five Elements

The five elements are the entire vocabulary of a threat-modelling DFD, and the discipline's power comes from the vocabulary being *small*: an entire team — architect, developer, product owner, risk delegate — can read a DFD in minutes because there are only five things on the page (the threat-modeling.com practitioner article makes exactly this point — ✅ verified live: "The power of Data Flow Diagrams is their simplicity. Limited component types and diagram symbols mean that an entire team can quickly and easily understand it"). The elements, per the Microsoft Learn DFD module (✅ verified live — the module names them by function: "Process — the task element", "Data store — the storage element", "External entity — the no control element", "Data flow — the data in transit element", "Trust boundary — the trust zone change element") and the MSDN 2006 symbol table (✅ verified live):

- **Process** — the task element: a computation that transforms inputs to outputs (a web app, a service, a scheduler, a batch job). The "core" of the diagram — the MSDN article: "Processes are computations or programs run by the computer." Notation: a circle (Yourdon–DeMarco) or rounded rectangle (Gane–Sarson); a multi-process is two concentric circles.
- **Data store** — the storage element: where data rests (databases, files, registries, queues, the data lake). Notation: two parallel horizontal lines (Yourdon–DeMarco) or an open rectangle / database cylinder. The rule of thumb: an arrow into a store is a write; an arrow out is a read.
- **External entity** — the "no control" element: a person or system outside the scope that provides or consumes data (a client, a vendor API, the regulator, the core-banking host). MSDN: "Interactors are the end points of your system: the people, Web services, and servers... outside the scope of your system, but clearly related to it." Notation: a rectangle. **The name matters for security:** the element you have *no control over* is precisely the element whose behaviour you must never trust.
- **Data flow** — the data-in-transit element: data moving between elements (network calls, file transfers, message queues). Notation: a one-way arrow (bi-directional as two arrows). The MSDN warning: a data flow "should only include data moving from one component to another and not include data transformation" — the transformation belongs in the process.
- **Trust boundary** — the trust-zone-change element: the border between trust zones, drawn as a dotted line (or a dotted rectangle enclosing a zone). This is the threat-modelling addition of the early 2000s, and it is what turns a systems diagram into a security diagram (§3.4).

### 3.3 The DFD Table — Element / Notation / Notes

| Element | Notation (Yourdon–DeMarco; Gane–Sarson variants) | Notes for threat modelling |
|---|---|---|
| **Process** | Circle (rounded rectangle in Gane–Sarson); two concentric circles = multi-process | Takes ALL six STRIDE categories (§4.2) — the richest analysis target; name it as a "major function", not an implementation detail (MSDN's "think 'major function,' not implementation" — ✅) |
| **Data store** | Two parallel horizontal lines (open rectangle / database symbol in Gane–Sarson) | T / I / D categories apply (§4.2); every store needs a named reader and writer — "beware of magic data sources or sinks" (MSDN ✅); encryption-at-rest is a store-level control |
| **External entity** | Rectangle | S / R categories apply (§4.2); "external" means *outside your control*, not *outside your concern* — the client's compromised laptop is a legitimate attack surface to model (MSDN ✅) |
| **Data flow** | One-way arrow (two arrows for bidirectional) | T / I / D categories apply (§4.2); label the flow with *what* it carries; record the protection (TLS, signing, mTLS) in the flow register — the protection state determines half the threat profile |
| **Trust boundary** | Dotted line (or dotted rectangle enclosing a zone) | The security element: every boundary crossing is an attack point; "you don't trust what's on the other side" (MSDN ✅); boundary placement is the analyst's most subjective — and most consequential — decision (§3.4) |

### 3.4 Trust Boundaries — the Element That Makes It a Threat Model

The trust boundary is the element that makes the DFD a *threat* model rather than a systems diagram, and the MSDN article's treatment of it is the canonical one (✅ verified live): "Trust boundaries are perhaps the most subjective of all: these represent the border between trusted and untrusted elements. Trust is complex. You might trust your mechanic with your car, your dentist with your teeth, and your banker with your money, but you probably don't trust your dentist to change your spark plugs." Two mechanics follow from that. **First, the boundary is a statement of control, not of malice:** "trusted" means *under the same control posture* — the internal network zone, the payment zone, the core zone — and "untrusted" means *outside it*; the DFD's job is to make every zone-to-zone crossing visible, because each crossing is where the controls must exist (authN at the edge, mTLS between services, a gateway between DMZ and internal — cross-ref the sibling's §3.7 Zero Trust micro-segmentation). **Second, the boundary is a modelling decision the analyst owns:** the MSDN article's example — a data flow "contained entirely within a trust boundary" — shows the two honest positions: the theorist says no threat inside a trusted zone, the practitioner says "anything can fail, and this isn't any different"; the article resolves it in terms of priority ("Data flow 1 is clearly more exposed than data flow 3, and the effort you spend examining data flow 1 ought to reflect that greater level of exposure") while keeping the inside-boundary threats on the list — defence-in-depth, because "situations change." The practical rules for a Cymbal Bank estate: **(1)** draw at least four zones — the Internet/DMZ, the internal application zone, the payment/core zone, and the third-party zone — and name every crossing (the worked example's §9.2 diagram shows the pattern); **(2)** treat every *internal* boundary as real — a bank's internal network is not one trust zone (cross-ref the sibling's §3.7 and the data-architect skill-gaps guide's Zero-Trust priority); **(3)** when in doubt about whether a boundary exists, draw it — a boundary you draw and dismiss is a reviewed decision; a boundary you never drew is a blind spot.

### 3.5 The Drawing Rules and the Sanity Checks

The MSDN 2006 article is also the source of the DFD sanity rules (✅ verified live, paraphrased from "some simple rules of thumb"): **(1) no magic data sources or sinks** — data does not appear from nowhere; every data store needs a named user who reads or writes it (a store nobody reads is either dead scope or a hidden exfiltration path); **(2) no psychokinesis as a data transport** — data moves through processes, not directly from "a user's head to the disk"; if two elements exchange data without a process in between, the diagram is wrong; **(3) collapse similar elements within a single trust boundary** — if elements share implementation and trust zone, model them as one element at the top level and break them out in a sub-diagram; **(4) context diagram + breakout diagrams** — model the whole system at one level (one process, all external entities — the classic "context DFD" of structured analysis, ✅ Wikipedia), then break each trust zone into its own diagram; resist modelling both sides of a boundary at equal depth, because "the attacker is under no obligation to use your tools or respect your protocols." Add the structured-analysis hygiene rules (✅ Wikipedia): processes numbered for traceability, a maximum of 6–9 processes per diagram (3 minimum) at any one level, flows named for the data they carry, and the DFD kept free of control flow — no decision diamonds, no loops: the DFD shows *data*, and the security analysis works on data movement, which is exactly where the threats live. A DFD that passes these checks is the Q1 deliverable (§2.3); one that fails them produces a threat model with blind spots no amount of STRIDE effort can fix — the tooling of §6 draws the same five elements, and the tool output inherits every diagram error.

### 3.6 The DFD Levels — Context, Breakouts and the Estate View

The single DFD of a system is actually a *family* of diagrams at different levels, and the level discipline is part of the notation's mechanics (✅-canon per the structured-analysis source record — the Wikipedia DFD article documents the hierarchy and the context diagram; the MSDN article's "context DFD and breakout diagrams" rule is ✅ verified this pass): **(1) the context diagram** — the whole system as *one* process, with all external entities and the flows to them: the level that fixes scope, because everything on the page is in scope and everything off it is a deliberate exclusion (the MSDN article's "the customer never mentioned... that part of the problem is out of scope. But from a security point of view, it's not out of scope at all" — ✅); **(2) the level-1 diagram** — the system's major processes, stores and internal flows, with the trust boundaries (§9.2's diagram is a level-1 view); **(3) the breakout diagrams** — one per trust zone or major process, showing the detail the level-1 view deliberately collapsed (§3.5's collapse rule — elements sharing a zone and technology are one element at level 1 and a sub-diagram below). The security reading of the levels: **the context diagram is where scope is decided, the level-1 diagram is where boundaries are decided, and the breakouts are where the per-element analysis (§4) gets its work list.** The estate view adds one more convention for a Cymbal Bank: the *system* DFD sits inside the *estate* DFD — the neighbour systems (the trading platforms of [../banking/capital_markets_architecture_guide.md](../banking/capital_markets_architecture_guide.md), the payments switch of [../banking/nets_software_systems_guide.md](../banking/nets_software_systems_guide.md)) appear as external entities at the estate level, and the trust boundaries between them are drawn before any single system's breakouts are — because in a bank the integration surface is where the threats concentrate (the sibling's §1.6 — cross-ref). ⚠-structural for the estate-view convention itself (the level hierarchy is ✅ canon; the estate extension is this guide's synthesis over the cluster's estate material).

## 4. The STRIDE-per-Element Mechanics

### 4.1 The Systematic Per-Element Application

STRIDE itself — the six categories, the violated properties, the 1999 Microsoft origin — is the sibling's §2.2 territory (cross-ref it; this section does not re-derive it). What this section covers is the *mechanics*: how the six categories are applied to a DFD *element by element*. The primary-source anchor is the MSDN Magazine article (Hernan, Lambert, Ostwald & Shostack, November 2006 — ✅ verified live this pass), whose core statement is: "Each of the elements (processes, data stores, data flows, and interactors) has a set of threats it is susceptible to... This chart, along with your DFD, gives you a framework for investigating how your system might fail." The article's Figure 5 — the *Threats Affecting Elements* matrix — is the canonical per-element table, and it was extracted live this pass (the matrix as published):

| Element | S | T | R | I | D | E |
|---|---|---|---|---|---|---|
| Data flows | | X | | X | X | |
| Data stores | | X | | X | X | |
| Processes | X | X | X | X | X | X |
| Interactors (external entities) | X | | X | | | |

Two readings of the matrix, both verified in the same article: **(1) processes take everything** — a process authenticates (S), transforms data (T), acts (R), holds data in memory (I — the article explicitly notes "a process holds lots of valuable data in memory. If an attacker can read from the memory of a process, he might not have to break into the database"), can be overwhelmed (D), and runs code (E) — so processes are the richest analysis target; **(2) the matrix is a floor, not a ceiling** — "interactors" get S and R in the matrix because an entity can *pretend to be* something (S) and can *deny* its actions (R), but the article's own worked example shows the analyst adding threats the matrix does not list (an external entity's compromised device feeding tampered data — a T threat on a flow). The modern practice inherits exactly this: the matrix is the checklist that guarantees *coverage*; the analyst's judgement adds the *specifics*. The Microsoft Threat Modeling Tool productises the same mechanics — its documented capability is literally "**STRIDE per Element**: Guided analysis of threats and mitigations" (✅ verified live, Microsoft Learn).

### 4.2 The Per-Element Table

The working table below expands the verified matrix with the *why* and the *example* per category — the version a session actually runs. (⚠-structural for the cell-by-cell example selection: the matrix itself is ✅ verified from MSDN 2006 Figure 5; the examples are this guide's synthesis over the same article's worked analysis and the sibling's §2.2 examples.)

| Element | Categories that apply (verified matrix) | Why they apply | Representative questions / examples |
|---|---|---|---|
| **Process** (P1, P2, ...) | **All six — S T R I D E** | A process authenticates, transforms, acts, holds memory, runs code, and can be overwhelmed — every property is at stake inside it | S: can this process be impersonated (a fake service collecting the data)? T: can its inputs/outputs be modified (corrupted memory, tampered request)? R: can it act without a provable trail (the collection process "submitting revised data and claiming it was not" — MSDN's own example)? I: can its memory be read? D: can it be starved (the last-day-of-quarter DoS example)? E: can a bug in it grant higher rights (buffer overflow → admin)? |
| **Data flow** (F1, F2, ...) | **T, I, D** | A flow is data in motion — the classic in-transit properties: modification, reading, blocking | T: MITM modifies the payment message; I: the flow is readable (plaintext HTTP, over-broad logs); D: the flow is blocked or the channel saturated; also ask the matrix-plus question — is the *sender* of the flow authenticated (an S threat the matrix routes to the entity)? |
| **Data store** (DS1, ...) | **T, I, D** | A store is data at rest — modification, reading, exhaustion | T: an attacker (or insider — "attackers may be insiders, not outsiders" — MSDN) alters stored records; I: the store leaks (unencrypted exports, over-broad query access); D: the store is filled or locked ("Filling up the database is a simple attack" — MSDN) |
| **External entity** (EE1, ...) | **S, R** | An entity is outside your control: its identity can be assumed, and its actions can be denied | S: an attacker poses as the client, the vendor, the batch scheduler; R: the client denies placing the order, the vendor denies the screening result, the trader denies the instruction — the audit-trail question (cross-ref the sibling's §2.2 R and §9 finding #5) |
| **Trust boundary** (TB1, ...) | (not a matrix row — the *crossings* are) | The boundary itself is not an element with properties; every flow crossing it inherits the analysis of both sides plus the crossing controls | For each crossing: what authenticates it? what protects it in transit? what happens if the trusted side is wrong? — the boundary-crossing review is where the gateways, WAFs and mTLS decisions live |

### 4.3 Reading the Matrix — Why Each Category Applies Where It Does

The matrix's logic is worth internalising, because it is what lets a team *reason* instead of *memorise*: **each category attaches to the property that element type can violate.** A data flow is data in motion, so the three in-motion properties apply — integrity (T), confidentiality (I), availability (D); authenticity (S) attaches to the *sender* of the flow, which is an entity or a process, not the flow itself — which is why the matrix puts S on entities and processes, and why the analyst's job includes *moving* the question: "the authentication system for the sales force has not been identified. An inadequate authentication system would present a spoofing threat to the sales force... A little redundancy is great" (MSDN ✅ — the article explicitly shows the analyst finding an S threat while analysing a T flow). A data store is data at rest, so the at-rest properties apply — same T/I/D, different controls (encryption at rest, access control, backup capacity). A process is the only element that *acts*, so it is the only one that can be *impersonated while acting* (S), *deny acting* (R), and *act beyond its authority* (E) — the three property violations that require agency. An external entity is the element you do not control, so the two threats are *identity* (S — you cannot verify what you do not control) and *accountability* (R — you cannot compel what you do not control); everything else the entity does to you arrives as a threat on the flows and processes it touches. This reasoning also explains the **matrix-plus discipline** (⚠-structural, the standard practitioner extension): the matrix guarantees the *default* set per element; a complete pass adds the categories that *reach* the element — a client's compromised device feeding a trusted flow is a T threat *on that flow* (and an S threat on the client entity); a process that writes to a store creates T/I/D questions *on that store's rows* even though the store already has them.

### 4.4 Running the Pass — the Session Mechanics

The session mechanics that turn the matrix into a completed register (⚠-structural — practice synthesis over the verified matrix and the sibling's §2.8 register shape): **(1) order the walk from the boundary in** — start with every flow that crosses a trust boundary (they are the highest-exposure elements; the MSDN article's own priority rule — the exposed flow gets the effort "that greater level of exposure" deserves), then processes, then stores, then entities; **(2) ask all six out loud per element** — the discipline is not "which of these look interesting" but "which of these *cannot* happen, and why?" — the answer to the why is a documented control, and a category dismissed without a why is an open finding; **(3) record verbatim into the register as you go** — no later transcription, no "we'll remember that"; every finding gets the register's columns (sibling §2.8) on the spot; **(4) note chaining without chasing it** — when a threat obviously leads to another ("If you can pretend to be the administrator... you can shut down the system"), record the chain in the row's notes but do not spawn a separate row for every follow-on (the MSDN advice — ✅); **(5) go deep on the top two goals** — after the per-element pass, run attack trees (sibling §2.5) on the two highest-value attacker goals to verify the register's top rows are the real paths; **(6) close with the matrix audit** — a coverage check that every element has a row or a written "not applicable because..." — this is the mechanical heart of §8's coverage metric. The sibling's §9.5 runbook slots this pass into its agenda step 2; this section is the *how* behind that step. Cross-ref [distributed_auth_guide.md](distributed_auth_guide.md) for the S/E deep-dive (the identity machinery) and [api_governance_guide.md](api_governance_guide.md) for the API-surface flavour of every category.

### 4.5 The Per-Element Pass in the Tooling

The matrix is not only a whiteboard technique — the verified tooling of §6 implements it directly, and knowing which tool automates which part of the pass changes how a team runs it: **(1) the Microsoft Threat Modeling Tool** productises the whole mechanism — its documented capability is "**STRIDE per Element**: Guided analysis of threats and mitigations" (✅ Microsoft Learn, §6.2): the tool knows the matrix, generates the per-element threat set from the drawn DFD, and offers the mitigation guidance per category; **(2) OWASP Threat Dragon** implements the same idea through its "rule engine to auto-generate threats and their mitigations" (✅ Wikipedia/OWASP, §6.3): the per-element threat stories fire as elements are placed and connected — the matrix-as-rules; **(3) pyTM** generates threats from the *properties* declared on the model elements in code (✅ OWASP, §6.4): the matrix becomes a rule set over the Python object graph, so the per-element pass runs on every commit (§7.4); **(4) the platforms** (IriusRisk-class) drive the same analysis through questionnaires and risk-model libraries (✅ Wikipedia, §6.5). The discipline's caveat applies to all four: the tool's generated threats are the *matrix's* questions, not the team's judgement — the session's value-add is the matrix-plus analysis of §4.3, the chaining notes, and the not-applicable decisions, which no generator produces. Run the tool to get the baseline rows fast; keep the human pass for the rows that matter (the §4.4 order — boundary flows first).

## 5. The Threat Libraries

### 5.1 Why Libraries — Knowledge Reuse Instead of Memory

Q2 (§2.4) has a ceiling: the unaided team knows only what it happens to remember. The MSDN article's warning is exact (✅ verified live): "If you stop at this point, your threat model will be limited not only by what you know, but what you happen to remember at the time you're working on it... you have to think like all attackers. Simultaneously." The **threat libraries** are the answer: curated, identifier-tagged knowledge bases that a threat-modelling session consults the way a developer consults an API reference — to find the attack the team has never seen, to get a stable ID for the finding (traceability to the audit trail), and to speak a common language with the tools (SAST rulesets, vulnerability feeds, SIEM detections all key off the same taxonomies). The four libraries this guide covers — CAPEC, ATT&CK, CWE, and the OWASP catalog — operate at different layers of the stack, and the analyst's skill is knowing which layer answers which question (the §5.7 mapping).

### 5.2 CAPEC — the Attack-Pattern Dictionary

**CAPEC — the Common Attack Pattern Enumeration and Classification** — is MITRE's community resource cataloguing *how attacks are carried out*. ✅ Verified live this pass (capec.mitre.org): "CAPEC™ helps by providing a comprehensive dictionary of known patterns of attack employed by adversaries to exploit known weaknesses in cyber-enabled capabilities. It can be used by analysts, developers, testers, and educators to advance community understanding and enhance defenses." The site's counter showed **559 attack patterns** at the time of extraction, organised into two browsable views — **by Mechanisms of Attack** (the view rooted at CAPEC-1000) and **by Domains of Attack** (the view rooted at CAPEC-3000) — both ✅ verified live on the site's navigation. Each pattern is an *abstract, technology-agnostic* description of an attack approach (CAPEC's own CAPEC-vs-ATT&CK comparison page — ✅ verified live — positions it exactly: CAPEC and ATT&CK "each focused on a specific set of use cases", with CAPEC as the pattern dictionary), and each pattern carries references and, in the modern form, mappings to the CWE weaknesses it exploits. In a threat-modelling session CAPEC plays the *"exactly how"* role: STRIDE says the flow is tamperable; CAPEC says the tampering happens by this family of patterns (interception, modification, injection); the attack tree (sibling §2.5) picks the specific path. PASTA's stage 6 ("attack modeling" — sibling §2.4) is built on exactly this: attack patterns as the simulation vocabulary.

### 5.3 ATT&CK — the Adversary-Behaviour Knowledge Base

**ATT&CK — the Adversarial Tactics, Techniques, and Common Knowledge** — is MITRE's knowledge base of adversary *behaviour*: real-world tactics and techniques observed in actual intrusions, organised into matrices (Enterprise, Mobile, ICS). ✅-canon (the MITRE CAPEC–ATT&CK comparison page, verified live this pass, confirms the relationship and the distinct role; the ATT&CK framing as "tactics, techniques and procedures observed during campaigns" is uniformly documented — the practitioner comparison sources retrieved this pass describe ATT&CK as documenting "real-world adversary tactics and techniques observed during campaigns, focused on behavior inside an environment"). Where CAPEC is the *abstract pattern dictionary* (what class of attack), ATT&CK is the *observed behaviour catalogue* (what real adversaries actually do, in order): tactics are the "why" columns (initial access, execution, persistence, privilege escalation, exfiltration...), techniques the "how" rows beneath them, each with detection and mitigation guidance. In threat modelling ATT&CK's role is the *reality check and the detection hand-off*: after the STRIDE pass names the categories and CAPEC names the patterns, ATT&CK says "this is what the adversary's chain actually looks like when it runs against your estate — and here is what to detect at each step" — the natural bridge from the design-time model to the runtime monitoring (cross-ref the sibling's §5/§9 logging findings). The ML-extension worth a light cross-ref: the adversarial-ML community maintains an ATT&CK-flavoured knowledge base for AI systems (the "ATLAS" framework — ⚠ **flagged**: its name and role are widely cited in the practitioner press but were not verified live this pass) — cross-ref [adversarial_ml_attacks_guide.md](adversarial_ml_attacks_guide.md) and [llm_development_risks_security_guide.md](llm_development_risks_security_guide.md) for the GenAI threat surface a modern bank estate must add to its ATT&CK-informed models.

### 5.4 CWE — the Weakness Taxonomy

**CWE — the Common Weakness Enumeration** — is MITRE's community-developed taxonomy of software *weaknesses*: the defects in code and design that attacks exploit (cross-site scripting, SQL injection, out-of-bounds write, IDOR...), each with a stable identifier (CWE-79, CWE-89, CWE-639...). ✅-canon (cwe.mitre.org — the sibling's §4.4 verified the CWE Top 25 2024 edition live this pass, with #1 CWE-79 XSS, #2 CWE-787 out-of-bounds write, #3 CWE-89 SQLi, #4 CWE-352 CSRF and their KEV counts; the MSDN 2006 article already pointed at CWE as "one emerging resource" for common flaws — ✅ verified live). CWE's role in threat modelling is the *weakness layer*: the STRIDE category says *what property* is violated, CAPEC says *how* the attack runs, and CWE says *which defect* in the code or design makes it possible — which is exactly what SAST rulesets, the OWASP Top 10 (sibling §4.2), and the CWE Top 25 all speak. The traceability chain closes here: threat → pattern (CAPEC) → weakness (CWE) → verification requirement (ASVS — sibling §4.3) → SAST rule → fixed defect. A threat-register row that carries its CAPEC and CWE identifiers is a row the tooling, the tester and the auditor can all pick up without a translation meeting.

### 5.5 The OWASP Threat Catalog — the Project-Flavoured Library

The "OWASP threat catalog" is a family rather than a single named artifact, and the honest framing matters: ⚠ the *term* "OWASP threat catalog" as a standalone named document is **flagged — not verified as a specific published artifact this pass**. What is verified (✅) is the family: **(1)** the **OWASP Threat Modeling community page** — the methodology guidance (definition, the four-question framework, the lifecycle-continuity doctrine — ✅ verified live, quoted in §1.2 and §2.1); **(2)** the **OWASP Threat Model Project** — the official project site the community page points to (✅ verified live via the page's own link); **(3)** **OWASP Threat Dragon's built-in threat rules** — the tool "implements a rule engine to auto-generate threats and their mitigations" (✅ verified via the Wikipedia threat-model tool survey), i.e. a curated, browsable threat catalogue *inside the tool*, organised around STRIDE/LINDDUN/CIA/DIE/PLOT4ai frames (✅); and **(4)** the **SAMM Threat Assessment practice** as the programme-level layer (✅ verified, §8.5). The practical reading for a session: the OWASP contribution to the library stack is *project-flavoured, tool-embedded threat knowledge* — where MITRE gives you the canonical dictionaries, OWASP gives you the practitioner-filtered, web-app-centric catalogue that ships inside its own tooling. ⚠-structural for any claim that the OWASP catalog is a specific downloadable document; cite the components above instead.

### 5.7 Using the Libraries in a Session

The layered use of the four libraries in one session, as a working method (⚠-structural — the mapping is a practitioner synthesis over the individually-verified libraries; the STRIDE↔library correspondence is this guide's organisation of the canonical sources): **(1) STRIDE names the property** — "this flow is tamperable" (per-element pass, §4); **(2) CAPEC names the attack family** — "tampering here happens via interception-and-modification patterns" (the dictionary); **(3) CWE names the enabling defect** — "the SQLi family is the concrete weakness this API pattern invites" (the taxonomy); **(4) ATT&CK names the observed chain** — "in the wild this is initial-access → execution → exfiltration, and here are the detections" (the reality check); **(5) the register records the IDs** — every accepted finding carries its CAPEC/CWE identifiers so the SAST ruleset, the pentest scope and the SIEM content all key off the same rows. The rule that keeps the libraries from becoming noise: **consult the libraries to verify and enrich a named STRIDE finding — never to generate findings by browsing.** The discovery engine is the per-element matrix; the libraries are its reference material, not its replacement. Cross-ref the cluster's threat-angle guides for the library flavours that matter in a bank: [distributed_auth_guide.md](distributed_auth_guide.md) for the identity-attack patterns, [api_governance_guide.md](api_governance_guide.md) for the API-attack families, and the adversarial-ML guides for the model-attack landscape.

### 5.8 The Fifth Library — the Organisation's Own Threat Ledger

A bank's threat-modelling practice should run one more "library" alongside CAPEC/ATT&CK/CWE/OWASP: **the organisation's own accumulated threat ledger** — the internal record of what has actually gone wrong or nearly gone wrong in the estate (⚠-structural — practice doctrine: the MSDN article's advice to "review current and past security advisories from your own organization as well as other organizations who have implemented similar technologies" is the ✅-verified seed of the practice). The contents, and why they are irreplaceable by the public libraries: **(1) incident and near-miss history** — the sibling's §5.6 red-team/GameDay layer and the post-incident "what did the model miss?" review (§7.3) feed the ledger; a fraud typology the bank has personally suffered is *the* highest-probability finding for its next model; **(2) the vendor and third-party catalogue** — the specific SaaS providers, their known incident patterns and their contractual controls (the sibling's §8.1 third-party register and [../banking/regtech_guide.md](../banking/regtech_guide.md) — cross-ref): the public libraries catalogue vendor-API attack *classes*; the ledger holds the vendor-specific history (e.g. the KYC vendor's past incidents) that makes F11/TM-010 specific; **(3) the estate's repeated-weakness register** — the CWE families that keep appearing in the bank's SAST output (sibling §4.4) are the weaknesses its next threat models should assume, not rediscover; **(4) the regulatory findings and examination themes** — what DORA/FSM-N05 examiners and auditors actually sampled, mapped back into the checklist (sibling §8). The ledger's format is deliberately boring: a structured, searchable list of *threat-observation records* (what happened, where, what library IDs it maps to, what the model should check next time), maintained by the security team and consulted in the §5.7 step 5 of every session. The public libraries answer "what is possible"; the fifth library answers "what has already happened here" — and for a bank, the second question is the one with the money attached.

## 6. The Tooling

### 6.1 The Tooling Landscape — Draw, Analyse, Report

The tooling layer exists to make the three mechanical parts of the discipline cheap: **draw** (the DFD — five elements, drag and drop), **analyse** (the per-element STRIDE pass, automated suggestion), **report** (the register and the document). The verified fact that shapes all of it: every tool's output is only as good as the DFD it is given — the sibling's §2.6 note ("the tool output is only as good as the DFD") and the MSDN canon ("Getting the DFD right is key to getting the threat model right" — ✅) both say the same thing. The tooling families: the free desktop/web **draw+analyse** tools (Microsoft Threat Modeling Tool, OWASP Threat Dragon), the **code-first** frameworks (pyTM), and the **commercial platforms** (IriusRisk, securiCAD, SD Elements) that add risk-management workflow, questionnaires and integrations. Wikipedia's threat-model article's tool survey (✅ verified live this pass) confirms this landscape: Microsoft's tool, IriusRisk, securiCAD, SD Elements, Threat Dragon and pytm are all documented there — the descriptions below follow it and the primary project pages.

### 6.2 The Microsoft Threat Modeling Tool

**The Microsoft Threat Modeling Tool (TMT)** — the free, Windows-desktop tool that productised the SDL methodology. ✅ Verified live this pass (Microsoft Learn): "The Threat Modeling Tool is a core element of the Microsoft Security Development Lifecycle (SDL). It allows software architects to identify and mitigate potential security issues early... we designed the tool with non-security experts in mind," with the documented capabilities including "**STRIDE per Element**: Guided analysis of threats and mitigations", automated guidance while drawing the model, and mitigation management. It draws DFDs (the five elements of §3), runs the STRIDE-per-element engine, and produces the classic TMT report with generated threats and mitigation guidance per element. History (✅ Wikipedia): formerly the **SDL Threat Modeling Tool**. ⚠ **Flagged:** the tool's maintenance has been a live question in the practitioner press since the early 2020s (retirement/archival reports circulate; the Microsoft Learn pages remain published but the update cadence has slowed) — not verified this pass, so before standardising on it, verify current download availability and support. For the record: it is the tool that made STRIDE-per-element a *product feature* rather than a methodology paragraph, and its threat-generation engine is the reference implementation of §4's matrix.

### 6.3 OWASP Threat Dragon

**OWASP Threat Dragon** — the free, open-source, cross-platform threat-modelling application, available as a web app and as a desktop app (macOS, Windows, Linux). ✅ Verified live this pass (the OWASP project page and GitHub): "OWASP Threat Dragon is a free, open-source, cross-platform threat modeling application. It is used to draw threat modeling diagrams and to list threats for elements in the diagram," created by **Mike Goodwin** as an OWASP community project; the web version stores models in GitHub, the desktop version on the local file system; models are JSON files. Capabilities (✅ via Wikipedia's survey): it "supports STRIDE / LINDDUN / CIA / DIE / PLOT4ai, provides modeling diagrams and implements a rule engine to auto-generate threats and their mitigations" — i.e. the OWASP catalog of §5.5 embedded as a rule engine. Threat Dragon's significance for this guide's reader: it is the *current default choice* for the free-tier draw+analyse category — cross-platform, no vendor lock-in, JSON models that sit in the repo (the as-code bridge of §7), and OWASP stewardship that matches the sibling's OWASP-centred secure-coding stack (§4).

### 6.4 pyTM — the Code-First Pioneer

**pyTM** — the OWASP "Pythonic framework for threat modeling" — is the code-first tool: the system is defined as a Python source file, and the tool generates the DFD, a sequence diagram, and the threats. ✅ Verified live this pass (the OWASP project page, the PyPI page, and the OWASP Developer Guide chapter): "Define your system in Python using the elements and properties described in the pytm framework. Based on your definition, pytm can generate, a Data Flow Diagram (DFD), a Sequence Diagram and most important of all, threats to your system." The PyPI description adds the motivation (✅): "Traditional threat modeling too often comes late to the party, or sometimes not at all... The goal of pytm is to shift threat modeling to the left, making threat modeling more automated and developer-centric." Wikipedia's survey (✅) calls it "the first Threat-Model-as-Code tool." pyTM is the bridge between §6's tooling and §7's as-code practice: the model is code, so it diffs, reviews and versions like code — and it is the natural tool for a developer-centric bank team that already lives in GitLab/GitHub and CI (its place in the as-code workflow is §7.2).

### 6.5 The Platform Tools — IriusRisk, securiCAD, SD Elements

The commercial/enterprise platforms add the risk-management layer around the modelling core. All three are ✅ verified to exist with the roles described, via Wikipedia's threat-model tool survey (verified live this pass); their commercial details (pricing, current feature sets) are ⚠-flagged as not verified this pass:

- **IriusRisk** — "provides both a community and a commercial version... focuses on creating and maintaining a living threat model throughout the SDLC. It drives the process using fully customizable questionnaires and risk model libraries, and connects to several other different tools (OWASP ZAP, BDD-Security, Threadfix) to enable automation" (✅ Wikipedia). The "living threat model" is the platform answer to §7's continuous threat modelling — the model stays current because the platform re-asks and re-links as the system changes.
- **securiCAD** (foreseeti) — "performs automated attack simulations on current and future IT architectures, identifies and quantifies risks globally, including structural vulnerabilities, and provides decision support based on results" (✅ Wikipedia) — the attack-simulation family: the model runs the attacks computationally instead of by checklist.
- **SD Elements** (Security Compass) — "a software security requirements management platform that includes automated threat modeling capabilities. A set of threats is generated by filling out a short questionnaire on the application's technical details and compliance factors. Countermeasures are included in the form of actionable tasks for developers" (✅ Wikipedia) — the questionnaire-driven family: threats as generated requirements, tracked to completion.

### 6.7 Choosing the Tooling

The selection logic for a Cymbal Bank delivery estate (⚠-structural — practice guidance over the verified catalogue): **(1) start free and standardised** — Threat Dragon for the draw+analyse teams and pyTM for the code-first teams covers the entire methodology of this guide at zero licence cost, with JSON/Python models that live in the repo (the §7 as-code foundation); **(2) escalate to a platform where the workflow demands it** — an estate with hundreds of applications, formal risk-acceptance workflows and regulator-driven reporting will outgrow the free tools; that is the IriusRisk-class argument (living model, questionnaires, audit trails), and it is a *workflow* purchase, not a methodology purchase — the methodology runs identically in both tiers; **(3) treat the tool as the smallest part of the discipline** — every tool inherits the DFD's correctness (the "getting the DFD right" canon, §6.1), the register's ownership discipline (sibling §2.8), and the re-review cadence (§7.3); a bank that buys a platform before it has a practice is buying a faster way to produce outdated models; **(4) price it as an investment decision** — the cost of the platform vs the cost of the breach it prevents is exactly the business-case frame of [../management/business_case_development_guide.md](../management/business_case_development_guide.md) (light cross-ref), and the DORA/FSM-N05 evidence expectations (sibling §8) give the platform purchase its compliance rationale.

## 7. The Threat-Modelling-as-Code

### 7.1 The Model in the Repo

**Threat-modelling-as-code is the practice of making the threat model a versioned artifact of the code repository** — the DFD definition, the element inventory, the threats and the mitigations live as text (JSON, Python, YAML) beside the source code, so the model gets what code gets: versioning, diffs, code review, and pipeline execution. The verified anchor for the term: Wikipedia's threat-model survey calls **pyTM** "the first Threat-Model-as-Code tool" (✅ verified live), and pyTM's own project description states the goal — "shift threat modeling to the left, making threat modeling more automated and developer-centric" (✅ verified live, §6.4). The practice's thesis is the sibling's §6.1 thesis applied to threat modelling: the same way DevSecOps made security policies "as code" so they version and gate like software, as-code threat modelling makes the *model* itself a first-class repo citizen. The three properties that fall out: **(1) reviewability** — a change to the architecture (new API, new integration, new data store) is a diff to the model, and the diff is reviewed like a code change; **(2) currency** — the model cannot drift quietly, because the pull request that changes the system can be *required* to change the model; **(3) executability** — the model file is input to a generator, so the DFD and the threat list are always derived artifacts, never hand-maintained copies.

### 7.2 The Code-First Workflow

The code-first workflow, as practiced with pyTM and the as-code tools (⚠-structural for the workflow shape — the components are verified: pyTM's generate-DFD/threats capability ✅, the as-code tool family ⚠; the ThreatSpec/ThreatPlaybook names are flagged ⚠ in §6.6): **(1) define** — the system is declared in code: elements (processes, data stores, external entities, flows), their properties (TLS, authentication, data classification), and the trust boundaries, using the framework's element vocabulary (pyTM's `Process`, `DataStore`, `ExternalEntity`, `Dataflow`, `TrustBoundary` classes); **(2) generate** — the tool renders the DFD (and in pyTM's case the sequence diagram) and runs its threat-generation rules over the model; **(3) review** — the generated threats are triaged like generated code: accepted, rejected-with-reason, or enriched; the human judgement of §4.3 sits on top of the generator; **(4) commit** — the model source, the generated artifacts and the triaged register live in the repo, one directory, one history; **(5) diff on change** — the architectural pull request must include the model diff, and the reviewer's first question is "did the threat model change with the design?" The workflow's payoff is the audit trail: every threat ever considered, and every acceptance decision, has a commit hash and a review thread — which is precisely the evidence shape the sibling's §8 regulatory layer (DORA's lifecycle risk management, the FSM-N05 TRM expectations) asks for.

### 7.3 Continuous Threat Modelling

**Continuous threat modelling is the discipline's answer to the fact that systems change** — the OWASP canon states it directly (✅ verified live): "Threat modeling is best applied continuously throughout a software development project... Ideally, a high-level threat model should be defined early on in the concept or planning phase, and then refined throughout the lifecycle. As more details are added to the system, new attack vectors are created and exposed," with the explicit update triggers: "a new feature is released; security incident occurs; architectural or infrastructure changes" (✅). The Manifesto's values make the same commitment: "**Continuous refinement** over a single delivery" (✅ verified live). The practice translates the doctrine into cadence rules: **(1)** the model is *created* at the concept/design phase (Q1's DFD before the first sprint); **(2)** the model is *re-opened* on every material change — new integration, new data flow, new API, first cloud migration, first AI feature (the sibling's §9.5 trigger list — cross-ref); **(3)** the model is *re-scored* on a cadence — threats move as the landscape moves, so the register's likelihood/impact columns get a quarterly review even when nothing changed (the sibling's §2.8 rule — cross-ref); **(4)** incidents feed the model — a real-world event is the highest-fidelity threat intelligence a bank has, and the post-incident review should ask "what did the model miss?" (cross-ref the sibling's §5.6 red-team/GameDay layer). Continuous threat modelling is the *opposite* of the "threat model as a delivery-gate document" anti-pattern — the sibling's phrase is exact: a threat model not updated when the design changes "is a historical document, not a control" (§2.7 — cross-ref).

### 7.4 The CI/CD Integration

The CI/CD integration is the mechanical embodiment of continuous threat modelling, and it exists in two verified-anchor forms plus the practice layer: **(1) the code-first form** — pyTM's model-as-code is *executable*, so the pipeline can re-generate the DFD and the threats on every commit and fail the build on un-mitigated high-severity generated threats (⚠-structural for the exact gate design — the generation capability is ✅, the gate conventions are practice); **(2) the platform form** — IriusRisk's "living threat model... throughout the SDLC" with its automation integrations (ZAP, BDD-Security, Threadfix — ✅ verified via Wikipedia) is the platform-native CI/CD coupling: scan results re-open the model's findings automatically; **(3) the practice layer** — the DevSecOps literature treats "threat modeling as code / automated threat modeling in the pipeline" as a standard stage (⚠-structural — the Practitioner-DevSecOps course canon and the DevSecCon talk "Boost Pipeline Efficiency with Threat Modeling" — the latter listed on the Manifesto's own resources page, ✅ verified live — document the practice). The gate design that makes the integration work (⚠-structural): **the pipeline enforces the model's currency and its top rows' closure, not zero threats** — a sensible gate chain is: (a) model-parses-and-generates (the artifact is never broken), (b) model-diff-required-on-architecture-change (the pull request must show the model updated), (c) no *new* high/critical unmitigated threat (the register's top rows stay owned), (d) the generated report is archived with the build (the evidence artifact — the sibling's §6.2 "green pipeline run is the evidence"). A gate that blocks on any generated threat is bypassed within a quarter; a gate that enforces currency and ownership survives contact with delivery pressure.

### 7.6 The Bank Read — Evidence and Audit

For a Cymbal Bank estate the as-code practice is not a developer convenience — it is the *evidence architecture* for the regulatory layer. The sibling's §8 verified the obligations: DORA's ICT risk management requires lifecycle risk identification and assessment as a formal control (sibling §8.1), the FSM-N05 TRM regime expects technology-risk frameworks with documented assessment (sibling §8.4), and the third-party register demands the vendor-inventory discipline. An as-code threat model delivers the audit shape those regimes ask for: **timestamps and history** (every model change is a commit with an author, a review and a date), **traceability** (every finding carries its element, its STRIDE category, its library IDs — §5.7 — and its mitigation's verification mapping, the sibling's §9.3 pattern), and **currency evidence** (the pipeline's model checks prove the model was regenerated and reviewed on a cadence — the "model is current" claim stops being an assertion and becomes a CI log). The one-paragraph pitch to a risk committee: *the model is not a document the team produced once; it is a control that runs with the system, and its audit trail is the pipeline's.* Cross-ref the sibling's §6 (DevSecOps) for the pipeline machinery this rides on, and [../banking/regtech_guide.md](../banking/regtech_guide.md) for the regulatory-reporting side.

## 8. The Metrics and the Maturity

### 8.1 Why Measure — Q4 Is a Measurement Question

Shostack's fourth question — *did we do a good job?* — is unanswerable without measurement, and the Manifesto supplies the thesis (✅ verified live): "Dialog is key to establishing the common understandings that lead to value, while documents record those understandings, and enable measurement." The honest history is in the MSDN 2006 article (✅ verified live): "There aren't any well-established ways to measure the quality of a threat model." Two decades on, the field has converged on a pragmatic answer with three layers: **model-level metrics** (density, coverage — §8.2–8.3), **register-level metrics** (health and flow — §8.4), and **programme-level maturity** (SAMM's threat-assessment practices — §8.5). None of them is a formal standard — flagged honestly throughout — but together they turn Q4 from a shrug into a dashboard.

### 8.2 Threat Density — Flagged

**Threat density** is the practitioner heuristic that counts the threats per unit of model — per DFD element, per data flow, per trust-boundary crossing — and uses the count as a *signal*, not a target. ⚠ **FLAGGED:** no formal standard definition was verifiable this pass; the term circulates in the practitioner literature (Shostack's own writings discuss threat counts per element as a model-quality signal — ⚠-structural, not live-verified this pass) but is not a standardised metric. The legitimate uses, and the abuses, are both worth knowing: **(1) use — the coverage tripwire:** an element with zero recorded threats in a pass is either genuinely clean (write down why) or skipped (the matrix audit of §4.4 catches it) — density makes the skipped elements visible; **(2) use — the normal-range signal:** a mid-size application's healthy register has a recognizable density shape (a few threats per process, more per boundary-crossing flow, fewer per internal store — the exposure-priority logic of §4.4); a density that is dramatically higher or lower than the estate's baseline is worth a look; **(3) abuse — density as a target:** gaming density — padding the register with low-value rows to hit a count — is the classic metric-failure mode; the discipline's answer is that the register's *top rows* and their closure are what matter, not the total (the sibling's §2.8: "a healthy register... is a few dozen rows, of which the top five get the team's attention this sprint"). Use density to *see*, never to *score*.

### 8.3 Coverage — Flagged, with a Verified Anchor

**Coverage** is the metric family that asks "did we look everywhere?" — the proportion of the model actually analysed: elements covered by the STRIDE pass, trust-boundary crossings examined, flows with a protection state recorded, STRIDE categories asked per element (the matrix audit of §4.4 is the mechanical form). ⚠ The *term* as a formal, standardised metric is flagged — no canonical definition was verified this pass — but the *concept* has a verified institutional anchor: the **OWASP SAMM Threat Assessment practice's Maturity Level 3 objective is literally "Proactive improvement of threat coverage throughout the organization"** (✅ verified live, owaspsamm.org — quoted in full in §8.5). The working definition this guide uses: **coverage = (elements × applicable categories actually analysed) / (elements × applicable categories in scope), plus (boundary-crossing flows examined) / (boundary-crossing flows drawn)** — with the honest qualifier that "analysed" means a recorded finding or a written not-applicable rationale (the §4.4 discipline). The Q4 use of coverage: the answer to "did we do a good job?" is never "100%" — it is "here is the coverage map, here is what the model deliberately did not cover, and here is why" — the explicit-gap answer of §2.6. The SAMM anchor matters because it makes coverage a *programme* objective, not a single-session nicety: an organisation at SAMM M3 is expected to be measurably improving coverage across all its projects.

### 8.4 The Register-Health Metrics

The register is the discipline's working artifact (sibling §2.8 — cross-ref for the column shape), and its health is measurable with four practice metrics (⚠-structural — standard practice doctrine, no single canonical source verified this pass): **(1) open-critical count** — the register's rows at critical/high severity without a mitigation landing date; the number the board and the regulator both read (mirror of the sibling's §5.7 gate-block-rate philosophy); **(2) mean-time-to-remediate (MTTR)** for register rows — the trend line that tells you if the design-review output actually flows into delivery; **(3) acceptance ratio with review dates** — rows marked "accepted" must carry an owner and a review date (the sibling's §2.8 rule); a high ratio of accepted rows *without* dates is the smell of silent risk acceptance; **(4) re-review cadence compliance** — % of models re-opened on their trigger events (design change / incident / quarterly re-score, §7.3) within the agreed window. The one metric to avoid as a target: raw threat count (the density-gaming failure of §8.2). The dashboard shape for a bank: the four register metrics plus the coverage map of §8.3 is the Q4 answer in one screen.

### 8.5 The SAMM Threat-Assessment Practices

**SAMM — the OWASP Software Assurance Maturity Model** — is the secure-development maturity framework (the sibling's §4.5 row: ⚠-canon there), and its **Threat Assessment (TA) practice** is the programme-level home of threat modelling. ✅ Verified live this pass (owaspsamm.org, the Threat Assessment practice page, quoted directly): "The Threat Assessment (TA) practice focuses on identifying and understanding project-level risks based on the functionality of the software being developed and characteristics of the runtime environment." The practice sits in SAMM's **Design business function** and has two **streams**: **Stream A — Application Risk Profile** (assess each application's risk; centralise the inventory; periodically review) and **Stream B — Threat Modeling** (model threats per project; standardise training, processes and tools; optimise and automate). The three **maturity levels** with their objectives (✅ verified, quoted from the page):

| Level | Objective (verified wording) | Stream A (risk profile) | Stream B (threat modeling) |
|---|---|---|---|
| **Maturity 1** | "Best-effort identification of high-level threats to the organization and individual projects." | A basic assessment of the application risk is performed to understand likelihood and impact of an attack | Best-effort, risk-based threat modeling using brainstorming and existing diagrams with simple threat checklists |
| **Maturity 2** | "Standardization and enterprise-wide analysis of software-related threats within the organization." | Risk profiles centralized for all applications, for stakeholders | Standardized threat modeling training, processes, and tools to scale across the organization |
| **Maturity 3** | "Proactive improvement of threat coverage throughout the organization." | Risk profiles periodically reviewed at regular intervals to ensure accuracy | Continuous optimization and automation of the threat modeling methodology |

The M1→M3 arc is the entire maturity story of this guide in three lines: **M1** is the §4 session (brainstorming + checklists — the per-element matrix *is* "simple threat checklists"); **M2** is the §5–§6 layer (libraries, standardised tools, training — the organisation scales the practice); **M3** is the §7–§8 layer (automation, continuous refinement, measurable coverage — "continuous optimization and automation of your threat modeling methodology"). A Cymbal Bank programme's honest self-assessment: most estates are at M1–M2 on the Threat Modeling stream and M1 on the Risk Profile stream — and the §9 worked example is a complete M1 session with M2-shaped outputs.

### 8.7 The Maturity Ramp

The ramp below ties the sections of this guide to the SAMM levels (⚠-structural for the stage naming — the SAMM levels and objectives are ✅ verified, the mapping to this guide's sections is the guide's own synthesis): **(Stage 0 — ad-hoc):** threat modelling happens "when someone remembers", output is a meeting's flip chart, nothing is tracked. **(Stage 1 — session, SAMM M1):** the §2–§4 core works — the Four Questions, a DFD, a per-element STRIDE pass, a register with owners (the §9 worked example is this stage, done well). **(Stage 2 — standardised, SAMM M2):** the §5–§6 layer — libraries used consistently, tooling standardised (Threat Dragon / pyTM / a platform), training in place, the register format and scoring calibrated estate-wide, risk profiles centralised. **(Stage 3 — automated, SAMM M3):** the §7–§8 layer — the model is as-code in the repo, CI regenerates and gates it, coverage is measured and improving, and the pipeline's model history is the audit evidence (§7.6). The ramp is the same shape as the sibling's DevSecOps maturity ramp (§6.7 — cross-ref) because both describe the same journey: ritual → discipline → standardisation → evidence. For a bank the regulatory read is direct: DORA's lifecycle risk-management expectations and the FSM-N05 TRM framework are satisfied by an organisation demonstrably at Stage 2+ — with the evidence-producing Stage 3 being what an examination can actually sample (the sibling's §8 — cross-ref).

## 9. The Worked Example — a DFD-Based Threat Model

### 9.1 The Scenario — a Cymbal Bank System

**The setting (illustrative — not a description of any real Cymbal Bank system ⚠):** the house is building **"ClientOnboard"** — a corporate-client **onboarding and e-banking activation** service: the relationship manager opens a corporate client, the client's treasurer completes the online activation, KYC screening runs against a third-party vendor, entitlements are provisioned, and payment functionality is activated through a maker-checker flow before the account goes live. The familiar Cymbal Bank context applies throughout (cross-ref [../banking/credit_agricole_software_systems_guide.md](../banking/credit_agricole_software_systems_guide.md) for the estate, [../banking/trade_finance_systems_guide.md](../banking/trade_finance_systems_guide.md) for the trade-services neighbours, and the sibling's §9.1 for the same house context seen from the review angle). The system is at architecture-approval stage: no code yet, which is exactly the right time for a DFD-based threat model (the Q1 artifact of §2.3, produced before the first sprint). **Why this example is not the sibling's §9:** the sibling's §9 is a *STRIDE-driven design review* — a findings table over an existing architecture, with a runbook. This example is the *methodology artifact itself*: the DFD, the element and flow inventories, the per-element STRIDE analysis, and the register — the complete Q1→Q4 cycle executed as §3–§4 prescribe. The two are complementary views of the same discipline.

### 9.5 The Lessons

1. **The DFD earned its keep before the STRIDE pass ran** — the element and flow inventories *forced* the questions that mattered (who talks to the core? what crosses TB4? what does the audit store actually store?). The MSDN canon ("getting the DFD right is key") is not advice; it is the mechanism. §3 is not the warm-up — it is the analysis.
2. **The per-element matrix found the threats in the seams** — the biggest rows (TM-001, TM-002, TM-005) came from *interactions*: workflow-state between processes, role-separation inside a flow, service identity between services — exactly the sibling's §9 lesson #1 repeated at the DFD level. The matrix's guarantee is coverage; its payoff is that the seams cannot be skipped.
3. **The libraries sharpened the generic into the specific** — the KYC-substitution finding (TM-001) and the synthetic-identity finding (TM-003) are the difference between "tampering" (the STRIDE label) and "the attack as it actually runs" (the CAPEC-pattern layer, §5.2); the CWE mapping (§5.4) turns each into a SAST rule the pipeline can enforce (§7.4).
4. **Trust boundaries are the control inventory** — every TB crossing in the diagram maps to a named control in the register (F1→WAF+MFA, F3→mTLS, F10→signing+idempotency, F11→vendor authN, F15→file signing). A threat model whose boundaries have no controls is a drawing; this one is a build plan.
5. **The register is the contract** — twelve rows, all owned, all with design-level mitigations, reviewed at architecture-approval — is the difference between a security conversation and a security decision. The same model discovered post-build would have been a re-platforming programme; the sibling's cost-curve argument (§9.4 lesson #5) applies verbatim: **security is a feature, and the threat model is its specification.**

## 10. The One-Page Summary

**Threat modelling is the structured activity of answering four questions about a specific system before the adversary answers them for you** (Shostack 2014, §2): **What are we building?** — answered by the DFD: the five-element notation of §3 (processes, data stores, external entities, data flows, trust boundaries — the Yourdon–DeMarco lineage with the early-2000s security addition), drawn with the §3.5 rules so that every trust boundary is visible and every crossing is named. **What can go wrong?** — answered by STRIDE applied **per element** (§4): the verified matrix — processes take all six categories, data flows and data stores take T/I/D, external entities take S/R — enriched by the threat libraries (§5): CAPEC for the attack patterns, ATT&CK for the observed adversary behaviour, CWE for the enabling weaknesses, the OWASP catalog for the practitioner-flavoured checklist. **What are we going to do about it?** — answered by the risk register (§9.4): every threat mitigated, transferred, avoided or explicitly accepted, owned and dated, using the sibling's design principles as the mitigation language. **Did we do a good job?** — answered by the metrics (§8): coverage of elements and boundary crossings, register health, and the SAMM Threat Assessment maturity levels (M1 session → M2 standardised → M3 automated, with "proactive improvement of threat coverage" as the verified M3 objective). The tooling (§6) and the as-code practice (§7) are the discipline's industrialisation: Threat Dragon and pyTM as the free-tier defaults, the platform tools for workflow-heavy estates, and the model-in-the-repo, CI-regenerated, gate-enforced pattern as the continuous form — the form that makes the model a *control* with an audit trail instead of a document with a date. The whole discipline fits on one page as a chain: **draw it (§3) → decompose it (§3) → analyse it per element (§4) → enrich it from the libraries (§5) → tool it (§6) → automate it (§7) → measure it (§8) → prove it on a real system (§9).**

**The ten-line checklist** — a system's threat model is in good shape when all ten are true:

1. The DFD exists, uses only the five elements, and every trust boundary is drawn — with the context diagram and per-zone breakouts (§3).
2. Every element has a per-element STRIDE analysis or a written not-applicable — the matrix audit passes (§4).
3. The trust-boundary crossings each have a named control — no crossing without a control (§3.4, §9.2).
4. The top findings are enriched from the libraries — CAPEC/CWE identifiers on the register rows that will become code (§5.7).
5. The register follows the column shape, every row is owned, and "accepted" carries a date (§2.5, sibling §2.8).
6. The tooling fits the estate — free-tier standardised, platforms justified by workflow, nothing justified by fashion (§6.7).
7. The model lives in the repo and changes with the design — the as-code pattern, not the PDF-once pattern (§7).
8. The pipeline regenerates and gates the model — currency and ownership gates, not zero-threat theatre (§7.4).
9. Coverage and register health are measured, and the SAMM level is known — M1, M2 or M3, assessed honestly (§8).
10. The model is current — re-opened on design changes, incidents, and the quarterly re-score (§7.3).

**The final word — the adversary's perspective.** Every page of this guide is a way of seeing the system the way the adversary sees it. The adversary reads the DFD from the outside in: the trust boundary is their checklist, not yours — each crossing is a door, each flow is a corridor, each process is a room with something valuable in it, and the register's "not applicable because..." rows are the doors they will try first. The attacker never skips the design review; they perform it relentlessly, on every release, with total focus and no meetings. The threat model is the same review, done first, done honestly, and done in writing — and the systems that survive are the ones whose designers looked at their own architecture through the adversary's eyes before the adversary ever saw it. *Model the threats, or the adversary will model your system for you.*

## The Glossary

| Term | Definition |
|---|---|
| **Threat modelling** | The systematic, structured activity of identifying, enumerating and prioritising threats to a specific system, and of deciding, documenting and tracking mitigations — analysis of a *representation* of the system (the DFD), not of the system itself (§1.2) |
| **Threat model** | The structured representation of the system through the lens of security: the DFD, the element and flow inventories, the threats, the mitigations and the verification mapping — "a view of the application and its environment through the lens of security" (OWASP, ✅) (§1.2) |
| **Shostack** | Adam Shostack — Microsoft SDL threat-modelling lead and author of *Threat Modeling: Designing for Security* (Wiley, 2014), the book that framed the discipline as the Four Questions; also a Threat Modeling Manifesto author (§2.1) |
| **Four Questions** | The Shostack 2014 framework: What are we building? What can go wrong? What are we going to do about it? Did we do a good job? — re-stated by the 2020 Manifesto as "What are we working on? / ... / Did we do a good enough job?" (§2) |
| **DFD** | Data-flow diagram — the five-element graphical notation (processes, data stores, external entities, data flows, trust boundaries) used to model the system being threat-modelled (§3) |
| **Data flow diagram** | The DFD in full — the 1970s structured-analysis notation (Constantine → Yourdon/DeMarco/Gane–Sarson) adopted by threat modelling, with trust boundaries added in the early 2000s (§3.1) |
| **Process** | The task element: a computation transforming inputs to outputs (web app, service, scheduler); the only element that takes all six STRIDE categories (§3.2, §4.2) |
| **Data store** | The storage element: where data rests (databases, files, queues); takes T/I/D; every store needs a named reader and writer (§3.2, §4.2) |
| **External entity** | The no-control element: a person or system outside the modelled scope that provides or consumes data; takes S/R (§3.2, §4.2) |
| **Data flow** | The data-in-transit element: data moving between elements (network calls, file transfers, queues); takes T/I/D; labelled with what it carries and its protection (§3.2, §4.2) |
| **Trust boundary** | The trust-zone-change element: the dotted-line border between zones of differing control posture; every crossing is an attack point and needs a named control (§3.4) |
| **STRIDE** | The 1999 Microsoft six-category threat-classification model: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege — cross-ref the sibling's §2.2 for the full basics table (§4.1) |
| **Per-element** | The STRIDE-per-element mechanics: applying the six categories per DFD element using the verified matrix — processes take all six, data flows and data stores take T/I/D, external entities take S/R (MSDN 2006 Figure 5, ✅) (§4) |
| **CAPEC** | Common Attack Pattern Enumeration and Classification — MITRE's dictionary of attack patterns (559 entries at verification; the Mechanisms view CAPEC-1000, the Domains view CAPEC-3000): how attacks are carried out (§5.2) |
| **ATT&CK** | Adversarial Tactics, Techniques, and Common Knowledge — MITRE's knowledge base of observed adversary behaviour (tactics/techniques, Enterprise/Mobile/ICS matrices): what real adversaries do, and what to detect (§5.3) |
| **CWE** | Common Weakness Enumeration — MITRE's taxonomy of software weaknesses (CWE-79 XSS, CWE-89 SQLi, CWE-639 IDOR...; the Top 25 2024 verified in the sibling): the defects attacks exploit, and the shared language with SAST/ASVS (§5.4) |
| **Threat library** | A curated, identifier-tagged knowledge base consulted during threat modelling (CAPEC, ATT&CK, CWE, the OWASP catalog) — replaces memory with reference material (§5) |
| **Microsoft Threat Modeling Tool** | The free SDL-era Windows tool that productised the methodology: DFD drawing + "STRIDE per Element: guided analysis" + mitigation guidance; formerly the SDL Threat Modeling Tool; ⚠ maintenance status flagged (§6.2) |
| **Threat Dragon** | OWASP's free, open-source, cross-platform threat-modelling tool (web + desktop, JSON models, rule engine auto-generating threats and mitigations) — the current free-tier default (§6.3) |
| **pyTM** | OWASP's Pythonic threat-modelling framework — "the first Threat-Model-as-Code tool": the system is defined in Python, generating the DFD, sequence diagram and threats (§6.4, §7) |
| **Threat-modelling-as-code** | The practice of keeping the model in the repo as versioned text (JSON/Python/YAML), diffed and reviewed like code, regenerated by tooling (§7.1) |
| **Continuous threat modelling** | The doctrine (OWASP ✅) that threat modelling runs throughout the lifecycle — defined early, refined as the system changes, re-opened on feature/incident/architecture change, re-scored on cadence (§7.3) |
| **CI-CD** | Continuous Integration / Continuous Delivery — the pipeline the as-code model rides: generate-on-commit, model-diff review, currency and ownership gates (§7.4) |
| **Threat density** | The ⚠-flagged practitioner heuristic counting threats per unit of model (per element, per flow, per boundary crossing) — a coverage tripwire and signal, never a target (§8.2) |
| **Coverage** | The ⚠-flagged metric family for "did we look everywhere": elements × categories analysed, boundary crossings examined — concept anchored by SAMM M3's verified "proactive improvement of threat coverage" objective (§8.3) |
| **SAMM** | The OWASP Software Assurance Maturity Model — its Threat Assessment practice (Design function, streams A: risk profile / B: threat modeling, levels 1–3) is the programme-level maturity home of threat modelling (§8.5) |
| **Risk register** | The working output artifact: every threat with ID, category, affected assets, score, mitigation, owner, status, due/verified date — the sibling's §2.8 column shape, this guide's §9.4 example (§2.5) |
| **Mitigations** | The design-level responses to threats — mitigate / transfer / avoid / accept-with-date; named controls with owners and verification mapping, never "we'll handle it in hardening" (§2.5) |
